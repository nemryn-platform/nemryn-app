2. WEBSITE REQUESTS ON A NON-LOOPBACK PREVIEW
---------------------------------------------
- Blocker recap: a production build refuses to build application links from a loopback origin (src/lib/app-url.ts).
  So Website Requests cannot render on http://localhost:3100. That guard is correct and was NOT changed.
- Method: a separate local production build whose NEXT_PUBLIC_APP_URL is this Mac's own mDNS hostname,
  http://vee-macbook-pro.local:3100.
  - That is a genuine non-loopback origin under the guard's own rule (only localhost / 127.0.0.1 / ::1 are refused).
  - It was served from the same isolated NemrynS1Iso stack, with fictional data only.
  - Headless Chrome reached that hostname through a browser-only host mapping (--host-resolver-rules, in a scratch copy
    of the CDP launcher). The app still received the non-loopback Host / origin.
- No guard, configuration, repository file or production resource was changed.
- Afterwards the normal localhost build was restored for every other gate. It has no preview hostname in its output.
- Result: 8 / 8 PASS. Each of the following, at 1440 and 768:
  - /operations/settings/website-requests
  - /form
  - /existing-form
  - /developer
  Each:
  - renders (no "couldn't be loaded" state);
  - has one h1;
  - shows the Settings sub-navigation with "Website Requests" active;
  - has 0 serious / critical axe findings and no horizontal overflow;
  - uses the D-14 copy: "Nemryn Requests"; "Request Hub" is no longer present.
- Limitation, stated plainly: this is a LOCAL non-loopback preview, not a Vercel preview deployment. A hosted preview
  needs a pushed branch, which is the owner's Git step. The production pages should be checked again after the owner
  deploys V2-3.

3. MOBILE AUTHENTICATION AT 390px
---------------------------------
Checked:
- sign-in;
- forgot-password;
- sign-up;
- invalid driver invite;
- invalid team invite;
- expired link;
- reset-password (no session).

Each was checked at 390×844 and 390×667 (a short phone) for:
- the card top never clipped, and its bottom reachable by scrolling;
- no horizontal overflow;
- every visible control in the card at least 40px tall (submits are 48px);
- the lowest control fully in view after scrolling and keyboard-focusable.

The two invalid-invite pages are informational by design (no action); they are checked for layout only.

Findings fixed:
- The standalone secondary links were 17–19px tall, too small as mobile tap targets: "Forgot password?", "Back to sign
  in", "Create your account again", and the footer "Create an account" / "Sign in".
  - They now have a 44px target: inline-flex min-h-11, with the same text, colour and position.
  - Files: SignInForm, ForgotPasswordForm, sign-in / sign-up / forgot-password pages, auth-code-error, reset-password.
- The first run's sign-up 390×667 "not in view" was a sub-pixel false negative: the link's bottom edge sat exactly on
  the viewport edge. The check now uses the same 1px tolerance as the card check.

Result: 14 / 14 PASS.
