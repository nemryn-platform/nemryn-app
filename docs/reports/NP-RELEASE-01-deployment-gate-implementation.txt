3. ENFORCEMENT ARCHITECTURE
---------------------------
Two independent layers share ONE checker; the database-first process sits on top.
L1 PR status check (GitHub Actions, .github/workflows/release-db-compat.yml; [01A: now `pull_request_target`, trusted
   base code, PR head inspected as data; result posted as the commit status "nemryn/release-db-compat"] → main):
- application change: every repository migration must already be applied in production; otherwise BLOCKED.
  Unreachable or unknown state is UNVERIFIABLE (fails).
- migration-only change: PASS as DATABASE-FIRST, with the pending versions listed. The check never applies
  migrations; the owner-run release applies them.
- documentation / test-only change: PASS, even with pending migrations or an unreachable production.
- drift always BLOCKS:
  - remote-only versions;
  - the same version under a different name;
  - repository migrations older than the production head that were never applied.
- a mixed application + migration PR is BLOCKED until its migrations are in production. Policy: split it, or release
  the migration first.
L2 Deploy-time gate (Vercel Ignored Build Step → scripts/release/vercel-ignore-build.sh):
- production builds proceed ONLY if, at build time, every repository migration of the commit is applied and there is
  no drift;
- otherwise the build is SKIPPED, and production stays on the previous deployment.
- This catches the race in which a PR check passed but the state changed before deploy (T11).
- It also catches merges with no PR, or with the check bypassed.
- Previews follow the preview policy (default: build without the check; §8).
L3 Process (database-first):
1. Migration-only PR merged. Production build of that commit SKIPPED: the app is unchanged, so this is harmless.
2. Owner-run migration release.
3. Application PR passes L1 and is merged. L2 allows its production build.
After step 2 a redeploy can also be triggered, but it isn't required, because the app was unchanged.
Fail-closed rules:
- unknown / malformed / empty / duplicate state, a wrong project ref or name, missing credentials, an unknown Vercel
  environment, a crashed checker, or a missing node binary NEVER produce a build;
- an unknown change set (a git failure) is treated as an application change.

5. SECURITY AND CREDENTIAL DESIGN
---------------------------------
- Never mutates: the transports are GETs only (no SQL / query endpoint) and the fixed CLI argv `migration list
  --linked`. Test T15 scans the gate code for push / reset / repair / query / up / dump / POST / PATCH / PUT / DELETE.
- No secrets in source, logs or bundles:
  - the token is read only from the environment;
  - it is redacted from any error;
  - the reports print versions, counts and the public project ref only.
  This matters because the repository is PUBLIC: Actions logs are publicly readable.
- Workflow hardening:
  - `pull_request` only (never pull_request_target);
  - permissions contents: read;
  - persist-credentials: false;
  - third-party actions pinned to commit SHAs (checkout v7.0.1 3d3c42e5…, setup-node v7.1.0 949feb24…);
  - the secret is exposed to ONE step through env;
  - no untrusted strings are interpolated into scripts (SHAs pass through env).
  - Fork PRs get no secrets, so they are UNVERIFIABLE (fail closed).
- Credential (NOT created; owner decision D2):
  - The management-api transport needs a Supabase access token. [CORRECTED by 01A: Supabase fine-grained personal
    access tokens can be restricted to the Nemryn project and to Project Settings: Read + Migrations: Read; that is the
    approved credential (D2). The original text here said all PATs are account-wide, which was outdated.]
  - Options:
    - (a) a dedicated machine Supabase account with access to the Nemryn project only; its token stored as a GitHub
      Actions secret NEMRYN_RELEASE_SUPABASE_TOKEN and a Vercel env var SUPABASE_ACCESS_TOKEN scoped to Production
      only;
    - (b, more least-privilege) a dedicated read-only Postgres role (SELECT on
      supabase_migrations.schema_migrations(version, name) only), connected through the pooler. This needs a
      reviewed production role change plus a small DB-client dependency; a transport can be added to the same core.
  - Whichever is chosen, code merged to main runs in the Vercel production build with access to that credential. The

8. LIMITATIONS AND BYPASS PATHS (none of these is closed until activation, §9)
-----------------------------------------------------------------------------
- B1 Not enforced today: no branch protection, no required checks, no Vercel Ignored Build Step. Any merge or direct
  push to main deploys.
- B2 Admin / owner bypass: until branch protection or a ruleset is configured with "do not allow bypassing", the owner
  (and any admin) can merge without the check. L2 still applies at build time once it is configured.
- B3 Self-modification:
  - a PR can change the workflow or the checker, and `pull_request` runs the PR's version;
  - mitigations: required review plus CODEOWNERS for .github/** and scripts/release/** (D4);
  - L2 runs the code that is actually on main, so it only changes through a reviewed merge.
- B4 Vercel paths that may not run the Ignored Build Step (to be verified at activation): `vercel deploy --prod` from
  the CLI, deploy hooks, dashboard "Redeploy", and Instant Rollback (which re-promotes an existing build; it is
  database-unsafe only when rolling back across a migration).
  - Mitigation: restrict Vercel team roles and tokens; disable unused deploy hooks; treat manual production deploys as
    owner-only; document "never roll back across a migration boundary".
- B5 Previews:
  - preview builds proceed without the check (policy "build");
  - if the Preview environment uses the PRODUCTION Supabase variables (not inspectable here), a preview of an app
    change can call missing RPCs against production (read failures; writes fail closed) before its migration exists;
  - decide the preview policy (D5): keep "build", gate previews too ("gate"), or point previews at a non-production
    database.
- B6 Version comparison is not a content proof. A migration applied with different SQL, or schema changes made outside
  migrations, are not detected by version / name alone. Mitigation: keep the post-release privilege contract and
  catalog fingerprint verification (S6-C2 scripts) mandatory for every migration release. Optionally extend the gate to
  compare a schema-contract fingerprint.
- B7 The management API migrations endpoint and its response shape were verified only against simulated responses
  here, because no token was used. Activation step A3 validates it live, read-only, before anything becomes blocking.
- B8 Residual race: the seconds between the Vercel build-time check and the deployment going live. Production schema
  changes happen only through the owner-run process, so this is accepted.
- B9 Skipped production builds do not auto-deploy later. After a migration is released, the next app merge deploys; or
  the owner triggers a redeploy of main.
- B10 Fork PRs: application changes are always UNVERIFIABLE (no secrets). Same-repo branches are the supported
  workflow.
