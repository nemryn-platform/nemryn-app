10. SERVER ACTION

mirrors `createTripAction`'s own established shape exactly:

14. DOUBLE-SUBMIT PROTECTION
---------------------------------
Two layers, mirroring `NewTripForm`'s own established double-submit
guard exactly: `disabled={pending}`/`loading={pending}` on the submit
button (React's own `useActionState` pending flag), plus a
`submittedRef` ref checked in the form's own `onSubmit` handler that
calls `event.preventDefault()` on any second submit attempt while the
first is still in flight — a defense-in-depth guard beyond the
disabled-button state alone, since `log_transportation_request` is
deliberately non-idempotent (mirrors `create_trip`/ZD-102's own
reasoning: two legitimate Requests can share every field). The RPC
itself was NOT modified to add any idempotency mechanism, per explicit
instruction.


15. SUCCESS BEHAVIOR
-------------------------
Chose: remain on the Log Request page, replace the form with a
restrained success panel ("Request logged" + the requester's name +
"has been recorded and is ready for review"), offering "Log another
request" (resets every field and remounts the form via a `key` bump,
which also resets `useActionState`'s own internal state back to idle)
and "Back to Overview" (`LinkButton` to `/operations`).

Reasoning: Log Request's own stated purpose (§3, phase brief) is FAST
DEMAND CAPTURE — an operator taking a phone call is a very plausible
scenario for logging several requests back-to-back, and staying on the
page avoids re-navigating to `/operations/requests/new` each time.
Neither option redirects into a Request Hub/Detail experience that
doesn't exist yet (S2D/S2E) — this is the explicit, documented
temporary behavior; when S2D/S2E ship, the natural replacement is
changing the success branch to redirect to the real Request Detail page
(the code comment directly above `handleLogAnother` in
`LogRequestForm.tsx` states this explicitly, pointing future
implementers at exactly this spot).
