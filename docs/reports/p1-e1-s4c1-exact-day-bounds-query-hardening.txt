PREVIOUS DST DEFECT
------------------------------------------------------------------------
`organizationDayBoundsUtc` previously computed `endUtc = startUtc + 24
hours` unconditionally. Correct for an ordinary day; wrong on the two
DST transition days per year in any zone that observes DST — a
spring-forward local calendar day genuinely has 23 elapsed hours, a
fall-back day genuinely has 25. This produced a window up to 1 hour too
wide (spring) or too narrow (fall) at its far edge, discovered and
explicitly accepted as a documented tolerance during P1-E1-S4C's own
work. This phase removes that tolerance entirely.

------------------------------------------------------------------------
EXACT DAY-BOUND CONTRACT
------------------------------------------------------------------------
`organizationDayBoundsUtc(instant, timezone)` now returns the EXACT UTC
instants of `[start of instant's own organization-local calendar date,
start of the NEXT organization-local calendar date)`. The duration is
whatever that specific local date's real duration is — 23, 24, or 25
hours — never assumed to be a fixed 24. The function's own public
signature and return shape (`{startUtc: Date, endUtc: Date}`) is
UNCHANGED, so every existing caller benefits automatically with zero
call-site edits required.

------------------------------------------------------------------------
IMPLEMENTATION
------------------------------------------------------------------------
Rewrote `day-bounds.ts` to compute `startUtc` and `endUtc` as two
INDEPENDENT calls to `organizationLocalToUtc` (`local-time.ts`, already
existing, already proven, NOT modified in this phase) — "local 00:00 of
this calendar date" — rather than deriving one from the other by adding
a fixed duration:

  const dateKey = /* the local calendar date containing `now`, via the
                     same Intl.DateTimeFormat("en-CA", {...}) technique
                     already used before this fix */
  const startUtc = localMidnightUtc(dateKey, timezone);
  const endUtc = localMidnightUtc(nextDateKey(dateKey), timezone);

`organizationLocalToUtc` already resolves an arbitrary local
date+time to a UTC instant correctly across DST by testing BOTH of a
zone's two possible yearly offsets against the real IANA-backed wall-
clock the resulting instant would actually show, keeping only the one
that round-trips correctly (already used elsewhere in this codebase —
Dispatcher pickup-time entry — never re-implemented, only reused).
Feeding it `{date: dateKey, time: "00:00"}` gives the exact instant of
that date's own local midnight, with its own, independently-correct
offset — no assumption that yesterday's or tomorrow's offset applies.

`nextDateKey` is pure calendar-digit arithmetic (`Date.UTC(year,
month-1, day+1)`, reformatted) — never timezone-sensitive, matching this
codebase's own established use of `Date.UTC` as a calendar-only
scratchpad elsewhere (`formatRequestServiceDate`).

`localMidnightUtc` throws a clear, diagnosable error if
`organizationLocalToUtc` ever returns a non-`"ok"` status for a
midnight boundary — a case that cannot occur for any IANA timezone this
product currently supports (real-world DST transitions occur at 2:00 AM
local in every zone actually used; midnight is never the transition
instant), documented rather than silently worked around, matching this
codebase's own "never fabricate a result" discipline.

No new library was added. No hardcoded offset or transition-date table
was introduced. `timezoneOffsetMs`, no longer used anywhere in
`day-bounds.ts` after this rewrite, was removed as dead code.

ACTIVE ASSIGNMENT QUERY STRATEGY
------------------------------------------------------------------------
Investigated PostgREST's actual embedded-relation-filter behavior
empirically (not assumed) before choosing a strategy: filtering an
embedded (LEFT-JOINed) relation via a dotted query parameter
(`trip_assignments.ended_at=is.null`) narrows WHICH rows of the embed
come back, WITHOUT excluding the parent row when zero rows match —
confirmed live, directly against this project's own local PostgREST:
a Trip with zero assignments still returned with `trip_assignments: []`
under this exact filter, never dropped. This is Option A from the
phase's own choice.

Implemented in `tomorrow-readiness.ts` as `.is("trip_assignments.
ended_at", null)` — deliberately `.is()`, never `.eq()`: confirmed
directly against the installed `@supabase/postgrest-js` source
(`PostgrestFilterBuilder.ts`) before relying on it — its own
documentation states explicitly "Using the eq() filter doesn't work
when filtering for null. Instead, you need to use is()." Using `.eq()`
here would have silently produced a query that never matches anything,
a real defect this direct source-verification caught before it ever
shipped.

Never `!inner` — that would turn the embed into an inner join and
silently drop every unassigned Trip, which is exactly the class of
Trip this query most needs to correctly surface as NEEDS_DRIVER.

Live-verified against a NEW, dedicated reassignment-history fixture (a
Trip with one ENDED `trip_assignments` row plus one ACTIVE row): the
hardened query returned exactly 1 assignment row (the active one) in
the raw PostgREST response — the historical, ended row never appeared
in the payload at all, confirmed both by inspecting the raw embed array
length and by confirming the resulting readiness evaluates `READY`
(correctly reflecting only the current, valid assignment). The
in-memory mapping logic was simplified accordingly: since the embed can
now contain at most one row (the schema's own partial unique index
already guarantees at most one `ended_at IS NULL` row per Trip, and the
query now filters to exactly that condition), `trip_assignments[0]` is
used directly — the previous `.find((a) => a.ended_at === null)` search
over potentially-historical rows was removed as no longer necessary.

DAY METADATA DECISION
------------------------------------------------------------------------
Added `timezone`, `tomorrowStartUtc`, `tomorrowEndUtc` to a new
`TomorrowReadinessData` interface in `tomorrow-readiness.ts` (extending
the pure `TomorrowReadinessAggregate` from `tomorrow-readiness-core.ts`,
which itself remains completely unchanged and unaware of any date/
timezone concept — matching its own established "date scope decisions
never happen in the pure core" design). `getTomorrowReadiness`'s return
type changed from `TomorrowReadinessAggregate` to `TomorrowReadinessData`.
No formatted/presentation string was added (e.g. no "Wednesday,
September 18") — only the raw, authoritative UTC boundary instants and
the timezone string, so a future UI (S4D) can render its own date
heading without needing to independently recompute `organizationDay
BoundsUtc` itself, per this phase's own explicit preference for "one
authoritative server result over presentation-layer duplicate date
logic."
