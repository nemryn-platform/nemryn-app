2. PLATFORM-VS-TENANT IDENTITY MODEL
====================================================================

Restated from the LOCKED `11-brand-lock-v1.md` §4 (re-verified against
the current codebase, not merely quoted):

  **PLATFORM IDENTITY = Nemryn.** Owns: the product name/wordmark/
  palette/type/iconography/voice, the marketing website, the
  authentication surface (sign-in, sign-up, forgot-password,
  reset-password, auth confirmation/error states), the application
  shell (sidebar, header, navigation chrome), and operator-neutral
  system/security messaging about the platform account (signup
  confirmation, password recovery — already correctly sender-branded
  Nemryn since P0-S2B/P0-S2B-C1, §12).

  **TENANT IDENTITY = the operator** (Zenward Mobility today, any
  future operator later). Owns: its own legal/trade name, its own
  logo (used as ITS identity, never the app's), the content of its own
  operational data, and communication that goes out AS the operator
  (driver invitations already correctly name the tenant dynamically,
  §6/§12).

  **The governing rule, restated exactly as this work item's own §6
  asks for:**

    PLATFORM CHROME = Nemryn
    ORGANIZATION CONTEXT = tenant.organization_name (already a live,
      resolved field — `organizationName` on the operations-access
      context type, `src/lib/auth/types.ts:15/24` — populated from
      `organizations.name` via `src/lib/auth/membership.ts:57`; NOT a
      hard-coded string anywhere it is correctly used today)

**Confirmed independently in this audit: no schema, RLS, or tenancy
change is required to support this split** — see §14.

  Signal Green   `#4FA57A`  → ready · confirmed · complete · healthy
  Attention Amber `#D79B45` → needs attention · potential problem
  Critical Red   `#C95C55`  → critical exception · failed condition
  Steel Blue     `#6F8798`  → information · selection · focus ·
                              neutral active / in-progress state

**LOCKED constraint, reconfirmed:** these are PRIMITIVE colors, not
directly usable as text/border/fill values — WCAG validation in
`05-semantic-color-system.md`/`12-design-token-specification.md`
already confirmed none of the four raw hues meets 4.5:1 contrast as
small text on Mineral White; the DERIVED, accessibility-corrected
token values (already computed, not something this audit needs to
re-derive) are what components will actually consume.

**Signal colors must remain semantic, never decorative** — reconfirmed
as a hard constraint this audit fully endorses: the current
`critical-*`/`success-*` etc. usage (StatusBadge, trip-status
indicators, exception flags — per the prior inventory's own component

decoratively, in this application; the migration's own job is to
re-derive the SAME semantic usages under new token names/values,
re-checking meaning where flagged (§8), not to introduce new
decorative color use anywhere.

**Primary CTA / primary action color is explicitly NOT one of the four
status hues** — per the LOCKED Brand Lock §9: "Signal Green is never
the default CTA. Primary CTA / primary application action = Deep
