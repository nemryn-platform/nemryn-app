4. DESKTOP STATE MODEL
---------------------------
Two states, `collapsed: boolean` (React `useState`, default `false` =
expanded):

  EXPANDED (collapsed=false): `<aside>` gets `lg:w-64`; full wordmark
    logo shown at lg+; workspace row (Buildings icon + org name +
    "Workspace") shown at lg+; user row shows Avatar + name + role text;
    nav items show icon + label.

  COLLAPSED (collapsed=true): `<aside>` does NOT get `lg:w-64` (falls
    back to the base `md:w-16`, i.e. the exact same width tablet already
    uses); symbol-only logo shown; workspace row hidden (matching
    tablet's pre-existing treatment exactly); user row shows only the
    Avatar circle; nav items show icon only, with hover/`title` tooltip
    and an explicit `aria-label` for the accessible name.

The key implementation insight: every "show the lg: extras" class is
computed as `!collapsed && "lg:X"` rather than always emitting `"lg:X"`.
This means `collapsed` never has to know or query the actual viewport
width — at md–lg (tablet) the `lg:` media query never matches regardless
of `collapsed`'s value, so tablet is structurally unaffected no matter
what; at lg+, the `lg:` classes only apply when `!collapsed`. This is
what makes tablet automatically stay compact (§3/§18), and what makes the
desktop preference automatically "reapply" the instant the viewport
crosses back over 1024px (§18's example) — there is no viewport-size
detection code anywhere; it falls entirely out of ordinary CSS media
query evaluation against a value that itself never depends on viewport
size.


5. PERSISTENCE IMPLEMENTATION
----------------------------------
`localStorage` only, key `nemryn.sidebar.collapsed`, value the string
`"true"`/`"false"`. No database column, no profile field, no Supabase
call, no cookie (localStorage was technically sufficient — no
architectural reason required a cookie), no cross-device sync of any
kind. Read once on mount (see §6); written on every toggle click, inside
a `try/catch` so a private-browsing storage-quota error or disabled
storage never crashes the sidebar — it just means the preference won't
survive a reload for that one session, not a functional failure.


6. HYDRATION STRATEGY
--------------------------
`useState(false)` — the component's very first render, on BOTH the
server (SSR) and the client's initial hydration pass, always renders
"expanded." This guarantees zero hydration mismatch, since server and
client output are byte-identical by construction, with the real stored
preference not yet applied.

The real preference is then read inside a tiny "isomorphic layout
effect":

    const useIsomorphicLayoutEffect =
      typeof window !== "undefined" ? useLayoutEffect : useEffect;

`useLayoutEffect` fires synchronously, after DOM mutations but BEFORE
the browser paints the frame — so if the stored preference is
"collapsed," the resulting `setCollapsed(true)` and its re-render are
both flushed before anything is ever shown on screen, meaning there is
no visible expanded→collapsed flash on reload. `useLayoutEffect` is
documented to do nothing during server rendering (and would print a
console warning if called unconditionally in an SSR context); the
`typeof window` check is the standard, widely-used ~1-line pattern that
avoids that warning by using the plain `useEffect` reference during
server module evaluation and the real `useLayoutEffect` in the browser —
not a new library, not new infrastructure, exactly as the phase asked
for ("keep implementation small").

Live-confirmed (§17, test D): reloading `/operations/dispatch` with a
stored "collapsed" preference produced `aside` width 64 immediately —
no intermediate 256-width frame was ever observed in the captured
screenshot or the immediate post-navigation measurement.

16. TRANSITION BEHAVIOR
----------------------------
A restrained width transition was added to the `<aside>` element only:

    transition-[width] duration-base ease-standard motion-reduce:transition-none

`duration-base` (180ms) and `ease-standard` are pre-existing design
tokens already defined in `globals.css` (`--duration-base`,
`--ease-standard`) — reused, not invented. `motion-reduce:transition-none`
is Tailwind's built-in `prefers-reduced-motion` variant (needs no
project-specific setup) — it fully disables the width animation for a
caller with that OS-level preference, satisfying "respect prefers-
reduced-motion" with zero new infrastructure.

No text-squeezing artifact was introduced: the labels/workspace/user
text blocks are toggled via `hidden`↔visible (a `display` change, which
is not animatable and therefore cannot visibly "squeeze") rather than
via any width/opacity animation on the text itself — they simply appear
or disappear instantly, while only the `<aside>` container's own width
transitions smoothly.
