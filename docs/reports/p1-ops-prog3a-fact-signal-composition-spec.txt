======================================================================
EXECUTIVE SUMMARY
======================================================================
PROG3 adapts EMPHASIS and ORDER to facts the product already derives. It never adapts to a business size.

Core decisions:
  1. The Overview's section order is decided by ONE pure function, from ONE server-derived signals object, using a
     fixed priority ladder:
       - work that needs the operator comes first, in a fixed order;
       - calm, informational summaries collapse into one compact group;
       - sections whose empty state says nothing to this organization are omitted, but only where the destination
         stays reachable elsewhere.
  2. Navigation is STABLE, with no size rules. Tomorrow and Recurring Care become permanent sidebar items. Dispatch
     keeps its place. Drive and Settings stay conditional on identity and capability, exactly as today.
  3. The required size question ("How are you operating today?") is retired:
       - signup no longer routes through it and never requires it;
       - organizations.business_stage stays nullable and untouched;
       - nothing reads it behaviourally.
  4. Assignment attribution ("Assigned by … · time", "Reassigned … · Reason") appears on Trip Detail for every
     viewer, from facts already stored.
       - Names are shown only where current RLS already allows them.
       - Showing other members' names to Dispatchers would need a backend read path. That is called out separately
         and is NOT in PROG3B.
  5. There are no hard thresholds. The only numeric caps reuse the Brief's existing 5-row list limit for
     consistency. Normal-work "folding" is DEFERRED because no threshold can be justified without pilot evidence.
PROG3B needs no migration, no RPC, no RLS change and no privilege change.

COMPOSITION INPUT
======================================================================
ProgressiveOperationsSignals is ONE server-derived object. It is assembled on the Overview page from data the page
ALREADY loads, with no new query:
  dayState                        "NO_TRIPS" | "ALL_COMPLETE" | "ACTIVE_DAY" | "UNAVAILABLE"
      Chooses the Today headline.
  attentionCount                  number | null
      P0 placement. null when today's data is unavailable.
  todayUnassignedCount            number | null
      Copy inside Attention ("2 trips need a driver").
  activeNowCount                  number | null
      Whether the Today block has live content.
  nextDepartureCount              number | null
      Whether the Today block has upcoming content.
  pendingRequestCount             number | null
      P1 placement.
  tomorrowTripCount               number | null
      The Tomorrow line.
  tomorrowNeedsPreparationCount   number | null
      P3 placement.
  activeRecurringCount            number | null
      Recurring visibility.
  recurringMissingCount           number | null
      P4 placement.
  proofCompletedCount             number | null
      Proof visibility (yesterday's completed trips).
  proofReviewCount                number | null
      P5 placement.
  activeDriverCount               number | null
      Driver Snapshot visibility.
  hasEverHadTrip                  boolean | null
      Fresh-organization composition.
  checklistComplete               boolean | null
      Fresh-organization composition and the checklist banner (unchanged).
Rules:
  - null ALWAYS means "could not be loaded". That section renders a visible "unavailable" row in the calm group. It is
    never treated as zero and never silently omitted.
  - EXCLUDED: business_stage, plan / pricing tier, self-reported size, membership counts, dispatcher presence, vehicle
    counts, historical averages, trailing windows.
  - The composition function is pure (composeOperationsBrief(signals) → ordered section list). It lives in a
    *-core.ts module with unit tests, like trip-readiness-core.

======================================================================
SIGNAL STABILITY
======================================================================
A. INSTANTANEOUS signals (safe for local defaults, badges and counts):
   - single active driver / vehicle → PROG1 prefill
   - attention / pending / preparation counts → the numbers shown inside a section
B. STRUCTURAL signals (safe for section VISIBILITY, and they change rarely):
   - activeDriverCount >= 2 (Driver Snapshot)
   - activeRecurringCount > 0 (Recurring block)
   - hasEverHadTrip (fresh-organization composition)
   - linked Driver (Drive nav, unchanged)
   - admin capability (Settings nav, unchanged)
C. VOLUME / STATE signals (these change daily):
   - attention > 0, pending > 0, tomorrow preparation > 0, recurring missing > 0, proof review > 0
Anti-flip-flop rule (the simplest stable rule):
  - NAVIGATION never changes with any B or C signal. Only identity and capability facts change navigation, exactly
    as today.
  - The Overview's SET of components never changes with C signals. Only their ORDER and their DENSITY (full row vs
    one line in the calm group) change. Each such move is explained by the section's own visible count ("2 need
    preparation"). So Monday/Tuesday differences are "tomorrow needs work today", not a different layout.
  - B signals may add or remove a whole section, but only where the destination stays in navigation (Recurring Care)
    or the information is carried elsewhere (Driver Snapshot → Active Now / Dispatch).
  - No hysteresis, no trailing averages. Explicit current operational state is the rule. Nothing here needs
    smoothing, because nothing structural keys off volume.

======================================================================
OPERATIONS BRIEF PRIORITY MODEL
======================================================================
One deterministic ladder. The composition returns sections in this order; a section is placed in its WORK slot when
its condition holds, and otherwise renders as one line in the CALM group (or is omitted where stated):
  P0  Needs Attention             when attentionCount > 0
  P1  Requests awaiting review    when pendingRequestCount > 0
  P2  Today (Active Now + Next Departures), when the day has live or upcoming trips:
        dayState = ACTIVE_DAY, or carryover active trips
  P3  Tomorrow                    when tomorrowNeedsPreparationCount > 0
  P4  Recurring Care              when recurringMissingCount > 0
  P5  Proof of Service            when proofReviewCount > 0
  P6  CALM group: one Panel of one-line summaries, in this fixed order, each with its link:
        Tomorrow         (all ready / nothing scheduled)
        Requests         ("No requests awaiting review")
        Recurring Care   (covered; omitted when activeRecurringCount = 0)
        Proof of Service (ready for review / nothing from yesterday)
        Driver Snapshot  (only when activeDriverCount >= 2; see DRIVER SNAPSHOT)
      plus any "… unavailable" line for a null summary
Terminology is neutral: "Needs attention", "Waiting for review", "Needs preparation", "Needs scheduling", "Needs
review". Nothing is called "urgent".
Semantics check:
  - P0 is the only tier of proven, today-scoped deviations (an exception, a missing assignment or a stale location on
    a trip happening today).
  - P1 is undecided inbound demand. It may be for today, which is why it sits directly under P0.
  - P2 is time-bound monitoring of today.
  - P3–P5 are preparation and administrative work that is not time-critical within the hour.
The Today headline stays at the top of the Brief: "All clear" / "Nothing scheduled today" / "No new trips scheduled
today" / unavailable, using the existing states.
Below the Brief, the existing "today" section (tables and Activity Log) is UNCHANGED in PROG3B (see OPEN QUESTIONS
Q1).

======================================================================
ATTENTION
======================================================================
  - Rule: attentionCount > 0 → Needs Attention is the FIRST Brief section (P0), for 1 vehicle or 30. There is no
    threshold.
  - When attentionCount = 0: the separate Needs Attention panel is NOT rendered. The Today headline carries one line,
    "Nothing needs attention right now", so a calm day does not open with an empty warning panel.
  - Unchanged: the 5-row cap with "+N more in Dispatch", the "N trips need a driver" line, and the Assign / Open Trip
    actions.
  - When attentionCount is null (today unavailable): the existing "Today's operations unavailable" state is kept.

======================================================================
PENDING REQUESTS
======================================================================
  - pendingRequestCount > 0 → P1, directly under Attention. The copy is unchanged: "N requests", the oldest date, and
    "Review requests" → /operations/requests?state=pending.
  - = 0 → one calm line, "No requests awaiting review".
  - An open trip exception (P0) outranks a pending request: P0 is a proven problem on a trip already committed for
    today, while a request is undecided demand.

======================================================================
NEXT DEPARTURES
======================================================================
  - Kept, inside the P2 Today block, beside Active Now, with the current 2-hour window.
  - It shows at most 5 rows plus "View today's trips" (anchor to the Upcoming Trips table below). The cap reuses the
    Brief's existing ATTENTION_ROW_LIMIT = 5, for consistency rather than as a size threshold.
  - Its empty state ("Nothing departing soon") renders ONLY when Active Now has content. When both are empty on an
    active day, the Today block collapses to one headline line ("Next trip at 4:15 PM" from todayTrips, or "No more
    trips today").
  - It is never moved below P3–P5.

======================================================================
DRIVER SNAPSHOT
======================================================================
Rule (structural, stable):
  - activeDriverCount >= 2 → "On trip now: X of N active drivers" as a line in the CALM group, with View Dispatch.
  - activeDriverCount == 1 → omitted. The single driver's live state is already in Active Now, and Dispatch and
    Drivers stay in the nav.
  - activeDriverCount == 0 and hasEverHadTrip → a WORK row placed after P1: "No active drivers — trips can't be
    assigned", with "Set up drivers" (/operations/drivers). This is actionable and never hidden.
  - activeDriverCount == 0 and a fresh organization → carried by the checklist ("Driver setup"); no separate row.
  - null → "Driver snapshot unavailable" line in the calm group.
No action becomes unreachable: Dispatch and Drivers are always in the nav.

======================================================================
TOMORROW
======================================================================
  - tomorrowNeedsPreparationCount > 0 → P3 work row: "N trips · X need preparation" → Review tomorrow.
  - Otherwise → calm line: "N trips · All ready" or "Nothing scheduled for tomorrow" → Review tomorrow.
  - It is always present, because tomorrow is meaningful at every size. No size threshold.
  - null → "Tomorrow unavailable" in the calm group.

======================================================================
RECURRING CARE
======================================================================
  - recurringMissingCount > 0 → P4 work row, with the existing copy plus "Review recurring care".
  - activeRecurringCount > 0 and no missing occurrences → calm line "Recurring care is covered".
  - activeRecurringCount == 0 → omitted from the Overview. There is no empty "No recurring transportation set up"
    block. The route stays in the nav, where the empty page explains the feature.
  - null → "Recurring care unavailable" line.
Copy alignment (retained open item, NOT PROG3B): the block still says "rides" in two places.

======================================================================
PROOF OF SERVICE
======================================================================
  - proofReviewCount > 0 → P5 work row, with the existing copy, the evidence-gap line and "Review".
  - proofCompletedCount > 0 and no review needed → calm line "Yesterday's completed trips are ready for review" with
    "Open".
  - proofCompletedCount == 0 → calm line "Nothing from yesterday to review" with "Open".
      - It is kept rather than omitted, because Proof of Service has no sidebar entry. The Overview row is its
        stable entry point and must not disappear.
  - null → unavailable line.
Ordering: after Attention (P0), Requests (P1), Today (P2), Tomorrow (P3) and Recurring gaps (P4). It is
administrative/revenue review of yesterday, not today's operation.

======================================================================
ASSIGNMENT ATTRIBUTION
======================================================================
Stored facts:
  - trip_assignments.assigned_by (auth user), assigned_at, ended_at, end_reason
  - the reassign reason is stored as end_reason on the ENDED row; the default is 'reassigned'; system values are
    'trip_completed', 'trip_cancelled' and 'no_show'
  - trip_events has driver_assigned / driver_reassigned with actor_user_id
  - audit_events holds the same records
Smallest meaningful surface: Trip Detail → Current Status, below Driver. It is shown for EVERY viewer and every
organization; there is no hasDispatcher condition, because attribution is a fact, not a mode. Copy:
  - "Assigned by <name> · Sep 25, 7:42 AM", for a first assignment.
  - "Reassigned by <name> · Sep 25, 7:42 AM", when an earlier assignment was ended with a non-system end_reason.
  - Plus "Reason: <text>", only when that end_reason is operator-entered: not 'reassigned', and not a system value.
  - "<name>" resolves as:
      - "you", when assigned_by = the viewer;
      - the member's display name, when the viewer's RLS can read it (Organization Admins can read their
        organization's user_profiles);
      - "a team member", otherwise. This is the case for Dispatchers viewing someone else's assignment.
  - assigned_by null (legacy / system) → "Assigned · Sep 25, 7:42 AM".
Nothing is inferred beyond the recorded action: no "responsible dispatcher" and no blame language.
Not in PROG3B:
  - Operations Brief attribution: not needed.
  - An Activity feed of assignments: that needs list_activity_events' action allowlist changed, which is a migration.
  - Names for Dispatcher viewers: that needs a new read path. See BACKEND IMPACT.

FRESH ORG EXPERIENCE
======================================================================
Fresh organization = hasEverHadTrip === false AND checklistComplete === false. Both are facts.
Overview shows ONLY:
  1. The checklist banner, as the primary block (unchanged component and items).
  2. A single "Get started" panel:
       - "Create your first trip" (/operations/trips/new).
       - Organization Admin only: "Set up website requests" (/operations/settings/website-requests).
       - Organization Admin only, when there is no active linked driver: "I also drive" (Settings → My Access).
  3. Requests awaiting review, only when pendingRequestCount > 0 (an inbound request can arrive before the first
     trip).
Suppressed:
  - the empty Needs Attention, Active Now and Next Departures panels
  - the Driver Snapshot, Recurring, Proof and Tomorrow zero rows
  - the lower "today" SummaryStrip of zeros and the empty tables and Activity Log
This state ends permanently at the first trip. Trips are never deleted in normal operation, so it cannot flip back.
