ADDENDUM — P1-COMM-D1R: FORM VERSION CONCURRENCY REVIEW
==================================================
Question: does "6 parallel first saves -> 1 row, version 6, 6 audits" mean identical concurrent saves inflate version/audit?

1. Classification of the ORIGINAL result: A — SIX DIFFERENT CONFIGURATIONS. The original script sent, for caller i, 
   p_title => 'Concurrent title i', p_submit_label => 'Send i', p_confirmation_message => 'Thanks i' (all other arguments
   equal). Six distinct titles/labels/messages = six committed content changes (1 creation + 5 changes) -> version 6 and 6
   audit events were correct, and the script's own comment said so. The version semantics were not violated; the test simply
   never exercised the identical case.
2. Implementation (unchanged, no fix needed): save_website_request_form takes a per-organization advisory lock, reads the
   row FOR UPDATE, canonicalises the input (trim, control-character checks, de-duplicated/sorted service list), and
   - no row -> insert version 1 + one audit (created=true);
   - content identical and status identical -> returns changed=false, NO update, NO version bump, NO audit;
   - status-only change (Draft <-> Ready) -> audit, version unchanged (a real state change, not a content change);
   - content change -> version+1 and one audit.
   Concurrent callers therefore serialise on the lock; each later caller compares against the committed row.
3. Tests added (supabase/tests/website_requests_form_concurrency_test.sh, 6 separate psql processes, same Organization Admin,
   the exact per-caller payloads are printed at the top of the script output):
   CASE A identical first saves            -> 1 row, version 1, 1 audit, exactly 1 caller changed=true.
   CASE B six different configurations     -> 1 row, version 6, 6 audits, 6 callers changed=true (the original scenario).
   CASE C two groups of three identical    -> 1 row; version == audits == callers reporting a change; audited versions are
                                              exactly 1..V with no gap/duplicate. V depends on how the two groups interleave in the
                                              (arbitrary) serialisation order (observed 2 and 4 over repeated runs), so the test
                                              asserts the invariant, not a fixed number.
   CASE D same content, different whitespace / service order / duplicate service -> canonicalised: 1 row, version 1, 1 audit.
   CASE E (added at release) identical saves against an EXISTING form (version 1, 1 audit) -> version stays 1, still 1 audit,
                                              0 callers report a change.
   Every case also asserts no caller errored. Ran 5 times: 0 failures each time. Existing SQL test F5 (sequential identical
   save: version 1, changed=false, no new audit) still passes (37/37).
4. Audit / Activity: no new audit subsystem, no code change. Creation and update share website_request_form_updated;
   Activity already distinguishes them ("created" vs "updated", from the audit's created flag). Identical no-op saves produce no
   event.
5. Result: NO PRODUCT DEFECT. Only the test was extended. Production release status of D1 unchanged (READY after owner review;
   migration first, app second). ACL contract 0 of 28. Nothing deployed, pushed or committed; Zenward-Web untouched; D2 not started.
