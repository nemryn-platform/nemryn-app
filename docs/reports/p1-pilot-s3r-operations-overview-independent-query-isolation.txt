ONBOARDING ISOLATION
-------------------------
`getOnboardingChecklist` is now started as its own promise, caught with
`.catch(() => null)` (a safe, fixed `console.error("[operations]
getOnboardingChecklist failed")` log, no dynamic error content). Per this
phase's own §4, no dedicated "unavailable" UI treatment was added: this is
a low-priority setup banner, not operationally load-bearing, and
`OnboardingChecklistBanner` already had an established "stop rendering
entirely" precedent (once setup is complete). The component's null-check
was extended one line: `if (checklist === null || checklist.isComplete)
return null;` — on a genuine fetch failure the banner is simply omitted,
never rendered as complete, never rendered with a fabricated count. This
was the documented, deliberate choice per §4's own explicit allowance
("omission is acceptable provided unknown is not presented as completed").

DRIVER SNAPSHOT ISOLATION
------------------------------
`getDriverSnapshot` is now started as its own promise, caught with
`.catch(() => null)` (page.tsx) — and, for consistency, the same fix was
applied to `getOperationsBrief()`'s own (still currently uncalled) second
call site in operations-brief.ts. `OperationsBriefData.driverSnapshot`
became `OperationsBriefDriverSnapshot | null` (the smallest type change
required — a straight pass-through nullable field, mirroring
`tomorrowReadiness`'s exact established convention; no Result<T>
framework). `DriverSnapshotBlock` gained a `snapshot === null` branch
rendering "Driver snapshot unavailable" with the same compact Panel shape
every other Brief block already uses, before its existing
`hasDrivers`/`totalActiveDrivers` logic (which is now unreachable when
`snapshot` is null, since the null branch returns first).

REQUEST SUMMARY ISOLATION
------------------------------
Identical shape to Driver Snapshot: `getRequestSummary` started as its own
independently-caught promise (both in page.tsx and, for consistency, in
`getOperationsBrief()`). `OperationsBriefData.requestSummary` became
`OperationsBriefRequestSummary | null`. `RequestsAwaitingReviewBlock`
gained a `summary === null` branch rendering "Request summary unavailable"
in the same compact Panel shape, before its existing
`hasPending`/`pendingRequestCount` logic.

UNKNOWN VS ZERO
-------------------
Hard invariant preserved and unit-tested: `driverSnapshot`/`requestSummary`
being `null` never renders as `0 active drivers` / `0 requests` / "No
drivers set up yet" / "No requests awaiting review" (all real,
successfully-fetched-zero copy, reserved for the actual `{
totalActiveDrivers: 0, ... }` / `{ pendingRequestCount: 0, ... }` cases).
4 new focused unit tests added to operations-brief-core.test.mjs:
  - driverSnapshot null passes through unchanged, never coerced to zero
  - requestSummary null passes through unchanged, never coerced to zero
  - driverSnapshot/requestSummary null does NOT force dayState into
    UNAVAILABLE (each failure stays independently representable, never
    coupled to Today's Operations' own contract)
  - driverSnapshot/requestSummary null AND data also null: every failure
    stays independently null, never conflated into one combined state

OPERATIONS BRIEF CONTRACT
------------------------------
`OperationsBriefData.driverSnapshot`/`.requestSummary` changed from
required to `T | null` — the smallest type change required, exactly
mirroring the already-established `tomorrowReadiness`/`recurringCare`/
`proofOfService` nullable-summary convention (each with its own doc
comment explaining the null-only-on-genuine-failure contract).
`deriveOperationsBrief`'s corresponding parameters changed to `T | null`;
the function body needed NO other change, since both values were already
pure pass-through fields (never derived from `data`/`getTodaysOperations`).

UNAVAILABLE contract (dayState/attention/activeNow/nextDepartures/
unassignedCount) was not touched in any way. Tomorrow Readiness, Recurring
Care, and Proof of Service were not touched in any way — confirmed by

`RecurringCareBlock`/`ProofOfServiceBlock` or their corresponding
