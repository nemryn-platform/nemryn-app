5. DATA-FETCH INTEGRATION
--------------------------------
`getTodaysOperations()` is called EXACTLY ONCE per /operations render —
the same single call the page already made before this phase, now also
feeding the Brief via a pure derivation, not a second query. The full
call sequence, in src/app/operations/page.tsx:

  const data = await getTodaysOperations(organization.organizationId, organization.organizationTimezone);
  const [checklist, driverSnapshot] = await Promise.all([
    getOnboardingChecklist(organization.organizationId),
    getDriverSnapshot(organization.organizationId),
  ]);
  const brief = deriveOperationsBrief(data, driverSnapshot, new Date());

`deriveOperationsBrief` (operations-brief-core.ts, S1B, untouched) is a
PURE function — it performs no I/O of its own, it only transforms the
already-fetched `data` plus the already-fetched `driverSnapshot` into
`OperationsBriefData`. The convenience `getOperationsBrief()` wrapper
(S1B, also untouched) — which internally calls `getTodaysOperations()`
a SECOND time — was deliberately NOT used here; it remains available
for any future caller that has not already fetched Today's Operations
data itself.


6. DUPLICATE-QUERY AVOIDANCE
------------------------------------
Measured explicitly, per instruction: before this integration decision,
calling both `getTodaysOperations()` (for the existing page sections)
and the S1B convenience `getOperationsBrief()` (for the Brief) would
have executed `getTodaysOperations()` TWICE per render — once directly,
once again inside `getOperationsBrief`'s own `Promise.all`. This was
identified and explicitly rejected.

Resolution (approach A from the phase's own two offered options, in
spirit — a minimal composition adjustment): `operations-brief.ts`'s
previously-private `getDriverSnapshot` function was exported (one
keyword, one doc comment — see the diff in §3) so `/operations` can
compose the Brief itself from data it already has: one
`getTodaysOperations()` call (shared with every existing page section,
unchanged from before this phase), one `getDriverSnapshot()` call (the
one genuinely new query S1B introduced, run in parallel with the
onboarding-checklist fetch via `Promise.all`), and one pure
`deriveOperationsBrief()` call to combine them. Confirmed via direct
code reading of the final `operations/page.tsx`: `getTodaysOperations`
is referenced exactly once in the entire file. No other file in the
request path calls it either (`getDriverSnapshot` and
`deriveOperationsBrief` do not call it).

--------------------------------------
`ATTENTION_ROW_LIMIT = 5`, exactly the phase's own recommended cap.

existing priority order — no re-sort) render, followed by a single
restrained link: "+N more in Dispatch" → `/operations/dispatch`.

existing (also-available) full Needs Attention table further down the

with no edge case beyond "fewer than 5" (already exercised live on
every fixture organization tested — see §17/§18).

A real defect was found and fixed during this phase (not merely
audited after the fact): `ActiveNowBlock`/`NextDeparturesBlock`
originally used the shared `SectionHeader` component, which renders an
`<h2>` internally — but every Brief sub-block must nest as `<h3>` under
the Brief's own `<h2>Operations Brief</h2>`, matching `NeedsAttention

Attention -> H2: Active Now -> H2: Next Departures -> H3: Driver
Snapshot -> H2: Needs Attention (existing) -> ...` — an inconsistent,
non-nesting structure a screen-reader heading-scan would find
confusing. Fixed by replacing both `SectionHeader` usages with a small
local `BlockHeading` helper rendering the identical visual styling at
`<h3>`. Re-verified AFTER the fix: `H1 -> H2 Operations Brief -> H3
(x4: Needs Attention, Active Now, Next Departures, Driver Snapshot) ->
H2 (existing panels, unchanged, flat siblings as before)` — a clean,
logical nesting, with zero visual change (confirmed via a final
screenshot, pixel-identical layout to the pre-fix version, since
`typography.subsectionHeading` styling is shared regardless of tag).

Other accessibility properties confirmed by direct code review: every
status is communicated by a `StatusBadge` (label text + color, never
color alone — the same existing, already-accessible component every
other Operations surface uses); every action is an explicit `<Link>`/

Dispatch", "Set up drivers" — never a bare icon, never "click here");
every list uses a real `<ul>`/`<li>` structure; the `WarningCircle` icon

`onClick`-only `<div>` anywhere in the component).
