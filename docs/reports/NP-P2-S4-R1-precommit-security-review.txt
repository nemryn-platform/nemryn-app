2. GENUINE DEFECTS AND MINIMAL CORRECTIONS
======================================================================
R1-1. Ambiguous timeout + page reload could create a duplicate REBOOKING (client only). FIXED.
- Defect:
  - The idempotency key lived only in the open form's React state.
  - If the network dropped after the server committed and the person then RELOADED the page, the reopened form made a
    NEW key.
  - For a conversion this was still safe (ZW004 already_converted).
  - For a rebooking it would have created a second pending Request: a legitimate operation from the server's point of
    view.
- Fix (src/components/growth/BookingRequestDialog.tsx only; no database or action change):
  - the key is written to sessionStorage, keyed per action and subject
    ("nemryn.plus.booking.<mode>.<opportunityId|contactId>"), at SUBMIT;
  - a reopened form restores it, until the server confirms success; then it is removed;
  - a restored form says "Continuing an earlier attempt. If that request was already created, you'll be shown it
    instead of creating a second one.", and the confirmation then shows "This request had already been created;
    nothing new was added.";
  - storage failures fall back to a fresh key (no crash).
- Proven by E2E C4 / C5 (new): a stored key of a committed rebooking -> reload -> resubmit gives the ORIGINAL Request,
  no new Request, the replay note, and the key cleared.
- Residual, by design: sessionStorage is per browser tab. A retry from a DIFFERENT tab or device after an ambiguous
  timeout uses a new key. Staff see the earlier Request in Linked requests, which reloads with the page. A server-side
  "same contact + same details within N minutes" guard would close this further, but changes product semantics.
  Owner decision OD-8 below.
No other code correction. Tests were added (section 7).

3. IDEMPOTENCY AND REPLAY FINDINGS
======================================================================
- Order inside both RPCs:
  1. authority (Plus write, Core role);
  2. key shape;
  3. advisory lock (organization, key);
  4. replay lookup;
  5. eligibility;
  6. Core insert.
- Replay-before-eligibility is deliberate and correct. A replay must succeed even though the opportunity is now
  converted, or its contact archived since: those are consequences of the original operation. Authority is never
  skipped, because it precedes the lookup.
- An in-flight original blocks a concurrent replay on the advisory lock until commit. If the original rolled back, the
  retry finds no attribution and performs the operation once (CONC-C1/C2/C8/C10).
- Replay after Core changed the Request: returns the same request_id and its CURRENT Core state (declined, accepted),
  changed=false, with zero new Request / event / activity / audit rows (SQL X1). The UI presents it as the existing
  Request with its live status.
- Leak resistance:
  - the lookup is scoped to the caller's organization, and the caller already holds read rights there;
  - a key of another operation returns ZW006 with the same generic message as any invalid input;
  - keys are not enumerable, because there is no read path by key.
- Finding (low; documented, no change): if a REBOOKING link is later corrected to another contact
  (plus_update_request_attribution, P2-S3), a replay naming the ORIGINAL contact is refused (ZW006), because the key
  now belongs to the corrected link. Safe: no duplicate and no leak. Only a retry racing a correction is affected.
- hashtext collisions between different keys only add serialization; there is no correctness effect.

4. CORE REQUEST ATOMICITY AND LOCKING FINDINGS
======================================================================
- Atomicity: each RPC is one plpgsql function, so one transaction. log_transportation_request, the attribution, the
  stage change, the activities and the audit commit or roll back together (SQL F1 / F3; CONC-C10).
- Lock order, conversion: advisory(org, key) -> plus_opportunities FOR UPDATE -> plus_contacts FOR SHARE -> Core
  INSERTs -> Plus INSERTs.
- Lock order, rebooking: advisory -> contact FOR SHARE -> Core -> Plus.
- No cycle with any existing writer. Verified in source:
  - plus_update_opportunity / stage / lost / reopen: opportunity FOR UPDATE (then the contact via
    _plus_require_active_contact);
  - P2-S3 link / correction: opportunity FOR SHARE, then contact FOR SHARE;
  - plus_update_contact and plus_archive_contact: the contact FOR UPDATE ONLY;
  - plus_log_contact_activity: the contact FOR NO KEY UPDATE only;
  - no other path takes the advisory lock;
  - Core never touches Plus.
- Contact archive vs conversion and rebooking: serialized both ways (CONC-C7, C9).
- The Core decision RPCs run independently of an in-flight conversion; the P2-S3 CONC-A4 analogue holds.

5. service_type ASSESSMENT AND RECOMMENDED SOLUTION
======================================================================
Facts (current source):
- log_transportation_request (Core) has NO service_type parameter. Every staff-logged Request (Core's own
  "Log Request" form) already has service_type NULL. Only trusted website intake (_create_public_request) sets it. So
  P2-S4 matches existing Core behaviour; it is a genuine gap, but not a regression.
- Downstream with NULL:
  - Request detail omits the "Service requested" row; there is no error.
  - The Request Hub list does not show the service at all.
  - New Trip and Recurring Care use service_type ONLY to pre-select the wheelchair requirement
    (wheelchair_transportation). A converted wheelchair opportunity's Request therefore gets no wheelchair
    pre-selection, and the dispatcher sets it manually. That is the only operational consequence.
  - Notifications show no service label.
  - Plus Linked requests shows "Request".
- Classification downstream: the opportunity keeps its service_type (Plus); the Core Request does not. Reporting by
  service across Core would miss converted and staff-logged Requests.
Recommended solution, in a SEPARATE, coordinated, owner-approved Core slice ("NC-REQUEST-SERVICE-TYPE"):
  1. Core migration: replace log_transportation_request with ONE trailing parameter, `p_service_type text default
     null`.
     - Signature change: it must be DROP + CREATE in the same migration. Keeping both overloads would make 14-argument
       calls ambiguous.
     - Backward compatible for every existing caller:
       - the app calls by NAMED arguments;
       - the P2-S4 RPCs call positionally with 14 arguments;
       - the trailing default keeps both valid.
     - Validate against the SAME closed set as transportation_requests_service_type_check, preferably by relying on
       the CHECK and mapping it to ZW006, so the list is never duplicated (it then includes airport_transportation
       automatically once NC-INTAKE-AIRPORT-S1 ships).
     - Grants: authenticated only. Update the privilege contract signature, mutation-api.md and database.types.ts.
  2. Core app (optional, same slice): a service select on Core's Log Request form.
  3. Plus follow-up (P2-S4.1, small):
     - conversion passes opportunity.service_type. The Plus closed set is a subset of Core's: no mapping is needed.
     - rebooking: an optional staff choice in the form.
     - Tests: the Request carries the service, and wheelchair pre-selection works for a converted wheelchair
       opportunity.
- Dependency order:
  - NC-INTAKE-AIRPORT-S1 (if first; widens the CHECK)
  - -> NC-REQUEST-SERVICE-TYPE (Core; review Core request / creation / privilege suites)
  - -> P2-S4.1 (Plus passes it).
  - P2-S4 itself can ship BEFORE these. It does not depend on them, and the gap is visible and harmless (NULL, like
    staff-logged Requests).
- Code paths to review in that slice:
  - Core: log_transportation_request; src/app/operations/requests/new/actions.ts; log-request option lists;
    request_mutation_* / create_trip_* / request_trip_passenger_integrity / privilege_contract tests.
  - Plus: plus_convert_opportunity_to_request, plus_create_rebooking_request, booking-core, BookingRequestDialog.
  - Website intake: unaffected (_create_public_request is separate).
- Not done here, as instructed: no Core function changed, no direct Core write, no change to the airport workstream.
