4. ADDRESS-DIGEST SECURITY ASSESSMENT (R1)
-----------------------------------------
The full comparison of plain SHA-256 and keyed HMAC-SHA-256 is in the decision lock §3. In summary:
- HMAC only helps against an attacker who has the digests but neither the plaintext (which sits in the same tenant
  row) nor the key.
- It would need new secret custody (Vault in every environment), key versioning and rotation semantics (a schema
  change), and a hard deployment dependency.
- No material blocker was found for plain SHA-256, given the narrow equality purpose and the absence of client read
  access.

5. SELECTED DIGEST IMPLEMENTATION AND RESIDUAL RISKS
---------------------------------------------------
- The digest is:

    sha256(convert_to('nemryn.plus.consent-address.v1|' || organization_id || '|' || kind || '|' || normalized, 'UTF8'))

  - stored as lowercase hex; built-in sha256(), no extension;
  - kind = email | phone (SMS and voice share the phone);
  - normalized = lower(btrim(email)) or the phone's digits only;
  - computed only on the server, from the locked contact row;
  - stored for grants only. Revocations cover the channel whatever the address.
- Residual risks:
  - (a) Not anonymisation. A phone digest is reversible by enumeration of about 10¹⁰ numbers; an email digest by
    dictionary. It is personal data.
  - (b) PD-11 erasure must remove or neutralise digests together with the plaintext. The append-only triggers make
    any such procedure an explicit, reviewed migration.
  - (c) Reformatting a phone so that its DIGITS change (for example, adding a leading "1") yields address_changed.
    That is the conservative direction: consent stops being effective until it is re-recorded.
  - (d) Only someone with database-owner access can read digests. No client role can (column-level SELECT, ZD-240).

7a. The write algorithm (_plus_append_consent):
1. _require_plus_write: ZW002 when the caller cannot read; ZW001 in read_only or with a read grant.
2. Validate the idempotency key with the existing _plus_require_idempotency_key (8–200 characters of
   [A-Za-z0-9._:-]).
3. Validate the input:
   - the channel and purpose sets;
   - staff methods only (do_not_contact / web_form / imported → ZW006);
   - captured_at within now − 366 days … now + 5 min;
   - note ≤ 500 characters, trimmed, blank = NULL;
   - a correction requires a note.
4. Lock the contact FOR NO KEY UPDATE. A missing or redacted contact gives ZW002.
5. Replay: the same key with the same contact, pair, status and correction → the existing row with changed=false.
   Otherwise ZW006 idempotency_conflict. A concurrent first use is caught as unique_violation and resolved the same
   way.
6. Correction: it must reference the pair's current latest row (else ZW003). A do_not_contact system row → ZW004.
7. Grant rules:
   - an archived contact → ZW004;
   - Do not contact → ZW004 do_not_contact;
   - no address for the channel → ZW006;
   - captured_at earlier than the latest revocation, excluding the row being corrected → ZW004 stale_evidence.
   Revocations are allowed for active and archived contacts, while DNC is on, and for any date.
8. Insert. The server sets recorded_by = auth.uid(), recorded_at = now(), seq, and (for grants) address_digest.
9. One audit_events row: plus_consent_granted / plus_consent_revoked, after_data = {consent_id, channel, purpose,
   captured_via, correction}.

Error codes are the existing ZW001 / 002 / 003 / 004 / 006 only. A caller cannot supply an actor, time, order,
digest or status parameter (verified by catalog; a named call with p_recorded_by → 42883).

10. DNC TRANSITION BEHAVIOUR (ZD-233)
------------------------------------
- false → true (plus_update_contact):
  - in the same transaction and under the existing FOR UPDATE lock, one revoked row (captured_via = do_not_contact,
    recorded_by = the editor, captured_at = now(), no note or digest, a system key "dnc:<hex>") is appended for each
    pair whose latest row is granted;
  - one audit row per revocation;
  - no activity row;
  - previous grants are untouched;
  - the released plus_contact_updated audit is unchanged (field names only).
- true → false: nothing is written. Every pair stays revoked (no revival). A grant dated before the DNC switch-on is
  refused (stale_evidence). A system revocation can never be corrected (ZW004).
- While DNC is on: grants → ZW004; revocations accepted; every pair resolves to suppressed_do_not_contact.
- Unchanged:
  - the plus_update_contact signature, grant, authorization, version token (ZW003) and archived rule (ZW004);
  - owner logic, the identical-values no-op (changed=false), and the quote DNC acknowledgment (ZD-223);
  - the booking DNC reminder and Growth Agent DNC suppression.
- Tests: N1 to N9, U-DNC0 to U-DNC2, I1, and concurrency S5, S6, S9 and S10.

16. DIFFERENCES FROM THE APPROVED DESIGN
----------------------------------------
- _plus_consent_address_digest takes the organization id (4 arguments instead of 3). This is the R1 domain separation,
  documented in design §2.6 and the decision lock §3.
- plus_list_contact_consent_events adds total_count, following the plus_list_contact_activities precedent, for the
  S6-B "History (n)".
- Two internal helpers were added: _plus_append_consent (the shared body) and _plus_consents_revoke_for_dnc (the DNC
  step). Both have no client EXECUTE and are listed in the contract.
- Stale-evidence precision: the row being corrected is excluded from the comparison (ZD-231 / ZD-234).
- A system DNC revocation cannot be corrected (ZD-233).
- unique (seq) is added as an explicit constraint; an identity column alone is not unique.
- A defensive TRUNCATE guard is added: a statement trigger, in addition to the row trigger.
All are recorded in the design / decision lock. No approved behaviour was replaced.

18. read_only OPT-OUT LIMITATION AND NP-P4 PREREQUISITE
-------------------------------------------------------
- In read_only, neither a revocation nor a DNC change can be recorded (ZW001), by design (ZD-239, tests A9 / A10).
  Nothing is sent in that state; Plus has no sending at all.
- MANDATORY before NP-P4 enables any outbound communication:
  - a separately reviewed, subscription-independent opt-out mechanism;
  - it must remain usable while Plus is expired, cancelled, read_only or otherwise refusing CRM writes.
  It is recorded in ZD-239, access model §6.5b and design §4.1. It is not implemented, and no read_only exception
  exists.
