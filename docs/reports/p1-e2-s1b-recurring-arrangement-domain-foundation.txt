CREATED_BY DECISION
------------------------------------------------------------------------
Audited every `references auth.users (id)` column across every
migration in this schema before choosing a shape (not assumed): three
distinct patterns exist —
  1. Identity-owning tables (`user_profiles.id`, `memberships.user_id`,
     `platform_admin_grants.user_id`) use `ON DELETE CASCADE` — these
     tables ARE the identity layer, so they vanish if the auth user
     truly vanishes.
  2. `drivers.user_id` uses `ON DELETE SET NULL` — explicitly documented
     in domain-model.md §H as Driver's own distinct case (a Driver row
     must survive intact even if login access is fully removed, since
     historical Trip/TripAssignment references `Driver.id`, never
     `user_id`).
  3. Every actor/provenance reference (`trip_assignments.assigned_by`,
     `trip_exceptions.created_by`/`resolved_by`, `trip_events.
     actor_user_id`, `trip_notes.author_user_id`, `audit_events.
     actor_user_id`, `driver_invites.invited_by`/`accepted_by`) uses a
     bare `references auth.users (id)` with NO `on delete` clause at
     all (Postgres default `NO ACTION`) — seven precedents, unanimous.

`recurring_arrangements.created_by` follows pattern 3 exactly: nullable,
bare reference, no `on delete` clause — it is provenance/history
(durable operational record, per this phase's own explicit
characterization), not identity, so pattern 1 does not apply; it is not
a distinct, separately-justified case like Driver, so pattern 2 does not
apply either. This does not block legitimate auth-user
cleanup/deletion any differently than the other seven precedents already
accept for the identical reason. The future S1D create RPC derives this
value from `auth.uid()` server-side; the browser never supplies it
(no client INSERT path exists at all in this phase — see MUTATION
BOUNDARY).

------------------------------------------------------------------------
DAYS-OF-WEEK VALIDATION
------------------------------------------------------------------------
PostgreSQL cannot contain a subquery directly inside a `CHECK (...)`
expression — a hard syntactic restriction (confirmed before writing any
SQL, not assumed), not merely a style preference. The dedup/sort/range
logic therefore lives inside a small, pure, `IMMUTABLE` SQL helper,
`public._is_canonical_days_of_week(smallint[])`, and the table's own
CHECK constraint calls it as a single function-call expression —
`check (public._is_canonical_days_of_week(days_of_week))`. Underscore-
prefixed, `revoke all ... from public`, never granted to `authenticated`
— no legitimate direct-client code path calls it (the table has no
authenticated INSERT/UPDATE grant at all this phase, and any future S1D
RPC runs `SECURITY DEFINER`, evaluating this CHECK under its own owner
privilege, not the caller's — the same reasoning already documented for
`is_valid_iana_timezone`'s own grant note).

ISO weekday numbering (1=Monday..7=Sunday) reused deliberately — the
exact vocabulary `EXTRACT(ISODOW FROM date)` already returns natively,
so the future S1C evaluator composes with zero translation layer.
Verified against every example the phase specified, both via the bare
function and via live INSERT attempts against the real CHECK constraint:

  {}              -> reject   (RA-04, and direct function call)
  {1}              -> accept  (direct function call)
  {1,3,5}          -> accept  (direct function call)
  {5,3,1}          -> reject  (RA-06, unsorted — never silently normalized)
  {1,1,3}          -> reject  (RA-05, duplicate)
  {0,1}            -> reject  (RA-07, out of range)
  {7,8}            -> reject  (direct function call, out of range)
  {1,2,3,4,5,6,7}  -> accept  (direct function call)

All 8 cases confirmed both by calling `_is_canonical_days_of_week`
directly and, for the cases the required test list names explicitly, via
a real `INSERT` against the live table.

STATUS INTEGRITY
------------------------------------------------------------------------
Vocabulary locked to exactly `active`/`paused`/`ended`
(`recurring_arrangements_status_check`, verified RA-02 rejects any other
value). Four targeted constraints, each independently verified live:
  - `paused` requires `paused_at is not null` (RA-14). The REVERSE
    direction — does a non-paused status require `paused_at` to be
    null — is deliberately NOT constrained: P1-E2-S1A1 did not settle
    whether `paused_at` is retained or cleared when an arrangement is
    ended directly from a paused state, and this migration does not
    presume an answer (carried forward explicitly, see OPEN ISSUES).
  - Non-`ended` status must not carry `ended_at`/`ended_reason` (RA-11/
    RA-12 exercise the inverse: `ended` without one or the other is
    rejected) — this direction IS explicitly locked by this phase's own
    instructions and is enforced.
  - `ended` requires both `ended_at` and a non-blank `ended_reason`
    (RA-11, RA-12, RA-13 for the valid shape) — mirrors `trips.
    cancellation_reason`/`trip_assignments.end_reason`'s own existing
    mandatory-reason precedent for terminal/closing transitions exactly.
No lifecycle TRANSITION is implemented or enforced here (no trigger
walks active→paused→ended) — only the STATIC SHAPE each status implies,
precisely matching the phase's own "design the constraint so future S1D
legal transitions can be implemented without schema surgery; do not
implement transitions themselves" instruction.

------------------------------------------------------------------------
TEXT / DATE CONSTRAINTS
------------------------------------------------------------------------
`pickup_description`/`destination_description`: nonblank
(`btrim(...) <> ''`, rejects whitespace-only per RA-09/RA-10, not only
the empty string) and length-bounded at 2000 characters — matching
`create_trip`'s own existing runtime validation of the identical two
fields exactly (`20260916110000_request_trip_passenger_integrity.sql`:
`btrim` nonblank, `length(...) > 2000` rejected). Enforced at the TABLE
level here (Trip's own equivalent validation lives only in the RPC, not
a table CHECK) — a deliberate strengthening, not an inconsistency: S1B's
own charter is a structural foundation that must reject malformed data
even before any RPC exists to validate it first, and the CHOSEN bound
(2000) is not a new number invented for this table, it is Trip's own
already-established number, reused.

`end_date is null or end_date >= start_date` (RA-08) — no maximum
duration invented, per the explicit instruction not to.

RLS MODEL
------------------------------------------------------------------------
`grant select on public.recurring_arrangements to authenticated;` — no
INSERT/UPDATE/DELETE grant to `authenticated` at all, matching the exact
precedent already established for `trip_events`/`audit_events` (both
structurally similar: real lifecycle/security semantics, deliberately
not client-writable until a controlled RPC mechanism exists). One SELECT
policy: `has_org_role(organization_id, array['organization_admin',
'dispatcher'])` — same organization only. Verified live: Org A admin and
Org A dispatcher both see the fixture (RA-22/23); Org B admin sees zero
Org A rows (RA-24); an inactive-membership actor sees zero rows despite
belonging to the right organization (RA-27); anonymous is denied outright
at the grant level, no rows returned even attempted (RA-26,
`permission denied for table recurring_arrangements` — not an empty
result set, a genuine privilege denial, since `anon` has no grant at
all).

MUTATION BOUNDARY
------------------------------------------------------------------------
Verified live, for every relevant actor, that no raw client mutation of
any kind exists on `recurring_arrangements`:
  - Org Admin raw INSERT: denied (RA-28, `permission denied`).
  - Dispatcher raw INSERT: denied (RA-29).
  - Raw UPDATE (Org Admin, on a row RLS would otherwise let them SELECT):
    denied (RA-30).
  - Raw DELETE: denied (RA-31).
  - Driver raw mutation: denied (RA-32).
  - A forged `organization_id` (Org A actor attempting to INSERT a row
    claiming Org B): denied (RA-33) — subsumed by the blanket no-grant
    boundary, verified explicitly anyway per the phase's own instruction.
Every denial occurs at the GRANT level (`permission denied for table
recurring_arrangements`), not merely at the RLS-policy level — meaning
even a future policy-authoring mistake (e.g. someone later adding an
overly permissive INSERT policy) would still not expose a raw mutation
path unless the grant itself were also separately widened. This is the
same defense-in-depth shape already used for `trip_events`/
`audit_events`.

TRIP COLUMN PRIVILEGE
------------------------------------------------------------------------
The HARD security requirement (§15) — verified two ways, not assumed:
  - Static introspection (RA-34): `has_column_privilege('authenticated',
    'public.trips', 'recurring_arrangement_id', 'UPDATE')` returns
    `false`. Postgres column-level GRANTs are additive and explicit —
    adding a new column to `trips` does not automatically add it to the
    pre-existing narrow `grant update (scheduled_pickup_at,
    appointment_at, pickup_description, destination_description,
    assistance_notes, instructions, pickup_facility_id,
    destination_facility_id) on public.trips to authenticated;` list
    from `20260830131700_rls_policies.sql` — this migration does not
    touch that GRANT statement at all, so it retains its exact original
    8-column scope, unchanged.
  - Live confirmation (RA-34b): an authenticated Org Admin attempting a
    real `UPDATE trips SET recurring_arrangement_id = ...` is denied
    (`permission denied for table trips`) — not merely theoretically
    unprivileged, empirically denied.
  - Regression check (RA-35): the pre-existing, already-granted
    `instructions` column remains genuinely updatable by the same actor
    — confirming this migration narrowed nothing it shouldn't have and
    widened nothing it shouldn't have.
