================================================================================
CREATE MUTATION
================================================================================
create_request_intake_integration(p_organization_id uuid, p_origin text).
Deviation from the conceptual (p_origin) signature, deliberately: a person can
administer several organizations, so the database cannot infer the workspace
from auth.uid() alone. p_organization_id is the caller's CURRENT workspace,
resolved server-side by the Server Action from the authenticated Membership
(the form carries only the website address), and the function re-authorizes it
with has_org_role -- so a crafted id for any organization the caller does not
administer is denied. Same convention as R4A's update_organization_settings.
Generated/fixed inside the function: external_id, integration_type='website',
is_active=false, actor (auth.uid() -> AuditEvent). No external_id / is_active /
type / created_by / service-role parameter exists (test SURFACE-1; and a
PostgREST call injecting external_id and is_active is rejected).

================================================================================
EXTERNAL ID GENERATION
================================================================================
_generate_intake_external_id(): 'web_' + 12 chars, alphabet
ABCDEFGHJKLMNPQRSTUVWXYZ23456789 (no 0/O/1/I), from pgcrypto
gen_random_bytes with `byte & 31` (no modulo bias) = 60 bits. Opaque,
non-sequential, URL/JSON-safe, encodes no org/user/name/sequence. Uniqueness by
the existing unique(external_id); the loop retries a collision up to 5 times.
500 generated IDs: all matched the format, all distinct. UI label is
"Integration ID" (never key/token/secret/password); the docs and UI state it is
a public identifier, not a secret. Internal helper, not executable by any
client role.

================================================================================
ORIGIN VALIDATION
================================================================================
_normalize_website_origin() (authority, in the database) mirrored by
normalizeWebsiteOrigin() in website-integration-core.ts (friendly pre-check),
with the SAME vector list asserted on both sides.
 Accepts: https://www.example.com, https://example.com, https://portal.example.
 com, example.co.uk, xn-- (punycode) hosts, optional port (:443 dropped).
 Normalizes: trailing slash; case; outer spaces.
 Rejects (44 vectors incl.): http; any path/query/fragment; userinfo;
 wildcards (*.example.com, https://*); javascript:/data:/ftp:; missing scheme;
 // and https:///; localhost/loopback/IP literals/IPv6; single-label or 1-char
 TLD; spaces/tabs/newlines; leading/trailing hyphen labels; underscores; bad
 ports (0, 99999, non-numeric); double trailing slash; non-ASCII IDNs
 (must be punycode); empty/blank/oversize.
 No localhost exception was needed: local testing uses a synthetic HTTPS origin
 and sets the Origin header on the server-to-server call. Sibling subdomains
 are never implied (exact origin match).

================================================================================
DUPLICATE / CONCURRENCY SAFETY
================================================================================
Multiple integrations per organization are supported (no one-per-org rule).
Smallest correct invariant: an organization cannot hold two website integrations
for the same normalized origin, enforced two ways:
 (1) partial unique index request_intake_integrations_org_origin_uidx on
     (organization_id, allowed_origins[1]) for single-origin website rows;
 (2) a per-organization advisory lock in create and update-origin, so a retry /
     second tab / different spelling of the same origin returns the EXISTING
     integration (changed=false) instead of erroring or duplicating.
A 10-per-organization cap bounds abuse. Legacy rows (NULL / multi-origin) are
outside the predicate.
Real-process tests (website_integration_concurrency_test.sh): 6 simultaneous
identical creates -> exactly 1 row, 1 audit, 1 shared Integration ID, 1 changed
=true, 5 changed=false, 0 errors. 4 simultaneous creates of 4 different origins
-> 4 rows, 4 IDs, 0 errors. Origin edit racing a create for the same target ->
never two rows for that origin.

OPEN ISSUES
================================================================================
 1. Origin OWNERSHIP is not verified: an Admin may register any https origin,
    including one another tenant also registers (the Integration ID selects the
    tenant; the origin is a constraint, and the same-origin invariant is per
    organization only). CORS uses the union of active origins. Acceptable for a
    pilot; a DNS/meta-tag ownership check is a possible later hardening.
 2. Legacy manual rows are listed and manageable, but the temporary production
    QA integration zenward-web-87553280 was deliberately not touched; its
    removal and the official Zenward integration creation remain for the R4E
    coordinated cutover. A legacy row with NO origin cannot be activated until an
    origin is set (intentional, since a null origin disables the RPC's origin
    check).
 3. Cap of 10 website integrations per organization is a pilot guard, not a
    product decision; easy to raise.
 4. Signature deviation from the conceptual create_request_intake_integration(
    p_origin): p_organization_id is server-supplied and DB-authorized (multi-org
    administrators make pure auth.uid() derivation ambiguous). Documented above.
 5. No built-in "Send test request" (per brief: prefer real flow evidence). The
    Setup instructions tell the admin to submit a clearly synthetic request from
    their own site; Connected only follows a real accepted Request.
 6. "Requests received" counts every Request ever tied to the integration
    (including ones later archived/cancelled in the Request Hub) -- it measures
    receipt, not open work.
 7. Public route unchanged: it still trusts the forwarded client IP for its
    per-client limit (pre-existing S4B behavior); the local E2E exploits that
    only by varying the header.
 8. Tracked, not addressed here (per brief): organizations.status /
    business_stage / service_area_description direct writes and the timezone
    default -> R4C/R4D audited-settings cleanup.
 9. R4B is uncommitted in the working tree (R4A is the last commit).
