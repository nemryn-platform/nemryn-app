NP-UI-P1b POST-RELEASE — SIDEBAR SCROLLBAR VISUAL REFINEMENT
===========================================================
Date: 2026-10-20.
Status: owner-approved. Committed on the dedicated branch np-ui-p1b-sidebar-scrollbar-polish, created from origin/main
9f42669 (PR #23 merge; also the current Production deployment). No production access.

1. ISSUE AND CAUSE
------------------
- The dark sidebar's nav list is the only scrolling element in the sidebar: `<nav aria-label="Primary">` with
  `overflow-y-auto` in src/components/operations/OperationsSidebar.tsx.
- On a short viewport, or with Growth expanded, the list overflows. Browsers that always show scrollbars (and
  headless Chrome) drew a 15px light-grey track and thumb on the graphite frame.
- In the 64px rail (tablet, or collapsed desktop) it took 15px of the width and pushed the icons off-centre.
- Not involved:
  - the Growth rail flyout (fixed-position, no overflow);
  - the workspace / account footer (outside the scroll area);
  - main content (its own container).

2. CHANGE (2 files, +12 / −1)
-----------------------------
- src/app/globals.css: a new opt-in class `.sidebar-scroll` with `scrollbar-width: none` (Firefox, Chromium 121+)
  and `.sidebar-scroll::-webkit-scrollbar { display: none }` (Safari, older Chromium).
  - It hides only the scrollbar track and thumb of an element that opts in.
  - It is NOT global; no other element uses it.
- src/components/operations/OperationsSidebar.tsx: the Primary nav's class list gains `sidebar-scroll`.
  `overflow-y-auto`, the padding and everything else are unchanged.

Not changed:
- sidebar widths (256 / 64), the logo, nav grouping, destinations, labels, the GrowthNavGroup, the footer;
- the AppHeader, main content scrolling;
- permissions, authorization, business logic, backend.

--------------------------------------------

  expanded).
- Viewport height 640px so the nav overflows.

|---|---|---|---|---|---|---|---|
| 1440 | 15 → 0px | yes | 400 → 400 | in view | in view | yes | 15 → 0px / in view |
| 1024 | 15 → 0px | yes | 400 → 400 | in view | in view | yes | 15 → 0px / in view |
| 768 (tablet rail) | 15 → 0px | yes | 63 → 63 (max) | in view | n/a (rail uses the flyout) | yes | n/a (always the rail) |

Coverage of the requirements:
- Mouse wheel / trackpad: the same container still scrolls by the same amount (CDP mouseWheel).
- Keyboard: Tab / focus moves to off-screen nav items and the browser scrolls them into view (verified for the last
  item and the last Growth child). The container has focusable children, so arrow / Page keys work as before.
- Collapsed sidebar: same results; the rail icons are centred again (15px no longer taken).
- Growth submenu: the expanded children scroll within the nav. The rail flyout is unaffected (P1b S13 passes).
- Workspace / account footer: outside the scroll area, always visible and reachable.

Main content: the page's own scroll container (<main>) keeps its normal scrollbar (15px, `scrollbar-width: auto`).
Re-verified on the dedicated branch.

Rail centring: at 768 all 12 rail icons are centred at x = 32 of the 64px rail (direct measurement). One automated
probe check reported "not centred" at 768 because it ran after earlier focus / scroll steps in the same session; the
direct measurement is authoritative.

Trade-off (disclosed): with no scrollbar, the overflow cue is the clipped item at the bottom edge of the list (as in
the after screenshots). Standard behaviour on macOS with overlay scrollbars. If a stronger cue is wanted, a subtle
bottom fade could be added later; not done here, to stay within scope.
