1. EXECUTIVE SUMMARY
====================================================================

The existing, uncommitted driver-invitation-email implementation was
reviewed line-by-line against every requirement in this phase's brief
and found to be architecturally sound: the self-signup + redemption
model is preserved untouched, authorization is entirely server-derived,
the invite token never reaches the browser, `RESEND_API_KEY`/
`EMAIL_FROM` are correctly confined to a `server-only` module, and
provider failures are represented as an explicit, honest delivery state
rather than a false "sent."

Live testing this phase FOUND ONE GENUINE DEFECT the prior session's own
testing had not exercised: `src/lib/app-url.ts`'s origin resolution had
no defense against a malformed `NEXT_PUBLIC_APP_URL` (missing scheme,
double slash, or — the one that actually fired in testing — a loopback
address reaching a real production build), and neither Server Action
caught a thrown error from that module, so the failure mode was an
**uncaught exception that crashed the whole page** ("This page couldn't
load") rather than the intended graceful "invite created, email could
not be sent" state. This was corrected this phase (§6/§7/§21) with the
smallest fix that closes the gap: origin resolution now goes through
`new URL()` normalization with explicit guards, and both Server Actions
route any thrown error through one small try/catch helper that reduces
it to the SAME honest, already-designed "failed" delivery state. The fix
was verified to actually work by deliberately reproducing the crash
against a real production build, then confirming it no longer crashes.

A genuine bug was also found and fixed inside the new focused unit test
itself before it was trusted: `isLoopbackOrigin` initially mis-detected
an IPv6 loopback literal (`[::1]`) because `URL#hostname` renders IPv6
addresses with their brackets — caught by the test that was written to
catch exactly this class of thing, fixed in one line.

No RLS, migration, schema, tenancy, or authorization-boundary change was
made or was needed. 317/317 pre-existing SQL assertions and both
concurrency tests re-ran clean, unchanged from the P0-S1 baseline. tsc,
lint, and a full production build all pass. 15 new focused unit tests
(Node's built-in test runner, zero new dependencies) and 33 live,
non-destructive integration checks against the local Supabase stack
(happy path, both negative-tenant cases, both stale-invite races, both

Production delivery remains genuinely BLOCKED — no Resend account/key

BEHAVIOR VERIFIED for the exact malformed-URL cases the brief named,
via `new URL()` normalization rather than string concatenation:

  LOCAL (`NEXT_PUBLIC_APP_URL=http://localhost:3000`): unchanged —
    resolves to `http://localhost:3000`, confirmed by unit test and by
    live use throughout this phase's own integration testing.
  PRODUCTION (`NEXT_PUBLIC_APP_URL=https://app.zenwardmobility.com`):
    unchanged — resolves to `https://app.zenwardmobility.com`, confirmed
    by unit test.
  Double slash (`https://x.com//`): now stripped — `.origin` never
    carries a trailing slash, so `/join/<token>` can never become
    `//join/<token>`. Verified by unit test.
  Missing protocol (`app.zenwardmobility.com`, no scheme): now rejected
    — `new URL()` throws for a bare hostname; treated as "not usably
    configured" (falls back to the request's own forwarded host) rather
    than silently building a schemeless, broken link. Verified by unit
    test.
  Unexpected pathname joining (`https://x.com/some/base`): now
    impossible — `.origin` is scheme+host+port only, so a stray path in
    the configured value can never leak into the built link. Verified by
    unit test.
  `localhost`/`127.0.0.1`/`[::1]` reaching a real deployment: NEW guard —
    `getAppOrigin()` now throws if `NODE_ENV === "production"` AND the
    resolved origin is a loopback address, rather than silently emailing
    an unreachable link to a real driver. Verified LIVE — see §16 for the
    crash this initially caused and the fix for it.

`NEXT_PUBLIC_APP_URL` confirmed used ONLY as a public origin value for
building a link — it plays no role in any authentication or
authorization decision anywhere in the codebase (confirmed by reading

8. RESEND INVITE ACTION
====================================================================

`resendDriverInviteAction` (`src/app/operations/drivers/actions.ts`) —
reviewed; same shared fix as §7, no other change.

  - Authenticated `organization_admin` only: `requireOperationsAccess`
    + an explicit `organization.role !== "organization_admin"` early
    return. Confirmed live: a Dispatcher never even sees the resend
    control (it renders only inside the admin-only Pending Invites
    panel) — §14 item 2.
  - Invite must belong to the caller's resolved organization: enforced
    TWICE, independently:
      1. Application layer — `invite.organization_id !==
         organization.organizationId` → `{ status: "error" }`.
      2. Database/RLS layer — the `.select(...).eq("id", inviteId)` call
         goes through `driver_invites_select_org_admin`
         (`has_org_role(organization_id, ['organization_admin'])`); a
         cross-tenant admin's session simply cannot see a foreign
         invite's row at all, so `invite` is `null` regardless of
         whether check #1 above even exists. Verified LIVE this phase
         via a direct, unmodified PostgREST request as an Org B admin
         for Org A's invite id — `[]`, zero rows (§14 item 3b). This
         means even a future accidental removal of check #1 would NOT
         open a cross-tenant hole — RLS is the real backstop, and the
         application check is defense-in-depth on top of it, not the
         sole guard.
  - Pending invites only: `invite.status !== "pending"` → error.
    Verified LIVE against a genuine race (an invite that became
    `accepted`/`revoked` in the database AFTER the page rendered the
    resend button but BEFORE the click was processed) — the action
    correctly rejects both, dispatches no email, and leaves the row's
    status untouched (§14 items 5/6).
  - Recipient cannot be changed: the function signature is
    `resendDriverInviteAction(inviteId: string)` — there is no parameter
    through which a different email address could ever be supplied; the
    address used is always `invite.email`, read from the database row.
    Verified live: the resent email's `to` field matched the ORIGINAL
    invite address exactly (§14 item 4d).
  - Existing token stays server-side: `invite.token` is read from the
    database and passed only into `buildDriverInviteUrl` — never
    returned in `ResendInviteState`. Confirmed by reading the interface
    (`{ status: "idle" | "sent" | "failed" | "not_configured" | "error"
    }` — no `token` field exists) and live, by inspecting the full
    rendered page DOM after a resend for the literal token string
    (absent).
  - No new `driver_invites` row is created: the function performs ZERO
    inserts/updates — confirmed by reading it (only a `.select()` and
    calls into `sendEmail`) and live (row count unchanged before/after
    resend, §14 item 4e).
  - Resend does not mutate organization identity: no `UPDATE` of any
    kind is issued by this function at all.
  - Revoked/accepted/invalid state handled safely: see "pending invites
    only" above — both non-pending states are rejected identically, with
    no distinct error message that would let a caller distinguish
    "revoked" from "accepted" from "doesn't exist" (matches this
    codebase's own "no existence oracle" discipline used everywhere
    else, e.g. `redeem_driver_invite`'s own wrong-email handling).

WHY resend reuses the existing token rather than rotating it (per the
brief's explicit request to document this): rotating the token on resend
would invalidate any copy of the link the invitee might already have
(an open tab, a forwarded email) for no security benefit — the token's
security property is "unguessable and valid only while the invite is
`pending`," not "single-use-per-email-sent." Resend is deliberately a
ZERO-database-write operation (by design, specifically to make "no
duplicate row, no duplicate Membership/Driver" a structural guarantee
rather than something to get right in application logic each time), and
since it touches no row, it has no mechanism to rotate a token even if
that were desired — re-inviting the SAME email through the ordinary
Invite Driver dialog (which DOES call the RPC again) already exists as
the separate, correct path for "I want a fresh token," via
`create_driver_invite`'s own refresh-if-pending behavior.

No security weakening was introduced to support resend — reviewed and
confirmed unchanged from the prior session's own design.

THE ONE GENUINE DEFECT FOUND AND FIXED THIS PHASE (documented in full
here since it is this report's most substantive finding):

  1. **The crash.** While deliberately testing the `not_configured`
     delivery state against a real production build, the actual result
     was an uncaught exception — the whole `/operations/drivers` page
     crashed with Next.js's generic "This page couldn't load / A server
     error occurred" screen, not the intended graceful failure message.
     Root cause: this phase's OWN new `getAppOrigin()` guard (refusing a
     loopback origin in production) fired because the specific local
     production build under test had `NEXT_PUBLIC_APP_URL` baked in as
     `http://localhost:3000`/`:3100` (from `.env.local`, since
     `NEXT_PUBLIC_*` values are inlined at BUILD time, not read at
     server-start time — a genuine, easy-to-repeat operational fact
     worth remembering for anyone testing this feature locally against
     a production build) — and NEITHER Server Action caught the
     resulting throw. This exact gap ALREADY existed before this
     phase's own change too (the pre-existing "cannot determine the
     application origin at all" throw was equally uncaught) — this
     phase's own hardening is simply what made the gap reachable in
     testing, not what created it.
  2. **The fix.** `deliverDriverInviteEmail(...)` (§7) — a small
     try/catch wrapper around URL-building + sending, shared by both
     Server Actions, reducing ANY thrown error to the same `EmailResult`
     shape a provider failure already produces. Verified this actually
     works by rebuilding with the SAME misconfigured
     (`NEXT_PUBLIC_APP_URL=http://localhost:3000`) value and confirming
     the page no longer crashes — it now shows the honest "Invite
     created...could not be sent" state, with the invite row preserved,
     exactly like every other failure mode (§14 item 4).
  3. **The unit-test bug.** While writing `app-url-core.test.mjs`, a
     test asserting `isLoopbackOrigin("http://[::1]:3000")` initially
     FAILED against the real implementation — `URL#hostname` renders an
     IPv6 literal with its brackets included (`"[::1]"`, not `"::1"`),
     which the first version of `isLoopbackOrigin` didn't account for.
     Fixed in one line (checking both forms). This is exactly the kind
     of thing a real, non-mock unit test exists to catch, and it did.

None of the three items above touches RLS, a migration, or the tenancy
model — all three are application-layer (`src/lib/app-url*.ts`,
`src/app/operations/drivers/actions.ts`) and covered by the regression
totals above (317/317 unchanged) plus the new/live tests in §13-§15.
