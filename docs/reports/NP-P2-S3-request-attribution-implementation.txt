6. ATTRIBUTION CONSISTENCY RULES
======================================================================
  1. One Core Request has at most one attribution (PK). Requests without one remain fully valid; nothing in Core
     references Plus.
  2. The Request must exist in the caller's organization. It may be in any state (pending / accepted / declined /
     cancelled) and is never changed. A link records the relationship; it does not rewrite history.
  3. The browser-supplied organization id is never trusted. The RPCs check membership, grant and role for THAT id,
     and the server action also binds it to the session workspace.
  4. Opportunity given: it must be a private-pay opportunity of the organization, in any stage. The contact dimension
     is ALWAYS its primary contact; a different contact gives ZW006.
  5. Contact only: it must be an ACTIVE contact of the organization (archived gives ZW006). A correction may keep an
     unchanged archived contact (history).
  6. Nothing is created or merged: no contact, opportunity, Request, Passenger or Trip. The picker searches existing
     active contacts only.
  7. The same link repeated returns changed=false (double click safe; concurrent proven). A different link on an
     attributed Request gives ZW004, pointing to "Correct link".
  8. Corrections:
     - require a reason (3-500), a row lock and the version (ZW003);
     - never delete the row;
     - never change link_method / linked_by / linked_at, so a manual correction never impersonates a conversion;
     - identical dimensions give changed=false with no history.
  9. Linking is NOT conversion: no opportunity stage changes (SQL L12, G2; E2E B6, D4). 'converted' remains P2-S4.
  10. Contact and opportunity rows are locked FOR SHARE during a link or correction, so they cannot be archived or
      re-pointed underneath it. The Core Request row is NEVER locked (SQL K3).

17. KNOWN LIMITATIONS AND OWNER DECISIONS
======================================================================
Owner decisions:
  OD1. Request facts require the Core role. The summaries, the attribution reads and the table's RLS require both Plus
       and the Core request-read role, as this brief directs. This is stricter than the access-model note for
       growth-only members (PD-18, still PROPOSED). If PD-18 is approved, decide whether growth-only members may see
       the minimum-necessary summaries without the Core role.
  OD2. Opportunity contact changes after linking. P2-S1's plus_update_opportunity can move an OPEN opportunity to a
       different contact. An existing attribution keeps the contact it was linked with until staff correct it.
