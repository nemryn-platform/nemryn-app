CURRENT PLATFORM ADMIN AUDIT (before R4E) — answers A–F
============================================================
A. What did Platform Admin have? Authority = a row in platform_admin_grants (user_id unique, no organization_id; no authenticated INSERT/UPDATE/DELETE — provisioned only by a privileged path). `is_platform_admin()` (SECURITY DEFINER, authenticated) is the only mechanism. RLS backed by it on exactly three tables: organizations (SELECT all tenants), audit_events (SELECT ALL tenants' audit history — team emails, settings changes), platform_admin_grants (SELECT). NO policy on memberships, requests, trips, passengers, drivers, etc. No route, no UI, no platform RPC, no mutation of any kind.
B. What did organizations.status mean? CHECK (status in ('active','inactive')), default 'active', set 'active' at creation. It was a stored label only.
C. Did status block tenant use? NO. Nothing in the schema read it: not is_org_member / has_org_role / current_driver_id, not any RLS policy, not any tenant RPC, not the public-intake RPC, not invitation acceptance, not the application's organization resolution.
D. What would have stayed available for an "inactive" organization? Everything — every read, every mutation, Driver access, public intake, invitations.
E. Did public intake check organization status? No (only integration.is_active and the origin allow-list).
F. Did Driver access check organization status? No (current_driver_id required drivers.status='active' and an active Membership only).
System tenant: none exists in the schema or seed; nothing special-cased.
Findings acted on: (1) status is now enforced (below); (2) the broad Platform Admin SELECT on audit_events was a pre-existing privacy exposure and was dropped.

============================================================
LIFECYCLE ENFORCEMENT
============================================================
Audit result: status was enforced nowhere; the smallest coherent shared enforcement was applied at the authorization chokepoints, then the two paths that bypass them:
 1. is_org_member, has_org_role, current_driver_id now additionally require organizations.status = 'active' (is_driver_assigned_to_trip inherits via current_driver_id). Every tenant RLS policy and every SECURITY DEFINER tenant RPC (trips, requests, passengers, settings, team, services, integrations, notification prefs, activity, recurring care, proof of service, driver reads…) already routes through these, so all are denied for a suspended tenant with no per-function edits. PlatformAdminGrant still never satisfies them.
 2. submit_public_transportation_request: after resolving the integration, requires the owning organization to be active, with a FOR SHARE lock on the organization row (strict against a concurrent suspension); rejection is the identical generic invalid_input (ZW006) as unknown/disabled — no lifecycle disclosure.
 3. accept_staff_invite and redeem_driver_invite refuse a suspended organization (ZW003 stale_state).
 4. Application: organization resolution (getActiveMemberships) excludes suspended organizations (never selectable); a member of only-suspended workspaces is shown "Workspace suspended … Your records have not been changed" (access-unavailable) instead of being sent to organization creation. Members can still read their own organization row (organizations_select_members rewritten to be status-independent) so the app can explain the state; that grants no operation.
Not changed: notification dispatch of an event enqueued BEFORE suspension still completes (recipients resolved from Memberships); an in-flight accepted website request may still email. No new Requests can exist after suspension commits.
Because central tenancy helpers changed, the FULL SQL/security regression battery was run (see DATABASE TESTS).
