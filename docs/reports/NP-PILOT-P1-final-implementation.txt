3. FUNCTIONALITY (what staff now see)
======================================================================================================================
  - Existing rider: pick from the list (rode before / same phone / same name hints), confirm, and the request arrives in
    Operations already linked — in the SAME transaction as the request. If that passenger was deactivated meanwhile or
    the id is not in this workspace, NOTHING is created and staff choose again.
  - New rider: type their name; Operations sees "Requested passenger: <name> · Passenger needed" and Add New Passenger
    opens prefilled with that name. No passenger record is created until Operations adds it.
  - Requester is the rider: tick the box; the contact's name is suggested (editable) and "The passenger themselves" set.
  - Family / caregiver / facility requester: nothing about the rider is assumed; the rider is chosen, named, or left
    for the request page.
  - Replay / double submit: returns the original request; its passenger is never changed by a replay.

Known limitations
  1. Deactivation race window: the passenger check (Plus pre-check and Core's own check) is a plain read at READ
     COMMITTED. A deactivation committing between the check and the request's commit is not detected — the request
     links a passenger who became inactive a moment later. Same behaviour as Core's existing New Request; no lock was
     added because Plus must never lock Core tables. Staff see the passenger on the request page as usual.
  2. The passenger list is loaded when the dialog opens; a passenger deactivated afterwards still appears until
     reload, but the database refuses it at submit and nothing is created (E2E I2).
  3. The rider name is free text: no duplicate detection. Core's Add New Passenger (staff-confirmed) decides whether
     a new passenger is created; Growth never creates one (D4).
  4. A replayed submit cannot change the passenger of the original request (by design); changes are made on the Core
     request page.
  5. The three pre-existing test-suite issues in 5.4 remain (follow-ups recommended there).
