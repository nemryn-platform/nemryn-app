3. NOTIFICATIONS
============================================================
Events OFFERED (both fire at an authoritative, transactional moment):
  - New website request  — a genuinely NEW public Request is created. Default recipients: Organization Admins.
  - Trip exception       — a TripException is newly reported (Operations or Driver). Default recipients: Organization Admins + Dispatchers.
Events OMITTED, with reason:
  - Upcoming unassigned trip, Recurring care gap — need periodic evaluation; no scheduler exists.
  - Proof needs review — a derived read-time state, not a persisted moment.
  A switch that never fires would be misleading, so none is shown.

Recipient model: organization_notification_settings(organization, event, recipient_roles). Staff roles only — no stored addresses. No row = default; empty array = off. Saved through set_notification_settings (audited notification_preferences_updated with before/after). Recipients are resolved LIVE at dispatch from active staff Memberships holding an enabled role: never Drivers, inactive members, Platform Admins without Membership, or other organizations.

Durable design (transactional outbox): notification_events is written IN THE SAME TRANSACTION as the business change (submit_public_transportation_request, report_trip_exception). It stores only the reference + outcome (status pending|dispatching|sent|partial|failed|skipped, counts, fixed failure reason) — no address, name, or record content. unique(event_type, entity_id).
Dispatch (server-side, after the response via after()): claim_notification_dispatch (service_role only) atomically claims the event — exactly one claimer wins the payload, others get NULL. One email per live recipient. complete_notification_dispatch (service_role only) records the outcome with a fixed vocabulary (provider_error | not_configured | build_failed | unknown) — never provider text.

Minimal email payload (verified in unit tests and E2E):
  - Website request: "A new transportation request was received through your website." + requested DATE (if given) + service CATEGORY (if given) + "Open Request Hub" link (list page).
  - Trip exception: "An issue was reported on a trip." + scheduled pickup time (org timezone) + "Open Trips" link (list page).
  - NEVER: requester/passenger names, phone, email, pickup/destination addresses, notes, exception type/description, UUIDs, integration details, secrets, provider text.

Failure behavior: notification failure never rolls back or fails the business transaction (dispatch runs after the response, never throws). Failure is recorded honestly as failed/partial with a fixed reason and shown on the page as "Not delivered". When production email is unavailable the Admin sees "Email delivery is currently unavailable." (getEmailTransportStatus(), no provider call, no secret). Tenants never configure the platform email key. No in-request retry.

Idempotent-replay design: a replayed public submission takes the existing-row path and never reaches the enqueue, so it returns no notification_event_id and never notifies again; unique(event_type, entity_id) is a second guard; the claim is exactly-once under concurrency.

Public intake contract: unchanged. Response is still {ok:true}; wrong Origin / unknown key / disabled service still 400. The only touch to public-intake code is passing the new event id to after() dispatch (route.ts, website-intake.ts).

5. ACTIVITY
============================================================
list_activity_events projects existing audit_events (no second audit table) via an SQL action whitelist: organization_*, website_integration_*, staff_invitation_*, membership_*, notification_preferences_updated. Operational trip/request audit rows are never returned. Unmapped actions are omitted.
Mapping: activity-core.ts converts each row to a human title + short safe summary server-side (changed field NAMES, not values; team emails; services in words). Raw before/after JSON, UUIDs and codes never reach the browser.
Actor: profile display name, else account email; NULL actor shows "System".
Pagination: keyset on (occurred_at, id), opaque base64url cursor, 30 per page (within the 25–50 brief), newest first, "Load older activity" / "Back to newest"; a tampered cursor is ignored (newest page shown). Verified 30 + 24 = 54 reconciling with the database, nothing lost or repeated.
