4. SOURCE COLUMN
---------------------
    alter table public.transportation_requests
      add column source text not null default 'other'
        check (source in ('phone', 'facility', 'email', 'web', 'other'));

`NOT NULL` with a `DEFAULT 'other'` — Postgres backfills existing rows
with the default in the same statement (confirmed live: both seed
fixtures show `source = 'other'` after the migration ran, §19). `other`
was chosen as the honest answer for a row whose real channel was never
captured — never inferred as a specific channel. `log_transportation_request`
always requires an explicit, validated `p_source` value for new rows
going forward; the column default exists only for safe backfill / any
other write path.

No public web intake was built merely because `web` is an allowed
value — confirmed: no route, action, or RPC in this phase or anywhere
else in the repository accepts an anonymous submission of any kind
(§21's threat review).


5. REQUEST_EVENTS DESIGN
-----------------------------
    create table public.request_events (
      id uuid primary key default extensions.gen_random_uuid(),
      organization_id uuid not null references public.organizations (id),
      request_id uuid not null,
      event_type text not null check (
        event_type in ('request_logged', 'passenger_linked', 'request_declined', 'request_cancelled')
      ),
      actor_user_id uuid references auth.users (id),
      occurred_at timestamptz not null default now(),
      metadata jsonb not null default '{}'::jsonb,
      foreign key (request_id, organization_id) references public.transportation_requests (id, organization_id)
    );

Mirrors `trip_events` exactly: append-only, allow-listed `event_type`
(4 values, only the actions this foundation actually implements — no
speculative vocabulary), tenant-safe composite FK. Deliberately NOT a
reuse of `audit_events` (Dispatcher has no access to that table at all,
per §2) and NOT an extension of `trip_events` (which is FK'd to
`trip_id`, not `request_id`, and extending it would require its own
schema change). `request_converted_to_trip` remains authoritative as the
existing `trip_events` row on the Trip side — this migration does NOT
touch `create_trip` to also duplicate that event into `request_events`,
per the explicit instruction ("Do NOT modify create_trip solely to
duplicate that event... unless a concrete implementation dependency
requires it" — none was found; Request Detail can derive conversion
history from linked Trips and their own existing events, exactly as
S2A's own §14 recommendation already anticipated).


6. REQUEST_EVENTS RLS/GRANTS
---------------------------------
    grant select on public.request_events to authenticated;

    create policy request_events_select_org_operations
      on public.request_events for select to authenticated
      using (public.has_org_role(organization_id, array['organization_admin', 'dispatcher']));

SELECT only, organization_admin + dispatcher, same organization — the
same two roles already granted access to `transportation_requests`
itself. No INSERT/UPDATE/DELETE grant to `authenticated` at all — every
row is written exclusively by the four SECURITY DEFINER RPCs below,
which bypass RLS for their own writes as the function owner, exactly as
`create_trip` already does for `trip_events`/`audit_events`. Driver gets
no policy at all (no standing access). No anonymous grant of any kind.

Live-confirmed (§16, privilege test file): a raw client INSERT into
`request_events` is rejected at the privilege layer; Driver SELECT
returns zero rows; Dispatcher SELECT returns their own organization's
rows; an Org A admin sees zero Org B rows.


7. LOG REQUEST RPC
-----------------------
    log_transportation_request(
      p_organization_id uuid, p_requester_name text, p_requester_relationship text,
      p_requester_phone text, p_pickup_description text, p_destination_description text,
      p_return_trip_needed text, p_source text,
      p_requester_email text default null, p_passenger_id uuid default null,
      p_preferred_date date default null, p_preferred_time time default null,
      p_assistance_notes text default null, p_additional_notes text default null
    ) returns request_creation_result

The sole controlled creation path — mirrors `create_trip`'s own
structure line for line: `auth.uid()` check (ZW001) → live
`has_org_role` check (ZW002, no existence oracle) → explicit field
validation (all ZW006: required fields trimmed/non-blank/length-capped;
`requester_relationship`/`return_trip_needed`/`source` revalidated
against their allowed sets even though the table's own CHECK
constraints would also catch a bad value, for a clean ZW006 rather than
a raw constraint error) → optional Passenger validation (identical
shape to `create_trip`'s own passenger check: exists, same org, active)
→ INSERT with `state` hard-coded `'pending'`, never a parameter, never
caller-influenced → one `request_events` row (`request_logged`,
`actor_user_id = auth.uid()`, never client-supplied).

Required/optional split matches the S2A-established minimum save
contract exactly (§8 below). Non-idempotent by design, matching
`create_trip`'s own documented reasoning — there is no natural
idempotency key for "record a new piece of demand."


8. LINK PASSENGER RPC
--------------------------
    link_request_passenger(p_organization_id uuid, p_request_id uuid, p_passenger_id uuid)
      returns request_passenger_link_result

Legal only while the Request is `pending` — `accepted` (passenger
reassignment on the original Request is deliberately prohibited once a
Trip exists, per the locked decision), `declined`, and `cancelled` are
all rejected with ZW004 `illegal_transition`. Passenger must exist, same
organization, `status = 'active'` (ZW006 otherwise, no existence oracle
— explicitly validated inside the RPC, never trusted merely because RLS
would otherwise hide a foreign-org row). Idempotent no-op
(`changed: false`) if the Request already links this exact
`passenger_id`. The Request row is locked `FOR UPDATE` before any
state-legality check (§13).


9. DECLINE RPC
-------------------
    decline_transportation_request(p_organization_id uuid, p_request_id uuid, p_reason text default null)
      returns request_transition_result

Only `pending -> declined` is legal (ZW004 from `accepted` or
`cancelled`). Idempotent no-op if already `declined` — the no-op check
runs BEFORE the illegal-transition check, matching `cancel_trip`'s own
established precedence (ZD-090). `p_reason` is optional free text
(≤500 chars, ZW006 if oversized), never a structured category — matches
the locked decision exactly. The reason is persisted directly in
`request_events.metadata` (`jsonb_build_object('reason', v_reason)` when
supplied, `'{}'::jsonb` otherwise) — never discarded, never only logged.
Live-confirmed (§16): a supplied reason is readable back from
`request_events.metadata->>'reason'` after the call.


10. CANCEL RPC
-------------------
    cancel_transportation_request(p_organization_id uuid, p_request_id uuid)
      returns request_transition_result

Only `pending -> cancelled` is legal (ZW004 from `accepted` or
`declined`). Idempotent no-op if already `cancelled`. The locked safe
rule is enforced exactly: ANY linked Trip row — regardless of that
Trip's own state (`scheduled`, `completed`, `cancelled`, `no_show`, or
any other value) — blocks cancellation with ZW004. No automatic cascade
into Trip cancellation exists or was added. The linked-Trip existence
check runs inside the same transaction, under the same Request-row lock
acquired at the top of the function, so it can never race against a
concurrent `create_trip` call (§13). Live-confirmed (§15, test CANCEL-2):
a pending Request with a linked Trip whose own state is `cancelled` is
still correctly rejected — proving the rule checks Trip *existence*, not
Trip *state*.

12. DIRECT UPDATE PRIVILEGE REMEDIATION
--------------------------------------------
    drop policy if exists transportation_requests_insert_org_operations on public.transportation_requests;
    revoke insert on public.transportation_requests from authenticated;

    revoke update on public.transportation_requests from authenticated;
    grant update (
      requester_name, requester_relationship, requester_phone, requester_email,
      pickup_description, destination_description, preferred_date, preferred_time,
      return_trip_needed, assistance_notes, additional_notes, source
    ) on public.transportation_requests to authenticated;

Two changes, both closing real gaps, both mirroring the exact
`create_trip`/`trips` precedent (ZD-101's retirement of the raw `trips`
INSERT grant once `create_trip` existed):

  - Raw client INSERT retired entirely, now that
    `log_transportation_request` is the sole controlled creation path —
    the prior grant had NO column restriction, meaning a raw INSERT
    could set `state` to any of the 4 allowed values at creation time,
    the same GAP-1 vulnerability class reachable via INSERT instead of
    UPDATE.
  - `state` and `passenger_id` removed from the UPDATE column grant —
    `state` closes the S2A-identified lifecycle-integrity gap directly;
    `passenger_id` is removed because passenger linking is now
    exclusively governed by `link_request_passenger`'s own
    state/organization/active-status validation, which a raw UPDATE
    would bypass entirely.

Live-confirmed (§16): `information_schema.role_column_grants` shows the
UPDATE grant is exactly the 12-column safe descriptive set, with neither
`state` nor `passenger_id` present; `has_table_privilege('authenticated',
..., 'INSERT')` is false; a raw `UPDATE ... SET state = ...` and a raw
`UPDATE ... SET passenger_id = ...` both fail with `insufficient_privilege`
at the privilege layer (never reaching any row).

No RLS policy was weakened — SELECT and the `has_org_role`-scoped
USING/WITH CHECK clauses on the remaining UPDATE policy are completely
unchanged. Database enforcement was tightened, not replaced with a UI
restriction.


13. CONCURRENCY/LOCKING MODEL
----------------------------------
`link_request_passenger`, `decline_transportation_request`, and
`cancel_transportation_request` all lock the target Request row
(`select * from transportation_requests where id = p_request_id and
organization_id = p_organization_id for update`) BEFORE any
state-legality check — identical to `create_trip`'s own existing lock
on the same row when `p_request_id` is supplied. This shared lock is the
serialization boundary: whichever transaction (a lifecycle RPC, or a
concurrent `create_trip` call referencing the same Request) acquires the
lock first runs to completion (commit or rollback) before the other's
lock acquisition can proceed; the second transaction then re-reads the
now-current row and evaluates its own legality check against reality,
never against stale data.

Genuinely proven, not merely argued: `supabase/tests/
request_lifecycle_concurrency_test.sh`, using the SAME two-separate-
psql-process methodology already established by
`mutation_concurrency_test.sh`/`driver_invite_concurrency_test.sh`.
Session A opens a transaction, locks a pending Request row `FOR UPDATE`,
holds it 2 seconds (simulating a real in-flight `cancel_transportation_request`
call), then actually calls `cancel_transportation_request` and commits.
Session B, launched 0.3s later, calls `create_trip(p_request_id =>
<same Request>)`. Result (live, this run): Session B blocked
1.823376000s (not near-instant — genuine lock contention, not lucky
interleaving), then correctly observed Session A's already-committed
`cancelled` state and rejected with `ZW006 invalid_input`. Final state:
Request `cancelled`, zero linked Trips — the race was fully closed by
the shared row lock alone, no additional locking (e.g. on `trips`
itself) was required, matching the phase's own suggestion to evaluate
this. `decline_transportation_request` and `link_request_passenger`
share the identical locking primitive (the same `for update` on the
same table inside a function body of the same shape) — proving the
primitive holds for one representative transition is representative of
all three, matching this repository's own established practice of one
concurrency script per shared primitive rather than one per RPC.


14. ERROR CONTRACT
-----------------------
Every new RPC reuses the existing 6-code contract (ZD-085) exactly,
branching on `sqlstate`, never message text:
  ZW001 unauthorized       — `auth.uid()` is null
  ZW002 not_found          — `has_org_role` fails (Driver, inactive
                              Membership, foreign org — indistinguishable
                              by design), OR the target Request doesn't
                              exist / isn't in the caller's organization
  ZW004 illegal_transition — the requested change is not a legal edge
                              from the Request's current state (e.g.
                              declining an accepted Request, cancelling
                              one with a linked Trip)
  ZW006 invalid_input      — malformed/missing/oversized field, invalid
                              enum value, nonexistent/foreign-org/
                              inactive Passenger

No new error code was introduced. Anonymous calls are rejected before
any function-body logic runs (`insufficient_privilege`, confirmed live
for `log_transportation_request` via a `set local role anon` test) —
none of the four functions grants EXECUTE to `anon`/`PUBLIC`.

    `organization_id = p_organization_id` + `status = 'active'`
    filtering in both `log_transportation_request` and
    `link_request_passenger` — no existence oracle (nonexistent and
    foreign-org produce the identical error).
  Forged request_id: rejected (ZW002) by the composite `where id = ...
    and organization_id = ...` lookup in all three lifecycle RPCs —
    foreign-org and nonexistent are indistinguishable.
  Operator attempting to convert/decline/cancel a declined/cancelled/
    already-accepted Request: rejected — `create_trip`'s own existing
    check (unmodified) plus each new RPC's own from-state check, all
    live-tested (§15).
  Duplicate conversion / duplicate lifecycle-mutation attempts: handled
    correctly and deliberately — `create_trip` remains non-idempotent by
    design (unchanged); each new lifecycle RPC IS idempotent for the
    "already at target state" case (`changed: false`, no duplicate
    event), matching ZD-090.
  Unauthorized driver access: rejected (ZW002) for all 4 new RPCs and
    for `request_events` SELECT — live-tested.
  Public unauthenticated spam: not applicable — no public path exists
    anywhere in this phase (public intake remains deferred, per the
    locked decision); anon EXECUTE is not granted on any of the 4 new
    functions, live-confirmed.
  Service-role leakage: none — every new function is SECURITY DEFINER
    with an explicit `search_path = public, pg_temp` and a trusted,
    non-`anon`/`authenticated`/`service_role` owner, live-confirmed via
    `pg_proc`/`pg_get_userbyid` introspection for all 4 functions.
  Client-side-only authorization: none introduced — every authorization
    and lifecycle-legality decision is enforced inside the SECURITY
    DEFINER function body or by RLS/column-grant, never left to
    application code to enforce "by convention."

The one gap S2A identified (direct client writability of
`transportation_requests.state` and, by extension, `passenger_id`) is
now closed at the database level, not merely documented — confirmed
live via the privilege test file, not asserted from reading the
migration alone.
