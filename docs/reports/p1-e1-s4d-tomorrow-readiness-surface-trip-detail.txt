decision below was made from the phase prompt's own description alone —
every visual/structural choice traces to a real, already-existing
pattern found during this audit.

Key findings that shaped the design:
  - `SummaryStrip` (inline mode) and `EmptyState` already exist and are
    exactly the "compact figures, never decorative KPI cards" primitives
    the phase asks for — reused directly, nothing new built.
  - `assuranceStatusCategory` (presentation.ts) already establishes the
    exact precedent this phase asks for independently: EVERY active
    attention condition renders as StatusBadge category="warning" — the
    same "never escalate to critical/red merely because it's an
    exception" reasoning that shaped Tomorrow Readiness's own reason
    badges below.
  - `CurrentStatusPanel` already links "Assign Driver"/"Manage
    Assignment" to a GENERIC `/operations/dispatch` (not a per-Trip deep
    link) — its own doc comment: "the Dispatch Board has no per-Trip
    deep-link parameter yet." This is the load-bearing fact behind the
    RESOLUTION-ACTION AUDIT section below.
  - Trip Detail currently has NO existing Trip Assurance banner of any
    kind (confirmed by grep — `trip-assurance.ts` is only ever imported
    by Today's Operations/Operations Brief, never by trip-detail.ts or
    the Trip Detail page). The "duplication" risk this phase warns about
    is therefore prospective, not an existing banner to remove — the
    real risk is Preparation duplicating CurrentStatusPanel's assignment
    affordance and TripExceptionsPanel's own exception list, both of
    which DO already exist on this exact page.
  - No schedule-edit mutation path exists anywhere in the codebase
    (grepped every `p_scheduled_pickup_at` write site — only
    `trips/new/actions.ts`, at creation time). This directly settled the
    NO_SCHEDULE TRIP DETAIL BEHAVIOR section.
  - The Assign/Reassign dialog's Vehicle field is optional on both
    `assign_trip` and `reassign_trip` — a Reassign (driver re-selected,
    vehicle added) CAN turn a driver-only assignment into a fully
    assigned one. This directly settled the NEEDS_VEHICLE BEHAVIOR
    section.

PAGE INFORMATION ARCHITECTURE
------------------------------------------------------------------------
Route: `/operations/tomorrow` (src/app/operations/tomorrow/page.tsx),
directly navigable, not linked from the sidebar or Operations Brief
(S4D §3/§28/§29 — deferred to S4E). Authorization is the ordinary
`/operations/*` boundary: the parent layout's own `requireOperationsAccess`
already gates every route under this segment, and this page ALSO calls
`requireOperationsAccess` itself (mirroring the exact convention every
other Operations page.tsx already follows) to obtain
`organizationId`/`organizationTimezone` for its own data fetch. No second
access model was introduced; no `organizationId` is ever read from the
client.

Hierarchy actually built (server component, PageHeader + Panels, no new
primitives):
  Tomorrow
  [organization-local long date]
  [inline SummaryStrip: N scheduled trips · N ready · (N need preparation,
   only rendered when > 0)]
  Needs preparation  [N Trips badge]     <- primary content, only when
    [row: time · passenger, reason badges, "View trip" link]  needsPrep>0
  Ready                                   <- quieter secondary section,
    [row: time · passenger — "Ready"]        always visible when any exist

No KPI-card wall, no invented severity scoring, no client state, no
polling — a pure Server Component rendering `getTomorrowReadiness`'s
already-proven output.

------------------------------------------------------------------------
SUMMARY PRESENTATION
------------------------------------------------------------------------
`SummaryStrip` in `inline` mode — the existing "bold value + lowercase
label, divided by a vertical rule" primitive (already used identically
on Today's Operations), never a new component. Three items: "N scheduled
trips", "N ready" (default tone), "N need preparation" (warning tone,
only present when > 0 — omitted entirely when every Trip is ready, so
the strip never shows a triumphant "0 need preparation" item). Not
rendered at all in the zero-trips state — no "0 scheduled trips" strip
sitting above a "no trips" empty state.

------------------------------------------------------------------------
NEEDS-PREPARATION PRESENTATION
------------------------------------------------------------------------
A `Panel` with a header row (title + `N Trips` StatusBadge, category=
"warning" — the exact category `assuranceStatusCategory` already uses
for the analogous case), then a `divide-y` list of rows (time ·
passenger name, wrapped reason badges beneath, "View trip" LinkButton).
Every applicable reason renders as its own StatusBadge — never
collapsed to one, matching S4B's own "preserve every applicable reason"
contract exactly (live-verified via the multi-reason fixture showing
"Vehicle needed" + "Open issue" together). All reason badges use
category="warning" uniformly (§10's own instruction — never escalate to
critical merely because it's an OPEN_EXCEPTION), matching the existing
`assuranceStatusCategory` convention exactly rather than inventing a new
severity rule.

------------------------------------------------------------------------
READY PRESENTATION
------------------------------------------------------------------------
A separate, visually quieter `Panel`: a muted-color "Ready" heading
(text-text-secondary, not text-primary), then a plain `divide-y` list —
time · passenger name as a single muted link, "Ready" as small
success-colored text (no StatusBadge, no icon) on the right. No
collapsible disclosure was introduced: this codebase has no existing
Disclosure/Accordion primitive anywhere (confirmed by inventory), and
S4D §13 only permits hiding/collapsing "if consistent with existing UI
patterns" — since no such pattern exists, Ready stays a plain, always-
visible, quieter secondary section, matching Operations Brief's own
"Active Now"/"Next Departures" precedent (always visible, differentiated
by content and tone, never by visibility).

Added `tripReadinessReasonLabel` to the existing shared

DATE/TIMEZONE PRESENTATION
------------------------------------------------------------------------
The page never recomputes day boundaries itself. `formatOperationsLongDate
(new Date(data.tomorrowStartUtc), data.timezone)` renders the heading date
entirely from S4C1's own authoritative `TomorrowReadinessData` fields —
`tomorrowStartUtc` and `timezone` — the same already-existing time-
formatting helper Today's Operations/Operations Brief already use. Every
row's own time is rendered via `formatOperationsTime(scheduledPickupAt,
timezone)` — always the ORGANIZATION timezone, never browser-local or
server-local. Live-verified indirectly at every step of this validation:
Org A (America/New_York) and Org B (America/Chicago) each rendered their
own correct "tomorrow" calendar date and correct local wall-clock times
for their own fixtures throughout — including the discovery (see LIVE
FIXTURE RESULTS) that "tomorrow" for each organization tracks the real
current moment exactly, including across the two different UTC offsets.

TRIP DETAIL INTEGRATION
------------------------------------------------------------------------
Added `TripReadinessPanel` (src/components/operations/trip-detail/
TripReadinessPanel.tsx) and wired it into `src/app/operations/trips/

ASSURANCE/READINESS DUPLICATION STRATEGY
------------------------------------------------------------------------
Trip Detail carries no generic Trip Assurance banner today (confirmed by
the audit above), so there was no existing banner to literally merge
with. The real duplication risk is Preparation restating what
CurrentStatusPanel's "Assign Driver"/"Manage Assignment" link and
TripExceptionsPanel's own exception list already express. Resolved by
making Preparation strictly SECONDARY and REFERENCE-ONLY:
  - No AttentionState banner, no icon, no per-reason action button — a
    small Panel with a single StatusBadge ("Prepared"/"Needs
    preparation") and a plain bulleted reason list.
  - OPEN_EXCEPTION is referenced as one line, "Open issue" — never a
    restatement of the exception's type/description/Resolve control,
    which stays exclusively in TripExceptionsPanel. Live-verified: on a
    Trip with an open exception, the rendered page contains exactly one
    "Resolve" control (found: 1), proving no duplicate exception UI was
    introduced.
  - NEEDS_DRIVER is referenced as "Driver needed" — the actual, only
    working control for it (CurrentStatusPanel's "Assign Driver" link)
    is left completely alone; Preparation adds no second button. Live-
    verified on a Trip scheduled TODAY with no assignment: the rendered
    page shows the Preparation panel's own "Driver needed" line AND
    CurrentStatusPanel's pre-existing "Assign Driver" link, with zero
    occurrences of any page-level "Needs Attention" banner text —
    confirming no loud, duplicated warning treatment was created for the
    exact case §18 calls out.

ERROR ISOLATION
------------------------------------------------------------------------
Tomorrow Readiness: live-forced via a reversible SQL fault injection
(`REVOKE SELECT ON trip_exceptions FROM authenticated`, matching this
codebase's own established reversible-fault-injection technique from
earlier phases) — the page rendered a contained "Couldn't load
tomorrow's trips" panel, never a fake "0 scheduled trips," never "No
trips scheduled for tomorrow," never "Tomorrow is ready." The grant was
restored immediately afterward and re-verified (Trip Detail/Tomorrow
both confirmed working normally again).

Trip Detail: the `getTripReadiness` call is wrapped in its own
try/catch, setting a `readinessUnavailable` flag that renders "Preparation
status isn't available right now." instead of throwing — the same
pattern already proven correct on the Tomorrow page. Attempting to
force ONLY this query to fail via the same REVOKE technique also broke
`getTripDetail`'s own PRE-EXISTING `trip_exceptions` query (both
wrappers read the identical table by design, since they describe the
same Trip's same facts), which took down the whole page before this
phase's own try/catch could ever be exercised — this is not a defect in
the new code, it is a property of both wrappers legitimately sharing the
same underlying tables, and no table-level grant could isolate one from
the other. This is a genuine validation limitation, recorded honestly
below (OPEN ISSUES) rather than worked around with a synthetic test;
the try/catch itself was verified correct by direct code review and by
its structural identity to the Tomorrow page's already-live-proven
version.

OPEN ISSUES
------------------------------------------------------------------------
1. Trip Detail's own readiness-fetch error isolation (the
   `readinessUnavailable` branch) was verified by code review and by its
   structural identity to the already-live-proven Tomorrow page pattern,
   but NOT independently live-forced in isolation — every available
   REVOKE-based fault injection that breaks `getTripReadiness`'s query
   also breaks `getTripDetail`'s own, pre-existing `trip_exceptions`
   query (both legitimately read the same table), which fails the whole
   page before this phase's own try/catch is ever reached. This is a
   property of the two wrappers correctly sharing the same underlying
   facts, not a defect; closing this gap would require a more invasive
   fault-injection technique (e.g. a temporary trigger) that was judged
   out of proportion for this phase's own explicit "no schema change"
   boundary.
2. `/operations/tomorrow` is not yet mapped in `OperationsLayoutClient
   .tsx`'s `SECTION_LABELS`, so the persistent chrome header shows the
   generic "Operations" context label rather than a dedicated "Tomorrow"
   title — the page's own in-content `<h1>Tomorrow</h1>` (PageHeader)
   already carries the real title, matching Trip Detail's own established
   "generic chrome label, real title in content" convention, so this is
   cosmetic only. Left unmapped deliberately, to avoid touching shared
   layout chrome in a phase whose explicit scope is the new page and Trip
   Detail alone; a natural candidate for S4E when Operations Brief
   integration and permanent discovery are built.
