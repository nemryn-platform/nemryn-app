2. ROOT CAUSE (from the code, not the reports)
======================================================================
The R1 loader (src/lib/operations/overlap-candidate-loader.ts) has two families:
  - A: `.gte("scheduled_pickup_at", lookback).lt("scheduled_pickup_at", to)`
  - B: `.lt("scheduled_pickup_at", lookback)` with an inner-joined active assignment
In SQL, a comparison against NULL is never true, so a trip with scheduled_pickup_at IS NULL can match neither family.
Such a trip was therefore never a candidate. The pure core (trip-overlap-core.ts) handled a pickup-less candidate
correctly ("missing"), but it was never given one.
Result: a driver or vehicle whose only other commitment was a pickup-less active trip derived "clear". That breaks
"unknown remains unknown".

Two further defects were found on inspection:
  1. The core's candidate reason was a single "missing" bucket. overlapNotices rendered every missing candidate as
     "…: duration not set.", so a pickup-less candidate would have been described with the WRONG missing fact.
  2. A TARGET with no pickup time (New Trip "Assign now" after a date is chosen but before a time; Trip Detail of a
     pickup-less trip):
       - getAssignmentOverlap has no window for it, so it loaded no candidates and used coverage "complete";
       - the core then returned "clear" for every resource;
       - no note appeared at all.
     Silence read as "nothing to check".

Affected surfaces, each confirmed in code:
  - AssignmentFields (the Assign / Reassign dialog, and New Trip "Assign now"): assignmentOverlapAction →
    getAssignmentOverlap.
  - Trip Detail current assignment: getAssignmentOverlap → CurrentStatusPanel / OverlapNotes.
  - Dispatch (today / tomorrow): getDispatchBoardData → getOverlapCandidates → deriveResourceOverlap per assigned
    block.
  - Tomorrow: getKnownOverlapTripIds. This surfaces KNOWN overlaps only, plus the R1 page-level incomplete note, so
    no "clear" claim was shown there, but the same candidate set was used.
  - OverlapNotes: the copy source (overlapNotices).

  - Recurring occurrences require a scheduled start (unchanged), so they cannot produce one.

4. FAMILY C DESIGN
======================================================================
A third family, in loadOverlapCandidates:
  C. trips WHERE organization_id = <org>
       AND state IN (non-terminal)
       AND scheduled_pickup_at IS NULL
       AND an ACTIVE assignment exists
     The assignment is inner-joined through trip_assignments_trip_id_organization_id_fkey, with ended_at IS NULL.
  - Minimal columns: id, state, scheduled_pickup_at, expected_duration_minutes, plus the active assignment's
    driver_id, vehicle_id and ended_at.
      - NO pickup or destination description, passenger or other trip detail. A Family C trip can never be a known
        overlap, so there is nothing to list.
      - The unit test asserts that the Family C select contains no route or passenger column.
  - Terminal trips, ended assignments and unassigned trips are never fetched.
  - It uses the same RLS session client and an explicit organization filter. No service role.

5. PAGINATION
======================================================================
  - Ordering: id ASC. id is unique, so this is a total order. There is no start time to order by.
  - Cursor: `.gt("id", lastId)`. Keyset, no OFFSET.
  - The same page size (500) and ceiling (20 pages = 10,000 rows) as R1.
  - Stopping condition: a page shorter than the page size proves exhaustion. A full page always triggers the next
    read.
  - Implementation: R1's pager was generalised to collectPages(fetchPage, options, cursorOf).
      - collectKeysetPages (A / B, cursor (scheduled_pickup_at, id)) keeps its exact R1 behaviour.
      - collectIdPages (C, cursor id) is new.
  - All three families run in parallel.

7. CORE-DOMAIN CHANGE (trip-overlap-core.ts, pure)
======================================================================
  - The pair outcome now names its reason:
      - missing_schedule (the candidate has no pickup time);
      - missing_duration (the candidate has a start but no duration, and could intersect);
      - missing_target (the target's own extent is unknown).
  - ResourceCheck gains:
      - missingSchedule: string[]
      - missingDuration: string[]
    missingExtent is kept as their union plus the target-caused entries, so the R1 / PROG4B semantics and tests are
    unchanged.
  - Resource-specific. Candidates are still filtered per resource: the driver by activeDriverId, the vehicle by a
    non-null activeVehicleId. A pickup-less trip on Driver A never touches Driver B. A NULL vehicle affects the
    driver only.
  - Precedence (R1 unchanged, plus one rule):
      1. overlap
      2. target without a pickup time → not_checkable
      3. target unknown + missing / still-open → not_checkable
      4. missing (schedule or duration) → not_checkable
      5. still open past planned end → not_fully_checkable
      6. candidate set incomplete → not_fully_checkable
      7. clear
    Rule 2 is new. A target that cannot be placed in time is never "clear", even with no other trips, because
    nothing can be checked against an unplaceable interval. No candidates are loaded for it; its window is null, as
    before.
  - A known overlap stays "overlap". missingSchedule, missingDuration, stillOpenPastPlannedEnd and
    candidateSetIncomplete are all still reported next to it.
  - Q7 is untouched. A pickup-less trip has no planned end, so it is never "still open past planned end". The two
    reasons stay separate. There is no lateness semantics.

8. MISSING-SCHEDULE vs MISSING-DURATION REPRESENTATION
======================================================================
  - Domain: the separate missingSchedule[] and missingDuration[] arrays in the pure ResourceCheck (not in React).
  - The view (trip-overlap.ts ResourceOverlapView) gains missingScheduleCount next to missingExtentCount.
  - overlapNotices takes an optional missingScheduleCount. The duration count is missingExtentCount minus
    missingScheduleCount. When the target is known, every missing entry is candidate-caused.
  - Target reason: deriveTripExtent already returns "no_schedule" before "no_duration". Pickup time is the more
    fundamental missing fact when both are absent. This is unchanged and tested.
