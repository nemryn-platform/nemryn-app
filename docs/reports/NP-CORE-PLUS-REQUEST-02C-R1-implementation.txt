3. ACCESSIBILITY FINDINGS A1–A4 — ALL RESOLVED
======================================================================================================================
  A1  Cancel -> focus returns to "Add contact".
      The button now has a ref. Cancel sets a one-shot flag before closing the form, and an effect focuses the button
      once the form has unmounted. Verified keyboard-only: Enter on Cancel, then Enter again re-opens the form from
      the restored focus.

  A2  Refused submission -> focus moves to what needs attention. The values are preserved; the fields still re-mount
      with the echoed values.
        - field errors: the first element with aria-invalid="true", in DOM order. Its error is already tied by
          aria-describedby (the Input / Select primitives), so assistive technology reads label, "invalid" and the
          message.
        - "A phone number or an email address is required": no single field is wrong. BOTH Phone and Email now carry
          aria-invalid plus aria-describedby pointing at that hint (previously the hint was an unattached
          role="alert"). Focus goes to the first invalid field.
        - server errors (not enabled, conflict, generic): focus moves to the error message (tabIndex -1).
        - possible duplicates: focus moves to the duplicate explanation (tabIndex -1). Tab then reaches the match and
          "Link this contact".
      Errors are no longer role="alert" live regions. Each is announced once, when it receives focus. This avoids
      the double announcement (live region plus focus) the handoff asked to prevent.

  A3  Success -> focus moves to the linked contact link in the Growth panel. This uses id contactLinkId(requestId),
      rendered by the server panel. Focus is moved only if it was lost (<body> or a removed node). It is retried for
      up to 60 animation frames while the refreshed panel arrives, and never taken from somewhere the person has
      since moved. This applies to "Add and link contact", "Create a separate contact" and "Link this contact" (all
      inside the add-contact flow), and also to the released "Link existing contact" / "Correct link" saves, which
      share the same success handler. Their focus was also lost before; there is no other behaviour change.

  A4  One persistent status region (role="status", data-testid="growth-status") is always rendered at the top of the
      controls, before anything is submitted:
        - pending: a visually hidden "Adding the contact…" (or "Linking the request…" / "Saving the correction…")
        - success: the visible success notice, which now lives INSIDE the region (one copy only; it lost its own
          role)
      The region keeps its node across the post-save server refresh, so the change is announced. A negative margin
      cancels the column gap while it shows nothing visible, so the layout is unchanged when it is empty.
      Link-editor errors keep role="alert" (released behaviour), outside the status region.
  Approach reused from the quotes module (NP-UI-P1a, components/ui/Dialog.tsx):
    - restore focus to the invoking control on close
    - only when focus was actually lost, never stealing it
    - never send it to a removed node
  The inline form is not a dialog, so the logic lives in the controls instead of the Dialog primitive.

5. LINK DESCRIPTION ("Linked from Request Details") — LEFT UNCHANGED (limitation)
======================================================================================================================
  The panel shows linkMethodLabel(link_method). Contacts created by this workflow are linked through the released
  plus_link_request, so their link_method is 'linked_existing_request', identical to a manual link of an existing
  contact. Provenance cannot be distinguished reliably without a schema or API change:
    - plus_get_request_attribution (released contract) returns no provenance field.
    - The only record is the audit row 'plus_contact_created_from_request'. `authenticated` has no SELECT privilege on
      audit_events, so a client read would need a new grant or RPC.
    - No plus_activities type records the creation.
    - A heuristic (the contact's created_at close to linked_at) would mislabel a contact created in Growth and then
      linked moments later.
  Per the handoff, the wording is unchanged. Making it accurate later needs one of:
    - a new optional field (e.g. created_from_request boolean) in plus_get_request_attribution, which is an RPC
      contract change
    - a new link_method value, which is a released contract change
  Both need a migration and owner approval.
