P1-PILOT-S2 — RECURRING CARE BULK TRIP CREATION
=================================================
Date: 2026-09-18
Base commit (HEAD, unmodified this phase): 5c1ca37dd5cfcd428e79e98202cb33daf85f62df
Scope: LOCAL IMPLEMENTATION ONLY. Not committed. Not pushed. Not deployed.

CURRENT FRICTION
-----------------
No scheduled-job infrastructure exists anywhere in this repository (confirmed
via grep before coding: no pg_cron, no edge function scheduler). Every real
Trip a Recurring Care arrangement produces required one individual "Create
trip" click per occurrence via OccurrenceRow.tsx on the Arrangement Detail
page — no bulk action existed. An operator with many standing arrangements
had to open each arrangement individually to cover its missing occurrences.

PRODUCT BOUNDARY
------------------
This phase built a human-reviewed BULK creation workflow, never an automatic
scheduler. No cron, no background job, no new recurring engine, no new Trip
creation authority was introduced. Every Trip created by this workflow is
still created by the existing, unmodified create_trip_for_recurring_occurrence
RPC — the same function the single-occurrence "Create trip" button already
calls. No occurrence is ever created merely because it is missing; an
operator must load the review page, see the list, and explicitly submit.

ENTRY POINT
------------
"Review N missing rides" (singular "Review 1 missing ride" when N=1) appears
as a secondary action in the Recurring Care list page's PageHeader, next to
the existing "New recurring arrangement" primary action — only rendered when
the missing count is greater than 0. Clicking it only navigates to
/operations/recurring-care/create-missing; it creates nothing. The route is
NOT added to permanent sidebar navigation (confirmed: src/config/navigation
and the sidebar component were not touched).

REVIEW ROUTE
-------------
/operations/recurring-care/create-missing — a new server component page,
gated by the same requireOperationsAccess(pathname) guard every other
Recurring Care route already uses. Reachable only via the list page's own
entry point or a direct URL (still access-controlled either way).

AUTHORITATIVE MISSING SOURCE
------------------------------
The review page calls the EXISTING, unmodified getRecurringArrangementsList
(recurring-care-list.ts) — the same function the list page itself already
calls — and maps its own already-computed assurance.occurrences into the new
pure flattenMissingOccurrences helper. No weekday/timezone/pattern/pause/
skip/cancelled-Trip logic was reimplemented anywhere in this phase; the real
evaluator (deriveRecurringCareAssurance, recurring-care-core.ts) was read in
full before coding and never modified. Only occurrence.state === "MISSING"
rows are included; SCHEDULED and SKIPPED are excluded by construction (never
an inferred "not SCHEDULED" check).

REVIEW LIST
------------
A compact table: Select / Date / Passenger / Pickup time / Route. No raw
UUIDs are rendered anywhere (verified live — see LOCAL E2E). Dates and times
are shown in the arrangement's own local wall-clock representation via the
existing formatServiceDateShortLabel/formatWallClockTime helpers, unchanged.

SELECTION MODEL
-----------------
Every MISSING occurrence is selected by default. A native
<input type="checkbox" name="occurrenceKey" value="...">  per row (no new
checkbox/table primitive was introduced beyond this — grep confirmed no
existing multi-select table convention existed to reuse). "Select all" /
"Clear all" controls. The submit button always states the true selected
count ("Create 7 trips" / "Create 1 trip") and is disabled at zero selected.
Unchecked boxes are simply absent from the submitted FormData — the existing
native multi-checkbox convention this codebase already uses for daysOfWeek.

SERVER ACTION
---------------
src/app/operations/recurring-care/create-missing/actions.ts — one new
Server Action, bulkCreateMissingTripsAction, mirroring the exact conventions
of every existing Recurring Care action in
src/app/operations/recurring-care/[arrangementId]/actions.ts:
requireOperationsAccess(pathname) for the trust boundary,
createServerSupabaseClient(), one supabase.rpc(...) call per unique
occurrence, mapRecurringArrangementError(error.code) on failure,
revalidatePath() on success. It never uses the service role and never
duplicates the RPC's own SQL logic in TypeScript.

INPUT AUTHORITY
-----------------
The browser submits ONLY occurrenceKey values (arrangementId::serviceDate
pairs). No Passenger id, pickup/destination text, pickup time, timezone,
organization id, or Trip state is ever accepted from the browser in this
action. organizationId comes exclusively from requireOperationsAccess's own
trusted resolution, never a form field. Every operational fact is derived by
the RPC itself from the arrangement's own current, freshly row-locked state
— identical to the single-occurrence path's existing trust boundary.

DEDUPLICATION
---------------
dedupeOccurrenceKeys (recurring-care-bulk-core.ts) runs BEFORE any RPC call,
deduplicating by exact key with first-seen order preserved and malformed
keys silently dropped. A duplicate value in submitted form data results in
exactly one RPC invocation, never relying solely on the RPC's own row-lock
idempotency to absorb an avoidable duplicate call.

EXECUTION STRATEGY
---------------------
Bounded concurrency: a small worker-pool runner (runBounded, actions.ts)
processes the deduplicated occurrence list with at most 5 RPC calls in
flight at a time. Chosen over full serial execution (unnecessary latency for
a batch of dozens) and over one unbounded Promise.all (an uncontrolled burst
against the database). Correctness was prioritized over throughput — no
special-cased retry/backoff logic was added since each call is already
independently transactional and idempotent at the RPC layer.

SAFETY BOUND
--------------
No hard cap was imposed on selectable/submittable occurrences. The realistic
maximum in the near-term horizon (confirmed live: 22 Org A arrangements
produced 48 missing occurrences without any UI degradation — see LARGE
OPERATOR below) stays comfortably within what bounded concurrency handles
safely. Imposing an arbitrary limit would risk silently dropping a
genuinely selected occurrence, which this phase's own instructions forbid.

PARTIAL SUCCESS MODEL
------------------------
Each RPC call is independently transactional; one occurrence's failure never
blocks or rolls back any other occurrence in the same batch. The action
always returns a full, per-occurrence result list
(CREATED / ALREADY_SCHEDULED / FAILED), never a single pass/fail verdict.
Verified live with a mixed batch (see LOCAL E2E, small-batch and race
scenarios).

ALREADY-SCHEDULED SEMANTICS
------------------------------
create_trip_for_recurring_occurrence's own `created: boolean` field is the
sole signal: created === true -> CREATED; created === false (a qualifying
non-cancelled Trip already exists) -> ALREADY_SCHEDULED. No new business
logic was written to detect this — it is a direct pass-through of the RPC's
own existing, unmodified idempotency contract. Verified live via a genuine
stale-page race (see LOCAL E2E).

ERROR PRESENTATION
---------------------
Every FAILED result is mapped through the EXISTING, unmodified
mapRecurringArrangementError / recurringArrangementErrorMessage
(recurring-arrangement-errors.ts) — the same narrow vocabulary
(UNAUTHORIZED / NOT_FOUND / ILLEGAL_STATE / INVALID_INPUT / UNKNOWN) every
other Recurring Care action already uses. No ZW code, SQLSTATE, PostgREST
JSON, or stack trace is ever rendered. Verified live: a genuine RPC failure
(arrangement ended mid-race) rendered as "Please check the information
provided and try again." with the Passenger/date shown for identification,
and a live full-page text scan confirmed no ZW-code/SQLSTATE/PGRST pattern
anywhere in the DOM.

REVALIDATION
--------------
On every batch resolution the action calls revalidatePath for
/operations/recurring-care, each touched arrangement's own detail route,
/operations, /operations/trips, /operations/tomorrow, and
/operations/dispatch — the same Next.js revalidation convention every
existing Recurring Care action already uses. No client state is manually
patched to fake an update.

POST-CREATION FLOW
---------------------
The operator stays on the review page. After a batch resolves, the client
component calls router.refresh(); successfully resolved occurrences
(CREATED or ALREADY_SCHEDULED) disappear from the list because they are no
longer MISSING once the server re-fetches, while FAILED occurrences remain
MISSING and reappear selected, ready for an immediate retry with zero extra
code path — a direct consequence of always deriving default selection from
the current row set rather than tracking retry state separately.

DRIVER/VEHICLE BOUNDARY
---------------------------
The bulk action never assigns a Driver or Vehicle — it calls the same RPC
the single-occurrence button calls, which is documented (and unchanged) to
never touch trip_assignments. Verified live: after a bulk batch, created
Trips appeared on /operations/dispatch in their normal unassigned state,
same as any other newly created Trip.

REQUEST BOUNDARY
-------------------
No TransportationRequest record is created by this workflow. Recurring
Care -> Trip remains the existing direct provenance path, untouched.

CANCELLED REPLACEMENT / SKIPPED / SCHEDULED BEHAVIOR
--------------------------------------------------------
All three are the RPC's and evaluator's own existing, unmodified behavior.
SKIPPED and SCHEDULED occurrences are excluded from the review list by the
same explicit state === "MISSING" filter (unit-tested: see APPLICATION TEST
RESULTS). Cancelled-only-occurrence replacement semantics inside the RPC
were read in full during the pre-coding audit and were not touched. These
were not independently re-validated end-to-end this phase (time-bounded
scope decision, see OPEN ISSUES) — they were already covered by this
repository's existing Recurring Care test history from prior phases and by
this phase's own unit tests for the flatten/exclusion logic.

ARRANGEMENT EDIT / PAUSE / END RACE
---------------------------------------
Simulated live: an arrangement was ended via the real end_recurring_
arrangement RPC after its review page had already loaded (stale selection
in the browser), then the stale page's bulk submission was still sent. The
RPC's own current-facts revalidation rejected the now-invalid occurrence
(ZW006, mapped to the safe INVALID_INPUT message) — result: FAILED, no
Trip created, no raw error text shown, batch still resolved cleanly for
every other selected occurrence. This is unmodified RPC authority; the bulk
action added no bypass and no extra validation of its own.

DST AUTHORITY
----------------
No new timezone-conversion logic was written anywhere in this phase. The
bulk orchestration sends only arrangementId + serviceDate; the existing
create_trip_for_recurring_occurrence RPC (unmodified,
_organization_local_to_utc) remains the sole source of the DST-safe
timestamp conversion, exactly as it already is for the single-occurrence
path.

AUTHORIZATION
----------------
Page level: requireOperationsAccess(pathname) — the same guard used
everywhere else under /operations. Server Action level: the action
independently calls requireOperationsAccess again inside itself (never
relies on the page alone) before touching FormData. Verified live: a Driver
Membership was redirected to /driver when navigating directly to the review
route.

ORG ISOLATION
----------------
Verified live in three ways: (1) Org B's own review page showed only its
own arrangement's own missing occurrences — Org A's fixture data never
appeared. (2) organizationId is taken only from the Server Action's own
requireOperationsAccess resolution, never a form field. (3) A malicious
cross-org input was directly injected into Org B's submitted form (an Org A
arrangementId paired with a real Org A service date) — the batch resolved
with 0 created, 1 failed, and a direct database check confirmed zero Trips
were ever created linking Org A's arrangement to Org B. The RPC's own
existing organization-scoped authorization (has_org_role / arrangement
organization_id match) enforced this; the bulk action added no additional
isolation logic of its own, matching its "identifiers only" input-authority
design.

DOUBLE SUBMIT
----------------
Two layers were verified: (1) UI level — the submit button is disabled
while a submission is pending (loading={pending} disabled={pending}),
preventing a literal double-click from firing two overlapping requests.
(2) RPC level — the stale-page race scenario above independently exercised
the exact mechanism a double-submit would hit: two separate invocations of
create_trip_for_recurring_occurrence for the identical occurrence resolved
to exactly one Trip (created: true once, created: false the second time),
with the bulk action correctly mapping the second one to ALREADY_SCHEDULED,
never a duplicate, never FAILED.

CONCURRENCY
--------------
Per this phase's own explicit instruction, the full concurrency battery was
NOT rerun. The underlying RPC's own row-lock (`for update`) serialization
was already proven safe under real concurrent load by the existing
recurring_trip_creation_concurrency_test from a prior phase and was not
re-executed here. This phase instead exercised the bulk action's OWN result
mapping against that same idempotency contract via the stale-page race
(above), which is a direct, real invocation of the RPC twice for the same
occurrence — functionally equivalent evidence to a live two-Dispatcher race
for the one thing this phase's own code could get wrong (the CREATED vs.
ALREADY_SCHEDULED mapping), without repeating the underlying RPC's own
already-proven serialization guarantee.

SMALL OPERATOR
-----------------
Verified live: 1 missing, 3 missing (exact selection + submit label +
mixed-state list after clear/select-all), deselect-one (count decrements by
exactly 1), Select all / Clear all, submit disabled at zero selected.

LARGE OPERATOR
-----------------
22 active Org A arrangements (2 hand-authored + 20 scripted, mixed
single/multi-weekday patterns) produced 48 missing occurrences in the
near-term horizon. The review page rendered all 48 rows in the same
DataTable/route/component used at every other scale — no pagination, no
separate "enterprise mode," no crash, no unusable page. This is the key
product benefit this phase targeted, directly observed.
