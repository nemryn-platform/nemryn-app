2. OWNER DECISIONS (carried from the brief; binding for PROG5B)
======================================================================
Driver availability comes in two forms:
  - A recurring weekly work schedule: organization-local, split shifts, overnight shifts, honest DST handling.
  - One-off unavailability windows: timing only, with no reason.
Schedule configuration is EXPLICIT:
  - A driver with no configured schedule is SCHEDULE NOT SET, never OFF SHIFT and never AVAILABLE.
Writes:
  - Organization Admin and Dispatcher can write schedules and unavailability.
  - The Driver can read their own data only, and cannot write.
  - No self-service scheduling, approvals, payroll, time clock or hours-of-service logic.
Vehicles:
  - Time-bounded out-of-service windows, distinct from vehicles.status. No fleet-maintenance features.
Capability vocabulary (only these four; UNKNOWN always representable):
  - wheelchair ramp (yes / no / unknown);
  - wheelchair lift (yes / no / unknown);
  - wheelchair positions (integer / unknown);
  - seated passenger capacity (integer / unknown).
  - Not included: stretcher, oxygen, bariatric, ADA / certification / Medicaid or any regulatory claim.
Trip requirement: a small factual tri-state "requires wheelchair access". It is never inferred from free text or
passenger history.
Warnings are advisory:
  - assign_trip / reassign_trip are unchanged except for the invariants they already enforce (active, same-tenant
    driver / vehicle).
  - No auto-selection, no scoring, no "best".

3. PRIVACY MODEL
======================================================================
Classification:
  - Driver weekly schedule and unavailability windows: PERSONNEL data, moderate sensitivity.
      - Visible to that organization's Admin and Dispatcher, and to the driver themself.
      - Never to other drivers, foreign tenants, anonymous users or any public surface.
  - Vehicle capability and out-of-service windows: operational fleet data, low sensitivity.
  - Trip wheelchair requirement: an operational trip fact.
      - It is necessary for dispatch. It is not a diagnosis.
      - It is stored as a tri-state boolean only, never a mobility or clinical taxonomy.
Data minimization (enforced by schema, not by guidance):
  - There is NO reason, category, note or free-text column on any unavailability table.
  - No medical, family, vacation, HR or disciplinary data can be stored, because no column exists for it.
  - Audit before / after data holds only times and IDs, never text.
Retention:
  - Windows persist until deleted. Admin / Dispatcher can delete them.
  - PROG5 adds no automatic purge (there is no scheduler infrastructure).
  - Recommended expectation, documented for operators: past unavailability windows have no ongoing operational use,
    and a later retention job may purge windows that ended more than 90 days ago (open question Q8).
  - Audit rows follow the existing append-only audit policy.

4. DRIVER SCHEDULE SEMANTICS
======================================================================
Weekly schedule: zero or more SHIFT rows, each (weekday, start_time, end_time).
  - weekday: ISO 1..7 (Mon = 1), the same convention as organizations.operating_days and
    _is_canonical_days_of_week.
  - start_time / end_time: organization-LOCAL wall-clock `time` (minute precision). They are NEVER converted to UTC
    at rest.
  - end_time > start_time: a same-day shift.
  - end_time < start_time: an OVERNIGHT shift that ends on the next local day. end_time 00:00 means "until
    midnight".
  - end_time = start_time: rejected (ZW006). A 24-hour day is two rows (00:00–12:00, 12:00–00:00).
  - Split shifts: several rows on the same weekday.
  - Overlapping shifts are rejected by the setter, including an overnight shift spilling into the next weekday's
    shift. Touching boundaries are allowed.
  - The schedule is a single CURRENT schedule. It has no effective-dated versions (Q5), and a change applies to every
    future evaluation.
Expansion to instants (pure, in the new availability core):
  - For each local date D in the needed range, and each shift whose weekday = isoWeekday(D), the instance is
    [local(D, start), local(D or D+1, end)), in the organization timezone. The range is D-1..D+1 around the target,
    so overnight shifts from the previous day are included.
  - Resolution uses a new pure helper, resolveLocalBoundary(date, time, timezone), which extends the existing
    local-time.ts logic without changing organizationLocalToUtc. It returns { earliest, latest }:
      - ok: earliest = latest = the single instant.
      - nonexistent (spring-forward gap): both = the first valid instant after the gap. The wall-clock time was
        skipped, so the shift truly starts or ends when the clock resumes.
      - ambiguous (fall-back hour): earliest = the first occurrence, latest = the second occurrence.
  - Each shift instance therefore has a CERTAIN core [start.latest, end.earliest) and a POSSIBLE extent
    [start.earliest, end.latest).
      - An instant is certainly on shift only inside the core.
      - It is certainly off shift only outside every possible extent.
      - Anything between is "not fully checkable". This is honest DST, with nothing fabricated.
  - Days are not assumed to be 24 hours. All arithmetic is on instants.
Schedule-configured state (explicit, see §17):
  - NOT SET: no schedule-configuration row. This is the default for every existing and new driver.
  - CONFIGURED: a configuration row exists. It is set only by the explicit set_driver_weekly_schedule RPC, which
    requires at least one shift.
  - Configured-state is never inferred from shift rows. Shift rows exist only under a configuration row, through a
    composite FK with cascade on clear.

5. TIME-OFF (DRIVER UNAVAILABILITY) SEMANTICS
======================================================================
  - A window is [starts_at, ends_at), timestamptz, half-open (the same convention as PROG4). ends_at > starts_at.
    The maximum length is 366 days (ZW006).
  - The UI records instants:
      - "all day(s)": converted from local dates through the organization timezone AT ENTRY (DST-correct, per
        date);
      - "from–to": local date-times converted at entry.
  - Stored instants never shift if the organization timezone later changes. That is documented.
  - A window applies even when the schedule is NOT SET: time off is a known fact on its own.
  - It overrides shifts. Time off during a shift means unavailable.
  - Overlapping windows for the same driver are allowed and merge logically. Evaluation is a union.
  - There is no reason field (§3).

======================================================================
6. VEHICLE OUT-OF-SERVICE SEMANTICS
======================================================================
  - vehicle_unavailability_windows: [starts_at, ends_at) timestamptz, half-open, with the same bounds as §5.
    There is no reason or category field.
  - vehicles.status stays the coarse lifecycle fact. inactive is still an assign_trip hard invariant, and the window
    does NOT block.
  - A window means: this ACTIVE vehicle should not be treated as available during the window. It is warning-only.
  - Touching boundaries do not overlap: a trip ending exactly at starts_at is clear.
  - An inactive vehicle keeps the existing behaviour (the assignment is refused by the RPC; VEHICLE_INACTIVE in
    readiness). Windows on inactive vehicles are allowed but irrelevant.

8. WHEELCHAIR TRIP REQUIREMENT MODEL
======================================================================
Decision: add trips.requires_wheelchair_access boolean NULL (NULL = unknown, true = required, false = not required).
Why not service_type:
  - service_type is a Request-level, single-valued purpose category.
  - It mixes purpose (dialysis) with mobility (wheelchair_transportation). A wheelchair user going to dialysis cannot
    be both.
  - It is not a capability fact, and trips do not carry it.
Why not passengers:
  - The brief forbids inferring need from passenger history.
  - A per-trip fact lets the operator state it for THIS trip.
Setting it:
  - New Trip: a tri-state control "Wheelchair-accessible vehicle needed? Yes / No / Not specified", default "Not
    specified".
  - create_trip gains a trailing `p_requires_wheelchair_access boolean DEFAULT NULL`. The 13-argument form is
    drop/create in the same migration, exactly like PROG4, so named-argument callers stay compatible.
  - Request → Trip: when the selected accepted Request has service_type = 'wheelchair_transportation', New Trip
    PREFILLS "Yes".
      - The operator can change it before submitting (a manual override).
      - No other service_type and no assistance_notes text is interpreted.
      - The SQL does not auto-copy, consistent with how create_trip treats request fields today. What was stored is
        what the operator confirmed.
  - Trip Detail: set_trip_wheelchair_requirement(p_trip_id, p_requires_wheelchair_access), for Admin / Dispatcher
    on non-terminal trips. NULL clears it to unknown. Audited.
  - Recurring occurrences (Q4): the arrangement's requires_wheelchair_access is SNAPSHOTTED onto each Trip at
    generation. Later arrangement edits never rewrite existing trips.
  - Existing trips: NULL. No backfill.

9. CAPABILITY MATCH DERIVATION (pure; three outcomes + not-applicable)
======================================================================
Input: trip.requires_wheelchair_access, plus the vehicle's four facts.
  - Requirement false → NOT_APPLICABLE (no message).
  - Requirement NULL → REQUIREMENT_UNKNOWN (no warning; see §12 / §13).
  - Requirement true:
      CAPABLE:
        wheelchair_positions ≥ 1 AND (wheelchair_ramp = true OR wheelchair_lift = true)
      KNOWN_MISMATCH:
        wheelchair_positions = 0 OR (wheelchair_ramp = false AND wheelchair_lift = false)
      NOT_CHECKABLE (capability not set): every other combination, i.e. any required fact NULL with no known-false
        condition. Examples:
          - positions 2, ramp NULL, lift NULL;
          - positions NULL, ramp true;
          - all NULL.
Rationale:
  - Boarding needs a ramp or a lift. Securement needs at least one wheelchair position. Both are required.
  - A known false on either dimension is a real mismatch.
  - UNKNOWN is never a mismatch.
Behaviour:
  - A mismatch is a warning. It is never assignment-blocking.
  - No vehicle is suggested and nothing is scored.

10. CANONICAL AVAILABILITY DERIVATION (pure; one model for every surface)
======================================================================
A new pure module, availability-core.ts, consumes:
  - PROG4 trip extent (deriveTripExtent);
  - PROG4 resource-check results (deriveResourceOverlap: overlap / clear / not_checkable / not_fully_checkable,
    including candidateSetIncomplete and missingSchedule);
  - the driver's configuration + shift instances (§4);
  - driver unavailability windows;
  - vehicle windows;
  - capability facts.
It never re-derives commitments. PROG4 R1 / R2 remain the only commitment source.

A) Driver versus a TARGET TRIP (assignment, Trip Detail, Tomorrow, Dispatch block).
   Facts, reported together and each independently:
     time_off:
       - "overlaps" if any window intersects the known interval;
       - if the duration is unknown: "overlaps" if a window contains the pickup; "not_checkable" if a window starts
         after the pickup (it could intersect); otherwise "clear".
     shift (only when the schedule is CONFIGURED):
       - "covered": the known interval lies inside the union of certain shift cores.
       - "off_shift": the pickup is certainly outside every possible extent, OR a part of the known interval is
         certainly outside every possible extent. Copy: "trip ends after this driver's shift" / "outside this
         driver's working hours".
       - "partly_unknown": the pickup is certainly on shift but the duration is unknown ("on shift at pickup; can't
         confirm the whole trip"), or the interval touches a DST-uncertain boundary.
     schedule_not_set: when the schedule is NOT SET (no claim either way).
     commitments: the PROG4 result, unchanged.
   AVAILABLE FOR THIS TRIP only if ALL of these hold:
     - the schedule is CONFIGURED;
     - the extent is known;
     - shift = covered;
     - time_off = clear;
     - the PROG4 driver check = clear (which already implies a complete candidate set and no pickup-less or
       missing-duration commitment).
   Otherwise there is no "available" wording: the specific facts are shown instead.

B) Driver status NOW (capacity rail, Dispatch Today row header). One status per driver, in this precedence:
     1. ON_TRIP: an active-state assignment now (existing "On Trip").
     2. TIME_OFF: an unavailability window contains now.
     3. OFF_SHIFT: CONFIGURED and now is certainly outside every shift extent.
     4. COMMITTED: a non-terminal assigned trip's known planned interval contains now (not yet started).
     5. NOT_FULLY_CHECKABLE: any of the following:
          - a still-open-past-planned-end commitment (Q7);
          - a pickup-less active commitment (R2);
          - a missing-duration commitment that could cover now;
          - an incomplete candidate set;
          - now inside a DST-uncertain shift edge.
     6. SCHEDULE_NOT_SET: NOT SET and none of 1–5.
     7. AVAILABLE: CONFIGURED, certainly on shift now, no time off now, not on a trip, not committed now, and the
        candidate set complete. The meaning is "free right now", never "free for the rest of the day".
   drivers.status = 'inactive' drivers are excluded from the rail, as today.
   A driver is NEVER "Available" merely because they are active, or because they are not on an active-state trip.

C) Vehicle versus a target trip:
     - out_of_service: overlaps / not_checkable (unknown duration, window after pickup) / clear.
     - capability: §9.
     - commitments: the PROG4 vehicle check.
   The rail shows no vehicle status. Vehicles appear only in assignment and trip facts.

13. TOMORROW BEHAVIOUR
======================================================================
New KNOWN-problem readiness reasons (NEEDS_PREPARATION), appended to REASON_ORDER after VEHICLE_INACTIVE:
  DRIVER_TIME_OFF
    The assigned driver's unavailability window intersects the trip (or contains the pickup when the duration is
    unknown).
  DRIVER_OFF_SHIFT
    The assigned driver has a CONFIGURED schedule and the pickup, or a known part of the interval, is certainly
    outside working hours.
  VEHICLE_OUT_OF_SERVICE
    The assigned vehicle's window intersects the trip (or contains the pickup when the duration is unknown).
  VEHICLE_WHEELCHAIR_MISMATCH
    requires_wheelchair_access = true and the assigned vehicle is KNOWN_MISMATCH.
Unknowns are NEVER readiness reasons. At most they are a neutral row note:
  - schedule not set;
  - duration unknown (partial shift proof);
  - capability not recorded;
  - requirement unknown;
  - a "not checkable" time-off or out-of-service window.
  The neutral row note is shown only for requirement true + capability unknown: "Wheelchair equipment not recorded
  for the assigned vehicle" (neutral badge, like PROG4's overlap badge).
readiness-actions-core mapping:
  - DRIVER_* → the existing "Change driver" (reassign dialog).
  - VEHICLE_* → "Change vehicle".
Backward compatibility (guaranteed by construction):
  - After migration, every schedule is NOT SET, there are no windows, capability and requirement are NULL.
  - So all four new reasons are false for every existing trip, and no Tomorrow count changes on release day.
Overlap stays a neutral badge, as in PROG4. It is not a readiness reason.

17. RECOMMENDED SCHEMA (PROG5B migration; expand-only; one migration file)
======================================================================
driver_weekly_schedules
  driver_id uuid PRIMARY KEY
  organization_id uuid NOT NULL
  configured_at timestamptz NOT NULL default now()
  updated_at timestamptz NOT NULL default now()

  driver_id uuid NOT NULL

  end_time time NOT NULL

  CHECK (start_time = date_trunc('minute', start_time) and the same for end_time)

  ends_at timestamptz NOT NULL

  updated_at timestamptz NOT NULL

  INDEX (organization_id, starts_at)

  The same shape, with vehicle_id and FK (vehicle_id, organization_id) → vehicles(id, organization_id).
vehicles

trips

recurring_arrangements (Q4)

18. PROPOSED RPCs (all SECURITY DEFINER, SET search_path = public, pg_temp; REVOKE ALL FROM PUBLIC; GRANT EXECUTE TO authenticated only)
======================================================================
Admin / Dispatcher of the resource's organization. Denial uses the existing ZW codes: ZW002 not found / unauthorized
tenant, ZW006 invalid input, ZW004 terminal trip. Each call takes a row lock and returns a `changed` flag
(idempotent).
  set_driver_weekly_schedule(p_driver_id uuid, p_shifts jsonb) → driver_schedule_result
    - p_shifts: [{weekday, start: "HH:MM", end: "HH:MM"}, …], 1..28 entries. It is validated as a whole: bounds, no
      overlap on the recurring WEEK AS A RING (Sunday overnight → Monday), minute precision.
    - It atomically upserts the configuration row and replaces ALL shifts.
    - Audit: driver_schedule_set (after_data = the shift list).
  clear_driver_weekly_schedule(p_driver_id uuid) → driver_schedule_result
    - Deletes the configuration row (shifts cascade), returning to NOT SET.
    - Audit: driver_schedule_cleared.
  save_driver_unavailability(p_driver_id uuid, p_window_id uuid DEFAULT NULL, p_starts_at timestamptz,
                             p_ends_at timestamptz) → unavailability_result
    - Creates when p_window_id is NULL, otherwise updates. The window must belong to the driver and tenant.
    - Audit: driver_unavailability_added / driver_unavailability_changed.
  delete_driver_unavailability(p_window_id uuid) → unavailability_result
    - Audit: driver_unavailability_removed (before_data = starts / ends only).
  save_vehicle_unavailability(p_vehicle_id uuid, p_window_id uuid DEFAULT NULL, p_starts_at timestamptz,
                              p_ends_at timestamptz) → unavailability_result
    - Audit: vehicle_unavailability_added / _changed.
  delete_vehicle_unavailability(p_window_id uuid) → unavailability_result
    - Audit: vehicle_unavailability_removed.
  set_vehicle_capabilities(p_vehicle_id uuid, p_wheelchair_ramp boolean, p_wheelchair_lift boolean,
                           p_wheelchair_positions integer, p_seated_capacity integer) → vehicle_capabilities_result
    - An atomic setter of all four facts (NULL = unknown).
    - Organization ADMIN only, matching the existing fleet-setup authority (vehicles UPDATE is Admin-only) (Q1).
    - Audit: vehicle_capabilities_updated.
  set_trip_wheelchair_requirement(p_trip_id uuid, p_requires_wheelchair_access boolean) → trip_requirement_result
    - Non-terminal trips only (ZW004 otherwise). NULL clears it.
    - Audit: trip_wheelchair_requirement_updated.
  create_trip(…12 existing…, p_requires_wheelchair_access boolean DEFAULT NULL)
    - Authorization is unchanged.
Driver (own only), if the §15 card is approved:
  driver_get_own_schedule(p_organization_id uuid) → driver_own_schedule_result
    - The caller must be the ACTIVE driver linked to auth.uid() in that organization (the same resolution as
      driver_get_profile).
    - Returns: configured flag, own shifts, and own windows intersecting [now, now + 14 days).
    - Never takes a driver_id parameter, so it cannot address another driver.

22. TIMEZONE / DST MODEL
======================================================================
  - Shifts are local wall-clock values stored as `time` + ISO weekday. They are expanded per local date in
    organizations.timezone with resolveLocalBoundary (§4).
  - Spring-forward: a boundary in the gap resolves to the first instant after the gap. A 00:00–06:00 shift on
    spring-forward night lasts 5 real hours.
  - Fall-back: an ambiguous boundary produces a certain core and a possible extent. A 00:00–06:00 shift lasts
    6 hours (core) to 7 hours (extent). Instants in the ambiguous difference are "not fully checkable", never
    asserted.
  - Overnight: an end on D+1 is resolved on D+1's own offset.
  - Windows and trips are timestamptz instants. Comparisons are always instant-based, half-open.
  - The day scope reuses organizationDayBoundsUtc. No day is assumed to be 24 hours.
  - Required tests: spring-forward, fall-back, overnight across both transitions, midnight crossing, split shifts,
    and 00:00 end.

23. QUERY / PERFORMANCE PLAN
======================================================================
Assignment action (per selection), bounded:
  - the selected driver's configuration + shifts (≤ 28 rows);
  - the driver's windows intersecting [target − 24 h, target end + 24 h];
  - the selected vehicle's windows intersecting the same range, plus its 4 capability columns;
  - the trip requirement.
  That is 3–4 small indexed queries in parallel, alongside the PROG4 candidate families.
Dispatch day / Tomorrow (one batch per scope, no N+1):
  - all active drivers' configurations + shifts for the organization (≤ drivers × 28);
  - all driver and vehicle windows intersecting [day start − 24 h, day end + 24 h);
  - capability columns on the already-loaded vehicle options;
  - the requirement on the already-loaded trips.
  Derivation is in memory through availability-core.
Pagination:
  - The PROG4 R1 keyset pager applies to the window queries at the same page size (500) with a ceiling. Coverage
    "incomplete" → "not fully checkable" for availability claims. PROG4 R1 / R2 semantics are untouched.
Scale:
  - At 1 / 3 / 10 / 30 / 100+ drivers the row counts stay in the hundreds per day.
  - Btree indexes on (organization_id, starts_at) are sufficient. No GiST or range types needed in PROG5.
