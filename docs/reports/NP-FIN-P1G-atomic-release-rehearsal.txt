3. FINDING THE PACKAGE CLOSES (also relevant to a plain `db push` of PR #44)
======================================================================================================================
  M1's zero-row gate (section 0) reads billing_payments without a write-blocking lock. billing_payments is only
  retired near the end of M1 (section 13). An old-app payment that commits between those two points would leave
  billing_payments non-empty after the release, violating ZD-268. The package takes EXCLUSIVE locks before M1 and
  re-asserts zero payments at the end. M1 itself is unchanged.

6. ROLLBACK REVIEW (section 4 of the authorization)
======================================================================================================================
  Removing the gate while leaving FIN-P1 writable is no longer possible with the prepared scripts:
    - the gate-only reversal is withdrawn;
    - NP-FIN-P1G-emergency-reversal.sql removes P1G and FIN-P1 together in ONE transaction. Order (after the
      rollback concurrency fix): schema-only structure check -> ACCESS EXCLUSIVE locks on the 12 financial tables,
      both enablement tables and supabase_migrations.schema_migrations -> every data / head check -> drops;
    - NP-FIN-P1-emergency-reversal.sql alone fails under the gate (R9).
  Exact safe conditions for the combined rollback (1-3 enforced by its guard):
    1. the FIN-P1 ledger is empty;  2. no LIVE enablement record, current or historical;  3. billing_payments empty;
       (plus migration head = 20261029120000) -- all evaluated UNDER the locks;
    4. explicit owner authorization;  5. the app rolled back to the pre-release build in the same window;
    6. the owner accepts the end state: NP-BILL-P1 exactly as before the release, with NO financial-write gate
       (invoice writes open to every organization's Organization Admins, i.e. production's state today).
  Incident response is DISABLE (one Platform Admin RPC call), never gate removal.
  Note: the header of NP-FIN-P1-emergency-reversal.sql (PR #44, not modified per ZD-284) suggests
  `supabase db query --linked -f`. That transport is unverified for multi-statement files (R1b); use psql.
