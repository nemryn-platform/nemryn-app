1. ROOT CAUSE
----------------
`resolveOrganizationContext()` (src/lib/auth/organization.ts) has always had
exactly one way to decide whether a multi-Membership caller sees the
picker: does the `zw_org_context` cookie already match one of their active
Memberships? If yes → `status: "selected"`. `/select-organization`'s own
page component treats `"selected"` identically to `"single"` — an
immediate `redirect(next ?? "/")`, no picker ever rendered.

This is completely correct for NORMAL navigation (a deep link, a stale
bookmark, a redirect chain arriving here mid-request) — there is nothing
to ask the caller in that case, they already have a valid selection.

But AccountMenu's "Switch Organization" link pointed at that exact same
route with no way to signal "I am not just passing through, I am
deliberately asking to change my mind." The route had no mechanism to
distinguish that intent from ordinary resolution, so it applied the same
immediate-redirect rule to both, and an explicit switch request always
silently no-opped.


2. PREVIOUS BEHAVIOR
------------------------
1. Multi-org user signs in, selects a workspace → `zw_org_context` cookie
   set, `resolveOrganizationContext()` now returns `status: "selected"`.
2. User opens AccountMenu → Switch Organization → navigates to
   `/select-organization`.
3. Page resolves `status: "selected"` (the cookie still matches) →
   `redirect(next ?? "/")` → user is bounced straight back to
   `/operations`, having never seen a picker.
4. Confirmed by this session's own P1-UX-R1 live testing (see that
   phase's report, §6) — the link fired and reached the correct route,
   but the workflow itself never accomplished anything.


3. FINAL SWITCHING MECHANISM
--------------------------------
AccountMenu's "Switch Organization" link now points at
`/select-organization?switch=1` instead of `/select-organization`.

`resolveOrganizationContext()` gained one new, optional parameter:

    resolveOrganizationContext(options?: { forceSelection?: boolean })

When `forceSelection` is true AND the caller genuinely has more than one
active Membership, the function returns `status: "select-required"`
(carrying the full membership list) instead of computing the normal
cookie-match branch — i.e. it takes the exact same code path this
function already uses for "no valid selection exists yet," just entered
deliberately rather than because the cookie was missing/stale.

`forceSelection` changes NOTHING for:
  - zero Memberships (`status: "none"`, unchanged)
  - exactly one Membership (`status: "single"`, unchanged — always, even
    if `forceSelection` is true, satisfying §7)
  - the normal, unflagged call path used by every other caller in the
    codebase (root `/`, `requireOperationsAccess`, `requireOnboardingAccess`,
    `requireDriverAccess`, `/complete-signup`) — none of these pass the
    new option, so their behavior is byte-for-byte identical to before.

`/select-organization/page.tsx` reads `?switch=1` from its own
`searchParams` (already an existing pattern there for `?next=`) and
passes `{ forceSelection: switchRequested }` through. This is the ONLY
place in the codebase that ever sets this flag.

A small, additive UX detail: when in explicit-switch mode, the page also
resolves which membership the caller was already using (via the
already-existing `getRequestedOrganizationId()` cookie reader, a plain
read with no new query) purely to mark that card "Current" in the
picker — see §6.


4. SECURITY MODEL
---------------------
`?switch=1` is a boolean UI-mode flag, never an organization identifier.
It cannot select, imply, or bias toward any specific organization — it
only chooses which of two ALREADY-COMPUTED, membership-validated
resolution outcomes (`"selected"` vs `"select-required"`) the route acts
on. The underlying computation — a fresh `getActiveMemberships()` call,
re-run on every single request, never cached — is completely unchanged.

The actual selection is, exactly as before, performed exclusively by
`selectOrganizationAction` (src/app/select-organization/actions.ts),
which independently re-validates the submitted `organizationId` against
a SEPARATE fresh `getActiveMemberships()` call and silently redirects
back to the picker (never accepting, never erroring in a way that leaks
existence) if it is not one of the caller's own active Memberships. This
phase did not touch that file at all.

Verified directly, not assumed:
  - No RLS policy touched (`git status --porcelain supabase/` empty
    throughout).
  - No query anywhere in this phase's 4 changed files trusts a
    client-supplied organization id — grepped for `searchParams`/`params`
    usage in `select-organization/page.tsx` and confirmed `switch` is
    read only as a boolean gate (`=== "1"`), never passed to any
    Supabase call.
  - `getRequestedOrganizationId()` (the "Current" badge's data source) is
    a plain cookie read used ONLY for display; it is never compared
    against anything to grant access — `resolveOrganizationContext`
    itself does that comparison separately and authoritatively.
  - A single-org caller cannot reach the picker by any means, including
    manually crafting `?switch=1` in the address bar — confirmed live
    (§8/§9 below): `resolveOrganizationContext` returns `status: "single"`
    for them regardless of the flag, and the page redirects onward
    exactly as for any other single-org request.
  - No service-role client introduced or used anywhere in this phase.

6. EXPLICIT-SWITCH BEHAVIOR
-------------------------------
1. AccountMenu → "Switch Organization" → navigates to
   `/select-organization?switch=1`.
2. Page calls `resolveOrganizationContext({ forceSelection: true })`.
3. For a genuinely multi-Membership caller, this now returns
   `status: "select-required"` EVEN THOUGH a valid cookie match exists —
   the picker renders instead of bouncing back.
4. The picker (`OrganizationSelector`) marks whichever membership the
   cookie currently points at with a small, restrained "Current" badge
   (pill, existing `typography.metadata` + `surface-secondary` tokens —
   no new visual language), so the caller can see at a glance which
   workspace they are already in while choosing. This is the one
   response to phase §6's invitation to show the current workspace "if
   the existing component already supports doing so without unnecessary
   complexity" — it did not before, so a small, explicitly-scoped
   addition was made (one boolean comparison per card, no new component,
   no redesign).
5. Selecting a DIFFERENT membership submits the existing, unmodified
   `selectOrganizationAction` form exactly as always — server-validates
   the choice, sets the cookie, redirects to `next ?? "/"`.
6. Root `/` (unmodified) then re-resolves the (now-updated) organization
   context and routes by the NEW membership's role — `/operations` for
   organization_admin/dispatcher, `/driver` for driver (see §10).


7. NORMAL-SELECTION BEHAVIOR (must remain unchanged)
--------------------------------------------------------
Every call path OTHER than the explicit "Switch Organization" link is
completely unaffected: no `?switch=1`, so `forceSelection` is
`undefined`/falsy, so `resolveOrganizationContext` takes its original,
untouched code path — cookie match → `"selected"` → immediate redirect
onward; no match → `"select-required"` → picker (the picker in this case
receives `currentOrganizationId: null`, since `switchRequested` is
false, so no "Current" badge renders — nothing to mark as current when
there was no valid prior selection anyway).

Live-confirmed (§8): a multi-org user who already has a valid cookie and
navigates DIRECTLY to `/select-organization` with no query string is
still bounced straight to `/operations`, byte-for-byte the same as
before this phase.
