2. CREDENTIAL MODEL (validated against the official Supabase documentation)
--------------------------------------------------------------------------
- Fine-grained personal access tokens "can be scoped to specific organizations, projects, and permissions"; each
  permission is Read or Read-write. Full-access ("Legacy") tokens also exist and must NOT be used.
- The two endpoints the gate calls, and the minimum permissions:

  | Endpoint | Purpose | Fine-grained permission (Dashboard label) |
  |---|---|---|
  | GET /v1/projects/{ref} | identity (ref, name) | project_admin_read ("Project Settings: Read"; OAuth projects:read) |
  | GET /v1/projects/{ref}/database/migrations | applied history, response [{version, name}] | database_migrations_read ("Migrations: Read"; OAuth database:read) |

  The documented response shapes match the transport's validation: `ref` and `name` on the project; an array of
  {version, name} for migrations.
- REQUIRED token: scoped to the Nemryn project (wyocbivzgrbekuyqdfts) ONLY, with exactly Project Settings: Read and
  Migrations: Read. No Read-write permission, no organization or account permission, an expiry as short as is
  practical, and rotation on schedule.
  - A permission can only narrow the creating account's role. Create it from an account whose role covers those reads.
- Explicitly NOT valid for this purpose:
  - a Legacy full-access token;
  - Migrations: Read-write (it unlocks apply / patch / rollback / upsert);
  - Database or Data API permissions;
  - the database password (password-based CLI commands such as db push are not limited by token permissions).
- Storage:
  - GitHub repository secret NEMRYN_RELEASE_SUPABASE_TOKEN, used only by the trusted workflow;
  - Vercel environment variable SUPABASE_ACCESS_TOKEN, scoped to Production ONLY;
  - never in the repository, a committed environment file or a NEXT_PUBLIC_* variable.
- Blast radius if leaked: read access to the Nemryn project's settings metadata and migration history. No data rows,
  no writes, no other projects.
- Verification status:
  - the permissions above come from the documentation and are not yet live-tested (no token was created);
  - activation step A3 proves them read-only before anything blocks;
  - a token missing a permission gets HTTP 401 / 403, which is UNVERIFIABLE (fail closed; test "01A identity").

3. CI TRUST-BOUNDARY REVIEW
---------------------------
Risk in the 01 design:
- `pull_request` ran the PR's OWN workflow file and the PR's OWN scripts/release with the token in the environment.
- Any same-repository branch could therefore change the checker or workflow to exfiltrate the token, or always pass.
Fix (01A):
- Trusted workflow release-db-compat.yml on `pull_request_target`:
  - GitHub runs the workflow file from the BASE branch, so a PR's edits to it do not apply until reviewed and merged;
  - it checks out the BASE commit (github.event.pull_request.base.sha) with persist-credentials false;
  - it runs the base checker;
  - it fetches refs/pull/<n>/head as git objects only and verifies they equal the event's head SHA;
  - it passes the head SHA to `--candidate`;
  - it never checks out, installs, builds, tests or executes anything from the PR.
- Permissions: contents: read, statuses: write. The result is posted as commit status "nemryn/release-db-compat" on the
  PR head SHA.
- Only SHAs and the PR number are interpolated, through env. No title, body or branch name reaches a shell.
- The checker's output is printed between `::stop-commands::<random>` markers. The step summary replaces "::".
- Untrusted workflow release-gate-tests.yml on `pull_request`: runs the PR's version of the gate tests with a
  read-only token and NO secrets.
- Fork PRs:
  - the token expression is `head.repo.full_name == github.repository && secrets.… || ''`, so fork PRs receive an EMPTY
    token;
  - application changes → UNVERIFIABLE (fail closed);
  - docs / test-only → PASS.
  The workflow-simulation test confirmed the empty-token path.
- Residual risks (documented, accepted or owner-mitigated):
  - (a) Someone with write access can push a malicious change to the trusted workflow directly to main. Mitigation:
    required PR on main (D3); only the owner has write access.
  - (b) pull_request_target runs with base-branch privileges for every PR, including forks. That is safe here only
    because no PR content is executed. Any future edit to that workflow must keep this property; static test "01A
    workflows" enforces it.
  - (c) GITHUB_TOKEN with statuses: write could set statuses on other commits if the trusted code were compromised.
    It is limited to base-branch code.

4. GITHUB PROTECTION RECOMMENDATIONS (single-maintainer workflow; no deadlock)
-----------------------------------------------------------------------------
On main (a ruleset or branch protection):
- require a pull request before merging, with **required approvals: 0**. GitHub does not allow authors to approve
  their own PRs; requiring 1 with a single maintainer deadlocks every merge;
- require status check "nemryn/release-db-compat" (the commit status posted by the trusted workflow);
- require branches to be up to date before merging (the check then reflects the merge base);
- block force pushes and deletions;
- include administrators / no routine bypass (D3).
CODEOWNERS: added as ADVISORY. Do NOT enable "Require review from Code Owners" until a second eligible reviewer
exists; it would deadlock in the same way.
Emergency procedure (no routine bypass): the owner temporarily relaxes the rule or sets NEMRYN_RELEASE_GATE_MODE back
to report, records the reason in a release report, then restores it.
Deadlock check: with 0 approvals and one required status, the owner can open a PR, wait for "nemryn/release-db-compat"
= success, and merge. No second person is needed.
- Docs-only PRs pass without production access.
- Fork PRs are UNVERIFIABLE for app changes, by design.
- Caveat: the status is posted only once the workflow exists on main. The PR that introduces the workflow will not
  receive it; merge that one PR before making the status required (A1 → A6).

6. VERCEL GATE: EXIT CODES, ROOT AND ENVIRONMENT (documentation-validated)
--------------------------------------------------------------------------
- Exit codes (Vercel): "If the command returns 0, the build will be skipped"; 1 or greater builds.
  The wrapper:
  - builds (exit 1) only on checker exit 0 AND the exact line VERCEL_BUILD_DECISION=BUILD;
  - every other outcome is 0: BLOCKED, UNVERIFIABLE, checker crash or signal, a near-miss line, missing node, a script
    error, TERM / INT / HUP.
  All tested (§7). SIGKILL cannot be trapped; a hard kill exits 137, which is ≥ 1, so it would BUILD. This is a
  residual risk; the checker's own timeouts (20s per API request) keep it well within normal build limits.
- Root: the command runs in the project's Root Directory. The wrapper resolves the repository from its own location,
  so it works from any start directory (tested from "/").
- Environment:
  - VERCEL_ENV is available only when "Automatically Expose System Environment Variables" is enabled. If it is
    missing, the wrapper SKIPS every build, previews included. Safe, but noticeable: enable the setting (A5).
  - Whether PROJECT environment variables (SUPABASE_ACCESS_TOKEN) are available to the Ignored Build Step is not
    stated in the documentation. Verify at A5; if absent, production builds SKIP (fail closed).
- Vercel clones with --depth=10. The deploy check reads migrations from the checked-out files, not git history, so it
  is unaffected.
- Manual production deploy paths (D6): the documentation does not say whether CLI deploys (`vercel --prod`), deploy
  hooks or dashboard Redeploy run the Ignored Build Step. Treat them as UNGATED:
  - owner-only;
  - no deploy hooks for production;
  - restrict Vercel team roles and tokens;
  - never Instant-Rollback across a migration boundary;
  - before any manual production deploy, run `node scripts/release/check-db-compat.mjs --mode deploy --source
    supabase-cli` locally and require PASS.
