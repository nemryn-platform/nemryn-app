EXCEPTION TABLE
===============
New migration: supabase/migrations/20260917100000_recurring_occurrence_exceptions.sql
(a new migration, not an edit to the S1B migration — S1B/S1B1 are a
separate, already-locked foundation this phase does not touch).

recurring_occurrence_exceptions:
  id                        uuid primary key default gen_random_uuid()
  organization_id           uuid not null references organizations(id)
  recurring_arrangement_id  uuid not null
  service_date              date not null
  reason                    text not null
  created_by                uuid references auth.users(id)  -- no ON DELETE, matches every actor/provenance column in this schema
  created_at                timestamptz not null default now()

Deliberately narrower than the arrangement itself: no Trip id, no
Passenger id, no medical reason, no facility, no return-leg concept, no
appointment data, no Driver/Vehicle, no billing. Records exactly one
fact: "do not expect an occurrence from this arrangement on this service
date." No ExpectedOccurrence table exists or was created — "expected"
remains a pure on-read derivation (recurring-care-core.ts).

No skip/unskip RPC exists yet (explicitly out of scope, S1C §10) — the
table carries no INSERT/UPDATE/DELETE grant to `authenticated` at all
(see EXCEPTION RLS below). A future controlled RPC deletes the row on
"unskip" — no soft-delete machinery (no `deleted_at`, no status enum)
was added, matching the phase's explicit instruction.


EXCEPTION TENANCY
=================
Composite-FK-anchored exactly like every other new relationship in this
schema: `foreign key (recurring_arrangement_id, organization_id)
references recurring_arrangements (id, organization_id)`, reusing
recurring_arrangements' own `unique(id, organization_id)` anchor
established in S1B. An Org A exception row referencing an Org B
arrangement is a schema-level impossibility — proven at REX-05 (rejected
with `foreign_key_violation`, not merely blocked by RLS).

No new `unique(id, organization_id)` anchor was added on THIS table —
nothing else in the schema needs to composite-FK against
recurring_occurrence_exceptions, so per the phase's own "only if
required by existing conventions" instruction, none was added.


EXCEPTION RLS
=============
- `grant select on recurring_occurrence_exceptions to authenticated;` —
  NO insert/update/delete grant at all (mirrors trip_events/audit_events
  exactly: a table meant to be read-only-to-the-application until a
  future controlled RPC exists).
- One SELECT policy: `has_org_role(organization_id, array['organization_admin','dispatcher'])`.
- No Driver policy (a Driver has no legitimate need to know which dates

- No `updated_at` column, no `set_updated_at`/`prevent_organization_id_change`
  triggers — matches the zero-client-UPDATE-grant precedent
  (trip_events/audit_events) exactly: a trigger guarding an UPDATE path
  that cannot exist at all would be dead code.

14-DAY HORIZON
==============
`generateHorizonDates(todayLocalDateKey)` in recurring-care-core.ts:
exactly `HORIZON_LENGTH_DAYS` (14) local calendar dates, todayLocalDateKey
through the following 13 dates inclusive, via pure calendar-digit
arithmetic (`addCalendarDays`, the exact `Date.UTC`-as-scratch-calculator
technique day-bounds.ts's own `addDaysToDateKey` already established —
never `now + 14*24h`, never touching real elapsed time, never
DST-sensitive because no real instant is ever involved at this layer).


EXPECTED-DATE GENERATION
=========================
Locked pipeline, implemented exactly as specified and never reordered:
  1. patternDateCount — horizon dates matching the weekday pattern, within
     [startDate, endDate], AND passing the active/paused/ended lifecycle
     cutoff — BEFORE skips (`isPatternDate`).
  2. skippedCount — pattern dates (per #1) that also carry a skip
     exception for that exact date. A skip recorded for a date that is
     NOT currently a pattern date (e.g. after a pattern edit) is silently
     ignored — proven at unit-test level ("a skip recorded for a date
     that is NOT a current pattern date is silently ignored, P1-E2-S1C
     §27").
  3. expectedCount = patternDateCount - skippedCount (never independently
     computed).
  4. scheduledCount + missingCount = expectedCount (invariant, proven by
     construction in the implementation and asserted directly in two
     dedicated unit tests plus every live fixture arrangement).


PAUSE SEMANTICS
================
`isPatternDate`'s `case "paused"`: a date is still a pattern date iff
`pausedEffectiveDate === null OR dateKey < pausedEffectiveDate` — no new
expected occurrences on or after the LOCAL calendar date `paused_at`
falls on, in the arrangement's own timezone. Earlier pattern dates within
the horizon remain real pattern dates (not deleted by pausing).

Live-proven: Arrangement C (America/New_York, daily, paused effective
2026-09-22) — patternDateCount = 5 (Sept 17-21), zero occurrences on or
after Sept 22.


ENDED SEMANTICS
================
Symmetric to pause, using `endedEffectiveDate`. Ended arrangements do not
retroactively erase pattern-date history before the effective end date —
"ended never deletes history" is enforced by construction (the same
`isPatternDate` date-comparison logic, not a special case).

Live-proven: Arrangement D (America/New_York, daily, ended effective
2026-09-24) — patternDateCount = 7 (Sept 17-23), zero occurrences on or
after Sept 24, with all 7 earlier dates still genuinely present.


OCCURRENCE SATISFACTION
=========================
`qualifyingTripsFor`: a linked Trip qualifies for date D iff
`state !== 'cancelled' AND serviceDate === D`, restated verbatim from
S1A1 §13 / S1C §13. No other interpretation exists anywhere in the pure
core. Proven at unit level (cancelled Trip -> still MISSING; a second,
non-cancelled Trip on the same date -> SCHEDULED) and live (Arrangement
A, Sept 25: a cancelled Trip plus a real scheduled replacement resolves
to SCHEDULED with only the replacement Trip listed).


CANCELLED TRIP BEHAVIOR
=========================
A cancelled Trip never satisfies any date, by itself. If no other
qualifying Trip exists for that date, the occurrence is MISSING despite
a cancelled Trip technically existing and being linked — proven at unit
level and, live, at Arrangement A Sept 25 (cancelled + replacement ->
SCHEDULED, cancelled Trip itself excluded from the `trips` list).


MULTIPLE TRIPS PER DATE
=========================
When more than one qualifying (non-cancelled, dated) Trip exists for the
same date, exactly ONE SCHEDULED occurrence is produced, with ALL
qualifying Trips listed in `occurrence.trips` — no aggregation, no
scoring, no arbitrary "pick one" logic invented. Proven live at
Arrangement A Sept 28: two independently-scheduled Trips both resolve to
Sept 28 under the arrangement's timezone; the live script asserted
`trips.length === 2`.


NULL-SCHEDULE BEHAVIOR
========================
A linked Trip with `scheduled_pickup_at IS NULL` (serviceDate = null) can
never satisfy any occurrence — `qualifyingTripsFor`'s `serviceDate ===
dateKey` comparison can never match `null` against any real date string.
Proven at unit level and live: Arrangement A's Sept 30 Trip (state
'scheduled', scheduled_pickup_at NULL) is present in the fetched Trip set
but Sept 30 still resolves to MISSING.


TRIP READINESS COMPOSITION
=============================
For a qualifying Trip still in `state === 'scheduled'`, the wrapper
(recurring-care.ts) calls the real, unmodified `deriveTripReadiness`
(trip-readiness-core.ts) and attaches the result as an opaque pass-
through `readiness` field on that Trip fact — never re-derived, never
re-labeled, never duplicated. For a Trip in any other state, `readiness`
is `null` (mirrors `deriveTripReadiness`'s own NOT_APPLICABLE-for-
every-other-state contract). recurring-care-core.ts never imports
trip-readiness-core.ts at all — it accepts an already-computed,
structurally-typed `TripReadinessResultLike` value, keeping the "zero
runtime imports" pure-core charter intact while still getting real type
safety.

No aggregate/collapsed readiness score is invented for a SCHEDULED
occurrence carrying multiple Trips — each Trip's own readiness stands on
its own in the `trips` list.


ASSURANCE VOCABULARY
======================
Exactly three occurrence states, no others, anywhere in this module:
SCHEDULED / MISSING / SKIPPED. No READY state at this layer (Trip
Readiness's own vocabulary, composed via pass-through, never
re-derived). No compliance/risk/adherence/severity score. Verified by a
dedicated unit test ("every possible reason/state combination still
yields a stable, fully-populated result") and by direct code
inspection — `RecurringOccurrenceState` is a closed 3-member union type,
enforced by TypeScript.


COUNT SEMANTICS
=================
patternDateCount, skippedCount, expectedCount, scheduledCount,
missingCount, nextExpectedDate, nextMissingDate, consecutiveMissingCount
— all exactly as locked in S1C §19/§20, computed once, never
independently re-derived. consecutiveMissingCount walks the EXPECTED
sequence only (SKIPPED dates are not part of it at all) from its
earliest date, stopping at the first SCHEDULED date — no threshold, no
severity label. Proven live: every one of the 5 live arrangements had
`scheduledCount + missingCount === expectedCount` asserted and passing.


TIMEZONE / DST
================
The pure core (recurring-care-core.ts) performs zero real timezone
resolution — it operates exclusively on already-resolved `YYYY-MM-DD`
date-key strings. All real IANA-timezone work lives in the server
wrapper (recurring-care.ts), reusing day-bounds.ts's already-DST-proven
`localDateKey`/`addDaysToDateKey`/`localMidnightUtc` (P1-E1-S4C1
hardened) rather than any new timezone math. The unit-test suite
includes horizon-generation tests spanning genuine DST transition dates,
proving the pure date-key arithmetic is immune (it never touches a real
instant in the first place).


MULTI-TIMEZONE QUERY STRATEGY
================================
Each candidate arrangement's own 14-date horizon is resolved
independently in ITS OWN stored timezone snapshot. The Trips query is
bounded to the UNION UTC envelope (min of all horizon starts, max of all
horizon ends) fetched in ONE round trip; each fetched Trip is mapped back
to its own `recurring_arrangement_id` and re-resolved to a local service
date using THAT arrangement's own timezone — never a shared/org-wide
assumption.

Live-proven at Arrangement B (America/Chicago, Wednesday-only): a Trip
timed at `2026-09-24T04:30:00Z` (= Sept 23 23:30 CDT = Sept 24 00:30 EDT)
correctly resolved to Sept 23 under the arrangement's own Chicago
timezone — NOT Sept 24 (which is what NY-local or a naive UTC-date-slice
approach would have produced). This is the single strongest proof this
phase has that the multi-timezone strategy is genuinely per-arrangement,
not organization-wide.


SERVER READ MODEL
====================
src/lib/operations/recurring-care.ts — `server-only`, exports
`getRecurringCareAssurance(organizationId: string, now: Date = new
Date()): Promise<RecurringArrangementAssurance[]>`. Caller-resolves-
context convention (organizationId is never re-derived/trusted from
inside this module — matches every other Operations data-access module).
Composes the real, unmodified `deriveRecurringCareAssurance` once per
candidate arrangement, purely in-memory from the bounded fetches — no
additional queries inside the per-arrangement loop.


QUERY ROUND-TRIP COUNT / NO N+1
==================================
Exactly 4 round trips, regardless of how many arrangements or Trips
exist:
  1. Candidate arrangements (coarsely filtered — see below).
  2. Occurrence exceptions for the candidate arrangement ids, bounded to
     the union date range.
  3. Linked Trips for the candidate arrangement ids, with driver/
     vehicle/passenger status embedded in the SAME round trip (mirrors
     trip-readiness.ts's composite-FK-hint convention), bounded to the
     UNION UTC envelope.
  4. Open trip_exceptions counts, scoped to exactly the resulting
     candidate Trip ids, grouped into a per-trip count in memory.
No query is issued inside a per-arrangement or per-Trip loop anywhere in
this module — confirmed by direct code inspection (the only two `.map()`
calls over `arrangements`/`trips` after round trip 4 do pure in-memory
work, no `await` inside either).

COARSE ARRANGEMENT FILTER (round trip 1): deliberately approximate — a
±2-day UTC margin around "now" — because no single UTC-based filter can
be timezone-exact across heterogeneous per-arrangement timezones without
reading every row first. This filter can only ever OVER-include a
borderline row, never incorrectly exclude a genuinely relevant one; the
pure evaluator's own exact per-arrangement `isPatternDate` logic is what
actually and precisely decides relevance. Documented in the wrapper's own
header comment as a deliberate, bounded simplification.

OPEN ISSUES
=============
None found that block S1D. Two items worth carrying forward as context,
not defects:
  1. The coarse arrangement pre-filter (±2-day UTC margin) is an
     intentional, documented approximation — it will over-fetch a small
     number of genuinely-irrelevant borderline rows in exchange for never
     risking an incorrect exclusion, and relies on the pure evaluator's
     own per-arrangement logic for exactness. This is the same class of
     tradeoff already accepted for Tomorrow Readiness; no different
     decision is proposed here.
  2. No pagination/limit exists yet on the candidate-arrangement query
     (round trip 1) — for an organization with a very large number of
