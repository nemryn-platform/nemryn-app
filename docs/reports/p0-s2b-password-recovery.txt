4. RECOVERY REQUEST ARCHITECTURE
====================================================================

`src/app/forgot-password/actions.ts`'s `forgotPasswordAction`:

  1. Reads and trims/lowercases the submitted email.
  2. Rejects anything that fails `isPlausibleEmail()` (a pure shape
     check — not an existence check) with a distinct validation
     message.
  3. Resolves the app's own trusted origin via `getAppOrigin()`
     (reused, unmodified, from P0-S2A).
  4. Calls `supabase.auth.resetPasswordForEmail(email, { redirectTo:
     \`${origin}/auth/confirm\` })` — Supabase's own supported
     mechanism; no custom token generated or stored anywhere in this
     application's schema.
  5. Returns exactly one of two outward states: `"sent"` (the neutral
     message) or `"error"` (a generic failure message) — see §6 for
     why this split does not reopen enumeration.

5. RECOVERY CALLBACK/SESSION ARCHITECTURE
====================================================================

`src/app/auth/confirm/route.ts` — the SAME Route Handler signup
confirmation already used, now branching on `type`:

  - `type=recovery`, `verifyOtp()` succeeds → sets the
    `zw-recovery-pending` marker cookie (httpOnly, `secure` in
    production, `sameSite=lax`, 10-minute `maxAge`) on the SAME
    redirect response, and redirects to `/auth/reset-password`.
  - Any failure (missing/invalid/expired/already-used token) → the
    pre-existing fallback: redirect to `/auth/auth-code-error`.
    Unchanged code path.

`src/app/auth/reset-password/page.tsx` renders the password-change
form only when BOTH a real session (`getUser()`) AND the marker cookie
are present — full reasoning, and the full table of unsafe cases
handled, in `docs/product/password-recovery-model.md` §6. Every unsafe
case listed there was independently exercised live (§16 below), not
just reasoned about.

6. PASSWORD UPDATE MECHANISM
====================================================================

`src/app/auth/reset-password/actions.ts`'s `resetPasswordAction`:

  1. Re-checks the marker cookie AND `getUser()` itself — defense in
     depth against a raw POST bypassing the page (never trusts that a
     request reached this action only through the page that normally
     leads to it).
  2. Validates the new password via `validateNewPassword()` (length
     ≥ 8, matches confirmation) — the SAME pure function the client
     form's own immediate feedback would use, but this is the
     authoritative check; the client-side one is a convenience only.
  3. Calls `supabase.auth.updateUser({ password })` — Supabase's own
     supported mechanism, scoped entirely to the caller's own current
     session. No custom/privileged RPC. The browser never receives a
     service-role key, an admin API, or any privileged credential —
     confirmed by `grep -rln "service_role\|SERVICE_ROLE\|
     SUPABASE_SERVICE" src/app/forgot-password/ src/app/auth/
     reset-password/ src/lib/auth/recovery*.ts src/components/auth/
     ForgotPasswordForm.tsx src/components/auth/ResetPasswordForm.tsx`
     → zero matches.
  4. On success: does NOT clear the marker cookie (a deliberate fix —
     see §16's live-validation finding below and the action's own doc
     comment for the full reasoning). On failure: never surfaces
     Supabase's raw error text.

**A real bug was found and fixed during this live validation, not
merely a test-timing issue:** the first full run of this script showed
20/21, with only step 17 ("password update succeeds — success state
shown") failing — yet step 19/20 (old password rejected, new password
accepted) both PASSED in that same run, proving the password update
itself genuinely succeeded on the backend. A focused debug script
isolated the cause: `resetPasswordAction` was clearing the recovery
marker cookie as part of its success path. Next.js automatically
refreshes the invoking route's Server Component tree after any Server
Action completes; that refresh re-evaluated `/auth/reset-password`'s
own `canReset` gate, found the marker now cleared, and re-rendered the
page's "link expired" branch in place of the just-rendered success UI
— unmounting the client component (and its local "success" hook state)
before a person would ever see the confirmation message, in a way that
raced with (and sometimes lost to) the client's own local re-render.
**Fixed** by removing the cookie-clearing call entirely (see
`src/app/auth/reset-password/actions.ts`'s own doc comment, and
`docs/product/password-recovery-model.md` §8, for the full reasoning —
in short: the underlying Supabase recovery TOKEN is already single-use
at the provider level regardless of this application's own cookie, so
clearing the cookie eagerly was both unnecessary for security and
actively harmful to the UI). Re-ran the full script after the fix:
21/21 PASS, including step 17. This is disclosed here in full rather
than only reporting the final clean result, per this phase's own
"do not alter test expectations merely to obtain PASS" discipline —
the fix changed application BEHAVIOR (removed an unnecessary,
UI-breaking side effect), not the test's own expectation.
