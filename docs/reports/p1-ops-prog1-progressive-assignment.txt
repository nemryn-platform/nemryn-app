PROGRESSIVE DEFAULT RULES   (src/lib/operations/assignment-defaults-core.ts, pure, no I/O)
======================================================================
  deriveAssignmentDefaults({ mode, currentDriverId, currentVehicleId, driverOptions, vehicleOptions })
  orderDriversForOperator(options, operatorDriverId)
  deriveDriverDayFacts({ targetTripId, dayStartUtc, dayEndUtc, trips })

Rules:
  - AUTO-PREFILL only. A default is an initial form value. It is derived once when the dialog mounts and is never
    re-applied over the operator's choice, even if a live refresh changes the option lists.
  - Nothing is written until the operator clicks "Assign Driver" / "Confirm Reassignment". Both selects stay visible,
    enabled and changeable.
  - Every prefilled value is explained in help text ("Prefilled: the only active driver. You can change it before
    assigning.").
  - A prefilled vehicle can be removed with "Clear vehicle". The "No vehicle" placeholder option is disabled by the
    shared Select component.
  - assign_trip / reassign_trip remain the only validators. The UI filtering and defaults are conveniences only.

======================================================================
ONE DRIVER BEHAVIOR
======================================================================
Exactly one eligible (active, same-org) Driver + Assign mode: that Driver is preselected. Zero or 2+ drivers: nothing
is preselected.

======================================================================
ONE VEHICLE BEHAVIOR
======================================================================
Exactly one eligible Vehicle + Assign mode: that Vehicle is preselected. This fixes the one-vehicle failure mode where
the operator forgot the only vehicle and Tomorrow later showed NEEDS_VEHICLE. With 2+ vehicles nothing is guessed:
there is no last-used or preferred vehicle, and no recurring preference. vehicle_id stays nullable. Nothing changed at
the database level.

======================================================================
OWNER-AS-DRIVER ORDERING
======================================================================
If the operator has an active linked Driver (current_driver_id) that is an eligible option:
  - that Driver is listed FIRST, labelled "<Display Name> (you)"
  - everyone else keeps alphabetical order
  - it is never preselected when there are multiple drivers
  - "(you)" is presentation only: drivers.display_name is never mutated (verified in the DB)
When the linked Driver is the ONLY active driver, the one-driver prefill applies ("<name> (you)" preselected).
Membership, Driver and AuthUser stay separate.

======================================================================
REASSIGNMENT DEFAULT PRIORITY
======================================================================
  1. Reassign: the EXISTING active assignment's Driver and Vehicle, each only while still an eligible option.
  2. Assign: unique-eligible Driver / Vehicle defaults.
Uniqueness defaults are NEVER applied in reassign mode:
  - An existing "no vehicle" stays empty even when exactly one vehicle is active (verified).
  - A current Driver or Vehicle that became inactive is NOT swapped for a different resource. The field is left
    empty for the operator (verified).
  - The existing vehicle is preserved even when several vehicles are active (verified).
The following are unchanged and verified:
  - p_expected_assignment_id (a hidden field, as before)
  - ZW005 / stale-reassign rejection
  - the optional reason, stored as end_reason on the ended assignment
  - assignment history (old assignment ended, new one active)
  - assigned_by attribution

======================================================================
DRIVER-DAY READ MODEL
======================================================================
The model is src/lib/operations/assignment-context.ts (server-only). It is exposed through driverDayContextAction in
src/app/operations/dispatch/actions.ts, a READ that writes nothing.
  - Authorization is re-derived with requireOperationsAccess on every call.
  - The organization id and timezone come from the server-resolved context, never from the browser.
  - The trip and driver ids are validated as UUIDs.
  - It uses the session Supabase client (RLS applies) plus an explicit organization_id filter. No service role and
    no privileged client query.
Queries (bounded):
  a) The target Trip's scheduled_pickup_at, looked up by id + org.
  b) The Driver's other Trips on the target Trip's ORG-LOCAL CALENDAR DAY:
       - organizationDayBoundsUtc(target scheduled_pickup_at, org tz), so this is not "today" and is correct for
         today, tomorrow or any later date, and DST-safe
       - inner-joined to an ACTIVE trip_assignment (ended_at is null) for that Driver
       - state in scheduled + in-progress states, so completed / cancelled / no_show are excluded
       - the target Trip excluded; limit 50
  c) The Driver's in-progress Trips on any date (state en_route_to_pickup .. arrived_at_destination), target
     excluded, limit 5. This answers "currently on a trip".
  b) and c) run in parallel. deriveDriverDayFacts then re-applies every rule (window, terminal exclusion, target
  exclusion, dedup, sort) so the logic is unit-tested without a database.
Output per trip: pickup time (org tz), pickup → destination. No passenger name and no other PHI. The data stays inside
the tenant through RLS and the org filter.
An unscheduled target Trip has no day list ("This trip has no scheduled pickup, so there is no day to show"). The
current-trip fact is still reported.

PERFORMANCE
======================================================================

    parallel with the existing board load.
  - Driver-day context is NOT pre-fetched per driver. It loads on demand for the one selected Driver, including the

    an assignable state. If loading fails it falls back to the previous Dispatch link.

router.refresh() runs once per action result.

Release-process rule (owner decision, applies to all future production smoke):
  Production QA must NOT temporarily change Membership roles through direct SQL merely to obtain a missing role
  credential.
  For a role check in production smoke:
    - use an existing safe synthetic credential for that role when one is available;
    - otherwise mark that role check MANUAL and rely on local authorization / adversarial coverage;
    - never mutate a production Membership role solely for QA.
The PROG1 release's dispatcher zero-driver check did exactly this once. The synthetic Siloan driver account was set to
`dispatcher` and restored, and it caused no product defect. It is recorded above for transparency and must NOT become
the standard test method. No new Dispatcher credential was created at closeout.
