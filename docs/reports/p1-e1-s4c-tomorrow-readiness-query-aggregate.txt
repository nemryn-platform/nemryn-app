TOMORROW DAY-BOUNDARY STRATEGY
------------------------------------------------------------------------
Verified `organizationDayBoundsUtc`'s actual implementation before use
(not assumed): it takes any instant `now` and returns THAT instant's
own organization-local day as `[startUtc, endUtc)`, where `endUtc =
startUtc + 24h` exactly, by construction.

"Tomorrow" is computed by composing the SAME real, unmodified helper
twice (`tomorrow-readiness.ts`'s own `computeTomorrowBoundsUtc`):

  const today = organizationDayBoundsUtc(now, timezone);
  return organizationDayBoundsUtc(today.endUtc, timezone);

`today.endUtc` is, by the helper's own contract, the exact instant that
belongs to the next organization-local calendar day — feeding it back
into the same function re-derives THAT day's own correct offset and
boundaries from scratch (via the function's own `Intl.DateTimeFormat`
re-read of the wall-clock date at that instant), rather than assuming
yesterday's offset still applies. No server-UTC or runtime-local date
arithmetic was invented; the exact same real function already used
everywhere else in this codebase is the only thing computing dates
here.

DST VALIDATION
------------------------------------------------------------------------
`day-bounds.ts` carries `import "server-only"`, which plain Node cannot
resolve directly (the real `server-only` npm package is not installed
at all — Next's bundler special-cases the literal specifier). Rather
than write a fake timezone implementation (explicitly forbidden), a
small, permanent, tracked Node ESM loader hook
(`src/lib/operations/server-only-stub-loader.mjs`) was written that
neutralizes ONLY the irrelevant "server-only" build-time marker,
leaving `organizationDayBoundsUtc` itself completely real and
unmodified. `src/lib/operations/day-bounds-tomorrow.test.mjs` (8 tests,
all passing) exercises it directly:

- Normal day (America/New_York, June): tomorrow's window is exactly
  24h, correct next calendar date.
- UTC (no DST at all): exactly 24h.
- America/Phoenix (never observes DST, fixed -7:00 year-round):
  exactly 24h even during a date that is DST-active elsewhere.
- Spring-forward (America/New_York, 2026-03-08, a genuine 23-hour local
  day): tomorrow's own START boundary is proven EXACTLY correct
  (2026-03-08T05:00:00Z, true midnight EST) — this is the boundary that
  actually determines WHICH calendar day is "tomorrow," and it is
  exactly right.
- Fall-back (America/New_York, 2026-11-01, a genuine 25-hour local
  day): tomorrow's own START boundary is likewise proven exactly
  correct (2026-11-01T04:00:00Z, true midnight EDT).
- A dedicated test proves the composed result DIVERGES from a naive
  `now.getTime() + 24*60*60*1000` on the spring-forward transition day
  — directly demonstrating "tomorrow means the next local calendar
  date," not "24 elapsed hours later," as required.

HONEST FINDING (documented, not hidden, not "fixed" with invented
arithmetic): `organizationDayBoundsUtc`'s own `endUtc = startUtc + 24h`
construction is a PRE-EXISTING, already-documented characteristic of
the shared helper (its own doc comment already says: "a query issued
in the exact minutes of a DST transition could see the offset shift
within the same org-day, an accepted edge case at this precision").
Composing it twice for "tomorrow" INHERITS this exact tolerance at the
FAR edge of a transition day, never introduces a new one: on the
23-hour spring-forward day, the computed window ends up 1 hour too
WIDE (spilling 1 hour into the day after); on the 25-hour fall-back
day, it ends up 1 hour too NARROW (excluding the last hour of that
day). Both are proven and asserted directly in the test file, with the
exact expected offset. This is the same class of tolerance already
accepted for TODAY's own boundary throughout `todays-operations.ts`/
`dispatch-board.ts` — S4C inherits it, does not create it, and does
not attempt to solve it with new date arithmetic (explicitly forbidden
by this phase's own instruction).

CANDIDATE QUERY
------------------------------------------------------------------------
`tomorrow-readiness.ts`'s `getTomorrowReadiness` — ONE bounded query
against `trips`:

  .eq("organization_id", organizationId)
  .eq("state", "scheduled")
  .gte("scheduled_pickup_at", tomorrowStartIso)
  .lt("scheduled_pickup_at", tomorrowEndIso)
  .order("scheduled_pickup_at", { ascending: true })
  .order("id", { ascending: true })

Selecting only: `id, state, scheduled_pickup_at`, plus the embedded
`passengers(display_name, status)` and `trip_assignments(id, ended_at,
vehicle_id, drivers(status), vehicles(status))` — the exact same
composite-FK-hint convention already proven in S4B's own `trip-
readiness.ts` (`trips_passenger_id_organization_id_fkey`,
`trip_assignments_trip_id_organization_id_fkey`,
`trip_assignments_driver_id_organization_id_fkey`,
`trip_assignments_vehicle_id_organization_id_fkey`). Never
`select("*")`. Ordering is deterministic: `scheduled_pickup_at`
ascending with `id` ascending as an explicit, stable tiebreaker.

A Trip with `scheduled_pickup_at IS NULL` can never satisfy either the
`.gte()` or `.lt()` comparison (SQL NULL comparisons are never true) —
it is excluded by the range filter itself, with no special-case code
required, exactly matching S4C §3's locked rule.

------------------------------------------------------------------------
ACTIVE ASSIGNMENT STRATEGY
------------------------------------------------------------------------
Identical authoritative meaning to Trip Assurance and S4B Trip
Readiness: `ended_at IS NULL`, found via `.find((a) => a.ended_at ===
null)` on the embedded `trip_assignments` array. No second
interpretation was invented. The schema's own partial unique index
(`trip_assignments_one_active_per_trip`) guarantees at most one active
row per Trip, so this is fetched embedded in the SAME query as the
Trip itself (query 1) — no separate second-phase assignment query was
needed (unlike the exception count, which genuinely does need its own
scoped query — see below).

------------------------------------------------------------------------
OPEN EXCEPTION STRATEGY
------------------------------------------------------------------------
ONE scoped query against `trip_exceptions`, filtered by
`organization_id`, `status='open'`, and `trip_id IN (<candidate ids>)`
— never one query per Trip. Only `trip_id` is selected (count/list
detail was not required by the aggregate contract); counted per Trip
in memory via a `Map<string, number>`, mirroring `todays-
operations.ts`'s own established pattern exactly. Skipped entirely
when the candidate list is empty (no trivial `.in("trip_id", [])`
round trip).

------------------------------------------------------------------------
AGGREGATE CONTRACT
------------------------------------------------------------------------
`TomorrowReadinessAggregate` (`tomorrow-readiness-core.ts`):

  totalScheduledTrips: number
  readyCount: number
  needsPreparationCount: number
  items: TomorrowReadinessItem[]  // { tripId, scheduledPickupAt, passengerDisplayName, readiness }

`readiness` is the full, unmodified S4B `TripReadinessResult` — `state`
(`READY`/`NEEDS_PREPARATION`, never `NOT_APPLICABLE` in a valid
aggregate — see below) and the complete `reasons` array. No date/
local-day-identity field was added to the aggregate itself — the raw
`tomorrowStartUtc`/`tomorrowEndUtc` boundaries are computed inside the
wrapper and available to a future caller if needed, but formatting a
human-facing date label is a presentation concern explicitly deferred
to S4D, matching this codebase's own established "keep state separate
from presentation" discipline (`request-readiness-core.ts`/`trip-
readiness-core.ts` both already draw this same line).

------------------------------------------------------------------------
AGGREGATE INVARIANTS
------------------------------------------------------------------------
All enforced, not merely tested-and-hoped:

- `totalScheduledTrips === readyCount + needsPreparationCount` —
  arithmetically guaranteed by construction (every item increments
  exactly one of the two counters) and additionally asserted by a
  dedicated unit test.
- `items.length === totalScheduledTrips` — `totalScheduledTrips` is
  literally defined as `items.length`.
- Every item belongs to the same organization — guaranteed by the
  wrapper's own `organization_id`-scoped query; the pure aggregator
  itself does not carry an organization field at all (it operates
  purely on an already-organization-scoped candidate list assembled by
  the caller), so there is no organization field to accidentally get
  wrong at the aggregation layer.
- Every item is `state='scheduled'` and has a non-null
  `scheduledPickupAt` — guaranteed by the SQL filter (§ CANDIDATE
  QUERY above) before a row ever becomes a candidate at all.
- Every item lies in tomorrow's exact organization-local window —
  guaranteed by the same SQL range filter, computed via the DST-safe
  composition above.
- Every item's `readiness.state` is `READY` or `NEEDS_PREPARATION`,
  never `NOT_APPLICABLE` — ENFORCED at the pure-aggregator level:
  `aggregateTomorrowReadiness` throws immediately if any candidate's
  own `readiness.state` is `NOT_APPLICABLE`, rather than silently
  counting it as `READY` or quietly dropping it (S4C §10's own explicit
  instruction). Verified by two dedicated unit tests that deliberately
  supply a `NOT_APPLICABLE` candidate and assert the function throws.

TRIP READINESS REUSE
------------------------------------------------------------------------
`deriveTripReadiness` (S4B) is called exactly once per candidate Trip,
inside `tomorrow-readiness.ts` (the server wrapper), never
re-implemented and never duplicated. `trip-readiness-core.ts` itself
was NOT modified in this phase — confirmed via inspection; only
`import type { TripReadinessFacts }` is referenced from
`tomorrow-readiness.ts`, and the pure aggregator (`tomorrow-readiness-
core.ts`) references only `import type { TripReadinessResult }` — no
runtime code was changed in S4B's own files.

DESIGN NOTE (a genuine implementation-time finding, not merely a plan
followed blindly): the FIRST attempt had `tomorrow-readiness-core.ts`
itself import and CALL `deriveTripReadiness` directly (matching a
literal reading of "every candidate must be evaluated by
deriveTripReadiness"). This exposed a real TypeScript/Node module-
resolution conflict — the first case in this codebase where one pure
`*-core.ts` module needed a genuine RUNTIME (non-type-only) import from
a sibling pure module. `tsc`'s own "bundler" resolution requires a
`.js`-suffixed relative specifier to reference a sibling `.ts` file's
compiled output; Node's native direct TypeScript execution (used by
`node --test`, exactly like every other `*-core.test.mjs` file here,
with no bundler in front of it) does NOT implement that convention and
looks for a literal `trip-readiness-core.js` file, which does not
exist — `tsc --noEmit` and `node --test` could not both be satisfied by
the same import statement. Rather than accept either a broken build or
a broken direct-Node test run, `tomorrow-readiness-core.ts`'s own
contract was narrowed: it now accepts ALREADY-EVALUATED
`TripReadinessResult`s (the wrapper calls `deriveTripReadiness` itself,
once per candidate, before handing the array to the aggregator). This
still satisfies "use the S4B evaluator, never a second definition" —
the evaluation happens exactly once, via the real function, one call
site earlier — and is arguably a cleaner separation besides: assembling
facts is already I/O-adjacent work living in the wrapper, so evaluating
them there too is a natural fit, and the pure aggregator's own job
stays exactly "sort + count + enforce the NOT_APPLICABLE invariant,"
never touching a raw fact or an evaluation rule at all. Both `tsc
--noEmit` and every `node --test` file now pass cleanly.
