2. ROOT CAUSE
======================================================================
Before R1, getOverlapCandidates made one request per query family and trusted the result as the whole set:
  - A (window family): `.limit(2000)`
  - B (older still-open family): `.limit(500)`
PostgREST caps every response at the project's max_rows. supabase/config.toml sets `max_rows = 1000`, and hosted
Supabase also defaults to 1000. The cap is SILENT:
  - there is no error;
  - there is no header the loader checked;
  - a capped response is indistinguishable from a naturally short one.
Consequences:
  1. Family A could never return more than 1000 rows, even though it asked for 2000. The "2000" bound was never
     real.
  2. Nothing distinguished "complete" from "truncated", in either family.
  3. The pure core then derived "clear" for any resource whose relevant trips fell beyond the cut. That is exactly the
     forbidden inference: unknown became clear.

Reproduced against the LOCAL database, with the pre-R1 query shape and the Org A admin session (RLS):
  - Setup: 1,102 window trips, where a same-driver trip and a same-vehicle trip sort after 1,100 earlier trips.
  - The `.limit(2000)` request returned exactly 1000 rows: no error, no signal.
  - Both relevant trips were absent.
  - The pre-R1 derivation reported driver "clear" AND vehicle "clear", despite two real overlaps.

4. CHOSEN PAGINATION / COMPLETENESS MODEL
======================================================================
Complete keyset pagination, with an explicit coverage result. There are still two query FAMILIES (never one query per
trip), both organization-scoped on the caller's RLS session client. There is no service role.
  - Page size: OVERLAP_CANDIDATE_PAGE_SIZE = 500. This must be ≤ max_rows, so a full page is never confused with a
    capped one. The unit tests assert 500 ≤ 1000.
  - Stable ordering: ORDER BY scheduled_pickup_at ASC, id ASC. This is a total order, since id is unique and both
    families exclude NULL starts through their range filters.
  - Cursor: strictly after the last row, using the PostgREST keyset predicate
      or=(scheduled_pickup_at.gt."<ts>",and(scheduled_pickup_at.eq."<ts>",id.gt."<id>"))
    The values are double-quoted, because timestamps contain reserved characters. It was verified against real
    PostgREST locally. There is no OFFSET, so there is no duplicate or skipped row between pages from unstable
    ordering.
  - Stopping condition: a page with fewer rows than the page size proves exhaustion (coverage "complete").
      - A page of exactly 500 always triggers the next read, so exact multiples are proven, not assumed.
  - Safety ceiling: OVERLAP_CANDIDATE_MAX_PAGES = 20 per family (10,000 non-terminal trips per family).
      - If the 20th page is still full, the family stops and reports "incomplete". Exactly 10,000 is also reported
        as incomplete, because more cannot be ruled out.
      - Nothing is silently sliced.
  - The set's coverage is "complete" only when BOTH families are complete; otherwise it is "incomplete".
  - Diagnostics (rows, pages and completeness per family) are returned for logs. When incomplete, the server logs one
    console.warn with those numbers. Row counts never reach operator copy.

5. INCOMPLETE-COVERAGE BEHAVIOUR
======================================================================
  - An incomplete set NEVER yields "clear", for any driver or vehicle.
      - Nemryn does not guess which resource the unread trips belong to.
      - A resource that would otherwise be clear becomes "not_fully_checkable", with the distinct flag
        candidateSetIncomplete = true.
  - Known overlaps found in the pages that were read still stand: the status stays "overlap", and the incomplete
    flag is carried alongside it.
  - Existing reasons are preserved, not collapsed. The status precedence is unchanged, with incompleteness added
    last:
      1. overlap
      2. not_checkable (missing extent)
      3. not_fully_checkable (still open past planned end, Q7)
      4. not_fully_checkable (candidate set incomplete)
      5. clear
    missingExtent[] and stillOpenPastPlannedEnd[] are still reported alongside the new flag.
  - Q7 is not weakened. A still-open trip past its planned end remains not_fully_checkable: never late, never an
    automatic overlap, never clear. Incompleteness is an ADDITIONAL uncertainty.
  - A target with no pickup time is unchanged. No candidates can be placed against it, so nothing is loaded and its
    coverage is trivially complete. The target itself is still reported as unknown ("can't check").
  - Failed reads are uncertainty too (see §8, UI):
      - Dialog / Assign now: a failed overlap read now shows the "can't fully check" line instead of nothing.
      - Trip Detail: the same.
      - Tomorrow: a failed read shows the incomplete note instead of silently showing no badges.
      - Dispatch: a failed candidate read still surfaces as a page error (unchanged), never silently.

======================================================================
  - New type CandidateCoverage = "complete" | "incomplete".
  - deriveResourceOverlap(target, candidates, nowMs, coverage). The coverage argument is REQUIRED, so TypeScript

      - In the target-unknown branch it is not added, because that line already says the time can't be checked.
  - There is still one semantics model, and no query-limit behaviour lives in React. The UI consumes the derived
    result.

9. QUERY-COUNT / PERFORMANCE BEHAVIOUR
======================================================================
  - Per candidate set: two families in parallel. Each family takes ceil((N + 1) / 500) sequential keyset requests for
    N rows, capped at 20.
  - The typical small or mid organization (1 → 3 → 10 → 30 vehicles) has far fewer than 500 non-terminal trips in a
    ~3-day window. That is 1 request per family, i.e. 2 parallel requests: identical to PROG4B.
  - At 100+ vehicles with, say, 1,200 window trips: 3 requests for A (sequential), usually 1 for B.
  - It is still never N+1 (no per-trip query). Terminal history is never fetched.
  - The window family is org-, time- and state-bounded. The still-open family is org- and state-bounded, with an
    active assignment only.
  - Keyset predicates use the existing (organization_id, scheduled_pickup_at) index path. No new index was added.
  - One candidate set per surface is unchanged: Dispatch day, Tomorrow, the dialog target, Trip Detail.

17. REMAINING OPEN ISSUES
======================================================================
  1. Production max_rows was NOT verified in this phase, because production access was not permitted. The
     completeness proof requires production PostgREST max_rows ≥ 500.
       - The hosted default is 1000, and the repository's config says 1000.
       - If production were configured below 500, a capped page would read as the last page.
       - This is a read-only release preflight (§18).
  2. A non-terminal ASSIGNED trip with NO pickup time is never a candidate. This is unchanged PROG4B behaviour: both
     families filter by start time. It is a separate completeness question, and needs an owner decision:
       - include such trips as "can't check" for that resource, with copy other than "duration not set"; or
       - leave them excluded.
     Not changed here, to avoid redesign.
  3. Keyset pages are successive reads, not one snapshot. A trip created or rescheduled between page reads can be
     seen or missed, like any read a moment later. No row is duplicated or skipped because of ordering.
  4. The local browser E2E harness is fragile under memory pressure (CDP websocket 1006), and an aborted run skips its
     own cleanup. This is local tooling only; the restore script and diagnostics are in .tmp-qa.
