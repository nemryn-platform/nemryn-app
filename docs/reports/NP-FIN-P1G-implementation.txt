1.1 Enablement state (deny by default)
  public.billing_write_enablements -- one row per organization
    status        enabled | disabled
    data_class    synthetic | live
    approval_ref  required for live + enabled: must name NP-LAUNCH-02 (12-200 chars) -- CHECK constraint, so even a
                  direct owner insert cannot create a live enablement without it
    reason        3-500 chars; version >= 1; set_by; set_at
    NO ROW = DISABLED. The migration inserts no rows.
  public.billing_write_enablement_history -- append-only, one row per version, written by trigger (so even a direct
    owner change is recorded); unique (organization_id, version).
  Guard trigger: rows are never deleted (ZW004 enablement_rows_are_kept); every change must be exactly version + 1
    (ZW003); a new row must be version 1; TRUNCATE refused on both tables; history UPDATE / DELETE refused.
  RLS on, and NO client privilege on either table (ZD-286, final refinements): tenants read only billing_write_status;
    reasons, approval references, data class, actor and history are Platform-Admin-only.

1.2 The gate
  _billing_require_write_enabled(org): reads the enablement row FOR SHARE; raises ZW004 billing_not_enabled unless it
    says enabled. FOR SHARE serializes with the platform RPC's FOR UPDATE: a disable committed first is always seen,
    and a disable waits for in-flight financial transactions.
  _billing_write_gate(): BEFORE INSERT / UPDATE / DELETE row trigger, named a_billing_write_gate so it fires before
    every other row trigger, on ALL 12 financial tables:
      billing_invoice_counters, billing_invoices, billing_invoice_trips, billing_invoice_lines, billing_payments,
      billing_receipt_counters, billing_receipts, billing_allocations, billing_refunds, billing_refund_reversals,
      billing_receipt_reversals, billing_assurance_events
    It checks NEW.organization_id (and OLD.organization_id on DELETE, or on an UPDATE that changes it).
  Because the gate sits on the tables rather than in each RPC, it covers every write path at once:
    - the 7 NP-BILL-P1 RPCs and the 7 FIN-P1 RPCs;
    - the compatibility wrappers billing_record_payment / billing_reverse_payment;
    - nested SECURITY DEFINER calls (e.g. _billing_record_receipt_core, _billing_apply_allocations);
    - older application builds (main and PR #44) calling the unchanged RPC signatures;
    - direct table writes, including by the table owner. Only a superuser in session_replication_role = replica
      bypasses triggers (the existing test-cleanup / demo-reset path).
  Reads are not gated: list, detail, ledger, summaries, print pages and billing_trip_status keep working.

1.3 Platform management and status
  platform_set_billing_write_enablement(org, status, data_class, approval_ref, reason, expected_version)
    - _require_platform_admin(): Platform Admins only (ZW001 / ZW002). Organization Admins cannot enable their own
      organization or any other.
    - Validates status / class / reason; live + enabled without an NP-LAUNCH-02 reference ->
      ZW006 live_requires_launch_approval.
    - Optimistic version: expected 0 / null for a new row, the current version otherwise (ZW003 when stale). Repeating
      the same state is a no-op (changed = false, no new version, no audit row).
    - One audit_events row per change: action platform_billing_write_enablement_changed, before / after = status,
      data_class, version, has_approval_ref. The free-text reason is NOT copied into the audit row.
  billing_write_status(org) -> (enabled, version, set_at): authorized with the existing 'view' permission; used by
    the UI. Never returns the reason, approval_ref or data class (ZD-286).
  platform_get_billing_write_enablement(org): Platform Admin only; the full row incl. reason and approval_ref.

1.4 Design change from the approved proposal (owner review requested)
  The gate proposal (NP-FIN-P1-release-gate-resolution.txt §4.7) said "re-define the 14 write RPCs with the check
  (CREATE OR REPLACE, same signatures)" plus a structural test that every write function calls the helper.
  Implemented instead: one table-level trigger on every financial table. Reasons:
    - zero RPC bodies re-defined: PR #44's reviewed function bodies stay byte-identical, so no regression surface;
    - it also covers direct table writes, nested definer calls and any FUTURE billing RPC with no extra code;
    - the structural tests are stronger: every public.billing_* table must carry the gate trigger (B2), and every
      table any billing function writes must be gated, a gate table or audit_events (B3). Both fail if a future
      migration adds an ungated financial table.
  Cost: one FOR SHARE lookup per financial row written (a primary-key read on a tiny table).

2. REFINEMENT A -- EMERGENCY CORRECTION PROCEDURE (DOCUMENTED, NOT IMPLEMENTED)
   SUPERSEDED IN PART by ZD-287 (final refinements): §2.1's temporary-enablement window is NOT adopted (EC-1). §2.2 is
   the approved direction (scoped by organization, operation, record and expiry), to be built before the first live
   enablement (EC-6). See NP-FIN-P1G-decision-lock.txt.
======================================================================================================================
Problem: the gate refuses every financial write, corrections included (unapply, refund correction, receipt reversal,
void). A disabled organization that holds a wrong record can't be corrected through the product.

2.1 Procedure possible with what exists today (no new code)
  1. Request: the Organization Admin reports the record by number only (e.g. INV-000123 / RCPT-000045). No customer
     details over email or chat.
  2. Owner approval: record ticket id, organization, record numbers, the correction (one of: unapply, reverse refund,
     reverse receipt, void), and the time window.
  3. Platform Admin opens the window: platform_set_billing_write_enablement(org, 'enabled', <current class>,
     <current approval_ref>, 'EMERGENCY CORRECTION <ticket>: <records>', <current version>).
  4. The Organization Admin makes ONLY the approved correction through the normal UI. Every correction is already an
     append-only, reasoned, audited entry; no record is edited or deleted.
  5. Platform Admin closes the window immediately: disable with the new expected version.
  6. Verify: history shows exactly enable -> disable; audit_events shows only the approved actions between those
     two versions.
  Limitation: during the window the organization can make ANY financial write, not only the approved correction.
  Steps 5 and 6 detect extra writes; they do not prevent them. The procedure never has platform staff make the
  correction inside the tenant (no impersonation path exists, and none is proposed).

2.2 Narrower option for later (needs code; NOT built)
  A third status, 'correction_only': the four correction RPCs set a transaction-local flag before writing, and the
  gate allows a write under correction_only only when that flag is set. Creating invoices, receipts, payments or
  refunds stays refused. Estimate: one migration, the gate function plus 4 RPC preambles, about 10 SQL tests.

2.3 Owner decisions needed for refinement A
  EC-1 Adopt 2.1 as the interim procedure, or forbid corrections on disabled organizations until 2.2 exists.
  EC-2 Who may approve a window (owner only?) and whether a second person must confirm (two-person rule).
  EC-3 Maximum window length (proposal: 30 minutes, closed by the same Platform Admin, same day).
  EC-4 Whether a LIVE organization suspended under NP-LAUNCH-02 may be corrected at all, and under which reference.
  EC-5 Whether to build 2.2 before the first live enablement.
  EC-6 Records to keep: ticket, approval, the two versions, and the audit ids of the corrections.
