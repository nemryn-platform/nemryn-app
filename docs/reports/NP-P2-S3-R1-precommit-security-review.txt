2. REQUEST / CONTACT / OPPORTUNITY CONSISTENCY FINDINGS
======================================================================
Confirmed gap.
- P2-S1 plus_update_opportunity (20261014120000) lets an OPEN opportunity's primary_contact_id change to any active
  contact. It does not check for linked Requests.
- Once P2-S3 has linked a Request to that opportunity, the attribution's contact_id (the old primary contact) then
  differs from the opportunity's primary contact. That breaks the domain rule "a private-pay opportunity's
  primary_contact_id must equal contact_id".
- This is not a tenant or security issue (same organization, same RLS). It is a reporting and consistency issue.
- Pinned by SQL test D1 (CURRENT behaviour) so it cannot change silently.
- Side effect today: "Correct link" pre-fills the old contact and the opportunity. Saving that pair now gives ZW006 (the
  pair is inconsistent), so staff must pick the contact or the opportunity deliberately. That is safe, but unexplained in
  the UI.

Options analysed:
  A. Preserve the original relationship as history (current behaviour).
     - + no change to P2-S1.
     - - The pair silently diverges. Reports by contact and by opportunity disagree. The canonical rule is broken after
       the fact.
  B. Prevent ordinary contact reassignment while linked Requests exist. RECOMMENDED.
     - + Keeps the invariant at the database layer with one guarded check. No data is rewritten. Explicit, auditable
       correction stays available.
     - - Staff must first correct each linked Request (a deliberate, reasoned step) before moving the opportunity to
       another person.
  C. Automatically re-point existing attributions.
     - - Silently rewrites Request-level history.
     - - Mutates rows the editing user did not touch, with no per-Request reason.
     - - Hides a real-world mistake.
     - - Needs its own reviewed design (which Requests really belonged to whom). Not recommended without an approved
       requirement; none exists.

Smallest safe implementation of B (PREPARED AND VALIDATED; NOT APPLIED; awaiting owner approval):
- A forward-only CREATE OR REPLACE of public.plus_update_opportunity with the IDENTICAL signature. It ships in the
  still-unreleased P2-S3 migration or its own migration. The deployed 20261014120000 file is not modified.
- The only change, inside the existing "contact changed" branch:

    if p_contact_id is distinct from v_old.primary_contact_id then
      perform public._plus_require_active_contact(p_organization_id, p_contact_id);
      -- NP-P2-S3-R1 (option B)
      if exists (select 1 from public.plus_request_attributions a
                 where a.organization_id = p_organization_id and a.opportunity_id = v_old.id) then
        raise exception 'linked_requests' using errcode = 'ZW004';
      end if;
    end if;

- Preserved: _require_plus_write first; the FOR UPDATE row lock and the version check (ZW003); the closed-stage
  ZW004; every field edit and the owner logic; the audit; SECURITY DEFINER; search_path = public, pg_temp; and the
  grants (CREATE OR REPLACE keeps the ACL and comment).
- The new query is organization-scoped: no cross-tenant access.
- Concurrency: plus_link_request locks the opportunity FOR SHARE, and plus_update_opportunity holds FOR UPDATE, so a
  link and a contact change serialize. Whichever commits second sees the first.
- Validated on the dev database INSIDE A ROLLED-BACK TRANSACTION (the dev function is verified unchanged afterwards):
  - B1: a contact change on a linked opportunity -> ZW004 linked_requests.
  - B2: other fields on the linked opportunity still editable.
  - B3: an unlinked opportunity's contact change still allowed.
  - B4: the documented path (correct the Request link first, then change the contact) succeeds.
  - B5: definer, search_path and grants (authenticated yes, anon no) preserved.
- The proposal file is in the session scratchpad (p2s3r1/option-b-plus_update_opportunity.sql), not in the branch.
- Required with B:
  - (1) opportunityErrorMessage maps ZW004 on "save" to "This opportunity is closed", which would be wrong here. The app
    must distinguish the 'linked_requests' message, or the RPC must use a distinct, documented code. A small app change.
  - (2) Replace test D1 with refusal tests (B1-B4 above) and a concurrency case (link vs contact change).
  - (3) Update domain model section 10 and the mutation API.
- Future explicit correction of a mistaken primary contact under B:
  - (a) open each linked Request and use "Correct link" (reason required): move it to the right contact, or remove the
    opportunity; then edit the opportunity's contact; or
  - (b) a later, separately approved RPC (e.g. plus_reassign_opportunity_contact) that, in one transaction with a
    reason, moves the opportunity and re-points its attributions, writing attribution_changed history per Request.
    That is option C made explicit and audited; it is not part of this milestone.

- The "≤ 100" premise is NOT CONFIRMED.
  - The domain model's "≤ 100" (plus-domain-model.md line 399) belongs to plus_inquiries.idempotency_key, the P2-S7 web
    inquiry table: a different column in a different, future table.
  - The canonical text for plus_request_attributions.conversion_idempotency_key (section 10, line 322) and the A02
    blueprint specify NO length, only "unique (organization_id, conversion_idempotency_key) where not null".
  - Nemryn Core's established idempotency-key bound is ≤ 200 (public intake: 20260919090000 / 130000 / 140000).
  - The implemented 8-200 therefore matches the Core convention and does not contradict the canonical model.
  - The constraint was NOT changed. If the owner prefers ≤ 100 for conversion keys, it is a one-line change before
    release (the migration is unapplied).
- Boundary tests added (C1, superuser fixtures in the rolled-back suite): 7 characters refused; 8 accepted; 200
  accepted; 201 refused; a key with linked_existing_request refused; a duplicate key in the same organization refused
  (unique); the same key in another organization accepted.
- P2-S3 cannot write converted_from_opportunity or rebooking (C2): no database function contains either value as a
  literal; every RPC-made row is linked_existing_request with a NULL key; the CHECK forbids a key for manual links.
- Only the future P2-S4 RPCs can create those outcomes. They do not exist; adding them is a reviewed migration.
- Manual attribution never marks an opportunity Converted:
  - C3: no Plus function sets stage = 'converted';
  - L12, G2: stages unchanged;
  - E2E B6, D4.
- Future idempotent conversion is supported by the schema: the nullable key, the per-organization partial unique
  index, the reserved link methods, and request_id as PK (one Request, one attribution). It matches the access model's
  T13 design (key + opportunity row lock).
