New tables (RLS enabled; composite tenant FKs with ON DELETE CASCADE; no reason / note / actor columns):

4. RPCs (all SECURITY DEFINER, SET search_path = public, pg_temp; REVOKE ALL FROM PUBLIC; GRANT EXECUTE TO authenticated)
======================================================================
All take a row lock, return an idempotent `changed` flag, and are audited. Error codes: ZW002 = foreign tenant, wrong
role or not found; ZW006 = invalid input; ZW004 = terminal or ended.
  set_driver_weekly_schedule(uuid, jsonb)                Admin / Dispatcher. 1..28 shifts. Atomic replace.
                                                         Week-ring overlap check. Marks CONFIGURED.
  clear_driver_weekly_schedule(uuid)                     Admin / Dispatcher. Returns to NOT SET (shifts cascade).
  save_driver_unavailability(uuid, tz, tz, uuid = NULL)  Admin / Dispatcher. Create or update.
  delete_driver_unavailability(uuid)                     Admin / Dispatcher.
  save_vehicle_unavailability(uuid, tz, tz, uuid = NULL) Admin / Dispatcher. Create or update.
  delete_vehicle_unavailability(uuid)                    Admin / Dispatcher.
  set_vehicle_capabilities(uuid, bool, bool, int, int)   Organization ADMIN ONLY (Q1). Atomic setter of the four facts.
  set_trip_wheelchair_requirement(uuid, boolean)         Admin / Dispatcher. Non-terminal trips. NULL clears.
  set_recurring_wheelchair_requirement(uuid, uuid, bool) Admin / Dispatcher (same roles as
                                                         edit_recurring_arrangement). Non-ended arrangements. Affects
                                                         only occurrences created afterwards.
  driver_get_own_schedule(uuid)                          Driver OWN data only, through current_driver_id(auth.uid()).
                                                         No driver_id parameter. Returns timezone, configured flag,
                                                         own shifts, and own windows in the next 14 days.
  create_trip(… 12 existing …, p_requires_wheelchair_access boolean DEFAULT NULL)
    Drop and create in the same transaction; one overload (13 arguments). The value is stored exactly as supplied and
    recorded in the trip_created audit row.
  create_recurring_arrangement(… 8 existing …, p_requires_wheelchair_access boolean DEFAULT NULL)
    Drop and create; one overload (9 arguments).
  create_trip_for_recurring_occurrence (identity unchanged)
    Now calls create_trip with NAMED arguments and passes p_requires_wheelchair_access => the arrangement's current
    value (the SNAPSHOT). The idempotency branch still returns an existing occurrence unchanged, so an arrangement
    change never rewrites an existing trip.
Why the recurring requirement has its own setter:
  - edit_recurring_arrangement passes every field. A new defaulted parameter would let an old caller silently reset the
    requirement to NULL.
  - So edit keeps its contract unchanged, and the requirement has its own audited setter.
  - The edit dialog calls the setter only when the value actually changed, and only after the edit succeeds.

7. DRIVER SCHEDULES, DST AND THE WEEK RING
======================================================================
Shift model:
  - Organization-local `time` + ISO weekday. Never stored as UTC.
  - end < start means overnight; end 00:00 means midnight; start = end is rejected.
Week-ring overlap (in the setter):
  - Each shift occupies [s, s + d) on a 10080-minute ring.
  - Pairs are compared, including ± one week, so a Sunday 22:00–02:00 shift versus Monday 01:00–05:00 is REJECTED.
  - Touching boundaries are allowed (Sunday 22:00–02:00 plus Monday 02:00–06:00 is accepted).
  - SQL S-2 / S-5 cover this.
DST (src/lib/operations/local-time-core.ts):
  - resolveLocalBoundary returns { earliest, latest }:
      - spring-forward gap → the first instant after the gap;
      - fall-back ambiguity → the first and second occurrences.
  - Each shift instance has a certain core [start.latest, end.earliest) and a possible extent
    [start.earliest, end.latest).
  - The core may be EMPTY and is never inverted: mergeSpans drops empty spans.
  - Anything in the possible-but-not-certain band is partly_unknown / NOT_FULLY_CHECKABLE.
  - Unit tests: spring (a 02:30 boundary resolves to 07:00Z; a 01:00–04:00 shift lasts 2 real hours); fall
    (01:30 → 05:30Z / 06:30Z); the empty-core case; midnight end; overnight; Sunday → Monday.
  - organizationLocalToUtc's contract is unchanged. Its helpers moved, unchanged, into the runtime-import-free
    local-time-core.ts; local-time.ts keeps its server-only marker and re-exports them.

8. TIME OFF, VEHICLE OUT-OF-SERVICE, CAPABILITIES AND REQUIREMENTS
======================================================================
Time off:
  - Half-open [starts_at, ends_at), unioned, a factual time even when the schedule is NOT SET, and it overrides shifts.
  - The UI converts organization-local "all day" or from–to input server-side (windowInputToUtc). A DST-gap or
    ambiguous input is refused, never guessed.
Vehicle out-of-service:
  - The same model. Advisory only. vehicles.status (the inactive hard invariant in assign_trip) is unchanged.
Capabilities:
  - Four nullable facts; NULL = "Not recorded"; false is never inferred.
  - UI: "Equipment on this vehicle", with no ADA, certification or approval wording (checked in E2E and unit tests).
Trip requirement:
  - New Trip has a tri-state control, "Wheelchair transport equipment needed?" (Yes / No / Not specified).
  - A Request whose structured service_type = wheelchair_transportation PREFILLS Yes, and the operator can override it.
  - No other service type, and no notes text, is interpreted. There is no SQL inference.
  - Trip Detail has a "Wheelchair transport equipment" panel with an Edit dialog (non-terminal trips only).
Recurring requirement:
  - The same tri-state control on New Arrangement and on Edit Arrangement. The detail page shows "Wheelchair
    transport equipment: … · applied to trips created from now on".
  - Request → arrangement prefill: NO such flow exists in the product today (recurring creation takes no Request), so
    there was nothing to attach a prefill to. None was built.

9. DERIVATIONS (pure; one model for every surface)
======================================================================
capability-core.ts:
  - requirement false → NOT_APPLICABLE; NULL → REQUIREMENT_UNKNOWN.
  - requirement true:
      - CAPABLE (positions ≥ 1 AND (ramp OR lift));
      - KNOWN_MISMATCH (positions = 0 OR (ramp = false AND lift = false));
      - otherwise NOT_CHECKABLE.
  - Unknown is never a mismatch. Nothing ranks or recommends.
availability-core.ts (runtime-import-free; time helpers injected via TimeTools):
  - Target trip:
      shift: schedule_not_set / covered / outside_start / outside_end / on_shift_at_pickup / partly_unknown /
             unknown_target
      time off and out-of-service: clear / overlaps / not_checkable / unknown_target
      capability: as above
  - availableForTrip is true ONLY when all of these hold:
      - the schedule is configured;
      - the extent is known and covered;
      - there is no time off;
      - the PROG4 driver check is clear.
    The PROG4 check already implies a complete candidate set and no pickup-less or missing-duration commitment.
  - NOW status, in precedence: ON_TRIP > TIME_OFF > OFF_SHIFT > COMMITTED > NOT_FULLY_CHECKABLE > SCHEDULE_NOT_SET >
    AVAILABLE.
      - Commitments come from the SAME PROG4 candidate set.
      - Any of the following gives NOT_FULLY_CHECKABLE:
          - an incomplete candidate or fact set (R1);
          - a pickup-less commitment (R2);
          - a still-open-past-end commitment (Q7);
          - a missing-duration commitment that could cover now;
          - a DST band.
      - AVAILABLE means free RIGHT NOW only.
  - Readiness reasons are KNOWN facts only: DRIVER_TIME_OFF, DRIVER_OFF_SHIFT (outside_start / outside_end),
    VEHICLE_OUT_OF_SERVICE, VEHICLE_WHEELCHAIR_MISMATCH.
  - One copy source for the notes (availabilityNotices) and the Dispatch flags (availabilityFlags).
  - No second commitment model: PROG4's deriveTripExtent, candidate sets and resource checks are consumed as-is.
