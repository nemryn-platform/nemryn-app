2. THE MIGRATION — NEW OBJECTS
======================================================================================================================
  2.1 table public.plus_request_contact_enablements    (activation guard; ZD-299)
      Columns:
        organization_id uuid    PK, FK organizations(id)
        data_class      text    NOT NULL   CHECK (data_class = 'synthetic')      -- 'live' cannot be stored
        reason          text    NOT NULL   CHECK (trimmed, 1..500)
        enabled_by      uuid    NOT NULL   FK auth.users(id)
        enabled_at      timestamptz NOT NULL default now()
      - Class A: RLS enabled, no policy, all privileges revoked from PUBLIC, anon, authenticated and service_role.
      - NO ROW = DISABLED. The migration inserts nothing.

  2.2 type public.plus_request_contact_enablement_result (organization_id, enabled, data_class, changed)
      type public.plus_request_contact_result (outcome, request_id, contact_id, opportunity_id, possible_duplicates,
                                               updated_at)
        outcome ∈ linked | possible_duplicates (nothing written) | already_linked (nothing written)

  2.3 platform_set_plus_request_contact_enablement(p_organization_id uuid, p_enabled boolean, p_data_class text,
      p_reason text)
      - Callable only via _require_platform_admin: ZW001 without a uid, ZW002 for everyone else, including the
        organization's own Admin.
      - Validation (ZW006 otherwise):
          * enabling requires p_data_class = 'synthetic'
          * disabling accepts NULL or 'synthetic'
          * a reason of 1–500 characters is required both ways
      - An unknown organization returns ZW002.
      - Locks the organization row FOR NO KEY UPDATE, which serializes toggles without blocking foreign-key checks.
      - Enable inserts the row; disable deletes it. A disable waits for any in-flight creation holding FOR SHARE.
      - If nothing changes it returns changed=false and writes nothing.
      - Audit: platform_plus_request_contact_enablement_changed, with before/after {enabled, data_class} and the
        reason.

  2.4 platform_get_plus_request_contact_enablement(p_organization_id uuid)
      Platform Admin only. Returns enabled, data_class, enabled_at, enabled_by display name and reason.

  2.5 plus_request_contact_enabled(p_organization_id uuid) → boolean
      - Never raises.
      - Returns plus_can_read(org) AND whether the row exists, so it is false for every non-Plus caller (no oracle).
      - Display only; it is not the authorization control.

  2.6 plus_create_contact_for_request(p_organization_id, p_request_id, p_display_name, p_phone, p_email,
      p_contact_kind, p_preferred_channel, p_do_not_contact, p_owner_membership_id, p_confirm_possible_duplicate)
      One transaction, in this order:
        1. _require_plus_write(org): ZW001 / ZW002, exactly as released.
        2. _plus_require_core_request_read(org): ZW002.
        3. ACTIVATION GATE: SELECT … FOR SHARE on the enablement row. No row → ZW004 'request_contact_not_enabled'.
           This runs after authorization (only authorized writers learn the state) and before any existence or
           duplicate check (no oracle).
        4. Request existence, by id and organization only. Unknown, foreign or NULL → ZW002.
        5. Existing attribution → outcome 'already_linked' with its ids. Nothing written.
        6. plus_create_contact(…, job_title NULL, …), UNCHANGED:
             - validation → ZW006
             - possible duplicates without confirmation → outcome 'possible_duplicates', NOTHING written
             - owner eligibility checked
             - audit plus_contact_created written
        7. plus_link_request(org, request, new_contact, NULL), UNCHANGED:
             - writes the request_linked activity and the plus_request_linked audit row
             - a concurrent attribution makes it raise ZW004 already_attributed, which rolls back the contact from
               step 6
        8. Audit plus_contact_created_from_request: entity plus_contact, after_data = {"request_id": …} only.
        9. Returns outcome 'linked'.
      What it never does:
        - It never reads requester_* or passenger columns; this is verified statically by test S5.
        - It never creates an opportunity, task, quote or consent row, never sets do_not_contact itself, and never
          changes a Core Request, Passenger, Trip, recurring arrangement, acquisition snapshot or billing row.

  2.7 Grants
      - Every new function: REVOKE ALL FROM PUBLIC, anon; GRANT EXECUTE TO authenticated.
      - service_role has no EXECUTE, per the database's default-deny privileges.
      - The privilege contract passes with 0 violations.

      * The gate lives inside the function; G1, G2, X3 and DIS1 call the RPC directly as `authenticated`, which is
        exactly what PostgREST does, and get ZW004 with nothing written.
      * The table cannot be written by any client role (S2), and 'live' is refused even for an owner INSERT (S6).
      * Mutation test: removing the gate from the function makes 8 tests fail (G1, G2, A1, A3, A5, X3, DIS1, DIS2).
  - Only authorized Platform Admins manage the allowlist: G3, G4, DIS1.

        passenger_id, requested_passenger_name or public.passengers.

      * The released plus_contacts / plus_request_attributions / plus_communication_consents / plus_inquiries

5. DESIGN DEVIATIONS FROM -01 / -02 (none of substance)
======================================================================================================================
  - The tenant helper is named plus_request_contact_enabled. -02 used this name, and it is unchanged.
  - The platform function locks the organization FOR NO KEY UPDATE, not FOR UPDATE as the inquiry allowlist does.
    The reason is in the migration header:
      * FOR UPDATE blocks every foreign-key check on the organization during a toggle.
      * It also opens a narrow lock-order deadlock window.
    A negative control with FOR UPDATE did NOT reproduce a deadlock under the scripted timing, because the window is
    microseconds wide. The choice rests on the conflict analysis, not on a reproduced failure.
  - When disabling, p_data_class may be NULL or 'synthetic'. -02 did not specify this case.
