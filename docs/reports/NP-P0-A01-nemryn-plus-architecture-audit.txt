1. EXECUTIVE ARCHITECTURE RECOMMENDATION
=====================================================================================================

VERDICT: Same repository, same Supabase backend/Postgres, same domain, same authentication --
CONDITIONAL YES.

The hypothesis holds. The codebase is already shaped for it: a single Next.js 16 App Router app with
surface-separated route trees (/operations, /driver, /platform, public), a single Supabase project
with deny-by-default privileges, every write routed through SECURITY DEFINER RPCs that re-check
tenant + role, and a machine-checked privilege contract that fails if a new table or function is not
explicitly classified. Nemryn Plus fits as a new module inside that model; nothing in the source
justifies a separate repo, database or auth realm.

The YES is conditional on four things, all of which are absent today:

  C1. A module entitlement mechanism that is NOT organizations.status. Today the only tenant-level
      switch is organizations.status ('active'/'inactive' = "suspended"), and it is wired into the
      core RLS helpers (is_org_member / has_org_role / current_driver_id). Re-using it for Plus would
      stop dispatch and drivers when a Plus subscription lapses. A separate, Plus-only entitlement
      check is required. [SRC: supabase/migrations/20260920130000_platform_admin_foundation.sql:98-102]
  C2. A decision on who may use Plus. memberships.role is a closed CHECK of exactly
      organization_admin | dispatcher | driver [SRC: 20260830130400_memberships.sql role CHECK;
      src/lib/auth/types.ts:10]. There is no sales/growth role and no per-member capability grant.
  C3. Plus must never become a second booking system. The Request Hub (transportation_requests +
      accept/decline/cancel RPCs + create_trip accepted-only) is the single controlled entry into
      operations and must stay that way. Plus records reference Requests; they never create Trips.
  C4. Explicit privacy separation. Plus (marketing/sales) data must not copy passenger assistance
      notes, trip content, or request free-text into CRM tables, analytics or ad integrations.
      No HIPAA assessment has been done [DOC: docs/commercial/sales-claims-boundary.md:11].

Shape of the recommendation:
  - Plus = new route tree /growth/* (sibling of /operations, same shell and design system), a small
    set of new plus_* tables, a new has_org_module() helper, and a handful of SECURITY DEFINER RPCs.
  - Core stays the system of record for Requests, Passengers, Trips, Recurring Care, Proof of Service.
  - Plus owns: accounts (B2B businesses), contacts, opportunities (one table, two channels), tasks,
    activities, consent ledger, and -- later -- quotes. It links to Core through a link table to
    transportation_requests, never by copying operational data.
  - The existing website intake + acquisition attribution is the private-pay acquisition entry
    point. Do not build a second public form.
  - Billing/fares/payments do not exist in Core at all; Plus quotes and payment status require a
    product decision before schema work (open question Q3).

5.2 Answers to the ten questions
  1. Storage: transportation_requests (+ request_events, request_acquisition_attributions).
  2. Org identification: ONLY from the opaque public key / integration external_id resolved inside
     the SECURITY DEFINER function; the body may never name an organization (route.ts doc block;
     20260919090000 header lines 12-30). Suspended orgs are indistinguishable from unknown (404).
  3. Auth & abuse: unauthenticated by design; service-role-only RPCs; closed schema; 16 KB body cap;
     Origin check (hosted) / per-integration origin allow-list (developer API); durable atomic rate
     limit ledger; uniform minimal responses. No CAPTCHA/bot challenge exists [SRC: no match].
  4. Duplicates: idempotency via partial unique index transportation_requests_intake_idempotency_idx
     on (intake_integration_id, external_submission_ref) (20260919090000:166-175). This dedupes
     retries, NOT a person submitting twice; human duplicates are handled by the 'duplicate_request'
     decline reason.
  5. Public forms create Trips?  NO. Locked decision: stops at 'pending'; no Trip/Passenger/Driver.
  6. Review: Request Hub (/operations/requests, /operations/requests/[id]) by Admin/Dispatcher.
  7. Request -> Trip: explicit accept, then create_trip requiring state='accepted' and the linked
     passenger; request becomes historically fulfilled by linked Trips/arrangements.
  8. Reusable customer records: NO customer entity. Requester details are per-Request columns.
     Passengers are reusable, but are the RIDER, not the payer/contact.
  9. Recurring <-> Request Hub: YES since R3 (recurring_arrangements.request_id). Also the public form
     can carry a structured recurring schedule (20260919130000_structured_website_intake_extension.sql).
 10. Where a private-pay pipeline should integrate: alongside the Request, never in place of it.

5.3 Smallest integration that keeps one booking system
  - Plus does NOT add a public form. The existing website forms remain the only public capture.
  - New "opportunity" (channel=private_pay) is a SALES wrapper. It links to zero or more Requests
    via plus_opportunity_requests (link table). The Request remains Core-owned.
  - Two entry paths into the pipeline:
      (i) Inquiry-first (phone/web question about price, no date yet): staff create an opportunity +
          contact in Plus; when the customer commits, a Plus RPC calls the SAME
          log_transportation_request primitive (source chosen explicitly) and links the result.
          The Request then lands in Request Hub as 'pending' -- dispatch still accepts/declines.
     (ii) Request-first (website submission): when the org has Plus, a staff action "Track in Plus"
          (or an opt-in automatic link at submission time -- decision Q2) creates an opportunity
          referencing the Request. No requester data is copied beyond what the contact needs.
  - Stage changes driven by Core facts, read-only: Request accepted -> "booked"; declined/cancelled ->
    "lost" with the Core reason; first linked Trip completed -> "won/served". Plus never writes to
    Core tables directly.
  - Quote and payment status sit on the opportunity (NP-P2), not on Request/Trip, until a fare model
    exists in Core (Q3).

=====================================================================================================

  Today [SRC]: facilities = locations; requests carry requester_relationship='facility_coordinator'
  and source='facility' but no FK to any facility or account. Trips reference facilities only as

  Proposed:

      plus_account_facilities (account_id, facility_id) -- REUSES facilities rows; no duplicate address

    contacts (coordinators, decision-makers) -> plus_contacts with account_id.
    pipeline -> plus_opportunities channel='facility' (contract/referral deals).

      Revenue/volume attribution is DERIVED: account -> linked Requests -> Trips (completed count) and,
      for pickup/destination-based volume, trips.pickup_facility_id/destination_facility_id via
      plus_account_facilities. No money until a fare model exists.
    onboarding -> an account "contracted" state + task checklist; facility self-service portal stays
      out of scope (scope register ZS-012..ZS-017 POST-MVP).

  UX consequence: the Operations "Facilities" page stays the list of PLACES. Plus "Accounts" is the
  business relationship, and an account page shows its linked locations read-only with a link to the
  Core facility page. One concept per page; no duplicate facility records.

IDENTITY RULE FOR LEAD -> REQUEST -> PASSENGER -> TRIP
  - Link by explicit IDs only: opportunity -> request (link table) -> passenger (Core's own
    link_request_passenger, chosen by staff) -> trips/arrangements (Core FKs).
  - Never auto-match a contact to a passenger by name/phone/email. A caregiver contact and the rider
    are different people; a phone number is shared within families and facilities.
  - Plus reads passenger/trip facts only through a minimum-necessary RPC (counts, dates, states --
    never assistance_notes, instructions, trip notes or exceptions).
  - Invoices: none exist; when Core billing is designed, invoice -> trip(s) -> request -> opportunity
    gives attribution without new identity assumptions.
