2. OD-6 IMPLEMENTATION AND LIMITATION
======================================================================
Finding: an AUTHORITATIVE, tenant-scoped do-not-contact status already exists.
- Column plus_contacts.do_not_contact (boolean, NOT NULL, default false), from NP-P1-S4. Its schema comment reads
  "Stored preference. Every FUTURE outbound action ... must refuse when true."
- It is set only by staff through plus_create_contact / plus_update_contact.
- It is read through plus_get_contact, which is Plus READ, tenant-scoped, and raises ZW002 for a foreign or unknown
  contact, plus RLS plus_can_read.
- It already appears as the "Do not contact" badge on Contact detail, Opportunity detail, Pipeline and the Growth
  Agent.
So the brief's "authoritative status exists" branch applies. Nothing was invented, and no consent is assumed.

Implementation (UI only; no database, RPC, migration or schema change):
1. src/lib/plus/booking-core.ts gains a pure helper, doNotContactNotice(doNotContact), and its copy:
   - true -> a warning. Title: "This person asked not to be contacted". Text: "Create this request only if they
     asked for this ride. Creating a transportation request does not send them a message; respect their preference
     when Operations follows up."
   - false -> no notice.
   - null / undefined (preference not available to the form) -> a neutral reminder that asserts nothing about the
     person: "Before contacting this person, check their communication preferences. Creating a transportation
     request does not send a message."
   - Only a strict boolean true counts as the preference. Look-alikes such as "true", 1 or "yes" are not treated as
     one.
2. BookingRequestDialog: BookingCustomer gains an optional doNotContact. The form renders the notice under the
   requester block:
   - data-testid booking-do-not-contact, as an AttentionState warning;
   - or booking-preference-reminder, as metadata text.
   The rest of the approved P2-S4 UI and interaction is unchanged: steps, copy, review, idempotency and the
   sessionStorage retry key.
3. Contact detail (rebooking) and Opportunity detail (conversion) pass doNotContact from the contact already loaded
   through the tenant-scoped getContact. No new query and no new data access.

Scope note: the approval names the rebooking flow. The same shared dialog also shows the warning in the CONVERSION
form when that opportunity's contact is flagged. That conversion also creates a Request for the same person, and the
opportunity page already shows the "Do not contact" badge, so the reminder is consistent. Removing it from
conversion is a one-line change if the owner prefers.

Behaviour guarantees:
- The notice never blocks or changes eligibility. The flagged Request is created exactly as before.
- Nothing is sent: P2-S4 has no messaging path. Notification behaviour is identical for flagged and unflagged
  contacts.
- The preference is never inferred from activity, notes or any other data; only the stored column is read.
- The preference is never written by this flow.
- No consent ledger, communication engine, email / SMS sender or schema change was introduced. Per-channel consent
  remains P2-S6, as already in the spec.
Limitation: the "unavailable" reminder state is defensive. Both current pages always pass the stored boolean, so in
practice staff see either the warning or nothing. The reminder state is covered by unit tests.
