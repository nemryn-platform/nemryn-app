PREVIOUS FAILURE MODE
-------------------------
src/app/operations/page.tsx (read fresh before any change) called
`const data = await getTodaysOperations(...)` as a plain, un-caught await
— unlike the three sibling promises immediately above it
(tomorrowReadinessPromise/recurringCarePromise/proofOfServicePromise),
each already wrapped in `.catch(() => null)`. A genuine getTodaysOperations
failure (any thrown Error from its 4 internal query round trips) would
propagate uncaught out of the Server Component, taking down the entire
/operations route with Next.js's generic route-level error boundary —
not a contained, informative degradation.

Additionally, `deriveOperationsBrief(data, ...)` (operations-brief-core.ts)
took `data: TodaysOperationsData` as a required, non-nullable first
parameter — so even the Operations Brief's own already-independent-looking
Tomorrow Readiness/Recurring Care/Proof of Service/Driver Snapshot/Requests
blocks could never render at all in a getTodaysOperations failure, because
`brief` itself could never be computed in the first place.

A second, currently-dormant call site of the identical bug was found during
the audit: `getOperationsBrief()` (operations-brief.ts, a fully-composed
alternative entry point with zero current callers) had the exact same
un-caught `getTodaysOperations(...)` call inside its own `Promise.all`,
sitting right next to the same three already-caught sibling promises.

    TRIP_COLUMNS embed used for both the "today" and "active" trip

     (Active Trips panel), `data.activityLog` (Activity Log panel).
  2. `deriveOperationsBrief(data, ...)` (operations-brief-core.ts) — which
     derives `dayState`, `totalTripsToday`, `attention`, `activeNow`,
     `nextDepartures`, and `unassignedCount` — the Operations Brief's own
     Needs Attention / Active Now / Next Departures blocks
     (src/components/operations/OperationsBrief.tsx).

No other section on /operations reads `getTodaysOperations`'s return value
— traced field-by-field, not assumed.

FAILURE CONTRACT
--------------------
`OperationsBriefDayState` extended with a 4th value, `"UNAVAILABLE"`
(operations-brief-core.ts), alongside the existing NO_TRIPS/ALL_COMPLETE/
ACTIVE_DAY — never conflated with NO_TRIPS, which is a real, successfully-
fetched "zero trips" answer.

`OperationsBriefData`'s today's-operations-derived fields were changed
from non-nullable to nullable, mirroring the exact `T | null` convention
already established for tomorrowReadiness/recurringCare/proofOfService:
  totalTripsToday: number | null
  attention: TodaysOperationsAttentionItem[] | null
  activeNow: TodaysOperationsTrip[] | null
  nextDepartures: TodaysOperationsTrip[] | null
  unassignedCount: number | null

`deriveOperationsBrief`'s first parameter became `data: TodaysOperationsData
| null`. When `null`, it returns `dayState: "UNAVAILABLE"` with every one
of the 5 fields above set to `null` — never `0`/`[]` — while still passing
`driverSnapshot`/`requestSummary`/`tomorrowReadiness`/`recurringCare`/
`proofOfService` through completely unchanged. `getTodaysOperations` ITSELF
was not rewritten into a nullable data source — it remains the single
authoritative read model, still throwing on a genuine failure exactly as
before; only its two callers (the page, and the dormant `getOperationsBrief`)
decide how to catch and represent that failure.

PAGE-LEVEL ISOLATION
------------------------
src/app/operations/page.tsx: `getTodaysOperations(...)` is now started
immediately (before the existing `Promise.all`), chained through
`.then((data) => ({ status: "ok", data })).catch(() => ({ status:
"unavailable" }))` — the exact conceptual shape specified in this phase's
own brief — and awaited alongside the pre-existing independent promises,
never serially. `getOnboardingChecklist`/`getDriverSnapshot`/
`getRequestSummary` remain in their own pre-existing, un-caught
`Promise.all` (unchanged — see OPEN ISSUES).

Rendering: `<OperationsBrief brief={brief} .../>` always renders (its own
internal UNAVAILABLE handling covers the compact summary). Below it, the
SummaryStrip + the 2-column grid of Needs Attention/Upcoming
Trips/Active Trips/Activity Log — the entire tightly-coupled group that
depends on `data` — is now gated behind one single conditional: `data ===
null` renders ONE contained `<EmptyState>` panel; otherwise the exact
pre-existing markup renders unchanged, using the now-guaranteed-non-null
`data`.

UNKNOWN VS ZERO
-------------------
Verified by construction and by live fault injection: a genuine
getTodaysOperations failure never produces "0 active trips" / "No trips
scheduled today" / "Nothing needs attention" anywhere on the page. Both the
Brief's compact block and the page's own larger detail region render the
explicit "Today's operations unavailable" treatment instead. Unit-tested
directly (operations-brief-core.test.mjs, new tests) that `attention`/
`activeNow`/`nextDepartures` are `null` — never `[]` — and
`unassignedCount`/`totalTripsToday` are `null` — never `0` — whenever
`data` is `null`.

SHARED-TABLE BEHAVIOR
-------------------------
Empirically discovered during fault injection (going beyond the static
`grep '.from('` dependency map, per this phase's own "trace every field,
do not assume names" instruction): `vehicles` is embedded via
`trip_assignments!...vehicles!...` in FOUR different query modules, not
just `todays-operations.ts` —tomorrow-readiness.ts, recurring-care.ts, and
trip-proof-of-service.ts each also embed a `vehicles` relation for their
own active/completion-assignment enrichment. `trip_events` is similarly
shared between todays-operations.ts (activity log) and
trip-proof-of-service.ts (lifecycle-event-chain verification).

Live result of revoking SELECT on `vehicles` (see FAULT INJECTION RESULTS):
Today's Operations AND Tomorrow Readiness AND Recurring Care all degraded
to their own independent "unavailable" states, while Proof of Service
happened to remain healthy in this specific run — not because it is
truly independent of `vehicles`, but because the local fixture data had
zero completed trips from yesterday, so its own vehicles-embedding query
branch was never actually evaluated against a row that needed it. This is
exactly the accepted "shared table reality" this phase anticipates (§12):
the correctness property that matters is that EVERY affected block failed
containedly and the route never crashed, not that the blocks were
perfectly independent — they demonstrably are not, and this report
documents that rather than asserting a false independence.

FAULT INJECTION METHOD
---------------------------
Local-only, reversible, no migration:
  docker exec -i supabase_db_ZenWard psql -U postgres -d postgres \
    -c "revoke select on public.vehicles from authenticated;"
Chosen after mapping dependencies (above) as the table with the narrowest
blast radius among Today's Operations' own dependencies while still
guaranteed to trigger a real failure (`vehicles` is embedded directly in
TRIP_COLUMNS, used by both the "today" and "active" trip queries — a
revoked embed causes PostgREST to fail the entire row-select for the
affected tables, mirroring the "real failure...observed during prior
controlled local fault injection" this phase's mission cites).

OPEN ISSUES
--------------
1. `getOnboardingChecklist`/`getDriverSnapshot`/`getRequestSummary` in
   page.tsx still share one plain, un-caught `Promise.all` — a genuine
   failure in any of the three would still take down the whole route.
   Deliberately NOT addressed this phase (out of the explicitly-scoped
   "Today's Operations must never take down the page" mission; expanding
   to these three would have broadened the diff beyond what this phase's
   own "small diff preferred" / "solve the actual pilot risk only"
   instruction allows). Flagged here as a candidate for a future,
   similarly-scoped hardening phase if it becomes a real pilot risk.
2. `getOperationsBrief()` (operations-brief.ts) has zero current callers
   in the codebase — it was still fixed (see FILES MODIFIED) for internal
   consistency, but its lack of any caller means this fix has no
   observable effect on the live product today; it only prevents a latent
   bug from surfacing if/when this function is ever wired up.
3. The shared-`vehicles`-embed cascade (Tomorrow Readiness, Recurring
   Care, and — situationally — Proof of Service) is real, current, and
   accepted per §12 of this phase's own instructions. A future phase
   focused specifically on Brief-block independence could reduce this
   blast radius (e.g., by making each block's own vehicle/driver status
   lookup independently fault-tolerant), but that is explicitly a
   different, larger phase than this one.
