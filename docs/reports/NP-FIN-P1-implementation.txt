======================================================================================================================
1. WHAT WAS BUILT
======================================================================================================================
Money received is now separated into four append-only records:
  - receipts: money received;
  - allocations: money applied to (apply) or removed from (unapply) ONE issued invoice;
  - refunds: money returned, recorded by staff;
  - receipt reversals: entered by mistake, returned check, or duplicate.
Plus a correction record for a refund entered in error, and staff evidence facts.

Confirmed by design and by tests:
  ✓ One receipt can be allocated to several invoices: one allocation row per invoice; their sum is at most the receipt.
  ✓ Excess funds stay as payer credit: unallocated = gross − net applied − recorded refunds. A receipt may be recorded
    with no allocation at all.
  ✓ Refunds never exceed refundable funds: refundable = the receipt's unallocated amount, checked under the receipt
    lock and again by a deferred invariant.

UI (Concept B, extends the existing Billing area; Organization Admin only):
  Billing page
    - "Record payment received" action.
    - A third view, "Payments received" (receipts list: number, payer, date, method, amount, payer credit, status +
      verification badge), with filters All / With credit / Reversed and search by RCPT number or payer.
    - A "payer credit" tile.
  Record payment received (/operations/billing/receipts/new)
    - Step 1, choose the payer: payers with an organization-scoped identity (from open invoices, labelled from their own
      record), or "Someone else" (typed, flagged as not verified).
    - Step 2, record the money: amount, date, method, provider, reference, processing fee (the agency's expense, OD-5),
      note, "I have the document".
    - Allocation editor with an oldest-first suggestion over the payer's own invoices. The rest is shown as "kept as
      payer credit".
    - Other or unverified payers' invoices are hidden until asked; using one requires a confirmation box plus a reason
      (OD-2).
  Payment page (/operations/billing/receipts/[id])
    - Summary: amount, payer credit, applied, refunded, payer, method / provider, reference, fee + net, note.
    - Applied-to list (Removed / Other payer marks), refunds (with Corrected), verification history.
    - Actions:
        Apply credit;
        Record refund (Admin; maximum = refundable);
        Correct refund (Admin);
        Reverse payment (Admin; reason code + details; disabled with an explanation while money is applied or refunded);
        "I have the document" (evidence).
  Invoice page
    - Record payment: the payer is the invoice bill-to.
      - Paying more than the balance is still REFUSED (NP-BILL-P1 behaviour) unless "keep the extra as payer credit" is
        ticked.
      - A likely duplicate (same method + reference + amount + date) asks for an explicit "not a duplicate"
        confirmation.
    - Apply payer credit: the same payer's credit, by identity only.
    - Payments list: RCPT number, assurance badge, Reversed / Removed / Other payer, links to the payment page and the
      receipt print.
    - Reverse: simple whole-receipt payments, through the NP-BILL-P1 compatible RPC.
    - Remove from invoice: unapply, Admin; the money becomes payer credit.
  Printing
    - /receipt-print/[receiptId]: RCPT-000123 (OD-4), invoices paid, credit kept, refunds, the REVERSED banner. Moved
      from /receipt-print/[paymentId]; there are no production payments, so no old links exist.
    - Invoice print: payments listed with RCPT numbers; reversed / removed entries marked "not counted".
  Copy rules
    - "Provider confirmed" / "Reconciled" never appear for staff entries.
    - A typed reference shows as "Reference noted".
    - Refunds read "Recorded by staff" and are explained as not provider or bank confirmation.
  Forms
    - Every ledger dialog dispatches by hand (keepValues): React 19 resets a <form action> after a refused submit and
      would otherwise erase what the person typed. This is the same fix as NP-PILOT-P1, found by the new E2E (E3).

Not built (out of scope): FIN-P2 pre-trip invoices, FIN-P3 clearance / dispatch, provider webhooks, accounting sync,
statement import, billing grant delegation (FIN-P4).

supabase/migrations/20261029100000_core_billing_ledger_foundation.sql (715 lines)
  0  Zero-row gate: raises "billing_payments is not empty -- STOP" if the retired table holds any row (ZD-268, D).
  1  _billing_looks_like_pan(text): a Luhn check on 13-19 digit runs, spaces / dashes allowed. Used in CHECKs so card
     numbers are never stored in references, notes or reasons.
  2  Tables, each with composite (id, organization_id) FKs:
       billing_receipt_counters;
       billing_receipts (gross, fee, generated net, method, provider, reference + normalized reference,
         provider_txn_id reserved, payer kind + scoped ids + snapshot name, source_invoice_id);
       billing_allocations (apply / unapply; an unapply mirrors exactly one apply of the same receipt and invoice;
         different_payer + reason);
       billing_refunds;
       billing_refund_reversals;
       billing_receipt_reversals;
       billing_assurance_events.
     The CHECK on billing_assurance_events: provider_confirmed / reconciled can NEVER have source 'staff'.
     Uniqueness:
       - idempotency keys per organization;
       - (organization, provider, provider_txn_id);
       - one unapply per apply, one reversal per receipt / refund, one evidence kind per receipt.
  3  Append-only: UPDATE / DELETE / TRUNCATE are refused on every ledger table, the owner included.
  4  Immediate BEFORE INSERT guards, locking parent rows in the global order (receipt → invoice):
       allocation: same organization (cross_organization), invoice issued, same currency, receipt not reversed,
         apply <= balance and <= unallocated, unapply mirrors its apply;
       refund: <= unallocated, not reversed, not before the receipt;
       receipt reversal: only at net zero (no allocation, no refund).
  5  DEFERRED constraint triggers, re-checked at COMMIT:
       - invoice: 0 <= paid <= total; money only on issued invoices; void / draft at net 0;
       - receipt: allocated + refunded <= gross; a reversed receipt is fully unapplied and unrefunded.
       These also fire on billing_invoices status updates, so a direct owner void of a paid invoice is refused.
  6  Permission catalogue (ZD-272): _billing_action_roles(action) and billing_can(org, action).
       - SENSITIVE actions (void, unapply, reverse, refund, refund_reverse, cross_payer_allocate) are Organization
         Admin only.
       - In FIN-P1 every action is Organization Admin.
       - RLS on each ledger table: SELECT through billing_can(..., 'view'); no client write grants.
  7  billing_payments retired: its guard now refuses INSERT too ("billing_payments_retired"). SELECT and its policy
     are kept for one transition release (ZD-268); the table is not dropped.

4. DEVIATIONS FROM THE APPROVED PLAN (all additive or stricter)
======================================================================================================================
  V1 billing_refund_reversals added.
     - Without it, a refund entered by mistake could never be corrected in an append-only ledger.
     - It is SENSITIVE (Admin), reason required, once only.
  V2 Card-number detection uses the Luhn check on 13-19 digit runs, not "any 13+ digits".
     - That avoids refusing legitimate 15-digit ACH trace numbers while still refusing card numbers.
     - It is mirrored in the UI.
  V3 billing_record_payment with a card-like reference now fails (ZW006 invalid_input). NP-BILL-P1 would have stored it.
     This is an intended tightening.
  V4 Invoice-page "Record payment" now calls billing_record_receipt with the payer derived from the invoice, plus the
     optional "keep the extra as payer credit".
     - The wrapper RPC stays for compatibility (older app build, tests) and is still exercised by the reverse path and
       the SQL / concurrency suites.
     - The overpayment refusal is preserved by default (E2E P3 and E7b-1).
  V5 _billing_require_admin and the existing NP-BILL-P1 invoice RLS policies are unchanged (still admin-only).
     - New code authorizes through the catalogue; the BILL-P1 policies move to the catalogue in FIN-P4 with the
       billing grant.
  V6 Possible-duplicate confirmation applies to staff references (method + normalized reference + amount + date,
     receipts that were not reversed). The wrapper skips it to keep NP-BILL-P1 behaviour.
  V7 The receipt print route segment was renamed ([paymentId] -> [receiptId]). With 0 production payments there are no
     external links to break.
  V8 billing_list_payers labels payers from their own record (passenger / requester / facility name), not from an
     invoice's bill-to snapshot. This was found by the E2E (E1b).
