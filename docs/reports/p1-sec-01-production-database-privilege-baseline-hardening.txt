  alter default privileges for role postgres in schema public revoke all on tables    from anon, authenticated, service_role;
  alter default privileges for role postgres in schema public revoke all on sequences from anon, authenticated, service_role;
  alter default privileges for role postgres in schema public revoke all on functions from anon, authenticated, service_role;

(contract check 24 fails loudly if that changes). (3) Supabase-managed schemas (storage, auth, ...) are untouched.

----------------------------------------------------------------------
POSTGRES DEFAULT EXECUTE BEHAVIOR   (PostgreSQL 17.6, transactional probes, all rolled back)
----------------------------------------------------------------------
Probe file (re-runnable): supabase/tests/support/default_function_privilege_probes.sql
1. Why functions get PUBLIC EXECUTE: with no pg_default_acl row at all (pristine), a new function created by
   postgres in public has proacl = NULL, i.e. the BUILT-IN default acldefault('f', postgres) =
   {=X/postgres, postgres=X/postgres}. PUBLIC's EXECUTE comes from that built-in default, not from any row we
   or Supabase created. Result: PUBLIC, anon, authenticated and service_role can all execute it.
2. Can `IN SCHEMA public REVOKE EXECUTE ... FROM PUBLIC` remove it?  NO. After
   `alter default privileges for role postgres in schema public revoke execute on functions from public`
   (plus revokes from anon/authenticated/service_role) a new public function still has PUBLIC EXECUTE
   (public_exec = t; anon can execute). Schema-scoped default entries are only ADDED to the global default;
   they cannot subtract from it.
3. The only removal is the GLOBAL form (no IN SCHEMA) for the owner role. Probe: after it, functions in
   public AND in an unrelated new schema both have no PUBLIC EXECUTE; a schema-scoped
   `GRANT EXECUTE ... TO PUBLIC` for one schema brings PUBLIC back for that schema only.
   => A public-schema-only default-deny cannot be expressed with default ACLs alone.

----------------------------------------------------------------------
SCHEMA-ONLY OPTIONS TESTED
----------------------------------------------------------------------
A. Global default revoke (as shipped in the first SEC-01 draft): works; side effect = every schema (see below).
B. Explicit `REVOKE ... FROM PUBLIC` in every function migration, enforced by the contract test: no side effects
   and it is already the convention of all 91 existing functions, but it FAILS OPEN: a forgotten revoke leaves a
   PUBLIC/anon-executable function until a human runs the contract test / production verify. Rejected as the sole
   control (kept as convention; the contract test still enforces the outcome).
C. Dedicated Nemryn function-owner role: not adopted. Migrations run as postgres (the CLI login role is a member
   of postgres); a second owner changes ownership of 91 functions, RLS helper behaviour (definer identity),
   every migration template, and Supabase tooling assumptions. Major operational complexity for architectural
   purity only.
D. DDL event trigger that revokes PUBLIC on new public functions: technically possible here (probe: postgres, not a
   superuser, could create one in the local Supabase image; production already has platform event triggers and
   `ensure_rls` owned by postgres). Rejected: a persistent hook on every CREATE FUNCTION can block all function DDL
   if it errors, silently changes ACLs outside the migration text, and cannot be pre-tested on production, which
   this phase must not mutate. Not a hack, but more moving parts than a declarative default ACL.
E. Global revoke + schema-scoped PUBLIC re-grant for the schema that relies on vendor defaults (FINAL, below).

Q: could a FUTURE `CREATE EXTENSION` by postgres yield functions without PUBLIC EXECUTE? Probe with a trusted
   extension (citext, 47 functions) under (a) pristine, (b) global revoke only, (c) final design: in ALL three the

   Reason: supautils (present in production: supautils.privileged_extensions lists citext, hstore, ltree, ...) runs
   CREATE EXTENSION through the privileged role, so postgres's default ACLs never apply to the extension's objects.
Q: what if extension objects ARE owned by postgres (as production's current three are)? Probe: a function created
   by postgres in schema extensions has NO PUBLIC EXECUTE under global-revoke-only (MATERIAL: an inserting role would
   get permission denied on any new column-default function), and HAS it under the final design.
Q: do extensions issue their own GRANTs? Typically not for PUBLIC (they rely on the built-in default); Supabase's
   platform event triggers (issue_pg_graphql_access, issue_pg_net_access, issue_pg_cron_access) grant only for
   those specific extensions.
Q: does ALTER EXTENSION UPDATE re-derive existing ACLs? No: existing function ACLs are stored (probe on uuid-ossp);
   only functions ADDED by an update script take defaults, and the extensions re-grant covers them.
Q: would the dashboard/CLI compensate? Dashboard/CLI extension enablement goes through the same supautils path
   (privileged role), i.e. unaffected. A hand-written migration creating a postgres-owned function in `extensions`
   or another schema is the only exposed case, and it is covered for `extensions` by the re-grant.
Operator procedure if a future non-Nemryn function outside public legitimately needs PUBLIC EXECUTE: add
`GRANT EXECUTE ON FUNCTION <signature> TO PUBLIC;` (or a schema-scoped default) in that migration and record the
exception in docs/security/database-privilege-contract.md section 2.1.
