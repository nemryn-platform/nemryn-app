================================================================================
Question: can a completely fresh customer, with no manual SQL / Dashboard /
manual auth.users edits / service-role scripts / manual Membership INSERT:

 A. sign up ............................. SUPPORTED
    /sign-up (supabase.auth.signUp, persists pending_full_name /
    pending_business_name in auth metadata).
 B. verify / authenticate ............... SUPPORTED
    Email-confirmation environments via /auth/confirm (token_hash, server
    verifyOtp) -> /complete-signup; local has confirmations off. Sign-in,
    password recovery also exist.
 C. create an Organization .............. SUPPORTED (with one exposure, fixed)
    complete_pending_signup / complete_pending_signup_manual ->
    signup_create_organization, all SECURITY DEFINER, atomic (UserProfile +
    Organization + Membership + AuditEvent in one transaction).
    EXPOSURE FOUND: signup_create_organization itself was still directly
    EXECUTE-able by every authenticated user. Any authenticated principal
    (including a Driver or Dispatcher of an unrelated tenant) could call it
    directly and repeatedly, minting unlimited organizations and Admin
    Memberships, and two concurrent direct calls from one fresh user produced
    two organizations -- bypassing the exactly-once gates. Fixed (see
    ORGANIZATION CREATION AUTHORITY).
 D. become Organization Admin ........... SUPPORTED
    role hard-coded organization_admin inside the function; never a parameter.
 E. enter Nemryn Operations ............. SUPPORTED
    -> /onboarding (business stage, basics, vehicle/driver/facility/passenger,
    all skippable) -> /operations. Onboarding checklist banner on Overview.

Also audited: the no-organization state. /, /operations/*, /driver/* all route a
zero-Membership user to /complete-signup, which auto-continues a pending
signup / driver invite, else sends to /complete-signup/form (an explicit
"recovery" form: full name + business name). It worked but was worded as an
error recovery ("We couldn't automatically finish setting up..."), not an
intentional first-run experience. PARTIAL -> presentation fixed.

Multi-organization assumption (audited, not invented): multi-org MEMBERSHIP is
supported (select-organization, workspace switching, org-context cookie). Multi-
org SELF-SERVICE CREATION was never reachable from any UI; only the exposed
direct RPC allowed it. This phase makes "one self-service organization per
person" the enforced behavior (flagged for owner confirmation in OPEN ISSUES).

================================================================================
MUTATION MODEL
================================================================================
update_organization_settings(p_organization_id uuid, p_changes jsonb) ->
(organization_id, changed). SECURITY DEFINER, EXECUTE to authenticated only.
 - Order: no session -> ZW001; not an active Organization Admin of that org
   (Dispatcher, Driver, inactive, foreign, nonexistent, null, Platform Admin
   without Membership) -> ZW002 (no existence oracle); then validation ZW006.
 - p_changes is a patch of six keys only. Unknown/privileged keys (status,
   business_stage, id, organization_id) -> ZW006, never ignored. Values must be
   strings/null. Blank clears optional fields.
 - The Server Action derives the organization from the session workspace; the
   form has no organization id field. The RPC re-checks authority regardless.
 - direct UPDATE of organizations.name and .timezone REVOKED from authenticated,
   so the audited RPC is the only way to change them (the new columns never had
   a grant). Remaining direct column grants: status, business_stage,
   service_area_description (unchanged).
 - No-op resubmission writes nothing (changed=false, no AuditEvent).
