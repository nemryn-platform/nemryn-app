9. COMPONENT-LEVEL TOKEN CORRECTIONS (documented, per §5 of the
   work item: "Document every such correction")
====================================================================

Three genuine semantic corrections were found and made while
migrating `brand-interactive-teal`'s 54 call sites (not merely a
rename — see §6's design-token-spec Appendix A.1 characterization,
"SPLIT — manual review, highest priority"):

  1. **`StatusBadge.tsx`'s `active` category** previously used the
     SAME teal as the (unrelated) primary-action/link color
     (`bg-brand-calm-mist text-brand-interactive-teal` / dot
     `bg-brand-interactive-teal`). Its actual meaning — "currently
     active/selected," used alongside a SEPARATE `informational`
     category — is Nemryn's `status.information` (Steel Blue)
     exactly. Corrected to reuse the SAME `info-bg`/`info-text`/
     `info-strong` tokens `informational` already uses, rather than
     inventing a second, redundant token family for what is the same
     underlying meaning.
  2. **`DriverActiveTripLegs.tsx`'s two-leg progress indicator**
     previously used the IDENTICAL teal color for BOTH the "current
     leg" state (`pickupCurrent`) and the "done" state (`pickupDone`)
     — conflating "in progress" and "already completed" into one
     color. Per the semantic mapping table (`05-semantic-color-
     system.md` §4: "Trip: in service/en route → status.information";
     "Trip: completed, proof recorded → status.ready"), these are two
     DIFFERENT meanings. Corrected: `pickupCurrent` → `info-strong`
     (in progress, Steel Blue), `pickupDone` → `success-strong` (done,
     Signal Green) — the two states are now visually distinguishable,
     which they were not before.
  3. **`FormSection.tsx`'s section-icon tint** used the interactive
     teal purely decoratively (a colored icon next to a heading,
     conveying no status or meaning). Per the LOCKED "mostly neutral"
     visual character (brand-lock-v1.md §6) and the explicit "status
     colors as decoration" prohibition (`05-semantic-color-system.md`
     §6), this was corrected to `text-muted` (neutral, matching the
     primitive table's own "Muted Slate... icon default" role) rather
     than migrated to any accent/status token.

**A broader semantic re-check was also performed, per §5's own
instruction, across every `critical-*` consumer in the application**
(the family most likely to be misused per Appendix A.3's own warning
about "routine notice" misuse): the overwhelming majority of
`critical-text`/`critical-strong`/`critical-bg`/`critical-border`
usage is `role="alert"` FORM VALIDATION ERROR text (every auth form,
every onboarding form, every operations dialog) and one genuine trip
EXCEPTION display (`operations/trips/[tripId]/page.tsx`) — both are
legitimate "failed condition"/blocking uses, not the "routine
account/security notice" misuse the spec warns against (e.g. "your
password was changed" wrongly styled critical). **No further
correction was found necessary** in this family — the existing
convention was already semantically sound; this is reported as a
confirmed non-finding, not skipped.
