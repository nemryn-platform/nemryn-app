2. PART 1 — CLOSING THE DIRECT-RPC ABUSE BYPASS
================================================================================
S4A granted `submit_public_transportation_request` EXECUTE to `anon` and
`authenticated` directly (callable via raw PostgREST, bypassing every
anti-abuse control this phase adds at the HTTP layer). Closed as follows:

- `supabase/migrations/20260919120000_public_intake_ingress_hardening.sql`,
  Section A: `revoke all ... from public, anon, authenticated; grant execute
  ... to service_role;` on the RPC.
- New privileged client: `src/lib/supabase/service-role-server.ts` — the ONE
  privileged Supabase client in this codebase. `import "server-only"` at the
  top (build-time guard against accidental client-bundle inclusion). Reads
  `process.env.SUPABASE_SERVICE_ROLE_KEY` directly (not via the shared
  `src/lib/supabase/env.ts`, deliberately — `env.ts` is imported by the
  client-side `client.ts` and must stay free of anything privileged).
  Exactly two legitimate callers: `website-intake.ts` (submission) and
  `rate-limit.ts` / `cors.ts` (the two other server-only helpers this route

  function, never WHAT it is allowed to do. Verified by re-running S4A's own
  full test suite unmodified in substance (only the `set local role` lines
  needed updating from `anon` to `service_role` to keep calling the RPC
  through its own now-correct path — see Part 8).

Proof (SQL): TEST S4B-1 / S4B-2 (anon / authenticated get
`insufficient_privilege` calling the RPC directly), TEST S4B-3 and TEST 20

3. PART 2 — DURABLE, ATOMIC RATE LIMITING
================================================================================
New table `public_intake_rate_limit_events` (append-only; one row per
allowed attempt) + `check_and_record_public_intake_rate_limit(text, text)`,
`security definer`, service_role-only. Atomicity is via two transaction-scoped
`pg_advisory_xact_lock`s (one keyed on the integration, one on the client) —
never an in-memory Map, never a process-local counter, never browser-only
throttling, never a disabled-button-as-sole-control. Locks are released
automatically on commit/rollback; no manual cleanup needed.

Thresholds (hard-coded, reviewable, documented in the migration's own
comment — not env-configured, not a multi-window scheme, both deliberate
pilot-scale simplifications):
  - PER-CLIENT: 8 attempts / rolling hour
  - PER-INTEGRATION: 120 attempts / rolling hour
Counts every attempt that passes the check, including ones that later fail
validation — deliberate (a flood of garbage is rate-limited exactly like a
flood of valid submissions).

Client identity: `src/lib/public-intake/rate-limit-core.ts` resolves the
caller's IP from trusted Vercel request-metadata headers only
(`x-forwarded-for` first entry, then `x-real-ip`, then the literal string
`"unknown"` — never null, never skips the check), then hashes it with
SHA-256 + a documented non-secret salt (`node:crypto`, one-way) BEFORE it
ever reaches Postgres. The raw IP is never stored, logged, or transmitted to
the database in any form.

Throttled responses stay inside the existing generic-error philosophy: HTTP
429, but the JSON body is the SAME generic `{ok:false,
error:"invalid_request", ...}` shape used for every other rejection — no
counter, threshold, or rate-limit-specific wording is ever exposed.

Proof (SQL): `public_intake_rate_limit_tests.sql` — 8/8, incl. per-client
threshold (12 attempts → exactly 8 allowed), per-integration threshold (125
distinct clients → exactly 120 allowed), integration-limiter isolation (one
integration's attempts never touch another's counter), anon/authenticated
denied direct RPC access, and the underlying table closed to anon/
authenticated SELECT.
Proof (concurrency): `public_intake_rate_limit_concurrency_test.sh` — 15
genuinely concurrent OS processes race the SAME client key against the
8/hour threshold; result is EXACTLY 8 allowed / 7 denied / 8 durably
recorded rows, proving the advisory lock closes the classic
count-then-insert read-before-write race a naive `SELECT count(*) ... IF ...
THEN INSERT` pair would be vulnerable to.
Proof (HTTP, real route): local E2E K/K2 — a burst of 12 real POSTs from one
spoofed `X-Forwarded-For` client allows exactly 8, then 429s.

4. PART 3 — CORS / ORIGIN
================================================================================
S4A's wildcard `Access-Control-Allow-Origin: *` is replaced with an explicit
allow-list: `src/lib/public-intake/cors.ts`'s `resolveAllowedCorsOrigin`
queries the UNION of every currently-ACTIVE integration's own
`allowed_origins` array (the OPTIONS preflight carries no JSON body to
identify one specific integration ahead of time, so a per-request union is
the smallest workable design at pilot scale) and returns the caller's exact
Origin only if it is a member — never a reflected arbitrary origin, never a
wildcard. `Vary: Origin` is set on every response (POST and OPTIONS alike),
including error responses. When there is no match, no
`Access-Control-Allow-Origin` header is set at all (verified: browsers block
the response client-side).

This required its own privilege grant: `service_role` needed to SELECT from
`request_intake_integrations` for this query, and — the SAME class of bug as
Part 1's own original EXECUTE gap — `service_role`'s BYPASSRLS attribute did
NOT imply that grant. This was caught during local E2E validation (P2 failed
with a missing header; root-caused to `permission denied for table
request_intake_integrations` via a direct `SET ROLE service_role; SELECT
...` probe) and fixed with Section A2 of the same migration: `grant select
on public.request_intake_integrations to service_role;` — SELECT only, no
write grant (provisioning remains exclusively a direct-SQL, `postgres`-role
operation). A permanent regression test (`TEST BONUS-A3
service-role-select-only-on-integrations-table`) now asserts this exact
grant shape so this class of bug cannot silently regress again.

Origin remains, exactly as required, a SECONDARY, browser-only courtesy
control. The RPC's own independent `p_origin` check (S4A, unchanged) is the
actual authoritative tenant/origin boundary and stays safe even if a caller
forges or omits the Origin header entirely — proven by TEST BONUS-B1 (wrong
Origin rejected), BONUS-B2 (correct Origin accepted), and the newly-added
BONUS-B3 (missing Origin header against an origin-locked integration is also
rejected — fail CLOSED, not fail open, once an integration has any
`allowed_origins` configured; this test was referenced by the section's own
pre-existing comment but had never actually been written until this phase).

Proof (HTTP, real route): local E2E O/O2 (wrong Origin → 400, no ACAO
header), P/P2 (correct Origin → 200, exact ACAO echo, never wildcard), and
newly-added U/U2/U3 (safe OPTIONS preflight: 204, empty body, same
allow-list resolution, `Vary: Origin` present alongside Next.js's own
internal RSC vary tokens).

5. PART 4 — INTEGRATION PROVISIONING
================================================================================
S4A's no-UI decision is kept. Provisioning mechanism:
`.tmp-qa/s4b-provision-integration.sh` (local-only, never staged/committed,
per this session's established "never ship `.tmp-qa/`" convention) —
`create` / `inspect` / `activate` / `disable` actions, `TARGET=local|prod`
switch (`docker exec psql` locally, `supabase db query --linked` for
production — the same safe, credential-free Management-API path used
throughout this engagement). No new RPC, no new UI, no new
authenticated-reachable surface. Smoke-tested through a full
create→inspect→activate→disable cycle locally; the smoke-test row was then
deleted.

Every integration row carries: `organization_id` (FK), `integration_type`
('website', CHECK-constrained), `external_id` (opaque, UNIQUE), `is_active`
(boolean, defaults `false`), `allowed_origins` (text[], nullable = no origin
restriction), `created_at`. New integrations begin **disabled**; activation
is a deliberate, separate step (`is_active = true` set explicitly, never as
a side effect of creation). Internal organization UUIDs are never exposed to
a tenant website — the website only ever holds the opaque `external_id`.

Kill switch: setting `request_intake_integrations.is_active = false` for a
given row immediately and completely stops that integration's HTTP path
from succeeding (every submission attempt for a disabled integration gets
the same generic ZW006 rejection as a nonexistent one — no existence
oracle), with zero effect on previously-received Requests. Proven directly
(TEST 9 `disabled-integration`, local E2E M) and by the provisioning
script's own `disable` action.

9. ZENWARD-WEB CONTRACT MISMATCH (FINDING) + RECOMMENDED RECONCILIATION
================================================================================
Zenward-Web's pre-written spec expects:
  - Bearer-token auth: `Authorization: Bearer <PLATFORM_INTAKE_TOKEN>`
    (a single shared secret selecting the tenant).
  - A versioned envelope: `{schemaVersion, submissionId, submittedAt,
    source, request: {...12 fields...}}`, with `submissionId` doubling as
    an `Idempotency-Key` HTTP header.
  - A success body `{ "accepted": true, "referenceId": "ZW-7F3K9Q" }` on
    `200`/`201`, and a `409`-with-`referenceId` form of idempotent replay.

What S4A/S4B actually built:
  - No bearer token at all — tenant resolution is via the opaque, per-
    integration `integrationExternalId` sent INSIDE the flat JSON body
    (not a header, not a secret — deliberately, per this phase's own Part
    4 design: "each integration needs... opaque external ID").
  - A flat JSON body (no envelope wrapper, no `schemaVersion`, no
    `Idempotency-Key` header — `idempotencyKey` is a body field).
  - A minimal response: `{ok:true}` / `{ok:false, error, message}` — no
    `referenceId` of any kind (deliberate: this phase's own "no existence
    oracle" / generic-error philosophy, ZW006 collapsing every distinct
    failure into one code).

Recommendation (not yet implemented — Part 14 scope, gated on Part 13):
adapt Zenward-Web's OWN adapter to Nemryn's actual, already-hardened
contract, rather than rebuilding Nemryn's endpoint to match a speculative
pre-written contract. Reasons: (1) Nemryn's endpoint is fully proven — 26
SQL tests, 2 independent concurrency proofs, a full 33-file regression, and
a 28-check real-HTTP local E2E rehearsal all pass against the contract as
built; reopening it now to add bearer-token auth and a `referenceId`
generator would touch security-critical, already-verified surface for zero
net security benefit. (2) Zenward-Web's own architecture doc explicitly
calls its adapter "the swappable seam" and states "No page, form component,
or Server Action needs to change" when the destination changes — this is
precisely the situation that seam was designed for. (3) Part 5 of this
phase's own brief says to preserve S4A's contract "unless proven necessary
to change," and nothing here proves it necessary.

Concretely, when Part 14 is reached: `PlatformRequestIntakeAdapter` would
need to (a) send Zenward-Web's own validated 12-field submission as
Nemryn's flat body shape, with `integrationExternalId` set to the
Zenward-Web pilot integration's own opaque external id (provisioned via
`.tmp-qa/s4b-provision-integration.sh`, NOT a bearer secret) and
`idempotencyKey` set to Zenward-Web's own already-generated `submissionId`
(no change needed there — it is already a stable-across-retries UUID,
exactly matching Nemryn's own idempotency-key requirement); (b) treat
Nemryn's `{ok:true}` as `delivered:true` and, since Nemryn deliberately
returns no `referenceId`, either mint a Zenward-Web-local display reference
the way `StubRequestIntakeAdapter` already does (`ZW-<base36 timestamp>`,
already implemented) or accept that Zenward-Web's copy says "Request
received" without a quotable reference number; (c) point `PLATFORM_INTAKE_URL`
at `https://app.nemryn.com/api/public-intake/website` and drop
`PLATFORM_INTAKE_TOKEN` entirely (Part 5's own contract still forbids any
privileged/shared secret reaching Zenward-Web). This is intentionally a
small, additive change confined to `adapter.ts` — no page, form, or Server
Action in Zenward-Web needs to change, exactly as that repository's own
docs anticipated.
