======================================================================================================================
1. SUMMARY
======================================================================================================================
- The UX can be built with no change to Core and no change to any released Plus RPC.
- It cannot be built safely with the released RPCs alone. Creating a contact and linking it are two separate RPC
  calls (plus_create_contact, then plus_link_request), and PostgREST runs each in its own transaction. Two problems
  follow:
    (a) If the link fails, the new contact is left behind with no link. This happens when someone else links the
        request first, on a stale page, or when access is revoked between the two calls.
    (b) Two submissions at the same time both pass the duplicate check before either commits, so both create a
        contact. No unique constraint exists on plus_contacts, and duplicates are allowed by design (warn, never
        merge).
  The requirement "prevent duplicate creation under concurrent submissions" therefore needs a database change.
- Recommendation: ONE new additive RPC, plus_create_contact_for_request. It runs plus_create_contact and
  plus_link_request, both unchanged, inside one transaction, following the pattern plus_convert_inquiry already uses
  (it calls plus_create_contact unchanged). The primary key of plus_request_attributions (request_id) is what
  serializes concurrent calls. The losing call raises an error, which rolls back its contact as well. No new table,
  column, constraint, index, grant change on existing objects, or Core change.
- Because this is a new migration, it needs a separate owner approval (decision D1) before coding.

2.2 Core request-to-Growth linking (migration 20261015130000_plus_request_attributions.sql)
  - plus_request_attributions: request_id is the PRIMARY KEY, which allows at most one attribution per Request
    (PD-06). It has composite FKs (id, organization_id) to transportation_requests, plus_contacts and
    plus_opportunities. link_method is one of linked_existing_request | converted_from_opportunity | rebooking.
    RLS: SELECT requires plus_can_read AND has_org_role(org, [organization_admin, dispatcher]). No client role can
    insert, update or delete.
  - plus_link_request(org, request, contact, opportunity):
      * Checks _require_plus_write, then _plus_require_core_request_read.
      * Confirms the Request exists in the organization. The Request is read only, never locked.
      * _plus_resolve_attribution requires the contact to be ACTIVE in the same organization. It locks the contact
        FOR SHARE.
      * INSERT ... ON CONFLICT (request_id) DO NOTHING. If the existing link is identical, it returns changed=false.
        If it differs, it raises ZW004 already_attributed.
      * Writes one request_linked activity and one audit row, ids only.
      * It never creates a contact, opportunity, Request, Passenger or Trip.
  - Concurrency is covered by supabase/tests/plus_request_attributions_concurrency_test.sh, scenarios 1 to 6. These
    include a link racing a Core Accept, where both succeed and the Core decision is untouched.

2.3 Plus contact creation (migration 20261014100000_plus_contacts_activities.sql)
  - plus_contacts columns: display_name, phone, email, contact_kind, job_title, preferred_channel, do_not_contact,
    owner_user_id and status. The table has no passenger link and no address, health or trip fields.
      * Phone CHECK: 7 to 20 digits, characters limited to [0-9+(). -], optional extension.
      * Email CHECK: stored lower(btrim()).
      * contact_kind: individual | family_caregiver | facility_staff | referral_source | other.
      * At least one of phone or email is required.
  - plus_create_contact(org, name, phone, email, kind, title, channel, dnc, owner_membership, confirm_dup):
      * Checks _require_plus_write and trims inputs.
      * A failed CHECK becomes ZW006.
      * Duplicate detection uses _plus_contact_matches: same normalized email, same phone digits (7 or more), or same
        name ignoring case. Up to 5 matches are considered, ACTIVE and ARCHIVED alike. If there are matches and
        confirm is not set, NOTHING is written and the call returns contact_id=NULL, possible_duplicates=n.
      * Writes an audit row plus_contact_created with no contact values.
      * It has no idempotency key.
  - plus_find_contact_matches (Plus READ) returns the match list (id, name, status, match_on) for the warning UI.
    ContactForm.tsx already renders this list as "Possible duplicate", with an explicit "create anyway" button.
  - src/lib/plus/contacts-core.ts: validateContactForm, normalizeEmail, phoneDigits, contactErrorMessage. These are
    the existing client and server validation rules. The database CHECKs remain the authority.

2.4 Duplicate matching precedent: plus_convert_inquiry (migration 20261024110000)
  - In a single transaction under the inquiry row lock, plus_convert_inquiry calls plus_create_contact UNCHANGED. A
    possible_duplicates result returns with nothing written, and staff then link an existing contact or confirm.
  - It maps the requester relationship to a contact kind: family / caregiver → family_caregiver, facility_staff →
    facility_staff, other → other, everything else → individual.
  - It is the closest existing pattern for this feature. The proposal reuses its structure but does not create an
    opportunity.

2.5 Entitlement and access (migrations 20261013120000, 20261013160100)
  - plus_can_read:
      * Entitlement write: Organization Admin, or a Dispatcher with an active read or write grant.
      * Entitlement read_only: Organization Admin only.
      * locked / none: nobody.
  - plus_can_write: entitlement write AND (Organization Admin, or a Dispatcher with an active WRITE grant).
  - _require_plus_write:
      * ZW001 when there is no uid.
      * ZW002 when the caller cannot read (no oracle).
      * ZW001 when the caller can read but not write (read_only entitlement, or a read grant).
  - _plus_require_core_request_read: ZW002 unless has_org_role(org, [organization_admin, dispatcher]).
  - plus_access_state / getPlusAccessState feed canOpenGrowth / canWriteGrowth in the UI. These are a mirror for
    display only, not the authorization control.
  - Disabled organization (organizations.status <> 'active'): has_org_role and _plus_member_access already return
    false or none, so every Plus RPC refuses.

2.6 Consent and Do-not-contact (migration 20261023100000_plus_communication_consents.sql)
  - plus_communication_consents is an append-only ledger. Rows are written only by plus_record_consent,
    plus_revoke_consent, the DNC switch in plus_update_contact (ZD-233) and inquiry conversion (web_form evidence).
  - plus_create_contact writes NO consent row, so a new contact resolves to no_consent_on_record.
  - The resolver: do_not_contact=true → suppressed_do_not_contact, which overrides every grant.
  - plus_link_request does not read or change DNC or consent. Linking is not contacting.

2.7 Boundary rules that constrain the design (docs/security/plus-access-model.md §4, §5)
  - "Plus → Core read ... Never: requester phone or email." Plus RPCs must not read transportation_requests.requester_*.
  - "Core → Plus: Nothing." Core code and Core RPCs never read or write Plus tables.
  - "Passenger identity: Plus never matches a contact to a Passenger by name, phone or email."
  - C2 consumer contact data (customer or caregiver name, phone, email) MAY live in plus_contacts, subject to PD-10
    (HIPAA / BAA) and PD-11 (retention / redaction). Both are still open. Every Plus migration header says
    "synthetic data only until PD-10 / PD-11".
  - C5 (pickup, destination, assistance, notes, passenger record) is never copied into Plus.

2.8 Audit pattern
  - audit_events(organization_id, entity_type, entity_id, action, actor_user_id, before_data, after_data). Plus rows
    carry ids, field NAMES and flags only, never contact values.
  - plus_activities is the append-only Growth timeline. request_linked rows carry contact, opportunity and request
    ids, with no body.

2.9 Requester data available on the Core page
  - transportation_requests has the following requester fields:
      * requester_name (not null)
      * requester_phone (not null; free text, with no format CHECK in Core)
      * requester_email (nullable)
      * requester_relationship: self | family | caregiver | facility_coordinator | other. This is the requester's
        relationship TO THE PASSENGER.
      * requester_user_id (portal requesters)
  - Separate passenger fields: passenger_id, requested_passenger_name.
  - Because Core phone values are unvalidated, some Core requester phones will fail the Plus phone CHECK. These must
    be corrected in the form, never silently altered.

3. PROPOSED IMPLEMENTATION (smallest safe change)
======================================================================================================================
3.1 Database: one forward-only, additive migration (requires owner approval D1)
  File: supabase/migrations/2026110x100000_plus_create_contact_for_request.sql. It is timestamped after
  20261029120000, which is the last FIN-P1 / P1G migration on the parked branch (see D6).

  Result type plus_request_contact_result:
    outcome text, one of:
      'linked'               a contact was created and linked
      'possible_duplicates'  nothing written; staff choose an existing contact or confirm
      'already_linked'       the Request already has an attribution; nothing written
    request_id, contact_id, opportunity_id, possible_duplicates integer, updated_at (attribution version token)

  Signature:
    plus_create_contact_for_request(p_organization_id uuid, p_request_id uuid, p_display_name text, p_phone text,
      p_email text, p_contact_kind text, p_preferred_channel text, p_do_not_contact boolean,
      p_owner_membership_id uuid, p_confirm_possible_duplicate boolean)
  - SECURITY DEFINER; set search_path = public, pg_temp.
  - Execute permissions: revoke all from public and anon; grant execute to authenticated only.

  Body (one transaction):
    1. Authorize:
         perform _require_plus_write(org);
         perform _plus_require_core_request_read(org);
    2. Check the Request exists in org: `exists (select 1 from transportation_requests where id and org)`. Unknown or
       foreign → ZW002. The Request is never locked or read beyond its existence.
    3. Check for an existing attribution. If one exists, return outcome='already_linked' with its contact and
       opportunity ids. Nothing is written. The UI re-renders the linked state.
    4. Create the contact: r := plus_create_contact(org, name, phone, email, kind, NULL title, channel, dnc, owner,
       confirm).
         - This is the unchanged released contract: validation, ZW006, duplicate warning, owner eligibility, and the
           plus_contact_created audit.
         - If r.contact_id is null, return outcome='possible_duplicates'. Nothing has been written.
    5. Link: l := plus_link_request(org, request, r.contact_id, NULL). This is also unchanged: it writes the
       request_linked activity and the plus_request_linked audit, and ON CONFLICT (request_id) waits for any
       concurrent attribution insert.
         - If a concurrent caller attributed the Request first with a DIFFERENT contact (always the case here,
           because our contact is new), plus_link_request raises ZW004.
         - That error aborts the whole transaction, so the contact created in step 4 and its audit row roll back.
           No orphaned contact is left and no duplicate exists.
         - l.changed=false is impossible for a just-created contact. Treat it as a defensive ZW004.
    6. Insert one extra audit row: action plus_contact_created_from_request, entity plus_contact. after_data holds
       {request_id} only, so the provenance is auditable without copying values. Alternatively, fold the source into
       step 4's row; see D5.
    7. Return outcome='linked'.

  What the function does not do:
    - It does NOT read requester_* columns. The values come from staff, prefilled in the browser from the Core page
      they are already authorized to see. This keeps the "Plus → Core read: never requester phone or email" rule
      intact (D3).
    - It does NOT create, convert or touch any opportunity, quote, task, consent row, Core Request, Passenger, Trip,
      recurring arrangement, acquisition snapshot or billing row.
    - It writes NO consent row, never sets do_not_contact on its own, and does not infer consent from the request.

  Why no idempotency key: the attribution primary key already provides exactly-once linking per Request.
    - A replay after a commit hits step 3 and returns 'already_linked'.
    - Concurrent submissions are serialized at step 5, and the loser rolls back.
    - This differs from conversion, where a key was needed because each call creates a NEW Request.

3.2 Server action (no migration)
  Add createContactForRequestAction to src/app/operations/growth/attribution/actions.ts.
  - It follows the same guard(organizationId, write=true) path, which checks requirePlusAccess, the organization
    binding and canWriteGrowth.
  - It validates the form with validateContactForm from contacts-core.ts, the same rules as the Growth contact form.
  - It calls the new RPC and maps outcomes:
      linked → success, with the message "Contact added and linked. The request itself is unchanged."
      possible_duplicates → state 'duplicates'. The action then calls plus_find_contact_matches (Plus read) to
        return the up-to-5 matches, showing name, status and match_on only.
      already_linked → an informational message, then refresh.
  - Errors are mapped with contactErrorMessage / attributionErrorMessage.
  - Logs are limited to console.error("[plus] request contact create failed", code). Form values are never logged.
  - It calls refresh(requestId), which reuses the existing revalidatePath calls.
  - It needs a regenerated database.types.ts entry for the new function.

3.5 Rejected alternative: no migration (two RPC calls from the server action)
  - It can leave an orphaned contact when the link fails after the create (concurrent "Link existing", stale page,
    grant revoked between calls).
  - Concurrent double submissions can create two contacts, because duplicate detection only sees committed rows.
    With confirm=true, even sequential double submissions create two.
  - Compensating by archiving the orphan is not safe. Archiving is a visible, audited state change and not a
    rollback, and a hard delete does not exist by design.
  - It fails "prevent duplicate creation under concurrent submissions". It is acceptable only if the owner accepts
    that risk (D1, option B).

5. DATA AND PRIVACY
======================================================================================================================
  - Requester and passenger stay distinct.
      * The new contact is the REQUESTER only.
      * No passenger field is read, prefilled, copied or matched.
      * No link to passengers is created.
      * The "self" relationship maps to contact_kind=individual, but the contact still has no passenger link, and
        Plus continues to see only "passenger linked: yes/no" through plus_get_request_summaries.
  - Validation and normalization: these are the existing plus_contacts CHECKs plus validateContactForm. Email is
    lower-cased and trimmed, and phone duplicate matching uses digits only. The Core phone value is never altered
    silently.
  - Consent and DNC:
      * No consent row is written.
      * The contact starts at no_consent_on_record.
      * do_not_contact defaults to false and is only what staff tick.
      * Linking an existing contact never changes its DNC or consent. A DNC contact in the match list shows its
        "Do not contact" badge, but linking stays allowed, because linking is not contact.
      * The existence of a transportation request is never treated as consent. Form copy must not suggest it.
  - Logs, audit and tests:
      * audit_events rows carry ids and counts only.
      * Server logs carry error codes only.
      * E2E and SQL tests use fictional names, the 555-01xx phone range and example.invalid email addresses.
      * Screenshots come from the isolated stack only.
      * .tmp-qa scripts must not print contact values.
  - Real data (D7): this flow copies a real requester's name, phone and email into Plus for any tenant with Plus
    write. PD-10 / PD-11 are still open, and Plus has so far been "synthetic data only". Approving the UX is not the
    same as approving real C2 data in Plus.
