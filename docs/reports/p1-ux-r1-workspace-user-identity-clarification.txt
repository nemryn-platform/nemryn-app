1. ORIGINAL CAUSE OF CONFUSION
-------------------------------
Two separate defects, both traced by direct code reading (not guessed):

(a) OperationsSidebar.tsx bottom rail rendered two stacked rows:
      Row 1 (workspace): {location}          → "Fictional Org A"
                          {orgUnit}           → "Organization Admin"
      Row 2 (user):       {dispatcherName}    → "Victor"
                          {dispatcherRole}    → "Organization Admin"
    `orgUnit` was populated by the caller (OperationsLayoutClient) as
    `ROLE_LABEL[organization.role]` — the signed-in user's OWN membership
    role, attached directly beneath the organization's name. This made
    the organization name and the user's name look like two peer
    identities of the same kind ("Org / Role" then "Person / Role"),
    each with its own role — nothing distinguished "this is the tenant"
    from "this is the account."

(b) AccountMenu.tsx's popup never rendered the signed-in user's own name
    anywhere. `avatarName` was used only to compute the Avatar's initials
    and to build the trigger button's `aria-label` — never as visible
    popup text. The popup's visible body opened with `{organizationName}`
    then `{roleLabel}`, i.e. it headlined with the ORGANIZATION, making
    the personal-account menu read as if clicking the avatar opened a
    second organization's own settings, not "your account."

Root cause in both cases: the membership role (a fact about the PERSON,
scoped to the CURRENT organization) was being rendered as if it were a
property of the ORGANIZATION itself, and the organization's own name was
being used as the headline of what is supposed to be a personal menu.


2. FINAL SEMANTIC HIERARCHY
-----------------------------
    PLATFORM   Nemryn                     — logo/wordmark, top of sidebar (unchanged)
    WORKSPACE  {organization.organizationName}   — sidebar bottom rail, labeled "Workspace"
    USER       {dispatcherDisplayName}, {roleLabel} — sidebar bottom rail (user row) AND
                                                        AccountMenu popup headline

The organization name is never again paired with a role. The role
appears in exactly one place per surface: once in the sidebar's user
row, once in the AccountMenu popup — always attached to the PERSON.

5. ACCOUNT MENU — BEFORE / AFTER
-----------------------------------
BEFORE (popup body, headlined by the organization):
  Fictional Org A
  Organization Admin
  ------------------
  Switch Organization
  Sign Out

AFTER (popup body, headlined by the signed-in person):
  Victor                                <- avatarName, the PERSON
  Organization Admin                    <- roleLabel (role of the person, in this org)
  victor@example.test                   <- dispatcherEmail, ONLY when distinct from
                                            the name line above (see dedup note)
  ------------------                    <- existing border-b divider = ACCOUNT/WORKSPACE seam
  Switch Organization
  Sign Out

`organizationName` is no longer rendered anywhere in the popup's visible
body. It remains used exactly once, in the trigger button's own
`aria-label` ("Account menu — {avatarName}, {roleLabel} at
{organizationName}") for screen-reader context — an aria-label
announcement does not create the same "two organizations" visual
ambiguity a rendered heading would, and removing it would discard real
accessibility context for no visual benefit.

Dedup guard (found via live testing, not assumed): `getDisplayName()`'s
own established fallback returns the raw email when no
`user_profiles.display_name` row exists yet. For fixtures with no real
display name set (org-a-admin@example.test, org-a-dispatcher@example.test,
multi-org-user@example.test — all confirmed NULL via direct query), the
name line and the email line would otherwise be byte-identical, rendering
the same string twice in a 2-line-tall popup. Fixed with:
  {dispatcherEmail && dispatcherEmail !== avatarName && (...)}
so the email line only renders when it is genuinely new information.
Confirmed both branches live — see §8.

7. ICON DECISION
-------------------
Replaced `MapPin` (a location-pin icon, semantically wrong for "this is
your organization/tenant") with `Buildings`
(@phosphor-icons/react/dist/ssr) in the sidebar's workspace row. This is
NOT a new icon: `Buildings` is already the established convention this
codebase uses for the organization/workspace concept elsewhere — it is
literally what OrganizationSelector.tsx already renders as the avatar
icon on /select-organization's own workspace cards (confirmed visually —
see the uxr1-B-multi-org-user.png screenshot, which shows the same
Buildings icon next to "Fictional Org A" / "Fictional Org B"). No new
icon package installed; @phosphor-icons/react was already a project
dependency.
