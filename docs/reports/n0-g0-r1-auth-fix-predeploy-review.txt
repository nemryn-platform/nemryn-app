4. AUTH CALLBACK REVIEW  (src/app/auth/confirm/route.ts)
====================================================================

Full implementation (32 executable lines): a single GET Route Handler.

  const { searchParams } = new URL(request.url);
  const tokenHash = searchParams.get("token_hash");
  const type = searchParams.get("type") as EmailOtpType | null;
  const requestUrl = request.url;

  if (tokenHash && type) {
    const supabase = await createServerSupabaseClient();
    const { error } = await supabase.auth.verifyOtp({ type, token_hash: tokenHash });
    if (!error) {
      return NextResponse.redirect(new URL("/complete-signup", requestUrl));
    }
  }
  return NextResponse.redirect(new URL("/auth/auth-code-error", requestUrl));

Checklist (§3 of the phase brief):

 1. token_hash validated before use — YES. Falsy token_hash short-circuits to the
    error redirect; a non-empty-but-bogus value is rejected by verifyOtp() itself
    server-side (verified live: token_hash=bogus123 -> /auth/auth-code-error).

 2. type validated appropriately — PARTIAL BY DESIGN, ACCEPTABLE. `type` is cast to
    EmailOtpType and passed straight to verifyOtp(); an invalid value is rejected by
    Supabase server-side (verified live: type=../../etc -> /auth/auth-code-error). This
    matches Supabase's own canonical Next.js SSR example. `type` is never used to build
    a path, a redirect, a log line, or a query — so an unvalidated value has no blast
    radius beyond "verifyOtp returns an error". No open surface.

 3. verifyOtp() executes server-side — YES. Called on createServerSupabaseClient()
    (a @supabase/ssr server client, publishable key, cookie-store bound). Verified
    live: after one /auth/confirm hit the user's auth.users.email_confirmed_at was
    populated in the database.

 4. Successful verification establishes the session correctly — YES. Verified live:
    the 307 success response carried Set-Cookie: sb-<ref>-auth-token=... (the real
    Supabase session cookie), and a follow-up request bearing that cookie was treated
    as fully authenticated by /complete-signup.

 5. Session cookies written through the established SSR adapter — YES. verifyOtp()'s
    cookie writes go through createServerSupabaseClient()'s setAll() -> Next.js
    cookies() store — the exact same adapter every Server Action in this codebase
    already uses. A Route Handler is a write-permitted cookie context, so the
    adapter's Server-Component no-op guard does not apply here.

 6. Failure cannot expose secrets — YES. On any failure the response is an
    unconditional redirect to a fixed internal path. No Supabase error object, message,
    status, stack, token_hash, or type value is ever placed in the response body,
    headers, or redirect URL. Verified live: the failure Location is exactly
    "<origin>/auth/auth-code-error" with no query string.

 7. Failure redirects to a safe application route — YES: /auth/auth-code-error, a
    static in-app page (HTTP 200, brand-consistent, "sign in" / "create account again"
    links only).

 8. No open redirect possible — YES. There is no code path in which any request-
    supplied value reaches a redirect target. Both destinations are string literals
    ("/complete-signup", "/auth/auth-code-error"). Verified live: appending
    &next=https://evil.example.com and &redirect_to=https://evil.example.com is
    silently ignored — the response still redirects to the fixed internal route.

 9. No arbitrary external URL trusted — YES. `new URL(path, requestUrl)` resolves a
    relative literal path against the app's own incoming request origin only. No
    external host is ever constructed or trusted.

10. Continuation route is valid — YES. /complete-signup is a built route (confirmed in
    the production build manifest) and is idempotent (ZD-201).

11. Operator signup flows correctly into /complete-signup -> /onboarding — YES,
    verified live (§5).

12. Driver-invite signup keeps its invite context — YES, verified live (§6). The
    context lives in auth.users.raw_user_meta_data (pending_driver_invite_token),
    written by joinSignUpAction at signUp() time and read by /complete-signup — it
    survives the confirmation boundary untouched. /auth/confirm neither reads nor needs
    it.

13. Duplicate callback invocation is safe — YES, verified live. Supabase OTP tokens are
    single-use: a second /auth/confirm with the same token_hash returns a verifyOtp
    error and redirects to /auth/auth-code-error. No second session is minted, and
    /complete-signup is never reached a second time from a stale link.

14. Refresh/retry does not create duplicate Organizations / Memberships / UserProfiles
    — YES, verified live. Idempotency is enforced downstream in /complete-signup +
    complete_pending_signup() / redeem_driver_invite() (pg_advisory_xact_lock keyed on
    auth.uid(), plus existing-Membership no-op). Operator path: 4 concurrent
    /complete-signup calls -> exactly 1 org / 1 membership / 1 user_profile. Driver
    path: 3 calls -> exactly 1 membership / 1 driver / 1 user_profile.

15. No service-role credential introduced — YES. The route uses only
    createServerSupabaseClient() (publishable key + the caller's own cookie session).
    grep confirms no SUPABASE_SERVICE_ROLE / service_role / SECRET_KEY reference in
    the new files.

Design notes worth carrying into the deploy review:

  * The route builds its redirect from request.url, whereas the sibling
    /complete-signup route uses request.nextUrl.origin. The difference is
    deliberate and documented (ZD-203): request.nextUrl.origin can be
    normalised by the Turbopack dev server to a different host than the
    one that received the request, which locally discards the just-set
    cookie. On the single-canonical-host production deployment both
    expressions resolve to https://app.zenwardmobility.com, so this is a
    local-only concern with no production effect.

  * A Route Handler (not a Server Component page) is used because a
    Server Component redirect issued after an internal await was
    observed to be silently dropped by the browser under chained
    navigation (ZD-200). NextResponse.redirect returns a real HTTP 307
    with a Location header — verified live.

Current problematic behaviour:
  The default template links via {{ .ConfirmationURL }}, which points at
  Supabase's own hosted endpoint
    https://<project>.supabase.co/auth/v1/verify?token=...&type=signup&redirect_to=<Site URL>
  That endpoint verifies the token and then redirects the browser to
  Site URL with the new session in a URL FRAGMENT
  (#access_token=...&refresh_token=...). A fragment is never transmitted
  to any server; this app has no client-side JavaScript that reads
  window.location.hash, so the session is silently discarded and the
  person lands unauthenticated. (Root cause confirmed by the prior phase
  by following the real link with curl and reading its Location header;
  independently re-confirmed in this review — the admin generate_link
  API's own action_link for a signup is the /auth/v1/verify?...redirect_to=
  shape.)
