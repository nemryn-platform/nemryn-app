INTEGRATION STRATEGY
=======================
Audited current source fresh before writing anything: `src/app/
operations/page.tsx`, `OperationsBrief.tsx`, `operations-brief-core.ts`,
`operations-brief.ts`, the existing `operations-brief-core.test.mjs`
suite, and both Recurring Care read-model files (`recurring-care.ts`,
`recurring-care-list.ts`). Found the EXACT precedent to mirror already
established by Tomorrow Readiness (P1-E1-S4E): a compact summary type
(`OperationsBriefTomorrowSummary`) added to the pure core, a narrow
server-only summary function (`getTomorrowReadinessSummary`) that reuses
an already-authoritative larger read model and discards detail, and an
independent best-effort promise in `getOperationsBrief`/`page.tsx`
(started before the existing `Promise.all`, caught separately so a
failure degrades only its own block). Recurring Care Brief integration
follows this same shape in every particular — `OperationsBriefRecurring
CareSummary`, `getRecurringCareSummary`, and a `recurringCarePromise`
mirroring `tomorrowReadinessPromise` line-for-line. No new architecture
was introduced; Overview itself was not redesigned.


DOMAIN OWNERSHIP
===================
The new block answers exactly one question: "Which expected recurring
occurrences do not yet have qualifying Trips?" Confirmed by direct
inspection of every string this phase's own code renders: it never
mentions Trip Readiness reasons, open Trip exceptions, Driver/Vehicle
inactivity, or today's execution problems — all already owned by Needs
Attention, Tomorrow Readiness, and Driver Snapshot respectively. No
duplicate warning is ever shown for the same underlying fact.


SUMMARY CONTRACT
===================
```
export interface OperationsBriefRecurringCareSummary {
  activeArrangementCount: number;
  missingOccurrenceCount: number;
  arrangementsWithMissingCount: number;
  nextMissingDate: string | null;
}
```
Exactly the 4 recommended fields, nothing more — no occurrence list, no
Passenger list, no score, no percentage, no adherence metric (confirmed
by direct inspection of the type and every consumer of it).


DATA AUTHORITY
=================
Zero recurrence/date/weekday/timezone logic was added anywhere in this
phase. `getRecurringCareSummary` (operations-brief.ts) calls
`getRecurringArrangementsList` (recurring-care-list.ts) — the SAME
2-round-trip read model `/operations/recurring-care` itself renders from,
which itself composes the unmodified S1C evaluator
(`deriveRecurringCareAssurance`, recurring-care-core.ts) — then reduces
the result via a new PURE function, `deriveRecurringCareSummary`
(operations-brief-core.ts). This pure function performs aggregation only
(filter-by-status, sum, count, earliest-date) — every date/weekday/
timezone/skip/readiness/cancellation rule that produced each row's own
`missingCount`/`nextMissingDate` already ran inside the S1C evaluator
before this function ever sees a row. No second weekday/date evaluator,
no duplicate timezone arithmetic anywhere in this phase's own code
(confirmed: `operations-brief-core.ts` still has zero runtime imports of
any kind, per its own long-standing header charter, extended, not
violated, by this phase).


ZERO ARRANGEMENTS
====================
`activeArrangementCount === 0` renders the restrained discovery state
exactly as specified: "Recurring care" (fixed heading) / "No recurring
transportation set up" / "Set up recurring care" → `/operations/
recurring-care`. Never framed as an error or warning. Live-verified: no
"0 missing"/"0 scheduled" number ever appears in this state (a direct
regex check against the full page text confirmed no such string exists).


ALL COVERED
=============
`activeArrangementCount > 0 && missingOccurrenceCount === 0` renders
"Recurring care is covered" / "All expected rides in the next 14 days
have trips scheduled." — deliberately never "will run successfully,"
since Trip Readiness/execution are separate concerns this block does not
speak to (confirmed absent from every rendered string). Live-verified
with a real Wednesday-only arrangement whose both near-horizon pattern
dates were covered by real Trips created through the actual
`create_trip_for_recurring_occurrence` RPC.


MISSING OCCURRENCES
======================
`missingOccurrenceCount > 0` renders factual planning language exactly
matching the phase's own examples: singular "1 recurring ride needs
scheduling" (live-verified, exact string match) and plural "N recurring
rides need scheduling" (live-verified with a real 14-missing-occurrence
daily arrangement, N=14). "Across M arrangement(s)" renders with correct
singular/plural, and "· Next gap: <date>" renders only when a
`nextMissingDate` exists. No occurrence or Passenger is ever listed in
this block — confirmed by direct inspection: the component renders only
the 4 summary numbers/derived strings, nothing per-occurrence.


SKIPPED BEHAVIOR
===================
Live-verified: an arrangement with one pattern date deliberately skipped
and its other pattern date covered by a real Trip shows "Recurring care
is covered" (0 missing) — the SKIPPED date never contributes to
`missingOccurrenceCount`, because the S1C evaluator's own
`expectedCount = patternDateCount - skippedCount` already excludes it
upstream, and this phase's own aggregation performs no re-derivation of
that rule (`deriveRecurringCareSummary`'s own unit tests independently
confirm this pass-through contract too — see TEST RESULTS).


SCHEDULED-BUT-NOT-READY BOUNDARY
====================================
Live-verified with a real Trip created for BOTH of a Wednesday-only
arrangement's pattern dates, deliberately left with no Driver/Vehicle
assignment: the Operations Brief shows "Recurring care is covered" (0
missing), while the SAME arrangement's own detail page independently
confirms the linked Trip genuinely shows "Needs preparation" — proving
the underlying NEEDS_PREPARATION fact is real (not merely absent from
the Brief) and that Recurring Care Brief correctly does NOT double-count
it as missing. This is treated as a hard semantic boundary, exactly as
specified — Tomorrow Readiness/Trip Readiness own preparation, Recurring
Care Brief never does.


CANCELLED TRIP BEHAVIOR
==========================
Live-verified: an arrangement with one pattern date's only linked Trip

recurring ride needs scheduling" — the cancelled-only date correctly
counts as missing, entirely because the S1C evaluator's own
`qualifyingTripsFor` rule (a cancelled Trip never satisfies an occurrence)
already decided this upstream. Zero cancellation-specific code exists
anywhere in this phase's own new files — confirmed by direct inspection.

QUERY EFFICIENCY
===================
Zero new queries were written. `getRecurringCareSummary` calls
`getRecurringArrangementsList` exactly once — the SAME already-bounded,
already-documented 2-round-trip read model (1 direct arrangement query
+ `getRecurringCareAssurance`'s own already-bounded 4 queries, run
concurrently via `Promise.all` inside that existing function) the
Recurring Care workspace itself uses. No query per arrangement, no
second database query architecture. Per §16's own explicit instruction,
loading each active arrangement's full assurance object (its complete
14-date occurrence list) and discarding the detail in a thin summary
wrapper — rather than building a leaner, dedicated aggregate query — was
the deliberate, accepted tradeoff; this phase's own `getRecurringCare
Summary` is exactly that discarding step and nothing more. Live-verified
at 20+ real arrangements: the Overview page loaded normally with no
observable N+1 behavior (a single Brief render, no per-row fetch).


ERROR ISOLATION
==================
`getRecurringCareSummary(...).catch(() => null)` is started as its own
independent promise BEFORE the existing `Promise.all` (mirroring
`tomorrowReadinessPromise`'s own exact position and shape), so it
overlaps in wall-clock time with the other fetches but is caught
completely independently. Live-verified via genuine fault injection (not
simulated): `revoke select on public.recurring_arrangements from
authenticated;` was run directly against the local database, the
Overview page was loaded, and:
  - The Recurring Care block alone showed "Recurring care unavailable."
  - It did NOT fall back to "No recurring transportation," "Recurring
    care is covered," or any 0-count — confirmed by direct string
    absence checks, not merely visual inspection.
  - Needs Attention, Driver Snapshot, Requests awaiting review, and
    Tomorrow readiness all continued to render their own real data —
    the whole Overview page remained fully usable.
The grant was then restored (`grant select on public.recurring_
arrangements to authenticated;`) and the page was reloaded, confirming
the Recurring Care block returned to normal rendering. This was the
ONLY fault injection performed in this phase, and it was fully reversed
immediately after — no permanent schema/grant change resulted (re-
confirmed via the `database.types.ts` zero-diff check above, and via a
fresh `supabase db reset` at the end of this phase's own validation).
