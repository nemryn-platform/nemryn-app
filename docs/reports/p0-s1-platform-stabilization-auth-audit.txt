3. AUTH ARCHITECTURE
====================================================================

- `getUser()` (`src/lib/auth/session.ts`) calls `supabase.auth.getUser()`
  — which re-validates the token against the Auth server — NOT
  `getSession()`, which only decodes the local JWT. This is the secure
  choice and is used consistently.
- `requireUser()` redirects to `/sign-in?next=...` (validated by
  `isSafeRedirectPath`/`safeRedirectPath`, an allowlist — not a
  denylist — that rejects protocol-relative URLs, absolute URLs of any
  scheme, backslashes, and any colon at all; see `src/lib/auth/
  redirect.ts`).
- `getActiveMemberships()` queries `memberships` filtered by
  `.eq("user_id", user.id)` AND `.eq("status", "active")` — the
  `user_id` filter is explicitly commented as load-bearing (not merely
  defensive) because `memberships` also carries an ADDITIVE org-admin
  "see my team" SELECT policy; omitting the filter would silently widen
  results for an org_admin caller. This is a genuinely subtle, correctly
  handled case.
- `resolveOrganizationContext()` (`src/lib/auth/organization.ts`): 0
  active memberships → `none`; 1 → auto-selected; >1 → requires the
  `zw_org_context` cookie to match one of the caller's OWN live
  memberships, else `select-required`. The cookie is re-validated
  against a fresh `getActiveMemberships()` call every time — a value
  that doesn't match is treated exactly like no cookie, never a foreign-
  tenant grant.
- Route guards (`requireOperationsAccess`, `requireOnboardingAccess`,
  `requireDriverAccess`) all: require a user → resolve org context →
  redirect `none` to `/complete-signup` → redirect `select-required` to
  `/select-organization` → check role for THAT resolved organization
  only. `requireDriverAccess` additionally calls the real
  `driver_get_profile` RPC (never infers driver identity from
  `Membership.role` alone) and returns a discriminated `link-missing`
  state instead of redirect-looping.
- Auth error vocabulary (`src/lib/auth/errors.ts`): a small, stable,
  named set; `INVALID_CREDENTIALS` deliberately never distinguishes "no
  such account" from "wrong password."

4. SIGN-IN AUDIT
====================================================================

- Form → `signInAction` (Server Action) → `supabase.auth.
  signInWithPassword({ email, password })` (real Supabase Auth call,
  confirmed by reading the action).
- Failure → generic `AUTH_ERROR.INVALID_CREDENTIALS` message; the raw
  Supabase error is discarded, never shown.
- Success → `redirect(safeRedirectPath(nextRaw, "/"))`. `/` resolves the
  real destination (role/org context) rather than duplicating that
  resolution in the sign-in action itself.
- Already-authenticated visitors hitting `/sign-in` are redirected to
  `/` immediately (checked in `page.tsx` before rendering the form).
- Tenant/workspace membership resolution happens downstream at `/`
  (`resolveOrganizationContext`), not inside `signInAction` — deliberate,
  documented design: a session can also be established WITHOUT ever
  submitting this form (the email-confirmation-link path), so the
  continuation logic lives at the one place ALL authenticated traffic
  passes through.

9. SESSION AUDIT
====================================================================

- Session cookie management goes through `@supabase/ssr`'s standard
  cookie adapter in three places (`server.ts`, `proxy.ts`, and the
  browser client relies on the same underlying storage) — not
  hand-rolled.
- `src/proxy.ts` → `updateSession()` runs on every non-static request
  (matcher excludes `_next/static`, `_next/image`, favicon, and image
  extensions) and calls `supabase.auth.getUser()` to trigger a refresh
  if the session is near expiry — this is what makes a browser refresh /
  new tab / direct protected-route navigation continue to see a valid
  session without every layout re-deriving it from scratch.
- Direct protected-route navigation: enforced server-side (§3) — a
  request that never touches `/sign-in` at all (e.g. a bookmarked
  `/operations/drivers`) still passes through `requireOperationsAccess`
  before any content renders.
- Expired/invalid session: `getUser()` re-validates against the Auth
  server every call; an expired/invalid token resolves to `user = null`,
  and every guard treats that as "not authenticated" → redirect to
  `/sign-in?next=...`.
- The `zw_org_context` cookie itself carries no authority — it is a
  REQUESTED selector only, re-validated against a live membership query
  every time it's read (§3); a tampered/stale value degrades to "no
  cookie," never a foreign-tenant grant.

VERDICT: PASS (by code inspection; not independently re-run as a live
browser session test this phase — the mechanism was exhaustively live-
tested in the P1-E3-S1/P1-E4-S0A2 phases and is unchanged since).

Full lifecycle trace (STEP 3, items 1-13):

 1. UI ACTION — `InviteDriverDialog` (`src/components/operations/
    drivers/InviteDriverDialog.tsx`): a form (fullName/email/phone)
    inside a Server-Action-backed dialog on `/operations/drivers`.
 2. CLIENT REQUEST — a React `useActionState` submit to a Server Action
    — no separate API route; Next.js Server Actions serialize the form
    POST directly.
 3. SERVER/API ACTION — `createDriverInviteAction`
    (`src/app/operations/drivers/actions.ts`).
 4. DATABASE WRITES — the action calls RPC `create_driver_invite`
    (`supabase/migrations/20260903100200_driver_invites.sql`), which
    locks any existing PENDING row for (organization, lower(email))
    `FOR UPDATE`; refreshes it if present, else INSERTs a new
    `driver_invites` row plus one `audit_events` row.
 5. SUPABASE AUTH/ADMIN INVITATION CALL — NONE. This design deliberately
    never calls `supabase.auth.admin.inviteUserByEmail()` or creates an
    auth user on the admin's behalf — the invitee signs up themselves
    through ordinary `supabase.auth.signUp()`. This is a correct
    architectural choice (no admin-created credentials, no orphaned
    auth users on partial failure), NOT the defect.
 6. EMAIL PROVIDER/TEMPLATE PATH (CATEGORY D) — **this was the defect.**
    Before the fix present in the working tree: `create_driver_invite`
    returns `(invite_id, token, email, status, reused)`; the CALLING

    in the request path. No email infrastructure of any kind exists in
    the committed codebase (confirmed again this phase: `grep -rniE
    "resend|postmark|sendgrid|nodemailer|ses|smtp|mailgun|sendEmail" src
    supabase` → zero matches outside comments and the commented-out
    `[auth.email.smtp]` block in `supabase/config.toml`; `package.json`
    has no email dependency). Despite this, the dialog's own success
    state was titled "Invite sent" — a false positive result reported to
    the operator.
 7. REDIRECT URL — none was ever generated (the token was discarded, so
    no `/join/<token>` link could be built or sent).
 8. INVITE TOKEN HANDLING — generated correctly at the database level
    (`driver_invites.token uuid default gen_random_uuid()`, 122-bit,
    unique-indexed) but never left the database/RPC-result boundary.
 9. ACCEPTANCE ROUTE — `/join/[token]` exists and works correctly
    (previews via the anon-callable, token-gated `get_driver_invite_
    preview` RPC) — this part of the lifecycle was already proven
    working in an earlier phase, PROVIDED the invitee somehow obtained
    the link out-of-band (the admin copy-pasting it manually — except
    the action never even returned the token to the browser, so not even
    that manual workaround was available through the UI).
 10. DRIVER-USER RECORD CREATION — `redeem_driver_invite` (SECURITY
     DEFINER) creates the Driver row atomically, using the INVITE's own
     admin-specified display_name/phone. Unaffected by the email defect;
     confirmed working via `operator_onboarding_tests.sql` REDEEM-1..5
     and a live end-to-end test in a prior session.
 11. ORGANIZATION MEMBERSHIP ASSIGNMENT — same RPC, same transaction;
     `redeem_driver_invite` takes NO `organization_id` parameter at all
     — the organization is resolved entirely from the invite row itself,
     making cross-org redemption structurally unexpressible. Unaffected.
 12. ROLE ASSIGNMENT — Membership role hardcoded to `'driver'` inside the
     RPC, never client-supplied. Unaffected.
 13. INVITATION STATUS UPDATE — `status: 'pending' → 'accepted'` inside

14. TENANCY / WORKSPACE RESOLUTION
====================================================================

How does the application determine which organization a logged-in user
belongs to?
  Live database query only: `getActiveMemberships()` selects
  `memberships` filtered by the caller's own `auth.uid()` (via RLS's
  `memberships_select_self` policy AND an explicit application-layer
  `user_id` filter — see §3) AND `status = 'active'`. Zero memberships →
  no organization. One → auto-selected. More than one → the
  `zw_org_context` cookie, itself re-validated against this same live
  query on every read, picks which.

How is that organization context applied to reads/writes?
  Every mutation-relevant Server Action re-derives the organization from
  the SERVER-resolved context object (`OrganizationContext.organizationId`,
  produced by `resolveOrganizationContext()`), never from a client-
  supplied field used for authorization. The organization_id passed into
  RPCs like `create_driver_invite`, `signup_create_organization`, etc.
  originates from this server-side value. Independently, every RLS
  policy re-derives authorization from `has_org_role(organization_id,
  roles)`/`is_org_member(id)`, which themselves resolve from
  `auth.uid()` against a LIVE `memberships` row — so even if a Server
  Action were ever compromised or a raw REST/RPC call were made with a
  forged `organization_id`, the database layer independently denies it
  (confirmed live this phase — see §17 item 2).

Can users belong to multiple organizations?
  Yes — modeled directly (`memberships` has no uniqueness constraint on
  `user_id` alone). Confirmed by the seed fixture `multi-org-user@
  example.test` (organization_admin in Org A, driver in Org B) and by
  `rls_adversarial_tests.sql` TEST P, which explicitly asserts the
  STRONGEST role is NOT inherited globally across a multi-org user's
  memberships.

Is organization context client-supplied anywhere it should not be?
  No instance found. Every RPC that accepts an `organization_id`
  parameter (`create_driver_invite`, `revoke_driver_invite`,
  `signup_create_organization`-adjacent calls, etc.) independently
  re-validates the caller's live membership/role for THAT id inside the
  function body — a client supplying a foreign org's id gets `ZW002`/
  `not_found`, never silent success. `redeem_driver_invite` goes
  further and accepts NO organization_id parameter at all — the org is
  resolved entirely from the invite row, so cross-org redemption is not
  merely denied, it is not expressible as an input.

DECISION: CONDITIONAL GO

The foundation this audit was asked to validate — auth, RLS, tenant
isolation, protected routes, and the core mutation/authorization
surface — is stable: 317/317 SQL assertions + 2/2 concurrency tests +

anywhere in the codebase. Nothing found in this audit would be made
worse, better, or different by a visual/brand rebrand — the rebrand (per
the existing `docs/brand/nemryn/10-brand-implementation-boundaries.md`
rules, already in this repo) is explicitly token/copy/asset work that
does not touch schema, RLS, or tenancy, and this audit found no reason
to doubt that boundary is safe to rely on.

The CONDITION: the two P1/P2 findings above (driver invitation email,
password reset) are real user-facing gaps that should be closed — or at
minimum, explicitly, consciously accepted as known-and-deferred by
whoever authorizes the rebrand — before or shortly after rebrand work
begins. Neither blocks the rebrand technically (they are unrelated
surfaces: email delivery and account recovery, not the visual/brand
layer), but shipping a rebrand while a known, already-diagnosed,
already-half-fixed defect (driver invitations) sits uncommitted would be
an avoidable inconsistency to carry forward.
