2. EXACT RESET PASSWORD TEMPLATE
====================================================================

**Subject** (verbatim, from `supabase/config.toml` line 288):

  Reset your Zenward password

**Template body** (verbatim, from `supabase/templates/recovery.html`,
the exact file `[auth.email.template.recovery]`'s `content_path`
points at):

```html
<h2>Reset your password</h2>

<p>Follow this link to reset your Zenward Mobility password:</p>
<p><a href="{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=recovery">Reset your password</a></p>
<p>If you didn't request this, you can safely ignore this email — your password will not be changed.</p>
```

**Variables used:**

  - `{{ .RedirectTo }}` — the origin, resolved from whatever
    `redirectTo` value the application passed to
    `resetPasswordForEmail()`. In this application that is always
    `` `${origin}/auth/confirm` ``, where `origin` comes from
    `getAppOrigin()` (`src/lib/app-url.ts`) —
    i.e. `NEXT_PUBLIC_APP_URL`, normalized. **Not** Supabase's own
    separately-configured "Site URL" setting — that is the one
    deliberate difference from the Confirm Signup template (§3 below).
  - `{{ .TokenHash }}` — the hashed one-time recovery token, populated
    by Supabase specifically for this template field.
  - The literal, hard-coded `type=recovery` query parameter — this
    tells `/auth/confirm/route.ts` which branch to take (the confirm
    route also handles `type=signup`, for the Confirm Signup template);
    it is not a Supabase template variable, it is fixed text this
    application's own route requires.

**Expected resulting URL structure**, once deployed with `EMAIL_FROM`/
`NEXT_PUBLIC_APP_URL` correctly configured and the template above
applied:

  https://app.zenwardmobility.com/auth/confirm?token_hash=<hashed-token>&type=recovery

That URL is a GET request to this application's own Route Handler
(`src/app/auth/confirm/route.ts`), NOT to any Supabase-hosted endpoint.
The handler calls `supabase.auth.verifyOtp({ type: "recovery",
token_hash })` server-side, and on success:

  1. sets a short-lived, non-credential marker cookie
     (`zw-recovery-pending`, 10-minute lifetime — see
     `src/lib/auth/recovery.ts`), and
  2. issues a 307 redirect to `https://app.zenwardmobility.com/auth/reset-password`,

where the person sets a new password (`docs/product/
password-recovery-model.md` §2 has the complete step-by-step).

**Why the standard/default Supabase template is insufficient for this
application (the exact, verified mechanism, not a general claim):**

Supabase's DEFAULT "Reset Password" template links via
`{{ .ConfirmationURL }}`. That variable resolves to Supabase's own
HOSTED verification endpoint:

  https://<project-ref>.supabase.co/auth/v1/verify?token=<token>&type=recovery&redirect_to=<Site URL or provided redirectTo>

Following that link, Supabase's own server verifies the token and then
redirects the browser to the target URL with the new session encoded
as a URL **fragment** — `#access_token=...&refresh_token=...&
type=recovery`. A URL fragment is **never transmitted to any server**
by design (it's a browser-only addressing mechanism) — only
client-side JavaScript running in that exact page can read
`window.location.hash`. This application's landing pages
(`/auth/reset-password` included) are React Server Components; a
Server Component has no access to the browser's URL fragment at
render time, so it would see no session at all — the person would
land on an unauthenticated page and the click would silently appear to
do nothing.

This is EXACTLY the same root cause `docs/deployment/
staging-auth-configuration.md` already documented and fixed for
`type=signup` in P1-E4-S0A2 (proven at the time by following the
default confirmation link with `curl` and reading its `Location`
header) — P0-S2B's Reset Password template applies the identical fix
for `type=recovery`: link directly to this application's own
`/auth/confirm` with `token_hash`/`type` as ordinary, server-readable
QUERY parameters (never a fragment), so the server-side `verifyOtp()`
call can actually see the token and establish the session by writing a
real cookie before ever redirecting anywhere.

**Not to be changed in production by this phase.** The human applies
this exact template manually via the Dashboard, after review — see the
checklist in §9.

7. RECOMMENDED NEMRYN/RESEND SMTP CONFIGURATION
====================================================================

**Goal:** every Supabase Auth-managed email (signup confirmation,
password recovery — the only two this application currently triggers)
sends through Nemryn's own verified `nemryn.com` domain via Resend,
presenting the identical commercial identity the driver-invitation
email already uses: `Nemryn <notifications@nemryn.com>`.

**Mechanism: Resend's SMTP relay**, configured in the Supabase
Dashboard (Authentication → Emails → SMTP Settings), NOT a code
change — Supabase Auth's SMTP integration is a pure Dashboard
credential/host configuration; this application's own code has no
hook into it and needs none:

  | Field | Value |
  |---|---|
  | Enable Custom SMTP | ON |
  | Sender email | `notifications@nemryn.com` |
  | Sender name | `Nemryn` |
  | Host | `smtp.resend.com` |
  | Port | `587` (STARTTLS) or `465` (implicit TLS) — either is a standard Resend-documented option; port 587 is the more commonly recommended default |
  | Username | `resend` (Resend's own fixed SMTP username — not a secret, this literal value is correct for every Resend account) |
  | Password | a Resend API key, generated for this exact purpose (see below) — the SECRET value; never printed in this report or any document |
  | Minimum interval between emails | Supabase's own separate "SMTP rate limit" field, distinct from `auth.rate_limit.email_sent` — set per the human's own judgment/Resend account limits, not prescribed here |

**On the API key specifically — a security recommendation, not a hard
technical requirement:** generate a SEPARATE Resend API key for this
SMTP integration, distinct from the application's own `RESEND_API_KEY`
(the one `src/lib/email/send.ts` uses for driver-invitation email,
configured as a Vercel environment variable). Reasons:

  - Independent revocation/rotation — a compromise or needed rotation
    of one credential never requires touching the other.
  - Independent scoping/monitoring in the Resend dashboard — Resend's
    own per-key sending logs and permissions become meaningful
    boundaries between "application-triggered transactional email" and
    "Supabase-Auth-triggered account-security email" if they are
    already separate credentials, not just separate code paths.
  - This mirrors the work item's own explicit instruction not to reuse
    the application's `RESEND_API_KEY` in browser code — extended here
    to "don't reuse it across trust boundaries at all," which is the
    stricter and safer reading, though the work item's literal text
    only prohibits the browser-code case (which was already
    structurally impossible — `RESEND_API_KEY` has never been
    `NEXT_PUBLIC_`-prefixed and is read only in a `server-only`
    module).

Neither the existing application `RESEND_API_KEY` nor this new
Supabase-SMTP-specific key is printed anywhere in this report, per
instruction.

**What does NOT change:** Supabase continues to OWN token generation
(the recovery `token_hash`, the signup confirmation token),
verification (`verifyOtp()`, called only from this application's own
server-side `/auth/confirm` Route Handler, using the publishable-key
client — unchanged), and session issuance. Configuring SMTP only
changes WHO relays the already-Supabase-generated email — it is purely
a transport-layer change. No auth-email token logic moves into the
Nemryn/Zenward application at any point; this phase does not propose
that and it would be a significant, unrequested architecture change if
it did.

8. SECURITY IMPLICATIONS
====================================================================

**Two separate transactional-email security boundaries, and they stay
separate even though both may soon present the identical Nemryn
sender identity:**

  APPLICATION TRANSACTIONAL EMAIL (driver invitation):
    - Trigger: `src/app/operations/drivers/actions.ts`
      (`createDriverInviteAction`/`resendDriverInviteAction`)
    - Sender module: `src/lib/email/send.ts` — `server-only`, reads
      `RESEND_API_KEY`/`EMAIL_FROM` from non-`NEXT_PUBLIC_` server-only
      Vercel environment variables.
    - Content/token: the driver-invite token (a 122-bit random UUID)
      is generated and verified entirely by THIS application's own
      `create_driver_invite`/`redeem_driver_invite` RPCs — Supabase
      Auth is not involved in this token's lifecycle at all.
    - Credential: the application's own `RESEND_API_KEY` (Resend's
      HTTPS API, called directly — no SMTP involved here).

  AUTH TRANSACTIONAL EMAIL (signup confirmation, password recovery):
    - Trigger: Supabase Auth itself, internally, in response to
      `supabase.auth.signUp()` (confirmation) or
      `supabase.auth.resetPasswordForEmail()` (recovery) — both called
      from this application, but the EMAIL ITSELF is composed, sent,
      and its token generated ENTIRELY inside Supabase Auth's own
      service, using the Dashboard-configured template + SMTP
      transport. This application never sees the token before the
      recipient does; it only exchanges it later, server-side, when
      the recipient clicks the link (`verifyOtp()` in `/auth/confirm`).
    - Credential: a SEPARATE Resend API key (§7), held only inside the
      Supabase Dashboard's own SMTP settings — never present in this
      application's own environment variables, codebase, or Vercel
      configuration at all.

**Why the boundary matters even with a shared sender identity:** a
shared "From" address is a BRANDING choice (what the recipient sees),
not a shared CREDENTIAL or shared CODE PATH. Compromise of the
application's own `RESEND_API_KEY` (e.g. a Vercel misconfiguration
exposing it) would let an attacker send email "from" Nemryn's identity
via the application's own Resend integration, but would grant NO
ability to generate a valid Supabase recovery/confirmation token, sign
in as any user, or touch any session — because that credential has no
relationship to Supabase Auth's own token/session machinery at all,
regardless of SMTP configuration. Symmetrically, the Supabase-SMTP
Resend key (even if it were somehow exposed) grants only the ability
to send email as Nemryn via THAT specific integration — it carries no
Supabase project credential, no JWT signing capability, no session
access. Neither credential is ever placed in browser-reachable code in
either design (confirmed for the existing key by `grep -rn
"RESEND_API_KEY" src/` → only `src/lib/email/send.ts`, a `server-only`
module; the new key, once created, will never touch this
application's own source tree at all — it lives exclusively in the
Supabase Dashboard).

**No change to RLS, schema, or the driver-invitation token model** is
implied or required by anything in this section — confirmed by this
phase's own read-only nature (§ GIT below).
