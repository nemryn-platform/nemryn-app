2. ORIGINAL RETRY BEHAVIOR
-------------------------------
Read `docs/reports/p1-e1-s2d-r1-request-queue-fail-visible-errors.txt`
in full before starting. R1's failure-state Retry action was a
hardcoded, unconditional link:

    <LinkButton href="/operations/requests" variant="outline">Retry</LinkButton>

Any failure occurring under a non-default view — `?state=accepted`,
`?state=declined&page=2`, `?state=all&q=Marguerite` — would have its
Retry action silently discard that context and reset the operator to
default Pending, page 1, no search. This is a real UX regression for
an operator who was deliberately working a specific status view or
search when the failure occurred.


3. SUPPORTED QUERY STATE
-----------------------------
Read `page.tsx` and `requests-list.ts` to confirm the page's actual
supported URL surface — exactly three query parameters, no others:

  - `q`      — free-text search, read as `typeof params.q === "string"
               ? params.q : ""`. No allow-list of values; passed
               through to `getRequestsList`, which internally trims
               and caps it at 200 chars before querying.
  - `state`  — status view, validated via the existing
               `parseRequestsListStateFilter`, which returns one of
               `"pending"|"accepted"|"declined"|"cancelled"|"all"` and
               falls back to `"pending"` for anything else (including
               missing/malformed values) — this validation already
               existed, unchanged by this phase.
  - `page`   — pagination cursor, parsed via `Number.parseInt(params
               .page, 10) || 1`.

No other query parameter is read anywhere in `page.tsx` or
`requests-list.ts`. Per phase §2's explicit instruction, no other
parameter is preserved — an arbitrary/unrelated query-string value
present on the failing URL (there is no legitimate case for one today,
but the mechanism guarantees it structurally) is simply never written
into a Request Hub URL this page constructs.


4. FINAL RETRY URL CONSTRUCTION
------------------------------------
A pre-existing helper already did exactly this job for pagination's
Previous/Next links, but was scoped inside the success-path branch
(defined AFTER the `if (!result.ok) return ...` early return),
so it was unreachable from the failure branch. Hoisted it above the
`!result.ok` check, generalized its name
(`buildPageHref` → `buildRequestHubHref`), and reused it, unchanged in
logic, for both:

    const buildRequestHubHref = (targetPage: number) => {
      const qp = new URLSearchParams();
      if (search) qp.set("q", search);
      if (state !== "pending") qp.set("state", state);
      if (targetPage > 1) qp.set("page", String(targetPage));
      const qs = qp.toString();
      return qs ? `/operations/requests?${qs}` : "/operations/requests";
    };

Retry now reads:

    <LinkButton href={buildRequestHubHref(page)} variant="outline">Retry</LinkButton>

where `search`, `state`, and `page` are the exact validated values
computed at the top of the component — BEFORE `getRequestsList` is
even called — so they represent precisely the Request Hub view this
failed render actually attempted, not a re-derivation or a guess.
Pagination's own Previous/Next links (`buildRequestHubHref(result.page
- 1)` / `buildRequestHubHref(result.page + 1)`) now share this exact
same function — one URL-construction implementation for the whole
page, not two.

No new Request Hub URL/query helper file was introduced; the existing
one was hoisted and reused, per §10's own "possibly one existing
helper if already appropriate."


5. VALIDATION / NORMALIZATION BEHAVIOR
---------------------------------------------
`state` and `page` were already normalized BEFORE this phase (`state`
via the pre-existing `parseRequestsListStateFilter`; `page` via the
pre-existing `Number.parseInt(...) || 1` fallback) — Retry inherits
this normalization for free, since it now reads the same top-level
`state`/`page` variables rather than raw `params.state`/`params.page`.

One small correctness fix was made to `page`'s own normalization,
directly in service of §4's "use the normalized positive page value
already used by the queue": the pre-existing fallback
(`Number.parseInt(params.page, 10) || 1`) does not clamp a negative
value (`Number.parseInt("-5", 10)` is `-5`, which is truthy, so `|| 1`
never fires) — `getRequestsList` itself already defensively re-clamps
via `Math.max(1, filters.page ?? 1)`, but `page.tsx`'s own top-level
`page` variable did not match that clamp, so a hypothetical
`?page=-5` URL could have produced a Retry/pagination link that didn't
reflect what the query actually used. Added the identical
`Math.max(1, ...)` clamp to `page.tsx`'s own computation so the value
used for both Retry and pagination is now provably identical to what
`getRequestsList` itself will use. This is the only behavioral change
in this phase beyond the Retry destination itself — confirmed narrow
in scope (one `Math.max` wrapper) and directly required by §4's own
instruction, not an unrelated addition.

`?state=bogus` (§4's own example): live-confirmed the resulting Retry
href is exactly `/operations/requests` (no `state` param at all) —
`parseRequestsListStateFilter("bogus")` already resolves to
`"pending"`, and the builder omits `state` from the query string
whenever it equals `"pending"` (the default), so an invalid state is
never echoed back, per §4.


6. URL ENCODING
--------------------
`buildRequestHubHref` uses `URLSearchParams.set(...)` exclusively — no
manual string concatenation of user-supplied search text anywhere.
Live-verified with a deliberately adversarial search string containing
a space, an ampersand, an apostrophe, and a question mark
(`"O'Brien & Sons?"`): the Retry href round-tripped to exactly
`/operations/requests?q=O%27Brien+%26+Sons%3F` (space encoded as `+`,
`&` and `?` and `'` percent-encoded) — provably safe, matching
`URLSearchParams`'s own standard encoding, never a hand-built string
that could break the URL or inject an unintended query parameter.
