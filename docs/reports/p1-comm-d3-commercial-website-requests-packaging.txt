RATE LIMIT CURRENT MODEL   (audited fresh from code)
======================================================================
/api/public-intake/website, before D3R:
  1. body cap (8 KB) -> JSON parse -> validateWebsiteIntakePayload (closed field set). Invalid -> generic 400 and NO
     rate-limit consumption.
  2. check_and_record_public_intake_rate_limit(p_integration_external_id = the SUPPLIED id, p_client_key = sha256(salt:IP))
     (20260919120000). Atomic under two advisory locks; within a rolling hour it counts rows by the lowercased
     integration key (limit 120) and by client_key (limit 8). The client bucket is GLOBAL across all integrations:
     two customers behind one outbound IP share one 8/hour bucket. Every attempt that passes is recorded, including
     unknown ids, wrong Origins, inactive connections and idempotent replays.
  3. submit_public_transportation_request (service_role RPC) resolves the integration (exact external_id, website
     type, is_active), org active, Origin exactly in allowed_origins (when set), retired -> rejected in
     _create_public_request; idempotent ON CONFLICT on (integration, idempotencyKey).
  Integration resolution / Origin / active checks therefore happened only AFTER the limiter; CORS resolution
  (resolveAllowedCorsOrigin) is a separate service-role read used only for response headers.
/api/public-forms/<key>/submit (hosted + embed, one route): its own same-origin check, then
check_and_record_public_intake_rate_limit(p_integration_external_id = publicKey, p_client_key = sha256(salt:IP)).
A separate browser-facing path; it shares the SQL function and the per-IP client key namespace.

======================================================================
SERVER-TO-SERVER THREAT MODEL
======================================================================
Legitimate website intake comes from the customer's SERVER, so every submission can share one outbound IP (Vercel,
Cloudflare, shared hosting, an agency backend). A per-IP limit meant for browsers then caps a real customer at 8
requests an hour, even though the integration has capacity left. Meanwhile the real abuse surface is unauthenticated
traffic with unknown ids, wrong Origins or disabled connections. Different threats need different buckets.

======================================================================
VALID INTEGRATION LIMITING
======================================================================
Before limiting, the route classifies the submission with the SAME rule the RPC applies
(isVerifiedWebsiteConnection): exact external_id found, integration_type website, is_active, not retired, and the
Origin header exactly one of allowed_origins (or no allow-list). It uses lookupIntakeConnection, the existing
service-role SELECT on request_intake_integrations that the CORS lookup already has (no new privilege). Organization
suspension stays enforced by the RPC.
VERIFIED -> websiteIntakeRateLimitKeys: integration bucket = the integration id (120 per rolling hour -- the commercial
boundary, unchanged), client bucket = sha256(salt:connection:<id>:<idempotencyKey>). The low per-client cap then
applies per SUBMISSION (bounding replays of one submission), never per IP. The same SQL function, ledger table and
atomic locking are used; no migration.

======================================================================
INVALID TRAFFIC LIMITING
======================================================================
NOT verified (unknown id, inactive, retired, form binding, wrong / missing Origin) -> client bucket = sha256(salt:IP)
(8 per rolling hour, as before), integration bucket = "unverified:<id>". Invalid traffic stays IP-limited, and it can
no longer consume a real connection's 120 by naming its Integration ID (previously possible from 15 IPs). The response
is byte-identical for every rejection (no existence oracle): the route still returns the one generic 400 / 429. The
classification lookup runs for every well-formed submission, so its presence doesn't distinguish outcomes.

======================================================================
SHARED IP BEHAVIOR
======================================================================
Verified connections never use the IP bucket, so integrations A and B behind the same IP each have their own 120/hour.
Proven live: A sent 9, then filled to 120 and got 429 on the 121st, while B from the same IP was accepted before and
after. Garbage filling that IP's abuse bucket did not block A's valid traffic.

======================================================================
IDEMPOTENCY
======================================================================
The DB invariant is untouched (ON CONFLICT on integration + idempotencyKey). A replay of an existing key returns 200 and
creates nothing. Replays do consume capacity (one ledger row each, as before) and are bounded per submission by the
per-client cap: 8 replays of one key per hour. The Node / Next.js examples retry once on a network error with the
same key.

======================================================================

(publicKey, IP) buckets, 8 per IP per rolling hour. Proven live: 8 x 200 then 429 from one IP. Embed uses the same
