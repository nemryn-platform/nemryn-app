Objective:
  A real operator can correct legitimate operational mistakes and recover stranded work without cancel / recreate, and
  without asking a developer to modify data.
  Preserved throughout: historical truth, actor attribution, tenant isolation, lifecycle and assignment integrity,
  Proof-of-Service meaning, auditability, and the PROG4 / PROG5 semantics.
  Nothing here is solved by broadening direct UPDATE rights; the opposite happens.

======================================================================
trips (columns):
  id, organization_id, request_id, passenger_id, state, scheduled_pickup_at, appointment_at, pickup_description,
  destination_description, pickup_facility_id, destination_facility_id, assistance_notes, instructions, completed_at,

  reason text). RLS SELECT: Organization Admin only (audit_events_select_org_admin). Append-only by RPCs.
trip_assignments:
  one active row per trip (unique partial index on trip_id where ended_at is null); ended_at and end_reason are set by
  the RPCs.
  driver_complete_trip closes the active row with end_reason = 'trip_completed'; cancel_trip uses 'trip_cancelled'.
Lifecycle RPCs:
  - Driver transitions (_driver_execute_trip_transition, migration 20260831100200): the assigned driver only;
    p_expected_current_state (ZW003 stale_state on mismatch); row lock FOR UPDATE; each writes its trip_events row.
  - driver_complete_trip: arrived_at_destination -> completed; sets completed_at; closes the assignment.
  - cancel_trip: any non-terminal state; reason required.
  - record_no_show: en_route_to_pickup / arrived_at_pickup only.
  - assign_trip / reassign_trip: scheduled / en_route_to_pickup / arrived_at_pickup only.
  - Exceptions: report (ops or assigned driver) / resolve (ops).
create_trip validation (to be reused verbatim by the edit):
  - pickup / destination descriptions trimmed, non-blank, <= 2000;
  - appointment_at >= scheduled_pickup_at when both are set;
  - facilities must be same-organization AND active;
  - ZW006 for every invalid input.
New Trip form (NewTripForm.tsx + trips/new/actions.ts):
  - org-local date + time converted with organizationLocalToUtc; nonexistent / ambiguous (DST) -> SCHEDULE_UNRESOLVABLE;
  - appointment date and time must be supplied together;
  - facility pickers, instructions, assistance notes, duration, wheelchair tri-state.
Trip Detail:
  - "Edit Trip" is rendered DISABLED (TripDetailActionBar.tsx lines 44-46).
  - Duration and wheelchair have their own audited setters (set_trip_expected_duration,
    set_trip_wheelchair_requirement).
Proof of Service (trip-proof-of-service-core.ts + -evidence.ts):
  - States: READY_FOR_REVIEW / NEEDS_REVIEW / NOT_APPLICABLE.
  - Reasons: EVIDENCE_INTEGRITY_GAP / MISSING_VEHICLE / OPEN_EXCEPTION.
  - EVIDENCE_INTEGRITY_GAP (fail-closed) fires when ANY of these is missing:
      - completed_at;
      - a passenger;
      - descriptions;
      - a completion assignment (end_reason = 'trip_completed', exactly one);
      - a complete 6-event chain (en_route_to_pickup .. trip_completed, each exactly once, ordered, and

Request readiness (request-readiness-core.ts):
  - needs_passenger / awaiting_decision / ready / trip_created / not_convertible.
  - trip_created = ANY linked trip (a cancelled one included).
  - Overview (operations-brief-core.ts) counts PENDING requests only.
Recurring occurrence identity:
  - A trip belongs to service date D of arrangement A when recurring_arrangement_id = A, state <> 'cancelled', and
    (scheduled_pickup_at AT TIME ZONE arrangement.timezone)::date = D.
  - Sources: create_trip_for_recurring_occurrence (idempotency select) and recurring-care.ts (linked-trip load).

4. TRIP EDIT STATE BOUNDARY -- DECISION
======================================================================
Options compared:
  A  scheduled only: too narrow. Wrong addresses and new instructions are routinely discovered once the driver is
     moving.
  B  through en_route_to_pickup: covers the common case, but blocks a legitimate destination change after pickup.
  C  through arrived_at_pickup: same limitation after onboard.
  D  field-specific by lifecycle: the smallest rule that is still operationally complete, and never rewrites anything
     that has already happened.
RECOMMENDED: D, with this exact matrix (Y = editable, - = locked):

  field \ state                      sched  en_route_pu  arrived_pu  onboard  en_route_dest  arrived_dest  terminal*
  scheduled pickup (date+time)         Y         Y            -          -          -              -            -
  pickup description / facility        Y         Y            -          -          -              -            -
  appointment time                     Y         Y            Y          Y          Y              -            -
  destination description / facility   Y         Y            Y          Y          Y              -            -
  instructions                         Y         Y            Y          Y          Y              -            -
  assistance notes                     Y         Y            Y          -          -              -            -
  (*terminal = completed, cancelled, no_show)

Rationale:
  - scheduled pickup / pickup location lock at arrived_at_pickup: the driver is physically there, so changing the
    plan now would rewrite what the pickup "was". en_route edits stay allowed (the owner default); the scheduled time is
    a PLAN, and the actual times live in trip_events, so a plan correction never falsifies history. The UI warns that
    the driver may already be travelling.
  - The destination (+ appointment) remains correctable until arrived_at_destination (the hospital or family diverts).
    Once arrived, the destination is where the trip DID end, so it locks. Mid-ride destination changes are
    audit-flagged (section 6).
  - Assistance notes describe preparation for the pickup; once the passenger is onboard they are no longer
    actionable, so they lock at onboard.
  - Instructions stay useful to the driver until arrival at the destination.
  - Terminal trips are immutable. There is no "fix the record after completion" in R2. If ever needed it is a
    separate, evidence-gated feature.
Recurring-occurrence rule (new, required):
  For a trip with recurring_arrangement_id set, an edit may change the pickup TIME but must keep the same
  arrangement-local service DATE (ZW006 otherwise).
  Reason: occurrence identity is the local date of scheduled_pickup_at (section 1). Moving it to another date would
  make the original date show as "missing" (re-creatable as a duplicate) and the new date show a stray occurrence.
  Moving an occurrence to another day = skip the date + create a one-time trip (existing tools).
Request-linked trips: the date may change freely (request_id is untouched; the request's preferred date is historical
  intent, not a constraint).
Clearing: a set scheduled_pickup_at can never be cleared (ZW006). A pickup-less trip (RPC-created) MAY be given one.

5. update_trip_details -- PROPOSED SIGNATURE
======================================================================
  update_trip_details(
    p_trip_id                  uuid,
    p_expected_updated_at      timestamptz,   -- optimistic concurrency (section 7)
    p_scheduled_pickup_at      timestamptz,
    p_appointment_at           timestamptz,   -- NULL = no appointment
    p_pickup_description       text,
    p_pickup_facility_id       uuid,          -- NULL = none
    p_destination_description  text,
    p_destination_facility_id  uuid,          -- NULL = none
    p_instructions             text,          -- NULL / blank = none
    p_assistance_notes         text           -- NULL / blank = none
  ) returns public.trip_details_update_result  -- (trip_id uuid, changed boolean, changed_fields text[],
                                               --  updated_at timestamptz)
Semantics:
  FULL-REPLACEMENT of the 8 owned fields: the caller always sends the complete desired set, pre-filled from the current
  values. Partial-patch ambiguity (NULL = "clear" vs "untouched") is avoided; the concurrency token protects against
  reverting another operator's change.
  SECURITY DEFINER; SET search_path = public, pg_temp; REVOKE ALL FROM PUBLIC; GRANT EXECUTE TO authenticated.
Algorithm:
  1. auth.uid() null -> ZW001.
  2. SELECT ... FOR UPDATE the trip.
     - Not found, foreign organization, or not has_org_role(org, [organization_admin, dispatcher]) -> ZW002
       (no existence oracle; Driver and Platform Admin land here).
  3. updated_at IS DISTINCT FROM p_expected_updated_at -> ZW003 stale_state.
  4. Normalise text: trim; blank -> NULL for the optional fields; the descriptions stay required.
     Validate exactly as create_trip (bounds, appointment >= pickup, facility same-org AND active). Clearing a set
     pickup -> ZW006. Recurring date rule (section 4) -> ZW006.
  5. Compute the changed set. EMPTY -> return changed=false, with NO write, NO audit and NO event (a no-op is not an
     edit).
  6. Any changed field not editable in the CURRENT state (matrix) -> ZW004 illegal_transition. Terminal -> ZW004.
  7. UPDATE only the changed columns; write the audit + event (section 6); return the changed fields + new updated_at.
  Facility activeness is enforced only for a CHANGED facility id: a trip whose original facility was later deactivated
  can still be edited in other fields without being forced to re-pick.

6. AUDIT / EVENT MODEL
======================================================================
audit_events (administrative mutation history; Admin-readable only):
  action = 'trip_details_updated', entity_type = 'trip', entity_id = trip id, actor_user_id = auth.uid(),
  before_data / after_data = ONLY the changed fields, keyed by column name.
  Values:
    - timestamps as ISO UTC;
    - facility ids as ids, never names;
    - descriptions / instructions / assistance notes as their text.
  These are the operational values being corrected, already stored on the same org's trip row. They are needed so a
  correction is evidenced rather than silently overwritten.
  No passenger fields and no requester data are ever included.
  after_data also carries "trip_state" (the state at edit time), making an in-progress change visible.
  OWNER DECISION D-1 (recommended YES): store before / after free text for descriptions / instructions / assistance
  notes. The alternative (field names only) loses the correction evidence the objective requires.
trip_events (operational timeline; visible on Trip Detail):
  event_type = 'trip_details_updated' -- NEW value; the CHECK vocabulary is extended additively.
  actor_user_id = auth.uid(); metadata = { "changed_fields": [...], "trip_state": "<state>" } -- field names only,
  never values.
  It is a NEW type, never a lifecycle type, so no driver action is fabricated. It is not part of the Proof
  6-event chain, so Proof evaluation is unaffected.
No write on no-op. Exactly one audit row + one trip_events row per effective edit.

======================================================================
7. CONCURRENCY / STALE-EDIT PROTECTION
======================================================================
  Token: trips.updated_at, read by the Edit dialog when it opens and sent as p_expected_updated_at.
  - Any intervening change to the trip row -- another operator's edit, a driver lifecycle step, a duration or
    wheelchair change -- bumps updated_at, so the edit fails with ZW003 and overwrites nothing.
  - Assignment changes live in trip_assignments and do NOT bump updated_at. That is correct: assignment is not an
    edited field, and the state matrix is re-checked under the row lock anyway.
  - UI copy (existing stale convention): "This trip changed since you opened it. Refresh and review the latest details."
    It offers Refresh and keeps the typed values visible for re-entry.
  Double submit: Save is disabled while pending. A replay after success carries the old token -> ZW003 (safe).

8. DRIVER VISIBILITY AFTER EDIT
======================================================================
Current behaviour:
  - The service worker never caches navigations: /driver pages are network-first with only an /offline fallback
    (src/lib/pwa/service-worker.ts line 104).
  - Driver pages are server-rendered from driver_get_trip_detail, so any navigation or refresh shows server truth.
  - A lifecycle action calls router.refresh() on success and on error.
  - Gap: a driver who keeps one trip screen open does not re-fetch, and an edit does not change `state`, so their next
    lifecycle tap still succeeds (only the state is checked) against details they have not re-read.
R2B minimum (no push, no notification system, no driver-contract change):
  (a) Driver trip pages call router.refresh() on visibilitychange -> visible and on window focus. A driver switching
      back from navigation / phone apps sees the new truth.
  (b) After an edit of a trip that has an ACTIVE assignment and state >= en_route_to_pickup, the operator's success
      message says: "Saved. The driver may already be on the way -- call them to confirm the change." It shows the
      existing Contact Driver link.
  (c) Not in R2B: a driver-side "details updated" marker. That would change driver_get_trip_detail's result. Recorded
      as R2 follow-up F-1, to decide on pilot feedback.

14. PR-03 -- ACCEPTED REQUEST WITHOUT A TRIP (Overview)
======================================================================
Relationship facts:
  - trips.request_id -> transportation_requests (1:N).
  - Trips are never deleted by the product (terminal states only); a cancelled trip remains linked.
  - Recurring occurrences never carry request_id.
Definition (R2B):
  A Request is STRANDED when state = 'accepted' AND it has no linked trip with state <> 'cancelled'.
  So an accepted request whose only trip was cancelled is stranded again. Cancelling a trip does not make the ride
  request go away; the operator must re-plan or cancel the request explicitly.
Factual query (org-scoped, RLS):
  - Preferred: PostgREST anti-join on the org's accepted requests, using an embedded LEFT join to trips filtered
    state <> cancelled, "trips is null", count exact + head. (Use the explicit FK hint -- the passengers embed is
    already known to need one.)
  - Fallback if the anti-join proves unreliable: a tiny SECURITY INVOKER SQL function (RLS applies), e.g.
    count_stranded_accepted_requests(p_org), added to the contract.
  - It must be verified in R2B against 0, 1 and many rows, and against cancelled-only trips.
Overview:
  - One fact line in the Requests block when the count > 0: "N accepted requests still need a trip" -> link
    /operations/requests?state=accepted&needs=trip (a filtered Accepted view; the existing list gains the "needs"
    filter using the same predicate).
  - No new dashboard, no urgency score, no aging.
  - Zero -> nothing shown (the calm state).
Readiness alignment (small, required so the list agrees with Overview):
  - deriveRequestReadiness gains "hasActiveTrips" (non-cancelled).
  - Accepted with only cancelled trips -> new readiness "trip_cancelled", labelled "Trip cancelled -- needs a trip".
  - "trip_created" means at least one non-cancelled trip.
  - The link_request_passenger rule in the DB is unchanged (still: no linking once any trip exists).
Pending / declined / cancelled requests are unaffected: the pending count is unchanged; terminal requests are never
  stranded.

15. FUTURE RECURRING FULFILMENT COMPATIBILITY (PR-03 x PR-04)
======================================================================
The predicate is expressed as a single "fulfilment" definition in one pure core (request-fulfilment-core.ts):
  fulfilled = hasActiveTrip OR hasLinkedArrangement
  - hasLinkedArrangement is always false in R2B (no linkage exists yet), so R2B behaves exactly as section 14.
  - R3 (PR-04) sets it from recurring_arrangements.request_id (an arrangement not 'ended'), without changing any

    trip. Until R3 it counts as stranded unless the operator creates a trip. The Overview wording stays
    "still need a trip"; R3 changes it to "still need a trip or arrangement".

16. PR-02 -- DISPATCHER RECOVERY: STATE ELIGIBILITY
======================================================================
Not trip editing. A separate, exceptional, audited contract. It never impersonates the driver and never fabricates
  events.
Eligible states: passenger_onboard, en_route_to_destination, arrived_at_destination.
Ineligible (existing recovery paths apply):
  - scheduled / en_route_to_pickup / arrived_at_pickup -> assign / reassign, no-show, cancel;
  - completed / cancelled / no_show -> terminal, denied.
Precondition: an ACTIVE assignment must exist. Onboard is structurally impossible without one; if it is missing, that
  is an integrity problem -> ZW006, never "fixed" by recovery.

17. RECOVERY RPC -- PROPOSED SIGNATURE + SEMANTICS
======================================================================
  record_trip_completion_by_operations(
    p_trip_id                 uuid,
    p_expected_current_state  text,         -- one of the 3 eligible states; ZW003 on mismatch
    p_completed_at            timestamptz,  -- the operator-stated completion time
    p_note                    text          -- required (section 18)
  ) returns public.trip_transition_result   -- the existing result shape
    (previous_state, current_state, changed)
  SECURITY DEFINER; pinned search_path; PUBLIC / anon revoked; authenticated EXECUTE.
Authorization: has_org_role(org, [organization_admin, dispatcher]) -> else ZW002. A Driver (even the assigned one)
  -> ZW002. The driver's own path stays driver_complete_trip.
Validation:
  - state = p_expected_current_state (else ZW003) and in the eligible set (else ZW004);
  - p_completed_at <= now() + 5 min (no future) and >= the occurred_at of the latest existing lifecycle event
    (no time travel);
  - note valid.
Writes (one transaction, row lock on the trip, then on the active assignment):
  - trips: state = 'completed', completed_at = p_completed_at.
  - trip_assignments (active row): ended_at = now(), end_reason = 'trip_completed'. The assigned driver DID perform the
    ride; the assignment ended by completion, so the completion-assignment fact stays truthful and the history is
    retained.
  - trip_events: ONE new event_type 'completion_recorded_by_operations' (added to the CHECK):
      actor_user_id = the operator;
      occurred_at = now() (when it was recorded);
      metadata = { previous_state, recorded_completed_at, note_present: true }.
    NOT 'trip_completed', and no en_route_to_destination / arrived_at_destination row is inserted for skipped steps.
  - audit_events: action 'trip_completion_recorded_by_operations', before_data { state }, after_data { state,
    completed_at }, reason = the note.
Races:
  - The driver completes first -> state = completed -> the dispatcher call fails ZW003 (stale) or ZW004. No double
    completion.
  - The dispatcher recovers first -> the driver's pending tap carries the old expected state -> ZW003 (the driver sees
    "This trip was updated -- refresh"). The driver can no longer act on a completed trip.
Dedicated column? NOT NEEDED.
  - trips.completed_at already exists.
  - Provenance is carried by the distinct trip_events type (plus the audit row), which is the smallest additive model.
  - An optional trips.completion_source column was considered and rejected (a duplicate fact).
