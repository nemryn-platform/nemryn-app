1. SCOPE SUMMARY
-----------------
Built Decline and Cancel lifecycle actions for Operations Request Detail,
plus a restrained, read-only Request Activity panel. Both mutations call
ONLY the existing P1-E1-S2B RPCs (`decline_transportation_request`,
`cancel_transportation_request`) — no raw `.update()` on
`transportation_requests.state`, no raw `request_events` INSERT, no
Supabase source file changed. Public intake, Operations Brief counts, the
recurring-care engine, `trip.leg`, request reopening, accepted-Request
cancellation, Trip cancellation, Passenger reassignment, and notification
infrastructure were all explicitly out of scope and were not touched.

2. PRODUCT SEMANTICS PRESERVED
-------------------------------
DECLINE = operator decision the Request will not be fulfilled.
CANCEL = Request withdrawn before conversion.
These are not interchangeable in copy, eligibility, or code path. Trip
cancellation remains a completely separate Trip-lifecycle action, never
touched or referenced destructively by this phase's UI (Cancel's own
dialog copy explicitly says "This does not cancel any trip.").

3. ACTION ELIGIBILITY (AS IMPLEMENTED)
----------------------------------------
- PENDING: Decline available for ANY pending Request (resolved or not).
  Cancel available ONLY when linkedTrips.length === 0. Create Trip
  available separately when readiness === "ready" — all three can
  coexist independently per the exact rules given.
- ACCEPTED: no Decline, no Cancel; Create Another Trip unchanged
  (S2F-B1 behavior untouched).
- DECLINED / CANCELLED: no lifecycle actions of any kind.
- No Reopen / Undo path exists anywhere in this phase.
- A rare legacy edge case (pending + already has a linked Trip) shows a
  restrained note ("This request has linked trips and cannot be
  cancelled here.") instead of an enabled Cancel button — Decline
  remains available in that same state, since Decline eligibility never
  depends on linked Trips.

4. ACTION HIERARCHY
--------------------
`RequestActionBar` mirrors `TripDetailActionBar`'s exact convention: one
flat row, no dropdown/overflow menu. Create Trip / Create Another Trip
keeps its existing default (filled, primary) `LinkButton` styling as the
sole productive action. Decline Request / Cancel Request both use
`variant="outline"` as TRIGGER buttons — same secondary weight as Cancel
Trip's own trigger in `TripDetailActionBar`. Destructive weight is
expressed only once, inside each action's own confirmation dialog
(`variant="destructive"` on the confirm button), exactly matching
`CancelTripDialog`.

6. DECLINE MUTATION (SERVER ACTION)
--------------------------------------
`declineRequestAction` (src/app/operations/requests/[requestId]/
actions.ts) calls `decline_transportation_request` ONLY.
`requireOperationsAccess()` re-derives `organizationId` fresh from the
validated session on every call — never read from the client. `requestId`
is the only client-supplied identifier. The optional `reason` is
normalized: empty/whitespace-only → `undefined` (never an empty string
sent over the wire). `actor_user_id` is never accepted from the client —
the RPC derives it itself from `auth.uid()`. Errors branch on `error.code`
via `mapRequestLifecycleError`; no raw DB error text is ever rendered to
the user.

9. CANCEL ELIGIBILITY LOGIC
------------------------------
`canCancel = request.state === "pending" && request.linkedTrips.length
=== 0` (src/app/operations/requests/[requestId]/page.tsx). When pending
but linkedTrips.length > 0, Cancel is not offered and the restrained note
renders instead — never a cascade into Trip cancellation, and Decline
remains independently available in that state.

10. CANCEL MUTATION (SERVER ACTION)
--------------------------------------
`cancelRequestAction` calls `cancel_transportation_request` ONLY, same
discipline as Decline (org re-derived server-side, no actor id from
client, error-code branching, no raw error exposure). Deliberately does
NOT perform a client-side linked-Trip check as authority before calling
the RPC — the RPC's own "ANY linked Trip row blocks cancellation
regardless of that Trip's own state" rule (S2B, locked) remains sole
authority. This was proven live (see §25, Cancel-D).

12. CONCURRENCY / STALE-PAGE HANDLING
-----------------------------------------
`mapRequestLifecycleError` maps RPC code `ZW004` (illegal_transition) to
calm copy: "This request has changed and can no longer be updated this
way." Verified directly: forged direct RPC calls against an
already-accepted Request (both decline and cancel) both raised
`illegal_transition` from the RPC itself, and the shared error mapper
translates that code to the required calm copy — never exposing "ZW004"
or raw Postgres error text anywhere in the UI. `router.refresh()` runs on
ANY settled action state (not just success), so the page behind an error
also reflects the current DB reality. No client-side optimistic lifecycle
locking exists anywhere in this implementation.

13. IDEMPOTENT RESPONSES
---------------------------
Verified directly via SQL: calling `cancel_transportation_request`
against an already-cancelled Request (R_G) returns `changed=false`,
`previous_state=cancelled`, `current_state=cancelled` — no error raised,
and confirmed zero duplicate `request_events` rows were written. The app
code treats this as an ordinary success branch (no special-casing
needed, since the RPC's own contract already makes idempotent re-calls
safe) — the page simply refreshes into the current (already-terminal)
lifecycle state.

19. ERROR MAPPING
--------------------
`src/lib/operations/request-lifecycle-errors.ts` is one shared mapper
used by both `declineRequestAction` and `cancelRequestAction`, following
the exact precedent of `link-passenger-errors.ts`. Confirmed directly
from the S2B migration source that both RPCs raise the identical
ZW001/ZW002/ZW004/ZW006 code set, justifying a single shared map rather
than two near-duplicates:
  ZW001 → UNAUTHORIZED ("Your session is no longer valid. Sign in
          again.")
  ZW002 → NOT_FOUND ("This request is no longer available.")
  ZW004 → ILLEGAL_STATE ("This request has changed and can no longer be
          updated this way.")
  ZW006 → INVALID_INPUT ("Please check the information provided and try
          again.")
  default → UNKNOWN ("Something went wrong. Try again.")
