3. FUNCTION DEPENDENCY ANALYSIS
======================================================================
[VERIFIED] Production catalog:
- pg_depend dependents on the function: NONE (no view, rule, default, trigger or constraint references it).
- views / rules calling it: none.
- Its own dependencies: type request_creation_result, plpgsql, schema public.
- PL/pgSQL call sites are not tracked in pg_depend. The two Plus RPCs resolve the name at EXECUTION time, so a DROP
  without CASCADE succeeds; they must find a compatible function the next time they run.
- Event triggers present: pgrst_ddl_watch (ddl_command_end) and pgrst_drop_watch (sql_drop). PostgREST reloads its
  schema cache after DDL automatically.
- Other functions already taking p_service_type: _create_public_request, submit_public_transportation_request,
  submit_public_form_request, plus_create_opportunity, plus_update_opportunity. There is no name clash.
Consequences [VERIFIED by PostgreSQL rules, to be proven in S1 tests]:
- CREATE OR REPLACE cannot add a parameter (it changes the identity signature), so DROP + CREATE is required.
- Keeping the old 14-argument function AND adding a 15-argument one with `p_service_type default null` would make
  every 14-argument call (PostgREST named, and the two positional Plus calls) match BOTH overloads: "function ... is
  not unique". The repository's own precedent (20260924090000 EXPAND notes) records exactly this hazard.
  => NO overload.
- A trailing parameter WITH a default keeps every existing call valid: named calls without p_service_type, and the
  two positional 14-argument Plus calls.

4. RECOMMENDED MIGRATION STRATEGY
======================================================================
[RECOMMENDED] One Core migration, e.g. 20261017100000_core_staff_request_service_type.sql (timestamp after
20261015140000), in ONE transaction (the CLI wraps each migration file):
  1. DROP FUNCTION public.log_transportation_request(uuid, text, text, text, text, text, text, text, text, uuid,
     date, time, text, text). Exact signature, NO CASCADE: it must fail loudly if anything unexpected depends on it.
  2. CREATE FUNCTION public.log_transportation_request(<the same 14 parameters, same names, types, order and
     defaults>, p_service_type text DEFAULT NULL)
     - Same RETURNS, LANGUAGE, SECURITY DEFINER and SET search_path = public, pg_temp.
     - The body is the existing body VERBATIM, plus:
       - v_service_type := nullif(btrim(p_service_type), ''), so '' is treated as omitted;
       - if not null and not in the 9 values (explicit list, the established defensive-duplication style, identical
         to _create_public_request) -> ZW006;
       - [DECISION OD-S1] tenant Services rule (section 6);
       - INSERT adds service_type = v_service_type.
     - The request_events metadata is UNCHANGED ({source} only).
  3. COMMENT ON FUNCTION (new signature): the existing comment plus the optional service_type.
  4. REVOKE ALL ... FROM public, anon, service_role; GRANT EXECUTE ... TO authenticated. The ACL is identical to
     today, and every SECURITY DEFINER keeps search_path.
  5. NOTIFY pgrst, 'reload schema' (belt and braces; the event triggers already do it).
- The transaction is atomic: other sessions see either the old or the new function, never neither.
  - A call already executing finishes on its cached body.
  - A Plus RPC's cached plan is invalidated by the pg_proc change; S1 must prove this with a same-session test.
- No table, column, CHECK or data change: transportation_requests.service_type and its 9-value CHECK already exist.
  NO existing row is rewritten.
- Rollback before release: DROP the 15-argument function and CREATE the 14-argument original (file 20260916100000
  body) in one transaction. Safe because the column stays.
- After release: forward-fix only. Requests may by then carry staff-chosen service types, which are legitimate data.

6. TENANT SERVICES POLICY FINDINGS
======================================================================
[VERIFIED]
- Website intake enforces Services: if the organization has ANY configured offering, a supplied service must be one
  of them (ZW006). No offerings configured means every canonical value is accepted.
- Staff creation (log_transportation_request) has no service today, so it has no Services rule.
- Plus opportunities accept any of the 8 regardless of Services.
[DECISION OD-S1] Should staff-created Requests be limited by the organization's Services setting?
  Option A (RECOMMENDED):
  - The database validates the closed set ONLY.
  - The staff UI LISTS the organization's enabled Services (or all 9 when none are configured), so the normal path
    respects Services, without the database refusing a staff record.
  - Rationale:
    - Services governs what the public may request.
    - Staff record what a customer actually asked for on the phone.
    - A hard database rule would make a Plus conversion FAIL whenever the opportunity's service is not currently
      offered (S2), which is a confusing failure for an internal record.
  Option B: the database enforces the same rule as intake for staff, too.
  - Strictest and consistent with intake.
  - Requires S2 to map a non-offered opportunity service to NULL (silent loss) or to refuse the conversion. Needs a
    UX decision.
  Do not silently change either behaviour; record the owner's choice before S1.
Related finding, not changed:
- website_request_forms / _publications CHECKs allow only 8 services (no airport). This is deliberate per
  NC-INTAKE-AIRPORT-S1 and is not part of this slice.

9. SECURITY AND BACKWARD-COMPATIBILITY RISKS
======================================================================
1. Accidental overload -> "not unique" for every existing caller. Mitigation: DROP + CREATE in one file, plus a test
   that exactly 1 function exists.
2. Lost grants after DROP. Mitigation: explicit REVOKE / GRANT in the migration; the privilege contract (signature
   updated) and request_mutation_privilege_tests must pass.
3. Deploy ordering. The NEW app sends p_service_type, and PostgREST rejects an unknown named argument (PGRST202).
   Mitigation: MIGRATION FIRST, then the app.
   - The deployed app (869c794) does not send it and keeps working after the migration (default NULL).
4. Plus RPCs (positional 14 args) after the change. Mitigation: S1 SQL tests run conversion and rebooking after the
   migration, including in a session that ran them BEFORE (plan-cache invalidation).
5. Validation drift between the explicit list and the CHECK. Mitigation: a parity test; the database CHECK remains
   the final guard.
6. Tenant Services semantics. Mitigation: owner decision OD-S1 before S1.
7. Information leakage. ZW006 stays generic; the cross-tenant role check is unchanged (ZW002 for foreign / driver /
   inactive).
8. Existing rows. No UPDATE or backfill. Historic staff Requests stay NULL; no inference from notes.
9. PD-10 / PD-11 open: service is an operational category, not health data. The Log Request help text must not
   invite medical detail. Fictional data in tests only.
