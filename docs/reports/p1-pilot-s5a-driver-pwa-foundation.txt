PWA ARCHITECTURE
============================================================
A delivery layer over the unchanged Driver domain:
 - /driver.webmanifest (route handler, static) and /sw.js (route handler, static per build) — both public, tenant-free, excluded from the session proxy.
 - /offline (public static page) and /api/ping (204, no-store reachability probe).
 - Client pieces inside the Driver shell only: DriverServiceWorker (registration + update notice), DriverNetworkStatus (global indicator), DriverInstallCard (Profile only).
 - Icons /pwa/* generated from the approved brand master by scripts/generate-pwa-icons.mjs (artwork reused byte-for-byte; only wrapped in a scale transform for maskable/apple).
 - Build id: next.config.ts sets NEXT_PUBLIC_BUILD_ID (Vercel commit SHA, else a local timestamp) and generateBuildId, so every deployment emits a different sw.js.
 - Service workers register in PRODUCTION builds only (dev chunks are not hashed).

============================================================
Software product name, not tenant: "Nemryn Driver" (full) / "Nemryn" (short). Decision: short_name is brand-only because launchers truncate around 12 characters ("Nemryn Driver" is 13) and "Driver" alone is ambiguous next to other apps; the Driver context is carried by the full name, the start URL and the icon label on iOS ("Nemryn Driver"). Not "Zenward Driver". Tenant identity appears only inside the authenticated workspace (Profile shows the Driver's active organization from context).
Orientation "any": drivers mount phones landscape; a Fold unfolds near-square.
Scope "/" (not "/driver"): sign-in, select-organization and email-confirmation pages a Driver passes through must remain inside the standalone window; an out-of-scope hop would open a browser bar mid-flow.

============================================================
SERVICE WORKER
============================================================
Scope "/driver" (deliberately without trailing slash: a scope of "/driver/" would not control the start page /driver itself — found in the first E2E run and fixed). Emitted per build by src/lib/pwa/service-worker.ts; the unit tests execute the exact emitted source in a sandbox.
 - install: precache the public /offline page, its own CSS/JS/fonts and the icons/brand symbol with credentials omitted. It does NOT skipWaiting.
 - activate: delete older Nemryn caches, claim clients.
 - fetch: only GET, same-origin. Navigations: network only; on network failure serve cached /offline; any server response (401/404/500…) passes through unchanged. Allowlisted static assets (/_next/static, /pwa, /brand): cache-first, only ok+basic responses stored. Everything else: NOT intercepted.
 - message: SKIP_WAITING (update) and LOGOUT (purge).
 - No background sync, no periodic sync, no push handlers.

============================================================

============================================================
NETWORK FAILURE
============================================================
Lifecycle actions and Report Issue now treat an unreachable network as an explicit, retryable failure (isNetworkFailure): message "Can't reach Nemryn. Your update was not sent. Check your connection, then try again."; no optimistic state, nothing queued (no IndexedDB/localStorage), no replay; the screen keeps its context (page did not reload or navigate; state still "Assigned"); the button is enabled again; router.refresh is skipped for a network failure (it would itself fail). Report Issue is now controlled-input so React's post-action form reset cannot erase what the Driver typed; text and choice retained (verified). Server truth: trips.state and trip_events unchanged, no exception created while offline; after reconnect the retry succeeds exactly once (1 exception, 1 notification event). Design note: if only a RESPONSE is lost, a retry sends the same expected-current-state and the database returns STALE_STATE (existing ZW003 handling) instead of double-applying.

============================================================
UPDATE STRATEGY
============================================================
New deployment -> new sw.js bytes -> the browser installs a new worker that WAITS. DriverServiceWorker shows "A new version of Nemryn is available. [Update]". The app reloads only when the Driver taps Update (SKIP_WAITING -> controllerchange -> one reload). It also checks for updates on returning to the foreground and every 30 minutes. Verified across a real second build in the same browser profile: notice appeared, worker stayed "waiting", the page did NOT reload by itself (marker persisted, also after 4 more seconds), Update reloaded onto the new worker, the old build's cache was deleted, only the new build's cache remained, the Driver stayed signed in.

OPEN ISSUES
============================================================
1. Real-device verification is still needed before production: install on a physical iPhone (Safari Add to Home Screen, standalone status bar, safe areas, keyboard) and a physical Android phone/Galaxy Fold (install prompt, maskable icon crop, gesture nav). Everything here is emulated Chrome; iOS behaviours (service worker in standalone, home-screen icon) cannot be proven from this environment.
2. The manifest scope is "/" so links to /operations opened inside the installed app stay in-app; Operations is not an installable app and gets no worker. If this is not wanted, narrow scope later and accept a browser bar at sign-in.
3. The location tracker still degrades quietly on network failure (existing S7A behaviour) and does not use the new network indicator's failure event; S5B decides background/foreground location.
4. First-ever load has no controlling worker until the second visit (standard); the offline page becomes available after that first controlled load.
5. SW update detection relies on the per-build id: locally it is a timestamp; in production it is the Vercel commit SHA (VERCEL_GIT_COMMIT_SHA must be exposed to the build, which is Vercel's default). If it were missing, each build still gets a unique timestamp id.
6. Notification "Connected" banner timing constants (2s/6s/3s) are conservative defaults chosen without field data.
7. Production release is a normal deploy (no migration); rollback = redeploy the previous commit. A previously installed worker keeps its cache until the next visit replaces it.
