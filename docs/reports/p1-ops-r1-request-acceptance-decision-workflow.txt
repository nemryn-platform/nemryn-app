  pending -> declined   decline_transportation_request(org, req, p_reason text default null)
  pending -> cancelled  cancel_transportation_request(org, req); blocked by ANY linked Trip

PRODUCT DECISION   (implemented; recorded as ZD-204, amends ZD-054)
======================================================================
DECISION (stored state), explicit operator actions only:
  pending  -> accepted   Accept Request
  pending  -> declined   Decline Request   (reason required)
  accepted -> cancelled  Cancel Request    (reason required; only while no Trip exists)
  declined, cancelled    terminal. No reopen / undo / restore.
READINESS (derived, never stored): what still prevents an ACCEPTED Request from becoming a Trip. This is only the

ACCEPTED STATE
======================================================================
Meaning changed from "a Trip exists" to "the operator reviewed it and intends to service it". The CHECK constraint is
unchanged. Accepted may exist with no Passenger and no Trip. An accepted Request may produce any number of Trips (1:N
preserved).

======================================================================
READINESS SEPARATION
======================================================================
request-readiness-core.ts (pure, unit-tested) now takes hasLinkedTrips and returns:
  awaiting_decision  pending + active Passenger          ("Awaiting decision")
  needs_passenger    no active Passenger, pending or accepted-without-Trips ("Passenger needed", warning)
  ready              accepted + active Passenger + no Trip ("Ready to schedule")
  trip_created       accepted + >= 1 Trip                 ("Trip created")
  not_convertible    declined / cancelled
A pending Request is never "ready". An unknown state is never "ready".
deriveRequestActions() in the same module is the single UI gate for Accept / Decline / Cancel / Create Trip /
Create Another Trip / Link Passenger. It mirrors the RPC rules exactly; the RPCs remain the authority.
Request Hub gets hasLinkedTrips via a bounded embed (trips(id), limit 1 per row), so Accepted rows read "Trip
created" vs "Ready to schedule" correctly.
Copy: "Passenger needed -- Link or create the passenger before this request can be scheduled." (old "mark this
request ready" copy removed).

======================================================================
ACCEPT MUTATION
======================================================================
public.accept_transportation_request(p_organization_id uuid, p_request_id uuid) -> request_transition_result
SECURITY DEFINER, search_path pinned. auth.uid() required (ZW001). has_org_role(org, [organization_admin,
dispatcher]) (ZW002 otherwise). Request row locked FOR UPDATE before any state check.
  already accepted       -> changed=false, no event, no audit (idempotent)
  declined / cancelled   -> ZW004
  pending                -> UPDATE state only; request_accepted RequestEvent; AuditEvent
Touches NOTHING else: no Passenger, Trip, TripAssignment, Driver, Vehicle, provenance, requester or acquisition field.
Server action acceptRequestAction (org re-derived from session, never from the client). UI: direct primary button, no
confirmation (not terminal). The button shows loading/disabled while the action runs.

decline_transportation_request(org, req, p_reason_code text, p_reason_note text default null). The old (uuid, uuid,

pending -> declined only. accepted/cancelled -> ZW004. Already declined -> no-op.

Writes a request_declined RequestEvent (reason_code, reason_note) and an AuditEvent (before/after state + reason_code;

UI dialog: title "Decline this request?", copy "This request will be marked as declined and will not move forward to

======================================================================
CANCEL MUTATION
======================================================================
cancel_transportation_request(org, req, p_reason_code text, p_reason_note text default null). The old (uuid, uuid)
overload is DROPPED.
accepted -> cancelled only. pending/declined -> ZW004. Already cancelled -> no-op.
ANY Trip for the Request (any Trip state) -> ZW004. No cascade into Trips (unchanged locked rule).

scheduled. Manage cancellation from the linked trip." Dialog: title "Cancel this request?", copy "This accepted request
will no longer move forward. Previous request history will remain available." Required reason.

======================================================================
REASON MODEL
======================================================================
No existing taxonomy existed (decline reason was optional free text; cancel had none). Stored on the immutable decision
record, request_events, as two typed columns rather than a jsonb blob, so the question is a plain GROUP BY:
  select reason_code, count(*) from request_events where event_type = 'request_declined' group by 1;
Columns rather than transportation_requests fields, because the event row is the append-only evidence of the decision
(actor, time, reason together) and there is exactly one decision event per terminal transition.
  request_events.reason_code  CHECK: only on request_declined / request_cancelled; closed per-event set
    decline: outside_service_area, no_availability, unsupported_transportation_need, requested_time_unavailable,
             duplicate_request, other
    cancel:  requester_cancelled, no_availability, unable_to_reach_requester, duplicate_request, other
  request_events.reason_note  CHECK: 1..500 chars, trimmed; required when reason_code = 'other'
  request_events_decision_reason_required  CHECK ... NOT VALID: every NEW decline/cancel event must carry a code.
    Historical rows (optional metadata.reason, or none) are deliberately not re-validated.
  Partial index (organization_id, event_type, reason_code) where reason_code is not null.
The app's code lists (request-decision-reasons.ts) are unit-tested to match the migration's constraint text exactly.

business decision from the one the operator clicked. Why not B (two app deploys): more moving parts for the same
result; the old UI already never generates new-model calls, and the new UI never generates old ones.
Why C is safe for the new state model: every row the legacy paths can write during the window has a shape
production ALREADY holds from before R1:
  - legacy decline: pending -> declined, optional free-text metadata.reason, no reason_code  (= all pre-R1 declines)
  - legacy cancel:  pending -> cancelled, no reason, only while no Trip exists           (= all pre-R1 cancels)

None of them can act on a new-model state. The legacy cancel refuses an ACCEPTED Request (ZW004, tested), so it
can never cancel something the new app accepted. Every path takes the same Request row lock, so the race
guarantees are unchanged. The only cost is that decisions made by the OLD app during the minutes-long window carry
no structured reason, exactly like history. Documented; no invented decision.
