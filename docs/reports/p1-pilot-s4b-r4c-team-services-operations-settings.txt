================================================================================
STAFF INVITATION MODEL
================================================================================
Table staff_invites (RLS on, zero policies, zero grants): organization_id, email,
role in (organization_admin, dispatcher), token_hash, status (pending|accepted|
cancelled), expires_at (7 days), invited_by, accepted_by/at. "expired" is derived.
Unique pending invitation per (org, lower(email)); cap 25 pending per org.
Functions: create_staff_invite(org, email, role), resend_staff_invite(id),
cancel_staff_invite(id), get_staff_invite_preview(token) [anon+authenticated],
accept_staff_invite(token), list_staff_invites(org). The browser supplies only an
email and one of two roles; the org is the session workspace and is re-authorized by
has_org_role. Driver/platform/unknown roles -> ZW006. An email that already holds an
ACTIVE staff or ANY driver Membership of this org is refused; an INACTIVE staff member
can be invited back. The admin UI says only "Invitation sent." -- never whether the
address has an account.

================================================================================
EXISTING USER INVITE
================================================================================

email; it creates the Membership for THAT org with THE INVITED role and leaves every

NEW USER INVITE
================================================================================
/team-invite/<token>: signed-out -> "Join <Org>" + role, sign-up form with the invited

================================================================================
INVITE TOKEN SECURITY
================================================================================
256 random bits (pgcrypto), hex, returned exactly once to the calling server action for
the email, never stored: only SHA-256 is persisted (verified in the DB: token_hash =
sha256(token), raw token absent from the table and from audit rows). Never logged,
never returned to the browser. Lookup is by hash; malformed/short tokens -> ZW002
without touching the table. Preview is anon-callable (deliberate, same precedent as
get_driver_invite_preview) and returns only organization name, invited email, role and
effective status (composite has exactly those four fields). function_privilege_tests
allowlist updated to name this second deliberate anon exception. Acceptance takes only
the token: no org/role/user parameter exists, so cross-org acceptance, another
identity, or role tampering is structurally impossible; a token for another email ->
ZW002; used tokens cannot be reused by anyone else.

================================================================================
INVITE EXPIRY / CANCEL / RESEND
================================================================================
Expiry 7 days; expired -> ZW003 and page "Invitation expired"; Admin list labels it
Expired. Cancel (pending only): row kept, token dead ("Invitation no longer
available"), audited. Resend = re-issue: fresh token + fresh expiry; the OLD link then
resolves to "Invitation not found" (never two valid tokens); works on expired-pending
invitations; not on accepted/cancelled (ZW003). A create for an email that already has
a pending invitation re-issues it (one row). Email delivery outcome is reported
honestly ("The invitation was created, but the email couldn't be sent. Use Resend.").

================================================================================
LAST ADMIN SAFETY
================================================================================
Cannot demote or deactivate the last ACTIVE Organization Admin (ZW004 last_admin,
"Every organization needs at least one active Organization Admin"), including
self-management; inactive admins do not count. Self-demotion/deactivation is allowed
only while another active Admin remains (confirmation copy says so). Serialized per
organization with pg_advisory_xact_lock; the caller is RE-AUTHORIZED after taking the
lock (an Admin removed by a concurrent transaction cannot complete one more admin
action). UI evidence: second Admin deactivates themselves (allowed); the sole Admin's
"Change to Dispatcher" and "Deactivate access" both show the clear error and change
nothing.
