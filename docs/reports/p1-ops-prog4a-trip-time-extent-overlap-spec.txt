2. PRODUCT DECISIONS (APPROVED, CARRIED INTO THIS SPEC)
======================================================================
  D1  Duration is operator-entered per trip, with an OPTIONAL organization default that the trip value overrides.
      There are no facility defaults, no route-derived durations, no external routing and no historical inference.
  D2  There is no Nemryn default. With no trip value and no organization default, the time extent is UNKNOWN.
  D3  Snapshot semantics: see §5. The recommendation is to SNAPSHOT at creation.
  D4  An overlap is a WARNING only. It never blocks, removes, reassigns or cancels.
  D5  An overlap is claimed only when BOTH intervals are known. UNKNOWN means no claim.
  D6  Resources: same driver and same vehicle only.
  D7  Running-late stays DEFERRED. No schema is added now (see §17).
  D8  Dispatch shows proportional blocks for known extents and an honest treatment for unknown ones.
  D9  Dispatch gets a Tomorrow scope on the same model. The /operations/tomorrow readiness page stays.
  D10 No drag-and-drop.
  D11 No PROG5 scope: shifts, time off, out-of-service windows, "available" and capabilities are all excluded.
  D12 No routing, traffic, deadhead, nearest-driver, sequencing, scoring or automated dispatch.

3. RECOMMENDED DATA MODEL
======================================================================
trips (additive, nullable):
  expected_duration_minutes  integer NULL
    CHECK (expected_duration_minutes IS NULL OR expected_duration_minutes BETWEEN 1 AND 2880)
  expected_duration_source   text NULL
    CHECK (expected_duration_source IN ('trip', 'organization_default'))
    CHECK ((expected_duration_minutes IS NULL) = (expected_duration_source IS NULL))
organizations (additive, nullable):
  default_trip_duration_minutes integer NULL
    CHECK (default_trip_duration_minutes IS NULL OR default_trip_duration_minutes BETWEEN 1 AND 2880)
Derived, never stored: expected_end_at = scheduled_pickup_at + expected_duration_minutes * interval '1 minute'.
It exists only when both are non-null.
Why duration rather than an end timestamp:
  - The duration is what an operator knows ("about 45 minutes").
  - It survives pickup-time edits: the end moves with the pickup.
  - It is DST-safe: minutes are absolute, and the arithmetic is in UTC.
  - It gives one source of truth.
Why a source column:
  - It is honest copy: "45 min (organization default)" versus "45 min".
  - It is audit clarity: a snapshot from the default is distinguishable from an operator entry, without guessing.
No backfill: every existing trip stays NULL / NULL, which means UNKNOWN.
Upper bound 2880 (48 h) -- OWNER DECISION Q1: an integrity ceiling only, chosen so legitimate long-distance medical
transports longer than 24 h are never rejected, and to keep the overlap candidate window finite (§8). It is NEVER a
default duration.

======================================================================
4. ALTERNATIVES REJECTED
======================================================================
  B. expected_dropoff_at only
     - The end would need recomputing whenever the pickup is edited, or it would silently diverge.
     - Operators do not think in drop-off timestamps for transport planning.
     - Its DST and day handling is error-prone in forms.
  C. Both a duration and an end
     - Two sources of truth that can contradict each other, which needs invariants or triggers. There is no benefit
       at this stage.
  D1. A dynamic organization default (inherited at read time)
     - Changing the default would silently rewrite the implied extent of every existing trip, including past and
       in-progress ones.
     - Overlap warnings on already-planned days would appear or disappear without any operator action.
     - It violates the rule of historical truth.
  D2. Per-facility, per-passenger or per-arrangement defaults, or historical averages
     - Out of scope by owner decision D1. Per-arrangement is listed as Q3.
  D3. Using appointment_at as the end
     - The appointment is a destination commitment, not a drop-off. Inferring from it contradicts D1.
  D4. A range type (tstzrange) column with an exclusion constraint
     - An exclusion constraint would BLOCK overlaps, which contradicts D4.
     - A stored range duplicates the start and must be kept in sync.
     - The pure derivation in memory is sufficient at the target scale.

======================================================================
5. ORGANIZATION-DEFAULT SEMANTICS (D3)
======================================================================
Recommendation: SNAPSHOT AT CREATION, inside create_trip:
  - If p_expected_duration_minutes is given, store it with source 'trip'.
  - Else, if organizations.default_trip_duration_minutes is not null, store it with source 'organization_default'.
  - Else store NULL / NULL (unknown).
Consequences:
  - The organization changes its default tomorrow: existing trips are unchanged. Only trips created after the change
    use the new default. The Settings copy says so.
  - Previously created trips never change implicitly. Changing a trip's duration requires an explicit operator
    action per trip (§7). A bulk "apply the default to upcoming trips without a duration" action is NOT in PROG4B
    (Q2).
  - Recurring occurrences: generated through create_trip, so they snapshot the default in force at GENERATION time.
    Deterministic, since the same inputs give the same stored value.
  - Edited pickup time: the duration is kept and the derived end moves with the new start.
  - Imported / intake-created requests: requests carry no duration. The trip created from a request follows the
    ordinary New Trip rules (operator value, or the default snapshot).
  - An operator clears a trip's duration: it becomes UNKNOWN (NULL/NULL). The default is NOT re-applied, so an
    explicit "unknown" is respected.

======================================================================
6. TRIP TIME-EXTENT SEMANTICS
======================================================================
Interval for a trip = [scheduled_pickup_at, scheduled_pickup_at + expected_duration_minutes) (half-open, UTC).
  - KNOWN only when scheduled_pickup_at IS NOT NULL and expected_duration_minutes IS NOT NULL.
  - UNKNOWN otherwise. There is no substitution, no estimate and no display of a made-up end.
  - Display: start–end in the organization timezone ("9:30–10:15 AM"; when crossing midnight, "11:30 PM – 12:45 AM
    (next day)").
  - The extent is PLANNED, not actual: in-progress and completed trips keep their planned interval. Actual times are
    lifecycle facts (trip_events / completed_at) and are never overwritten by the plan.

8. OVERLAP DERIVATION (ONE CANONICAL PURE MODEL)
======================================================================
Module: src/lib/operations/trip-overlap-core.ts (pure, unit-tested; the same code runs for every surface).
Input: the target interval, plus candidate trips with {tripId, state, scheduledPickupAt, expectedDurationMinutes,
activeDriverId, activeVehicleId}.
Rules:
  - Intervals are half-open [start, end). A and B overlap iff A.start < B.end AND B.start < A.end.
      - Touching boundaries (A.end == B.start): NO overlap.
      - Partial overlap, full containment and identical intervals: overlap.
  - Only ACTIVE assignments count: ended_at IS NULL. Reassignment history (ended rows) is ignored.
  - Candidate states: scheduled plus the five in-progress states. completed, cancelled and no_show are EXCLUDED; a
    completed trip's plan is history, not a commitment.
  - A same-trip pair is excluded. For a hypothetical assignment (the dialog), the target's resources are the
    SELECTED driver/vehicle.
  - Resource match: driverOverlap if activeDriverId == target driver; vehicleOverlap if activeVehicleId == target
    vehicle and both are non-null. Different resources never match.
  - UNKNOWN: if the target interval is unknown, or a candidate's is, that pair is "not checkable".
      - It is never "overlapping" and never "clear".
      - The output counts uncheckable same-resource candidates so the UI can say so factually.
  - Output per target:
      { driverOverlaps: tripId[], vehicleOverlaps: tripId[],
        driverUncheckable: number, vehicleUncheckable: number,
        targetKnown: boolean }
    There is no score, no ranking and no probability.
Candidate window: every trip whose START is in [dayStart − 2880 min, dayEnd). The 48-hour bound makes it complete
for any trip whose PLANNED interval can reach the day, including across midnight.
AMENDED (owner decision Q7): the candidate set ALSO includes every older still-non-terminal trip that holds an active
assignment. Its commitment past an expired planned end is UNRESOLVED (see §8a).

======================================================================
8a. AMENDMENT (OWNER DECISION Q7) -- STILL-OPEN TRIPS PAST THEIR PLANNED END
======================================================================
A planned extent does not prove that a resource became free when the plan ended. Take a candidate that:
  - still holds an ACTIVE assignment;
  - is still NON-TERMINAL (scheduled or in progress);
  - has a KNOWN planned end that is earlier than `now`.
Its commitment AFTER that planned end is UNKNOWN. Nemryn neither extends it to an invented end nor calls it clear.
The pure derivation therefore distinguishes four outcomes per resource:
  1. KNOWN OVERLAP: the target intersects a candidate's planned interval. A still-open candidate's planned portion
     can still produce a known overlap.
  2. KNOWN NON-OVERLAP: every same-resource candidate has a known interval, none intersects, and none is unresolved.
  3. NOT CHECKABLE (missing extent): the target or a candidate has no scheduled start or no duration.
  4. NOT FULLY CHECKABLE (still open past its planned end): a still-open candidate's expired planned end is before
     the END of the target interval, so the time after it cannot be judged.
     - This is NOT an overlap and NOT clear.
     - Copy: "Can't fully check this driver: an assigned trip has passed its planned end and is still open."
     - The same applies to vehicles.
This is not running-late: no threshold, and never the word "late". `now` is a factual input to the pure function.

10. ONE-VEHICLE UX
======================================================================
  - The organization sets a default once (Settings → Operations → "Default trip duration", optional). New trips then
    carry it with no typing, and the field shows "45 min · organization default" and can be changed.
  - Without a default, the field is empty: "Not set". Nothing nags, nothing blocks, and no overlap is claimed.

  - Dispatch stays a simple one-row board. Blocks gain real widths, and there are no new controls.
  - PROG1/2 behaviour is unchanged: prefills, "(you)", Assign now, Tomorrow actions.

11. GROWING-FLEET UX (NO SIZE MODES)
======================================================================
The same model scales by facts alone:
  - 1 → 3 vehicles: warnings help when juggling two drivers.
  - 10: the Dispatch grid with proportional blocks shows free and busy spans per driver at a glance.
  - 30+: the Tomorrow scope on Dispatch plus the overlap count make next-day balancing practical.
Nothing reads business_stage, vehicle counts or membership counts. Warnings appear only where facts exist, so a
larger operation sees more of them only because it has more overlapping commitments.

20. MIGRATION STRATEGY
======================================================================
ONE expand-only migration, for example 2026MMDDhhmmss_trip_expected_duration.sql, in a single transaction:
  1. alter table trips add column expected_duration_minutes integer, add column expected_duration_source text,
     plus the three CHECKs (NOT VALID is unnecessary, since every existing row is null and passes).
  2. alter table organizations add column default_trip_duration_minutes integer, plus the CHECK.
  3. drop function create_trip(11 args); create function create_trip(12 args, trailing default null) with the §5
     snapshot. Re-comment; revoke all from public; grant execute to authenticated.
  4. create set_trip_expected_duration and update_organization_trip_defaults, with revoke / grant.
  5. No data backfill.
  6. Update the column / table comments.
Why a single migration and not expand/contract:
  - The change is purely additive, and the new parameter is trailing with a default. The currently deployed app
    (11 named arguments) and the recurring function (5 positional) both resolve to the new function immediately.
  - No behaviour changes for callers that don't pass it: they get the organization default snapshot, which is null
    until an admin sets one.
