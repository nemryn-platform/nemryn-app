4. DATA-MODEL RISKS RESOLVED
=====================================================================================================
  R-1 request_id uniqueness conflict: plus_opportunity_requests is REPLACED by plus_request_attributions
      with request_id as PRIMARY KEY and three independent nullable dimensions (contact_id,
      opportunity_id, referral_account_id). One attribution per Request -> no double counting; private-pay
      booking credit and facility-referral credit coexist on one row; reports count once per dimension
      and never sum across dimensions (domain model section 8; PD-06).
  R-2 Stage drift between Plus and Core: post-conversion stages (Booking pending / Booked / Served /
      Declined / Cancelled) are DERIVED at read time, never stored; no Core triggers (PD-05).
  R-3 Opportunity vs repeat booking confusion: rebookings attach to contact_id with link_method
      'rebooking'; recurring uses Core Recurring Care.
  R-4 Location double counting: plus_account_facilities has unique(facility_id).
  R-5 Duplicate conversion: opportunity FOR UPDATE + unique (organization_id, conversion_idempotency_key).
  R-6 Unsafe identity matching: no passenger_id anywhere in Plus; conversion passes passenger_id null;
      contact<->passenger only via staff-linked Requests.
  R-7 Table sprawl: plus_opportunity_attributions DROPPED for v1 (3 columns on opportunities + Core's
      existing request_acquisition_attributions); polymorphic subject ids avoided (typed FKs +
      num_nonnulls checks); no metadata jsonb on activities.
  R-8 Manual payment status misread as settlement: named payment_reported_status, always labelled
      "reported", never revenue (PD-09).
