2. ORIGINAL FAILURE MODE
-----------------------------
Read `docs/reports/p1-e1-s2d-request-hub-queue.txt` §32 in full before
starting. Original bug (already fixed in S2D itself, at the query
level): `transportation_requests` carries two foreign keys to
`passengers`, making the unqualified `passengers(...)` embed ambiguous
to PostgREST (error PGRST201). Before that fix, and structurally still
true of every OTHER query in the file even after that specific fix:
`getRequestsList`'s error handling converted any query error into
`rows: []` while independently-succeeding count queries kept reporting
real numbers — producing a page that looked like a genuinely empty,
caught-up queue when it was actually a failed data load. This phase
closes that class of bug at the CONTRACT level, not just the one query
that happened to trigger it once.


3. QUERIES AUDITED
-----------------------
Read `requests-list.ts` and `page.tsx` in full and enumerated every
query Request Hub depends on, confirming each one's PRE-R1 failure
behavior first (§6-§9 of the phase spec explicitly warned against
assuming only the main query can fail):

  a. Main row query (`transportation_requests` select, embedded
     Passenger relation, search filter, ordering, `.range()`) —
     PRE-R1: `if (error || !data) return { rows: [], totalCount: 0,
     ... }` — the exact bug already documented in S2D §32.

  b. Pending count (`transportation_requests`, `state=pending`,
     `head:true`) — PRE-R1: `const { count: pendingCount } = await
     ...` — the `error` field was not even destructured. On failure,
     Supabase returns `count: null`, so `pendingCount ?? 0` silently
     became `0` — indistinguishable from a genuine zero-pending
     organization.

  c. Organization-total count (`transportation_requests`, no state
     filter, `head:true`, powers `organizationHasAnyRequests`) —
     PRE-R1: same pattern, error silently discarded.
     `organizationTotalCount ?? 0` silently became `0` on failure,
     which would have rendered empty-state A ("No requests yet") for
     an organization whose real history is simply unknown — arguably
     the most misleading of the four silent failures, since it
     actively fabricates a specific, wrong claim rather than just an
     empty table.

  d. Passenger-id search-resolution query (`passengers`, only runs
     when `?q=` is present) — PRE-R1: `const { data: matchingPassengers
     } = await ...` — error not even destructured. On failure,
     `matchingPassengers` is `null`, `(matchingPassengers ?? []).map
     (...)` silently became `[]`, and the main query's `.or()` filter
     was built WITHOUT the Passenger-linked branch — a search could
     silently return an INCOMPLETE result set with no indication
     anything was wrong. This is the case explicitly called out in
     phase §7.

There is no separate pagination/count query — `totalCount` comes from
the SAME `count: "exact"` option on the main query (query a), so its
failure mode is identical to (a), not a fifth independent case.


4. FINAL RESULT / ERROR CONTRACT
-------------------------------------
Chosen approach: an explicit discriminated result type on
`getRequestsList`'s own return value (the "smallest architecture
consistent with existing code" instruction, §4) — scoped to Request
Hub only, no repository-wide list-helper refactor, `trips-list.ts` and
every other list helper untouched.

    export interface RequestsListSuccess {
      ok: true;
      rows: RequestsListRow[];
      totalCount: number;
      page: number;
      pageSize: number;
      pendingCount: number;
      organizationHasAnyRequests: boolean;
    }

    export type RequestsListErrorCode =
      | "requests_query_failed"
      | "pending_count_failed"
      | "org_total_count_failed"
      | "passenger_search_failed";

    export interface RequestsListFailure {
      ok: false;
      errorCode: RequestsListErrorCode;
    }

    export type RequestsListResult = RequestsListSuccess | RequestsListFailure;

Each of the 4 queries audited in §3 now has its own explicit `if
(error) { ...; return { ok: false, errorCode: "..." } }` guard,
placed immediately after that query executes, in call order: search-
resolution (only when a search term is present) → main rows+count →
pending count → organization-total count. The very first one to fail
short-circuits the whole function — no partial result is ever
assembled. TypeScript's discriminated-union narrowing means
`page.tsx` cannot access `.rows`/`.pendingCount`/etc. without first
checking `result.ok` — this was enforced by the compiler, not just by
convention (confirmed by the clean `tsc --noEmit` pass, §12).

No raw Supabase/PostgREST error object, message, or code is exposed
anywhere in the returned type or in what `page.tsx` renders — the UI
layer only ever sees `result.ok === false`, never `errorCode` (it
exists purely for server-side diagnostic logging, §9).


5. UI ERROR STATE
----------------------
No new component was built. Reused the EXISTING `AttentionState`
component (`src/components/ui/AttentionState.tsx`) — already built,
already documented in its own code as "distinct from EmptyState, which
is neutral," already has a `critical` level (red/critical border+
background, `WarningOctagon` icon) that no other Request Hub surface
uses. This satisfies §4/§13 by construction: the "possibly one small
error-state component" the phase spec anticipated turned out to be
unnecessary.

`page.tsx`, on `!result.ok`:
  - Keeps `PageHeader` (title, description, "Log Request" action) —
    Log Request is a functionally independent feature; an operator
    can still record a request by phone even while the QUEUE READ is
    failing, so it stays reachable.
  - Renders NOTHING ELSE from the normal success layout (no
    SummaryStrip, no status tabs, no search form, no table, no
    pagination footer) — replaced entirely by one `AttentionState`:
      level="critical"
      title="Unable to load requests"
      description="Request information could not be loaded. Try again."
      action={<LinkButton href="/operations/requests" variant="outline">Retry</LinkButton>}

"Retry" is a plain link back to the same URL — a fresh GET request,
fresh server render, fresh query attempt — the same mechanism already
used by `RequestsTable`'s own "Clear filters" empty-state action, no
new client-side retry/polling logic invented.

Live-confirmed (screenshot, §10): visually and texturally distinct
from every EmptyState A/B/C — red-tinted bordered banner with a
warning-octagon icon vs. EmptyState's neutral centered box — genuinely
impossible to mistake for "no requests exist."


6. PARTIAL-QUERY FAILURE BEHAVIOR
--------------------------------------
Per phase §6 ("prefer correctness over partial presentation"): ANY of
the 4 queries failing is treated as a full page-level load failure —
there is no degraded/partial render path. Concretely:
  - Main query fails, pending count would have succeeded → FAILURE
    shown, no "N pending" figure rendered at all (never partially
    trusted).
  - Pending count fails, main rows would have succeeded → FAILURE
    shown — rows are never rendered without a trustworthy pending
    figure alongside them, since the two are read together as one
    page state.
  - Organization-total-count fails → FAILURE shown, never silently
    resolved to `organizationHasAnyRequests: false` (which would
    incorrectly trigger empty-state A's specific "brand-new
    organization" claim).
This was live-verified for all 4 individual query-failure sources,
not just asserted — see §10.


7. SEARCH FAILURE BEHAVIOR
-------------------------------
The Passenger-id resolution query's error now short-circuits the
ENTIRE function before the main query is even built — a failed search
resolution can never silently fall back to "zero Passengers matched"
and continue. Live-verified with an explicit combined case: a real
search request (`?state=all&q=Marguerite`) with the search-resolution
query forced to fail renders "Unable to load requests," not a
(potentially incomplete) result table — confirmed the table is not
rendered at all in this case (§10).


8. COUNT / PAGINATION FAILURE BEHAVIOR
---------------------------------------------
`totalCount` is sourced from the same `count: "exact"` option as the
main rows query — a single Supabase call, not two — so it shares that
query's own error guard exactly; there is no separate path where rows
could succeed while their own count silently reports 0/1-page/no-
requests. Confirmed by direct code reading: `count` is only read from
the SAME destructured `{ data, error, count }` that already gates on
`error`.


9. PII-SAFE LOGGING
------------------------
A single small logging helper:

    function logRequestsListFailure(operation: string, error: { code?: string } | null): void {
      console.error(`[requests-list] ${operation} failed`, { code: error?.code ?? "unknown" });
    }

Called at each of the 4 failure points with a static operation name
("passenger_search" / "requests_query" / "pending_count" /
"org_total_count") and ONLY `error.code` (a short Postgres/PostgREST
SQLSTATE-style string, e.g. "42501") — never the full error object,
never `error.message` (which can occasionally echo back filter
values), never any row data, requester name, phone, email, address,
or note. Confirmed by direct code reading — this is the entirety of
what reaches the log on every one of the 4 failure paths, with no
other logging statement added anywhere in this phase.
