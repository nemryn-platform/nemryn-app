3. EXISTING ARCHITECTURE FINDINGS
---------------------------------
F1 Contacts (20261014100000_plus_contacts_activities.sql)
   - plus_contacts has:
     - unique (id, organization_id), the target for tenant-isolating composite FKs;
     - phone / email normalised by CHECK;
     - preferred_channel in (phone, email, none);
     - do_not_contact boolean ("Every FUTURE outbound action must refuse when true");
     - status active / archived / redacted ("redacted" is reserved; no function sets it before PD-11).
   - Reads go through plus_get_contact; a foreign / unknown / redacted contact gives ZW002 (no oracle).
   - Writes are create / update / archive. plus_update_contact is the ONLY path that changes do_not_contact:
     - it uses a version token (ZW003);
     - archived contacts give ZW004;
     - it audits the NAMES of changed fields only.
F2 Activities: plus_activities is append-only. There is no update / delete privilege, policy or function (T20).
   - The activity_type CHECK has been replaced additively by named constraint, most recently in 20261021100000:54.
     "consent_recorded" is not in it, and staff cannot log it:
     - L4 in plus_contacts_activities_tests.sql:330;
     - src/lib/plus/contacts-core.test.mjs:26.
   - plus_log_contact_activity shows the established patterns:
     - FOR NO KEY UPDATE on the contact to serialize writers;
     - a 30-second duplicate guard;
     - ZW004 for archived contacts.
F3 Access helpers (20261013120000, replaced by 20261013160100):
   - plus_can_read / plus_can_write are grant-aware;
   - _require_plus_write gives ZW002 (cannot read) or ZW001 (readable but not writable);
   - read_only means Admin-only reads with no writes; locked / none mean nobody;
   - Drivers, inactive members, suspended organizations and Platform Admins without a membership are always refused.
F4 Owner eligibility: _plus_user_can_write(org, user) is reusable for "is this person a Plus writer".
F5 Idempotency: _plus_require_idempotency_key (20261015140000:100) validates 8–200 characters of [A-Za-z0-9._:-]. It
   is owner-internal and reusable.
F6 Audit: audit_events (20260830131500) is system-owned and append-only, readable by Organization Admins.
   - The Plus convention is entity_type 'plus_contact' and actions plus_contact_*, with field NAMES only and never
     values. Plus actions are not in the Core Settings → Activity allow-list.
F7 DNC handling today:
   - a badge and definition on Contact Detail;

4. CONTRACTS P2-S6 MUST PRESERVE
--------------------------------
C1 RLS deny-by-default. Client SELECT only, via plus_can_read. No client insert / update / delete (access model §3.2).
C2 Every write RPC calls _require_plus_write first. No existence oracle: foreign, unknown and unauthorised all give
   ZW002.
C3 Tenant isolation by composite FK (id, organization_id), not by policy alone (T12).
C4 Append-only for activities and consents (T20). No function updates or deletes either.
C5 read_only never writes (T6). Grant holders lose read in read_only. locked / none mean no access (T6a / T7).
C6 do_not_contact semantics:
   - a stored preference, changed only through plus_update_contact;
   - reminders never block Core Requests;
   - the ZD-223 acknowledgment is not consent;
   - Growth Agent drafts are suppressed for DNC.
C7 Nothing is sent, called or scheduled. Plus has no service-role path (access model §1.4). No Core change; Core never
   calls Plus helpers.
C8 audit_events records field names / enumerations, never contact values. The Core Activity allow-list is unchanged.
C9 Privilege contract: every new object is listed with a decided ACL. Privilege contract 0 violations in production
   after release.
C10 Free-text C6 notice ("Don't record medical details").
C11 Synthetic data only until PD-10 / PD-11 close.
C12 PD-12: Plus enquiry consent (S7) never touches Core intake objects.
C13 Brand Lock v2 / V2 UI:
    - raised panels with icon headers;
    - one teal primary per view;
    - destructive-outline only for destructive triggers;
    - the EmptyState anatomy;
    - dialog keyboard behaviour.
C14 Existing regression baselines unchanged:
    - QA2 199;
    - P1a 48 / P1b 52;
    - Quotes 272;
    - the 15 SQL suites;
    - unit tests;
    - the a11y sweep.

5. DESIGN VERIFIED AGAINST THE CONTRACTS
----------------------------------------
| Contract | How the design complies |
|---|---|
| C1 | One SELECT policy (plus_can_read); no write privilege; column-level SELECT recommended (OD-S6-12) |
| C2 | Both write RPCs start with _require_plus_write; read RPCs use the plus_get_contact error semantics |
| C3 | (contact_id, organization_id) FK and a (corrects_consent_id, organization_id, contact_id) self FK |
| C4 | No update / delete function; plus triggers that refuse UPDATE / DELETE / TRUNCATE for every role |
| C5 | ZW001 in read_only for grants AND revocations (OD-S6-11 A); readers per plus_can_read |
| C6 | DNC overrides in the resolver. Grants refused while DNC; revocations allowed. DNC switch-on appends revocations (OD-S6-5 B is the ONE change to a released function body, signature unchanged). Booking / quote / Agent DNC behaviour untouched |
| C7 | No sending, no service role, no route handler, no Core object, no proxy / config change. The effective resolver has no client grant |
| C8 | audit after_data = consent id, channel, purpose, method, correction flag. No note or address |
| C9 | Every table / function is added to the allow-lists in the same change |
| C10 | The note carries the C6 notice; 500-character limit |
| C11 | Synthetic only; the release does not imply real data (OD-S6-13) |
| C12 | Only a future inquiry_id → plus_inquiries; no Core FK (test P22) |
| C13 | Panel after Details; outline "Record consent"; no new teal; existing Dialog / RadioGroup / EmptyState |
| C14 | Timeline untouched (OD-S6-8 B); only additive tests and one strengthened side-effect counter |

6. SUMMARY OF THE PROPOSAL (details in the design document)
-----------------------------------------------------------
- Schema: plus_communication_consents (§2 of the design):
  - channel email / sms / voice;
  - purpose service_followup / marketing;
  - status granted / revoked;
  - staff methods;
  - server-set actor, time and sequence;
  - address digest;
  - corrections;
  - idempotency key.
- Rules (§3):
  - A, recorded = the latest row by seq;
  - B, effective = archived / DNC suppression, then the recorded state, then the address match;
  - C, lawful permission = never computed; the UI never says "allowed".
- RPCs (§4):
  - plus_get_contact_consents, plus_list_contact_consent_events (read);
  - plus_record_consent, plus_revoke_consent (write);
  - internal _plus_effective_consent and _plus_consent_address_digest;
  - the plus_update_contact body gains the DNC revocation step.
- UI (§5): Contact Detail → "Communication preferences" panel: a state table, history, dialogs, the DNC warning, the
  empty state.
- Privacy (§6): every PD-10 / PD-11 dependency is marked. Everything can be built and tested on fictional data.
- Tests (§7): the new SQL suite P1–P23, a concurrency script, deliberate contract updates, E2E and a11y.
- Slices (§8):
  - S6-A database;
  - S6-B application;
  - S6-C release.
  Each needs separate owner authorization.
