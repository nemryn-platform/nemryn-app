CURRENT OWNER-OPERATOR AUDIT (read fresh, nothing assumed)
======================================================================
The capability ALREADY existed (P1-E3-S9 "Owner-Operator Mode"); S5A1 hardened and
surfaced it rather than building it.

- First-run onboarding: /onboarding/driver, "Do you also drive?", button
  "Yes, I also drive" (+ "Not right now"). Server action setOwnerAlsoDrivesAction
  called the RPC link_self_as_driver directly.
- Self-driver RPC: public.link_self_as_driver(p_organization_id, p_display_name,
  p_phone) SECURITY DEFINER, EXECUTE to authenticated only (anon revoked).
  Returns owner_driver_link_result (driver_id, organization_id, linked).
- Schema: public.drivers (id, organization_id, user_id nullable FK auth.users ON
  DELETE SET NULL, display_name NOT NULL, phone, status 'active'|'inactive',
  timestamps; UNIQUE (id, organization_id)). A Driver is an operational resource,
  not an auth identity. Status vocabulary: active / inactive.
- Driver <-> auth user: drivers.user_id. Set ONLY by link_self_as_driver and
  redeem_driver_invite (client UPDATE of user_id was retired in S9).
- Membership <-> Driver: independent. Membership.role in {organization_admin,
  dispatcher, driver}; a Driver row does not imply a Membership and vice versa.
- current_driver_id(org): active drivers row for auth.uid() AND active Membership
  (ANY role) AND active organization (R4E). Unchanged by S5A1.
- requireDriverAccess(): lets organization_admin/dispatcher through to the SAME
  driver_get_profile RPC; if no linked Driver they are sent back to /operations.
  Navigation only; the database decides. Unchanged.
- Drive navigation: operations layout calls current_driver_id() live and passes
  hasLinkedDriverProfile to the sidebar; "Drive" is appended only when it resolves.
  Role alone never shows it. Unchanged (verified).
- Driver profile requirements: display_name required (<=200); phone optional.
  Nothing else is required by the schema or business logic.
- Activation/deactivation: there is NO controlled deactivate/reactivate mutation
  and NO UI for it. drivers.status can only change by an Organization Admin's raw
  UPDATE grant (display_name, phone, status), unused by the app.
- Assignment: active assignment = trip_assignments.ended_at IS NULL (one active
  per trip). assign_trip rejects unknown/inactive drivers (ZW006).
- Audit: audit_events row 'driver_self_linked' (new row only) already written by
  link_self_as_driver; invites write driver_invite_created/revoked/redeemed.
- Duplicate prevention BEFORE S5A1: function-level only, and only for ACTIVE rows.
  No unique constraint.
- Driver invitation/redeem flow: create_driver_invite (Org Admin) ->
  /join/[token] -> redeem_driver_invite (email match, driver-only Membership if none,
  reuses an existing ACTIVE linked Driver else inserts).

GAPS FOUND in link_self_as_driver (all fixed in S5A1):
  1. Any ACTIVE member (Admin, Dispatcher, Driver) could self-link. Pilot rule is
     Organization Admin only.
  2. An INACTIVE linked Driver made it INSERT a second Driver row (duplicate).
  3. No schema-level guard against two ACTIVE Driver rows for one (org, user)
     under a race.
  4. No protection against silently creating a look-alike beside an UNLINKED Driver
     with the same name.
  5. The audit action was not visible in tenant Settings -> Activity.

DUPLICATE HANDLING  (deterministic per state)
======================================================================
A. no Driver row for this user/org  -> create new row (audit driver_self_linked)
   - unless an UNLINKED Driver in the org has the same name (case/space-insensitive):
     ZW003 driver_identity_conflict, nothing written, message tells the person to
     contact Nemryn support. A different name is never matched; the unlinked row is
     never claimed.
B. linked ACTIVE row                 -> returned unchanged, linked=false (idempotent)
C. linked INACTIVE row (exactly 1)   -> reactivated, same row, audit driver_self_reactivated
   linked INACTIVE rows (>1)         -> ZW003, nothing changed, "Needs attention" in UI
D. unlinked look-alike               -> see A (fail safe, never linked by name/phone/email)
E. pending Driver invite             -> not blocking. If the admin later redeems an
   invite to their own email, redeem_driver_invite reuses the existing ACTIVE linked
   Driver (no duplicate). Invites are never matched by name.
F. multiple organizations            -> see MULTI-ORG.
