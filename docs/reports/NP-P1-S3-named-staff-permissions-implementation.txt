======================================================================
Verified on the local schema before writing the migration:
- memberships constraints: pkey (id), unique (organization_id, user_id), FKs to organizations and auth.users
  (ON DELETE CASCADE), and the role and status CHECKs;

5. GRANT / REVOKE IMPLEMENTATION
======================================================================
plus_grant_member_access(p_organization_id, p_membership_id, p_access, p_expected_grant_id)
  1. _require_plus_admin_write(org): Organization Admin of the org and entitlement write.
     - ZW001: no uid, or an Admin while Plus is read_only.
     - ZW002: everyone else, including a Dispatcher with a write grant, a Driver, a foreign tenant, a Platform Admin
       without membership, and the none/locked states.
  2. _lock_org_admins(org), the advisory lock change_membership_role and set_membership_status already take. Then
     _require_plus_admin_write is called AGAIN, so an Admin demoted or deactivated, or an entitlement that ended, while
     the call waited cannot complete it.
  3. p_access must be 'read' or 'write' (ZW006).
  4. The membership is looked up by id AND organization_id, FOR SHARE. A forged, foreign or unknown id gives ZW002.
  5. The membership must have role = 'dispatcher' and status = 'active'. Otherwise ZW006 (Admins need no grant,
     Drivers never, inactive never).
  6. The active grant is locked FOR UPDATE.
     - Same access already active: changed = false, nothing written, no audit (duplicate submissions).
     - Otherwise p_expected_grant_id must equal the active grant id (NULL = none), or ZW003.
  7. A change revokes the old row (revoked_at, revoked_by) and inserts a new one, so history is kept.
  8. Audit event:
     - action plus_member_access_granted; entity_type membership_module_grant; entity_id = new grant; actor =
       auth.uid();
     - before = {module, membership_id, access, grant_id} of the previous grant, or NULL;
     - after = {module, membership_id, access, grant_id, email}.

plus_revoke_member_access(p_organization_id, p_membership_id, p_expected_grant_id)
  - Organization Admin while Plus is write or read_only, so grants can be cleaned up after Plus ends. Otherwise ZW002,
    including locked and none. Uses the same lock and re-check.
  - Any membership of THAT organization qualifies, so a deactivated or re-roled member's grant can still be revoked.
    Otherwise ZW002.
  - No active grant: changed = false (duplicate submit). A wrong expected id gives ZW003.
  - Stamps revoked_at and revoked_by; the row is never deleted. Audited as plus_member_access_revoked.

plus_list_member_access(p_organization_id)
  - Organization Admin while Plus is write or read_only; otherwise ZW002 (ZW001 without a uid).
  - Returns staff memberships (Admins and Dispatchers; Drivers are never listed) with name, email, Core role, status,
    is_self, and the active grant (access, grant_id, granted_at).

Not automatic: nobody receives Plus implicitly. There is no invitation, role conversion or staff management in S3.
A salesperson is never made an Admin.

  _plus_member_access(org) returns:
    - none for no uid or a NULL org;
    - write for an active Organization Admin of an active org (has_org_role);
    - for an active Dispatcher of an active org (has_org_role), the access of their active grant joined through the
      membership (user_id = auth.uid(), status active, role dispatcher), or none;

    - member access none -> false;

      trial_ends_at is returned to Admins only.
    - Grant holders: state 'write' with access read or write, while the entitlement is write; otherwise none/none.
    - Everyone else: none/none. Never raises.
    - The four effective states are unchanged; no state value 'read' was introduced.

9. RLS AND TENANT ISOLATION EVIDENCE
======================================================================
- membership_module_grants is class A: RLS on, no policy, no table privilege for anon, authenticated, service_role or
  PUBLIC.
  - Direct SELECT, INSERT, UPDATE and DELETE as authenticated all give 42501 (SQL S3/S4).
  - Deviation, stricter than the domain model's proposed select policy: Admins read through plus_list_member_access,
    and members read their own access through plus_access_state. Documented in plus-access-model.md section 3.1.
- Structural isolation: the composite FK refuses a grant that pairs Org B with an Org A membership (SQL S8). The
  partial unique index refuses two active grants (S9). Module and access CHECKs (S10).
- Cross-tenant and forged-id attacks:
  - an Org B Admin cannot list, grant or revoke for Org A (A4);
  - an Org A membership posted under Org B, and the reverse, give ZW002 with nothing written (A5/A6);
  - unknown or NULL ids give ZW002 (A7);
  - in the browser, a forged handle (an Org B membership) and a form for another organization are both refused (E2E
    D5/D7).
- Platform Admin without a membership: plus_can_read/write false/false, plus_access_state none/none, and cannot list,
  grant or revoke (A3).
- Multi-organization identities:
  - a person who is a Dispatcher in A (granted) and in B (not granted) has Plus in A only, even with Plus active in B
    (M1, E2E I1-I5);
  - c1 (Admin in A, Driver in B) has none in B (M3);
  - A and B grants and audits stay independent (M4-M6, E2E I6).
- Core isolation:
  - no Core function references a Plus helper or table (C1, and S2 P6 widened to the Plus naming convention);
  - no RLS policy references Plus objects (C2);
  - Core role checks are unchanged for a grant holder (B22);
  - the granted Dispatcher's membership row is unchanged (B21, E2E B11).
- The privilege contract registers the new table (class A) and the four functions (_plus_member_access internal;
  three RPCs 'u'). Result: 0 violations of 29, on the dev DB, the isolated clean stack and the upgraded stack.
