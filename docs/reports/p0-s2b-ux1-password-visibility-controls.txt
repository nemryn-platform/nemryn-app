3. VISIBILITY IMPLEMENTATION
====================================================================

A single shared component, `PasswordInput`
(`src/components/ui/PasswordInput.tsx`), used by all 5 password
fields — rather than duplicating toggle logic 5 times, or retrofitting
the existing `Input` primitive (which has no reason to carry a
`relative`/`absolute` wrapper for its many non-password call sites).
It mirrors `Input.tsx`'s label/help/error chrome and styling exactly
(same typography tokens, same border/focus classes, same `size="md"`/
`"lg"` height options) so the visual result is indistinguishable from
`Input` except for the added control.

  - Local `useState<boolean>` (`visible`, default `false`) drives the
    underlying `<input>`'s own `type` attribute directly: `type={visible
    ? "text" : "password"}`.
  - Every `PasswordInput` instance has its OWN independent state — two
    on the same form (`ResetPasswordForm`'s "New password"/"Confirm
    new password") never share or influence each other's visibility,
    by ordinary React component-instance semantics (confirmed live,
    §10).
  - The toggle button is `<button type="button" onClick={() =>
    setVisible((v) => !v)}>` — flips only this local boolean, touches
    no form state, no `FormData`, no Server Action.
  - Icons: `Eye`/`EyeSlash` from `@phosphor-icons/react/dist/ssr` —
    the SAME icon package already used elsewhere in this codebase
    (e.g. `DriversPageClient.tsx`'s `PaperPlaneTilt`). No new icon
    library was added, per instruction.
  - Positioning: the button is absolutely positioned inside a
    `relative` wrapper around the `<input>`, `inset-y-0 right-0`,
    sized `w-12`/`h-full` for `size="lg"` (48×48) or `w-10`/`h-full`
    for `size="md"` (40×40) — filling the input's own height exactly,
    so the control never increases the input's height. The input
    itself gets asymmetric padding (`pl-4 pr-12` for lg, `pl-3 pr-10`
    for md) so entered text never runs under the button.

4. ACCESSIBILITY BEHAVIOR
====================================================================

  - The control is a real `<button type="button">` — confirmed live
    this phase (`tagName === "BUTTON"`, `type === "button"`) for every
    one of the 5 instances. `type="button"` means it can never submit
    the enclosing `<form>` on click or on Enter-while-focused —
    confirmed live: clicking it never navigates or changes
    `location.pathname` (§10).
  - `aria-label` changes with state: `"Show password"` while masked,
    `"Hide password"` while revealed — confirmed live for every
    instance, both states.
  - `aria-pressed` is set (`"false"`/`"true"`) reflecting the current
    visibility state — confirmed live for every instance, both states.
  - Being a native `<button>` element, standard browser keyboard
    semantics apply automatically (Enter and Space both activate it
    when focused) — this is guaranteed by using the real element
    rather than a styled `<div>`/`<span>` with a click handler, which
    is exactly why a native button was used rather than a custom
    clickable element.
  - The icon (`Eye`/`EyeSlash`) is marked `aria-hidden` — the
    accessible name comes entirely from `aria-label`, never from the
    icon alone, per instruction.

**Process note, disclosed for transparency:** the first run of this
suite showed 70/72 (two failures, both on the reset-password
independence check). Investigation found the failures were caused by a
bug in the TEST SCRIPT itself — a shared `testToggle()` helper
performed one additional, undocumented toggle click as part of its own
"does not navigate" sub-check, leaving the "New password" field in an
unexpected state before the subsequent independence check ran, which
assumed a default state it didn't actually have. This was a test
sequencing bug, not an application defect — confirmed by the fact that
`aria-pressed`/`type` were changing CORRECTLY and CONSISTENTLY on every
single click throughout the run (i.e., the component's own behavior
was never in question, only my test script's expectation of what
state a given click would land on). Fixed by reloading the
reset-password page (a full navigation, resetting all client component
state to its true default) before running the independence check,
rather than chaining more clicks onto a page instance already exercised
by the shared helper. Re-run after the fix: 74/74 PASS.
