2. PASSENGER NAME GAP
=============================================================================
R2's own report (§3, "PASSENGERNAME FINDING") correctly discovered that
Zenward-Web's form collects `passengerName` but Nemryn's public intake
never had a field for it, and — as a stopgap, not a considered design —
recommended a future Zenward-Web adapter fold it into `additionalNotes`
(e.g. `"Passenger: <name>"`). That recommendation is now WITHDRAWN (R2's
own report has been corrected in place, §3/§16/§17 there). Passenger name
is first-class intake information a requester explicitly provides — who
the trip is FOR — not an incidental note, and deserves its own structured
field exactly like `serviceType`/`recurringSchedule` already got in R2.

=============================================================================
3. DOMAIN SEMANTICS
=============================================================================
The critical distinction this entire phase is built around: **REQUESTED
PASSENGER NAME != PASSENGER ENTITY.**
  - A REQUESTED passenger name is a plain string the requester typed on a
    public form, with zero verification, zero relationship to any
    account, and no guarantee it even refers to a real, distinct person
    (the requester and passenger are very often the same person —
    `requesterRelationship: "self"`).
  - A Passenger ENTITY (`public.passengers`) is an operator-managed,
    reviewed record — created and linked exclusively through the
    existing, unrelated `AddPassengerDialog`/`link_request_passenger`
    controlled workflow, requiring a deliberate operator action.
Conflating the two — auto-creating, auto-matching, or auto-linking a
Passenger from a public, unauthenticated, unverified string — would be a
serious integrity and safety regression (a malicious or mistaken
submission could silently attach itself to, or fabricate, a real
Passenger record). This phase adds NOTHING that narrows that gap in any
way: no matching, no fuzzy lookup, no email/phone reconciliation, no
`passenger_id` write of any kind from this code path.

=============================================================================
4. COLUMN NAMING
=============================================================================
Audited before writing any code:
  - `transportation_requests`' own original table comment: "Requester is
    snapshot fields here, not a standalone table (ZD-045)" —
    `requester_name`/`requester_relationship`/`requester_phone`/
    `requester_email` are the established precedent for exactly this
    category of data: free-text, captured-at-submission-time, never a
    foreign key.
  - `passenger_id` (existing column): the ONLY column on this table that
    is a real FK to `public.passengers` — reserved exclusively for
    `link_request_passenger`'s own controlled write.
  - `passenger_display_name` (existing, but a DIFFERENT concept —
    `20260831110000_driver_read_result_types.sql`'s own driver-read
    result types): a *joined, live* Passenger's own `display_name`,
    surfaced through an API result shape — never a stored column on
    `transportation_requests`, and a name that could be confused with
    what this phase needed if chosen carelessly.
  - Request Detail read model (`request-detail.ts`) and the Passenger
    reconciliation UI (`RequestPassengerPanel.tsx`/`AddPassengerDialog`)
    were both read in full to confirm neither has any existing concept
    this could collide with.
  - Zenward-Web's own `passengerName` (its `TransportationRequestInput`
    type) is a simple required string with no further semantics — no
    guidance needed from that side beyond "it's free text."
CHOSEN: `requested_passenger_name` — exactly the phase brief's own
preferred direction. Parallels `requester_name`'s snapshot semantics,
cannot be mistaken for `passenger_id` (the FK) or `passenger_display_name`
(the live/joined entity's own name elsewhere in the codebase). Never
called `passenger_name` alone, which could misleadingly suggest it
belongs to (or mirrors) the `passengers` table itself.

5. PUBLIC CONTRACT
=============================================================================
Added `passengerName` to `website-intake-core.ts`'s `ALLOWED_KEYS` — one
new OPTIONAL top-level field. Every other existing field, bound, and enum
is unchanged; the closed-contract behavior for unknown/protected fields
(including a direct attempt to smuggle `passengerId`, the entity FK — not
this snapshot — or `organizationId`) is unaffected and re-confirmed by a
dedicated unit test (§17 below).

=============================================================================
6. VALIDATION
=============================================================================
Uses the SAME `optionalString(value, maxLength)` helper `requesterEmail`/
`assistanceNotes`/`additionalNotes` already use — no new validation
primitive introduced. Behavior: `undefined`/`null` -> `null` (absent is
fine, backward compatible); wrong type -> rejected (`invalid_request`);
empty or whitespace-only string -> normalizes to `null` (matches the
existing optional-string convention exactly, chosen over "reject empty
string" per the phase brief's own explicit "according to existing
optional-string convention" instruction); a non-empty string is trimmed
and length-capped at 200 (matching `requester_name`'s own bound exactly —
same category of field); over 200 chars -> rejected. Enforced identically,
independently, at both the pure-core pre-check AND the RPC (the
authoritative layer) — the same double-validation discipline as every
other field in this endpoint.

7. PERSISTENCE
=============================================================================
One new nullable `text` column,
`transportation_requests.requested_passenger_name` — no JSONB, no CHECK

proven directly (SQL TEST R2A-1, live UI check, §13/§17). NULL for every
pre-existing row and every row that does not explicitly set it — no

8. RPC SIGNATURE
=============================================================================

version of this function exists after this migration. Every field's own

rate-limiting integration point, hard-coded `state='pending'`/`source=
'web'`, and "no side effects" contract are byte-for-byte carried forward
from R2 — only the one new parameter and its own validation block were
added.
