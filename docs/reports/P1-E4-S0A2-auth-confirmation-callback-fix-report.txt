2. INSPECTION — WHERE THE ACTUAL GAP WAS
--------------------------------------------------------------------
Read the current source directly (not assumed): `/sign-up`'s Server
Action, the Supabase SSR client (`src/lib/supabase/server.ts`,
`client.ts`, `proxy.ts`), `/complete-signup` (S0A1's Route Handler),
and the Supabase Auth Site URL/Redirect URL configuration already
documented in `docs/deployment/staging-auth-configuration.md`.

Root cause, confirmed directly by following the actual confirmation
link with `curl` and reading its `Location` header (not assumed from
documentation): Supabase's DEFAULT "Confirm signup" email template
uses `{{ .ConfirmationURL }}`, which points at Supabase's own hosted
`https://<project>.supabase.co/auth/v1/verify?token=...&type=signup&
redirect_to=<Site URL>`. That endpoint verifies the token server-side,
then redirects the browser to Site URL with the new session encoded
as a URL **fragment** — `#access_token=...&refresh_token=...` — never
a query parameter. A fragment is never transmitted to any server by
the browser; only client-side JavaScript can read
`window.location.hash`. This application has NO client-side code
anywhere that reads it (confirmed: `grep -rn "location.hash" src/`
returns nothing). The fragment was therefore silently discarded every
time — no session was ever established, regardless of how correctly
Site URL/Redirect URLs were configured, and regardless of `/complete-
signup`'s own correctness (S0A1's fix was never even reached). This
exactly explains the reported symptom: the person lands back on an
unauthenticated state, which (depending on exactly which unauth path
the browser hit) can read as "returned to the sign-up screen."

3. THE FIX — `/auth/confirm`
--------------------------------------------------------------------
`src/app/auth/confirm/route.ts` — the canonical Supabase Next.js SSR
confirmation pattern, adapted to this codebase's conventions:

  export async function GET(request: NextRequest) {
    const { searchParams } = new URL(request.url);
    const tokenHash = searchParams.get("token_hash");
    const type = searchParams.get("type") as EmailOtpType | null;
    if (tokenHash && type) {
      const supabase = await createServerSupabaseClient();
      const { error } = await supabase.auth.verifyOtp({ type, token_hash: tokenHash });
      if (!error) return NextResponse.redirect(new URL("/complete-signup", requestUrl));
    }
    return NextResponse.redirect(new URL("/auth/auth-code-error", requestUrl));
  }

Reads `token_hash`+`type` as plain, server-readable query parameters
(never a fragment). Calls `verifyOtp()` on the SERVER Supabase client
(`createServerSupabaseClient()` — the same helper every Server Action
already uses), which writes the real session cookie directly into
this response via its cookie adapter. On success, redirects to
`/complete-signup` — S0A1's own continuation, unchanged, picks up
from there. On any failure (missing params, an expired or
already-used token), redirects to a new calm retry page,
`/auth/auth-code-error` (`src/app/auth/auth-code-error/page.tsx`) —
same visual shell as every other auth surface in this app, never a
raw Supabase error. `token_hash` (a genuine, short-lived credential)
is never logged anywhere in this route — confirmed by reading the
final file: the one debug `console.log` added during development
(logging only the request HOST, never the token) was removed before
this report.

A Route Handler, not a Server Component page — consistent with S0A1's
own ZD-200 finding (a Server Component's `redirect()` after a
mutating `await`, reached via a chained navigation, was not reliably
followed by the browser). This endpoint mutates (establishes a
session) and then redirects, exactly the pattern that motivated
ZD-200 in the first place.

6. DUPLICATE-CLICK / REFRESH / INVALID-TOKEN — TESTED DIRECTLY
--------------------------------------------------------------------
- **Clicked twice:** the SAME confirmation link, followed a second
  time (`curl`, direct HTTP request to `/auth/confirm`) — first
  request: `307 → /complete-signup`. Second request, same
  `token_hash`: `307 → /auth/auth-code-error`. Supabase's own OTP
  tokens are single-use; `verifyOtp()` correctly rejects a repeat.
  This means `/complete-signup` (and therefore
  `complete_pending_signup()`) is structurally never even reached a
  second time from a stale link — not merely idempotent by
  convention, but unreachable a second time by construction.

  confirmation, stays on `/onboarding` — no bounce, no error, no
  re-triggered creation (verified as part of the 6/6 operator run,
  §4).

  invalid-garbage&type=signup` → `307 → /auth/auth-code-error`.
- **Missing params entirely:** `GET /auth/confirm` (no query string
  at all) → `307 → /auth/auth-code-error`.
- **The error page itself:** `/auth/auth-code-error` renders
  correctly, HTTP 200, calm copy ("This link has expired"), links to
  both `/sign-in` and `/sign-up` — never a raw Supabase error or a
  stack trace.

8. A GENUINE LOCAL-DEV-ONLY BUG FOUND AND FIXED WHILE BUILDING THIS
--------------------------------------------------------------------
`/auth/confirm` initially appeared not to work even once implemented
correctly — same symptom, session never established. Root-caused via
direct `curl` inspection of the actual `Set-Cookie`/`Location`
headers (not guessed): the session cookie WAS being written correctly
by `verifyOtp()` (confirmed: real `sb-*-auth-token` cookies present
in the response, correct `Path`/`Expires`/`SameSite`), but the
redirect's `Location` header used `localhost` even when the actual
incoming request was to `127.0.0.1` — a genuine Next.js dev-server
(Turbopack) behavior that silently normalizes `request.url`/`nextUrl.
origin`'s reported host, regardless of the literal Host header the
client used. The browser correctly refused to send `127.0.0.1`-scoped
cookies to a `localhost` redirect target — two different origins from
a cookie's perspective, even on the same machine.

Fixed at the root, not worked around: local Supabase's own `site_url`
(`supabase/config.toml`) changed from `http://127.0.0.1:3000` to
`http://localhost:3000` — matching what Next's dev server actually
canonicalizes to, and matching `.env.local`'s own pre-existing
`NEXT_PUBLIC_APP_URL` value (which was ALREADY `localhost:3000` —
this fix aligns Site URL with an existing convention, not introducing
a new inconsistency). Recorded as ZD-203. Confirmed as local-only: the
real deployed app has exactly one canonical host at all times
(`app.zenwardmobility.com`), so this specific mismatch structurally
cannot occur there.
