4. ACTUAL DISCOVERED PRIORITY_RANK ORDER
------------------------------------------------
Read directly from src/lib/operations/todays-operations.ts (lines
181-186) — this is the SOURCE OF TRUTH, and it differs subtly from how
P1-E1-S1A's own prose described it (that report grouped "LOCATION_STALE/
LOCATION_UNAVAILABLE" together as if interchangeable-priority; the
actual numeric ranks are NOT equal):

  const PRIORITY_RANK: Record<string, number> = {
    OPEN_EXCEPTION: 0,
    NEEDS_ASSIGNMENT: 1,
    LOCATION_STALE: 2,
    LOCATION_UNAVAILABLE: 3,
  };

Exact order, lowest rank sorts first (most urgent, shown first):
  1. OPEN_EXCEPTION (0)
  2. NEEDS_ASSIGNMENT (1)
  3. LOCATION_STALE (2) — a location EXISTS but has gone stale
  4. LOCATION_UNAVAILABLE (3) — no location has EVER been recorded for
     the current assignment

So a trip with a stale-but-present location outranks (is shown before)
a trip with NO location at all yet — the opposite of what a naive
reading of "unavailable sounds worse than stale" might suggest, and the
exact opposite of the informal pairing implied by S1A's own prose. This
distinction was preserved EXACTLY as-is: neither this module nor its
tests re-sort, re-rank, or second-guess this ordering anywhere —
`attentionItems` is consumed strictly as already-ordered input.

This constant lives inside todays-operations.ts itself (not trip-
assurance.ts) and is applied BEFORE `getTodaysOperations()` ever
returns — meaning Operations Brief never needs to reference
PRIORITY_RANK at all; the array it receives is already correctly
ordered.

12. DRIVER-SNAPSHOT QUERY
--------------------------------
Two small, explicit-column, sequential (not N+1 — the second only runs
if the first returns any rows) queries in operations-brief.ts's private
`getDriverSnapshot()`:

  Query 1 — `select id from drivers where organization_id = :org and
  status = 'active'` — gives `totalActiveDrivers` directly (a plain row
  count) and the candidate driver-id list for query 2. If this returns
  zero drivers, query 2 is skipped entirely (an early return) rather
  than issuing a trivially-empty `IN ()` query.

  Query 2 — `select driver_id, trips!trip_assignments_trip_id_
  organization_id_fkey(state) from trip_assignments where
  organization_id = :org and ended_at is null and driver_id in
  (<query 1's ids>)` — the exact PostgREST embed syntax, LIVE-VERIFIED
  against the real local database (not merely assumed to work): the
  foreign-key constraint name `trip_assignments_trip_id_organization_id_
  fkey` was independently confirmed to exist via `pg_constraint`, and
  the exact query (URL-encoded, identical shape) was run directly
  against the local PostgREST endpoint, signed in as
  org-a-admin@example.test, returning real embedded `trips: {state:
  ...}` objects for Organization A's own two seeded active drivers —
  confirming both the constraint name and the embed shape are correct
  before ever being exercised through the TypeScript client.

Neither query uses `select("*")`. Neither is a duplicate of
getDispatchBoardData()'s own much larger query (which additionally
fetches vehicles, locations, exceptions, and every non-terminal trip's
full column set) — this is a two-query, narrowly-scoped alternative
built specifically for the two numbers Operations Brief needs, exactly
per the phase's own explicit instruction not to reuse the large board
query "just to obtain two numbers."


13. DRIVER-SNAPSHOT SEMANTICS
------------------------------------
`totalActiveDrivers` / `driversCurrentlyOnTrip` — NEVER called
"available drivers" anywhere in code, comments, or this report, per the
phase's own explicit naming instruction (the schema has no live
availability/shift/break concept — P1-E1-S1A §5's own confirmed gap).

Row-to-count logic is split across two layers, mirroring §4's own
reasoning for why the pure core has zero runtime imports:
  - operations-brief.ts (server-only): for each `trip_assignments` row
    returned, unwraps the embedded `trips` relation (the same defensive
    `unwrapOne` pattern todays-operations.ts/dispatch-board.ts each
    already carry their own private copy of) and calls
    `isActiveTripState(trip.state)` ONCE per row, producing a plain
    `{ driverId, isActiveState: boolean }` row.
  - operations-brief-core.ts (pure): `countDriversCurrentlyOnTrip(rows)`
    collects `driverId` into a `Set` for every row where `isActiveState`
    is true, then returns the Set's size — a driver with two
    simultaneous active-state assignment rows (not currently possible
    given the one-active-assignment-per-TRIP constraint, but not
    schema-prevented across two DIFFERENT trips) is still only ever
    counted once.

Verified by test (§22-G below): a completed-trip assignment row does
NOT count, a cancelled-trip row does not count, a future-scheduled-trip
row does not count, each of the 5 real active states DOES count (each
independently asserted via `isActiveTripState`, imported directly since
presentation.ts has no sibling imports of its own and is therefore also
safely Node-loadable), and an inactive driver is excluded from
`totalActiveDrivers` BY CONSTRUCTION — the drivers query itself only
ever selects `status = 'active'` rows, so an inactive driver's id never
enters either query's result set at all; this is enforced by the same
single, already-proven `.eq("status", "active")` filter pattern used
throughout this codebase, not a new mechanism requiring its own parallel
JS unit test.


14. DAY-STATE RULES
-------------------------
`computeDayState(todayTrips)`, pure, in operations-brief-core.ts:
  - `todayTrips.length === 0` -> `"NO_TRIPS"`
  - `todayTrips.length > 0` AND every trip's `state === "completed"` ->
    `"ALL_COMPLETE"`
  - anything else -> `"ACTIVE_DAY"`

The "anything else" branch deliberately covers a day containing
`completed` mixed with `cancelled`/`no_show` (real terminal outcomes
that are NOT "everything completed") as well as any day with a
`scheduled`/in-progress trip — all correctly fall through to
`ACTIVE_DAY`, never misreported as `ALL_COMPLETE`. Six dedicated tests
cover every branch explicitly, including both terminal-outcome-mixing
cases named in the phase's own instructions (completed+cancelled,
completed+no_show).


15. QUIET-DAY BEHAVIOR
----------------------------
When `todayTrips.length === 0`: `attention`/`activeNow`/`nextDepartures`
are not FORCED empty by any special-case code — they fall out naturally
empty because `getTodaysOperations()`'s own `attentionItems` is derived
from `todayTrips ∪ activeTrips` and `needsAssignmentTrips` is a filter
over `todayTrips` — confirmed by a dedicated test asserting all three
collections are empty and `unassignedCount === 0` when `todayTrips` is
empty. `driverSnapshot` is NEVER zeroed or suppressed in this case — a
dedicated test (`deriveOperationsBrief — zero trips today still reports
real driver counts`) explicitly asserts a non-zero driver snapshot
passes through unchanged even when `dayState === "NO_TRIPS"`, matching
P1-E1-S1A §16's own instruction ("driverSnapshot may still contain real
driver counts").

One genuine edge case, documented rather than silently special-cased:
`getTodaysOperations()`'s own `activeTrips` query has NO day boundary at
all (it is a flat "every currently in-progress trip" query, by that
file's own design comment, ZD-131) — so a trip that began on a prior
calendar day and is still in progress could theoretically make
`activeNow` non-empty even while `todayTrips.length === 0` (and
therefore `dayState === "NO_TRIPS"`). This module does not suppress that
real data to force an artificially "pure" empty day — per the phase's
own literal rule ("NO_TRIPS: todayTrips.length === 0"), `dayState` is
computed from `todayTrips` alone, and `activeNow` is never filtered
against it. This is a rare, honest edge case, not a bug — flagged here
explicitly so S1C does not assume `dayState === "NO_TRIPS"` implies
"nothing to show anywhere on the page."
