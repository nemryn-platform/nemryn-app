======================================================================
NEW TRIP ASSIGN NOW
======================================================================
A new "Assignment" section in the New Trip right column, replacing the old "assign after creating" notice:
  [ ] Assign now
When ticked, it renders AssignmentFields: the SAME controls PROG1's dialog uses, extracted into one shared component
(src/components/operations/dispatch/AssignmentFields.tsx). So:
  - Driver/Vehicle prefill applies only when exactly one active option exists, with the same help text.
  - The linked operator's own driver is listed first as "<name> (you)" and is never auto-selected.
  - Driver-day context is shown for the chosen pickup date. It reuses driverDayContextAction with a new
    { kind: "date" } target, and says "Choose a pickup date…" until one is entered.
  - The no-vehicle note, Clear vehicle and zero-driver guidance are the same as PROG1.
  - Nothing is written until Create Trip is clicked.
  - With Assign now ticked but no driver chosen, the action rejects BEFORE create_trip ("Choose a driver for Assign
    now, or turn Assign now off…"), so nothing is created.
Double-submit: the existing guards are kept (submittedRef + disabled button). After ANY success, including a partial
one, the form navigates away and submittedRef stays set, so it can never submit a second Trip. A rapid triple submit
(two clicks plus requestSubmit) produced exactly one Trip and one assignment (E2E).
Limitation (unchanged, documented): create_trip has no idempotency key. A browser- or network-level replay of the POST
outside the page's own guard is not deduplicated server-side. PROG2 did not invent one silently.

======================================================================
ASSIGN NOW DEFAULT DECISION
======================================================================
FINAL: Assign now is OFF by default for everyone, including a 1-driver / 1-vehicle operator. The operator opts in with
one click, and the fields inside are then prefilled.
Why:
  - Default-ON would turn "Create Trip" into "create AND assign" without the operator having looked at the
    assignment.
  - That is exactly the hidden-assignment behaviour the invariants forbid.
  - With the fields visibly prefilled, opting in costs a single click.
  - Default-ON can be revisited once pilot operators ask for it.

======================================================================
CREATE THEN ASSIGN MODEL
======================================================================
The existing two calls are used; there is NO combined RPC, and create_trip is unchanged:
  1. create_trip, exactly as before.
  2. Only when Assign now is on: assign_trip for the new trip id, through callAssignmentRpc.
callAssignmentRpc (src/lib/operations/assignment-mutation.ts) is new, but it is the extracted body of PROG1's
assignmentAction, so both the dialog and New Trip still go through ONE assignment call path. The flow is
intentionally NON-ATOMIC:
  - The created Trip is never rolled back or re-created.
  - The assignment is attempted exactly once, with no automatic retry.
  - assign_trip re-validates everything (organization, active driver and vehicle, assignable state, one active
    assignment).

======================================================================
PARTIAL SUCCESS
======================================================================
The three outcomes are kept distinct (state.assignment = not_requested | assigned | failed):
  A. Assign now off: the existing behaviour. Navigates to Trip Detail with no notice.
  B. Assign now on, assignment OK: Trip Detail shows "Trip created and assigned."
  C. Assign now on, assignment failed: Trip Detail shows an alert with:
       "Trip created, but the assignment could not be completed."
       + the mapped reason (e.g. "That driver or vehicle is no longer available. Choose another.")
       + "The trip is saved without a driver — you can assign it from Current Status on this page."
The outcome travels in a display-only query parameter (?created=assigned | assignment_failed, &reason=<allowlisted
dispatch error code>). It changes only copy. The page's own data (Current Status, readiness) is the authority on what
happened. The partial-failure E2E confirmed:
  - exactly one Trip was created
  - 0 active assignments existed afterwards
  - the operator landed on that Trip
  - assigning there succeeded
  - no second Trip was created

======================================================================
TOMORROW INLINE ASSIGN
======================================================================
The /operations/tomorrow "Needs preparation" rows now carry a compact button next to "View trip". It is a button that
opens a dialog; there are no inline selects (0 <select> elements on the page, verified).
  - "Assign": the trip is unassigned (NEEDS_DRIVER). Opens the PROG1 AssignmentDialog in assign mode.
  - "Add vehicle": the trip is assigned without a vehicle (NEEDS_VEHICLE). Opens the SAME dialog in reassign mode:
    the current driver is kept, the vehicle is chosen, and reassign_trip records the history.
Eligibility is decided by deriveTomorrowAssignAction (pure). BOTH conditions must hold:
  - an assignment-related reason
  - a trip state that assign_trip / reassign_trip accept
The readiness reason alone is not enough, and the backend stays authoritative at submit time.
The option lists, operator driver id and recurring hints are loaded only when at least one row qualifies. If loading
fails, the rows keep "View trip" only.
Refresh: the dialog calls router.refresh() on success, and assignmentAction also revalidates /operations/tomorrow.
Readiness is then RE-DERIVED from facts, never set to Ready.
getTomorrowReadiness now also returns `assignmentTargets`: the per-trip fields the dialog needs (descriptions,
recurring_arrangement_id, active assignment driver/vehicle ids and labels). This is additive; the pure readiness core
is untouched.

RECURRING RELATION AUDIT
======================================================================
The strongest explicit relation:
  - trips.recurring_arrangement_id: nullable, with a composite FK (recurring_arrangement_id, organization_id) to
    recurring_arrangements, and indexed.
  - It is set by the occurrence-creation RPC (20260918090000).
The completing assignment:

  - That exact row is "the assignment that completed the occurrence".
  - An assignment still open on a completed trip is also accepted as a fallback.
No passenger, address or pickup-time-text matching is used anywhere.

======================================================================
RECURRING HISTORICAL PREFILL
======================================================================
Read model: getRecurringAssignmentHints(org, targets) in assignment-context.ts.
  - It makes ONE bounded query for any number of target trips:
      - completed trips of the targets' arrangements (explicit linkage)
      - organization-filtered, session client (RLS)
      - within 90 days before the latest target, limit 500
      - with their assignment rows embedded
  - selectRecurringAssignmentHint (pure) then picks, per target, the NEAREST EARLIER completed occurrence of the SAME
    arrangement that has a completing assignment.
  - Only { driverId, vehicleId } reaches the client, and only for assign mode.
Surfaces:
  - Trip Detail: getRecurringAssignmentHintForTrip, used only when the trip is unassigned.
  - Tomorrow inline Assign.
  - The Dispatch Needs Assignment queue: one batched call for all unassigned trips, since it is the same dialog.
  - New Trip trips are never recurring, so no hint applies there.
Help text: "Prefilled from the most recent completed occurrence. You can change it before assigning." Nothing says
"preferred", "usual" or "required".
Bound: an occurrence completed more than 90 days before the target does not prefill. The window keeps the batched
read bounded (open issue 2).

======================================================================
PREFILL PRIORITY
======================================================================
REASSIGN:
  1. The existing active assignment's driver and vehicle, while each is still eligible.
  2. Nothing else overrides them: recurring history and uniqueness are both ignored.
ASSIGN, deciding driver and vehicle independently:
  1. The recurring-history value, if still an active option in this organization.
  2. Otherwise, the only eligible option (the PROG1 uniqueness rule).
  3. Otherwise, no default.
Rules:
  - A historical "no vehicle" contributes no vehicle. The field falls through to rule 2 and is never invented from
    history.
  - An inactive historical driver or vehicle is ignored and never substituted by "something similar". Only the
    ordinary uniqueness rule can then apply.
  - Defaults are derived once when the dialog or section mounts and never re-applied over operator edits.
  - "(you)" ordering remains presentation only.

======================================================================
RECURRING EDGE CASES   (unit tests + E2E)
======================================================================
  - No prior occurrence: no hint (unit).
  - Non-recurring target: no hint (unit).
  - Prior occurrence unassigned, cancelled, no-show or scheduled: never counts (unit + E2E, whose history includes
    no-show and cancelled occurrences assigned to Driver B, and an unassigned one).
  - Completed occurrence whose driver is now inactive: driver ignored; multiple others give no prefill; exactly one
    other gives the uniqueness prefill (unit + E2E).
  - Completed occurrence whose vehicle is now inactive: the same rules apply to the vehicle (unit + E2E).
  - Completed occurrence with driver and vehicle both still active: both prefilled from history (E2E: Driver A + Van
    A).
  - Multiple prior occurrences: the newest EARLIER completed one wins. Older (Driver C, 14 days) and later occurrences
    and other arrangements are ignored (unit + E2E).
  - A completed occurrence with no vehicle: no vehicle is invented (unit).
  - Reassign mode ignores history (unit).
Nothing in any of these paths auto-assigns (E2E: 0 assignments until confirm).
