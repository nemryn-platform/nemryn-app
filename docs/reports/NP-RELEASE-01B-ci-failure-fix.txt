2. ROOT CAUSE
-------------
- T15 exercises the supabase-cli transport with a fake spawn, but it used the DEFAULT repository root.
- That transport reads the linked project ref from supabase/.temp/project-ref. The file is git-IGNORED
  (supabase/.gitignore:3 ".temp"), so it exists on a developer machine where the Supabase CLI is linked, but never on a
  CI runner.
- With no linked ref, validateProductionState correctly rejects the state ("production state has no valid project
  ref"), so r.ok = false.
Classification:
- an ENVIRONMENT ASSUMPTION in the TEST (it depended on local, untracked state);
- not platform-specific (Linux vs macOS);
- not a workflow configuration problem;
- not an implementation defect. The checker FAILED CLOSED exactly as designed when no linked project exists.
Reproduced:
- in a clean copy containing only tracked plus unignored files (CI's file set; no supabase/.temp) on macOS: 26 / 27;
- in a Linux node:24 (Debian) container running the PR #34 version of the test file: 26 / 27, the same T15 failure.

3. FIX (smallest correct; no assertion weakened; no test disabled)
-----------------------------------------------------------------
scripts/release/db-compat.test.mjs only (+22 / −1 vs the PR head):
- new helper `linkedRoot(ref)`: a temporary repository root whose supabase/.temp/project-ref contains the given ref
  (or none);
- T15 now passes `root: linkedRoot(REF)`, so it no longer depends on the developer's machine. All of T15's assertions
  are unchanged: the fixed argv ["supabase","migration","list","--linked"], `r.ok === true`, and the static no-mutation
  scan.
- NEW test "01B supabase-cli transport: no linked project or a wrong linked project fails closed (the CI-runner case)":
  - no project-ref → not ok, "no valid project ref", and the deploy verdict is UNVERIFIABLE;
  - a project-ref of another project → WRONG PROJECT.
  This turns the behaviour CI exposed into an explicit, permanent fail-closed guarantee.
- No change to the checker, the core, the Vercel wrapper, either workflow, package.json or any application code.
- The trusted CI boundary (pull_request_target, base code, PR head as data), fail-closed behaviour, credential
  isolation and the database-first policy are untouched.
