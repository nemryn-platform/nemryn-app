RPC SET
=======
Seven new SECURITY DEFINER functions, one per legal action (never a
single generic "mutate" function), all in one new migration:
supabase/migrations/20260917110000_recurring_arrangement_lifecycle_mutations.sql

  create_recurring_arrangement(p_organization_id, p_passenger_id,
    p_pickup_description, p_destination_description, p_pickup_time,
    p_days_of_week, p_start_date, p_end_date default null)
    -> recurring_arrangement_result

  edit_recurring_arrangement(p_organization_id, p_arrangement_id,
    p_pickup_description, p_destination_description, p_pickup_time,

  pause_recurring_arrangement(p_organization_id, p_arrangement_id)
    -> recurring_arrangement_result

  resume_recurring_arrangement(p_organization_id, p_arrangement_id)
    -> recurring_arrangement_result

  end_recurring_arrangement(p_organization_id, p_arrangement_id, p_reason)
    -> recurring_arrangement_result

  skip_recurring_occurrence(p_organization_id, p_arrangement_id,

Two new composite return types (mirroring trip_exception_result's own
shared-shape precedent): recurring_arrangement_result (shared across all
5 arrangement RPCs) and recurring_occurrence_exception_result (shared
across skip/unskip). Both carry a `changed: boolean` idempotency signal.


AUTHORIZATION
=============
Every one of the 7 functions: `if auth.uid() is null then raise
'unauthorized' ZW001`, then `if not has_org_role(p_organization_id,
array['organization_admin','dispatcher']) then raise 'not_found' ZW002`.
Organization Admin and Dispatcher both allowed; Driver, inactive
membership, unauthenticated, and anon all denied (uniformly ZW002/ZW001,
no existence oracle — matches the exact convention already established
for create_trip/log_transportation_request). No Platform Admin access was
added anywhere — the already-verified 3-table PA scope
(organizations/platform_admin_grants/audit_events) is unchanged; these
RPCs simply never check is_platform_admin() at all, exactly as S1B/S1C
never did. No function accepts a caller-supplied actor/user id parameter
of any kind — auth.uid() is the sole, structurally-enforced actor
identity throughout.

Proven live: CREATE-01/02 (Admin/Dispatcher succeed), CREATE-03/04/05
(Driver/inactive-membership/anon all denied), PRIV-02 (Driver denied on
both create and skip specifically).


ORGANIZATION CONTEXT
=====================
Audited how create_trip/log_transportation_request/link_request_passenger/
cancel_transportation_request already handle this before writing anything
(work item §4's own explicit instruction) — found and reused the SAME
pattern throughout: `organization_id` is accepted as an explicit
parameter (required for a user who may hold ACTIVE Memberships in more
than one organization — has_org_role alone cannot disambiguate WHICH
organization a multi-org caller means without it), but it is NEVER
authority on its own. Every function independently re-derives
auth.uid() -> has_org_role(p_organization_id, roles) -> same organization,
live, every call — never a cached JWT claim, never trusted merely because
it was supplied. Every target-row lookup is ALSO scoped by
`organization_id = p_organization_id` in the identical WHERE clause as
its own id (double-checked, not merely implied by the earlier
has_org_role call) — a forged organization_id can therefore only ever
produce a ZW002 not_found (the row genuinely does not match that
selector), never privilege escalation. Proven live: CREATE-06 (Org A
actor supplying Org B's own organization_id, denied), PRIV-04's forged-
org spot checks, and every not_found path throughout the focused suite.


CREATE SEMANTICS
==================
create_recurring_arrangement accepts only operator-controlled pattern
facts (passenger_id, pickup_description, destination_description,
pickup_time, days_of_week, start_date, end_date) — no organization_id-
as-authority parameter distinct from the requested-context one already
described, no timezone parameter at all, no created_by/status/paused_at/
ended_at/ended_reason parameter of any kind. status is hard-coded
'active', paused_at/ended_at/ended_reason are hard-coded NULL,
created_by is hard-coded auth.uid(), timezone is read live from
Organization.timezone AT CREATION TIME ONLY and stored as a snapshot
(never re-read afterward — matches recurring_arrangements.timezone's own
S1B column comment, written in anticipation of exactly this RPC).

PASSENGER STATUS DECISION: audited create_trip's own existing convention
(20260916110000_request_trip_passenger_integrity.sql) before locking
anything fresh — create_trip already requires status='active' for its own
required passenger_id parameter. The identical rule is reused here,
unweakened: an inactive Passenger cannot receive a NEW standing
transportation commitment. The composite FK itself is untouched either
way (an inactive Passenger's id still satisfies it) — the additional
status='active' predicate lives in the RPC, exactly where create_trip
enforces its own equivalent rule. Proven live: CREATE-12.

Proven live: CREATE-01/02 (success), CREATE-07 (timezone = Organization's
own, America/New_York for Org A), CREATE-08 (created_by = auth.uid()),
CREATE-09 (status=active, the other three fields all NULL), CREATE-11
(cross-org Passenger rejected).


IMMUTABLE FIELDS
==================
organization_id, passenger_id, timezone, and created_by are immutable
after creation — structurally, not by convention: no field of this shape
appears as a parameter on edit_recurring_arrangement (or any other RPC)
at all, so there is no code path through which any of the 7 functions
could ever write to them post-creation. Proven live: EDIT-04/05/06/07
(all four fields read directly off the row after an edit call and
confirmed byte-identical to their pre-edit values).


EDIT SEMANTICS
================
edit_recurring_arrangement may change exactly pickup_description,
destination_description, pickup_time, days_of_week, start_date, end_date
— its own UPDATE statement's SET list mentions no other column, so
status/paused_at/ended_at/ended_reason are equally structurally
unreachable from this function (lifecycle changes have their own
dedicated RPCs). Legal only while active or paused; ZW004 from ended.
Never touches trips (no bulk update, no cascade, no schedule rewrite) —
an existing linked Trip is an already-independent operational record; the
edit affects only future derived occurrences that do not yet have one.
days_of_week is normalized identically to create (see DAYS-OF-WEEK
NORMALIZATION below). No idempotency no-op path exists for edit — every
call always performs the UPDATE and writes one audit event (matching
create_trip's own non-idempotent-by-design posture; no idempotency test
was required by the phase spec for this RPC).

Proven live: EDIT-01 (active edit succeeds), EDIT-02 (paused edit
succeeds, status remains paused), EDIT-03 (ended edit rejected, ZW004),
EDIT-08 (linked Trip completely unchanged), EDIT-09 (weekday
normalization).


PAUSE SEMANTICS
==================
Legal: active -> paused only. On success: status='paused',
paused_at=now(). Never touches linked Trips or occurrence exceptions.
Idempotent no-op if already paused — changed=false, paused_at NOT
touched, no duplicate audit event. ZW004 if ended. No reason parameter at
all (work item §11's own explicit preference honored — no existing
mutation convention in this schema strongly favors an optional reason for
a reversible, non-terminal transition; kept deliberately minimal).

Proven live: PAUSE-01/02 (active->paused, paused_at set), PAUSE-03
(repeat pause idempotent, paused_at unchanged, exactly 1 audit event
total across both calls), PAUSE-04 (ended pause rejected), PAUSE-05
(linked Trip unchanged).


RESUME SEMANTICS
===================
Legal: paused -> active only. On success: status='active',
paused_at=null. Idempotent no-op if already active. ZW004 if ended.

Proven live: RESUME-01/02 (paused->active, paused_at cleared), RESUME-03
(repeat resume idempotent, exactly 1 audit event total), RESUME-04 (ended
resume rejected).


END SEMANTICS
===============
Legal: active -> ended OR paused -> ended. Reason required (nonblank,
<=500 chars — the same bound cancel_trip/record_no_show already use for
every other terminal-transition reason in this schema; the table's own
ended_reason column carries no length CHECK, only nonblank, so this RPC
supplies the missing ceiling rather than leaving it unbounded).

LOCKED PROCEDURAL DECISION, implemented with zero branching: the UPDATE
statement never mentions paused_at in its SET list at all. Ending from
'active' therefore leaves paused_at at its already-NULL value unchanged;
ending from 'paused' leaves paused_at at whatever timestamp it already
held, RETAINED as historical context — the exact locked behavior for both
cases, achieved by omission rather than two separate code paths that
could drift apart. Idempotent no-op if already ended — the ORIGINAL
ended_at/ended_reason are never overwritten by a later, redundant end
call, even one supplying a materially different reason string. Never
touches linked Trips or occurrence exceptions (no cascade, no
cancellation, no cleanup).

Proven live: END-04 (blank reason rejected), END-01/03 (active->ended,
ended_at set, paused_at remains NULL), END-02/05 (paused->ended,
ORIGINAL paused_at retained, verified byte-identical to its pre-end
value), END-06/07 (repeat end idempotent, original 'discharged' reason
preserved against a second call supplying 'a completely different later
reason', exactly 1 audit event total), END-08 (linked Trip unchanged).


IDEMPOTENCY
=============
Every idempotency-bearing RPC (pause/resume/end/skip/unskip) follows the
identical shape: lock the target row first, THEN check whether the
requested end state already holds; if so, return the REAL, already-
persisted row (never the caller's own redundant input) with changed=false
and write no audit event. This mirrors resolve_trip_exception's own
established "idempotent no-op returns the real already-persisted
resolution, never overwritten by a stale/redundant caller" precedent
exactly. Proven for every applicable RPC: PAUSE-03, RESUME-03, END-06/07,
SKIP-08/09, UNSKIP-02 — each confirmed changed=false, the original value
preserved, and (where an audit trail exists) exactly one event total
across both the real mutation and its subsequent no-op retry (AUDIT-02
spot-checks this explicitly).


SKIP SEMANTICS
================
skip_recurring_occurrence creates a recurring_occurrence_exceptions row.
Inputs: arrangement_id, service_date, reason (required, nonblank,
<=2000 chars — the same bound the table's own S1C CHECK constraint
already enforces, validated here first for a clean ZW006 instead of a
raw constraint-violation error). Locks the ARRANGEMENT row (not merely
the exception table) FOR UPDATE — this serves two purposes at once: its
CURRENT facts (start/end/days_of_week/status/paused_at) are exactly what
SKIP DATE VALIDITY must check against, and it is simultaneously the
serialization boundary that makes concurrent duplicate-skip requests for
the SAME arrangement safe (identical technique to
link_request_passenger/cancel_transportation_request using their own
parent Request row's lock, and to redeem_driver_invite's own invite-row
lock).

SKIP DATE VALIDITY (every check ZW006, describing "this date does not
currently describe a legitimate pattern occurrence" — except the ended
check, ZW004, describing "this action is unavailable for this
arrangement's own lifecycle state regardless of date"): on/after
start_date, on/before end_date if set, on/after the arrangement-local
current date (resolved via Postgres's own `now() at time zone
<arrangement's timezone>`, the direct equivalent of day-bounds.ts's
localDateKey technique used at the application layer), weekday matches
days_of_week, and — if paused — strictly before the pause-effective local
date. An ended arrangement rejects unconditionally, for any date (ZW004,
no date-specific carve-out, per the phase's own explicit instruction).
The skip horizon is deliberately NOT limited to the 14-day assurance
window — an operator may know about a future closure earlier than that;
the assurance engine will naturally begin honoring the skip once that
date enters its own horizon.

Proven live: SKIP-01 (valid future pattern date succeeds), SKIP-02
(non-pattern weekday rejected), SKIP-03 (before-start rejected), SKIP-04
(after-end rejected), SKIP-05 (past date rejected), SKIP-06a/b (on/after
pause-cutoff rejected; a date before the cutoff still succeeds on the
SAME arrangement), SKIP-07 (ended arrangement rejected, ZW004), SKIP-08/09
(duplicate skip idempotent, original reason preserved).


UNSKIP SEMANTICS
===================
unskip_recurring_occurrence removes an existing skip fact — a genuine
DELETE, never soft-delete machinery, with one audit_events row capturing
the removed fact for history. Deliberately does NOT re-validate current
pattern facts (locked decision, work item §18): a skip created when a
date was a legitimate pattern occurrence remains removable even after a
later pattern edit, pause, or end changes what "legitimate" would mean
today — reversal of an existing explicit fact must never become
impossible because later facts changed. Only the exception row itself is
locked (FOR UPDATE) — simpler than skip's own arrangement-level lock,
since no current-facts validation is needed here at all, mirroring
resolve_trip_exception's own simpler single-row-lock shape. Idempotent
successful no-op if no such skip exists (changed=false, no audit event)
— covers "never skipped," "already unskipped," and a nonexistent/
foreign-org id combination alike, with no existence oracle.

Proven live: UNSKIP-01 (existing skip removed, 0 rows remain), UNSKIP-02
(missing skip idempotent no-op), UNSKIP-03 (a skip made stale by a
subsequent pattern edit — days_of_week changed to exclude that weekday —
still removable), UNSKIP-04 (a skip on an arrangement subsequently ended
still removable).


AUDIT EVENTS
==============
Every state-changing mutation writes exactly one audit_events row (never
more, never fewer) on a REAL mutation; an idempotent no-op writes none.
entity_type='recurring_arrangement' throughout (including for
skip/unskip, per the phase's own explicit instruction to keep history
retrievable around the standing commitment itself, not a separate
exception-entity type) with entity_id=the arrangement's own id. Actions:
recurring_arrangement_created / recurring_arrangement_edited /
recurring_arrangement_paused / recurring_arrangement_resumed /
recurring_arrangement_ended / recurring_occurrence_skipped /
recurring_occurrence_unskipped. actor_user_id is always auth.uid().
before_data/after_data carry only operational pattern/lifecycle fields
(passenger_id as an identifier only, never name/phone; pickup/
destination text; pickup_time; days_of_week; start/end_date; timezone;
status/paused_at/ended_at/ended_reason where relevant; service_date/
reason for skip/unskip) — no secrets, no unrelated Passenger PII. No new
history table was created (audit_events is what the phase itself
specified); no RPC ever updates or deletes a previous audit_events row.

Proven live: AUDIT-01/03/04/05 (exactly 1 create event, correct actor,

CONCURRENCY DESIGN
=====================
New file: supabase/tests/recurring_arrangement_concurrency_test.sh — same
technique as the existing mutation_concurrency_test.sh exactly: two
SEPARATE psql OS processes (never simulated via sequential calls within
one script) against the SAME row at overlapping wall-clock times. Session
A always opens an explicit transaction, takes the row lock (a raw `SELECT
... FOR UPDATE`, necessarily issued as the postgres role since
`authenticated` holds zero UPDATE grant on either table and Postgres's
FOR UPDATE clause itself requires the UPDATE privilege — discovered and
fixed during this phase's own test-authoring, see CONCURRENCY RESULTS),
sleeps ~2s, THEN switches to `SET LOCAL ROLE authenticated` + the actual
actor's JWT claim and calls its own RPC (which re-acquires the
already-held lock harmlessly, same session), then commits. Session B,
launched ~0.3s later while A is still sleeping, calls its own RPC
directly under `authenticated`/its own actor claim — its own RPC's
internal `FOR UPDATE` lock (taken under the RPC's SECURITY DEFINER
execution context, which needs no client-side table privilege at all)
blocks on A's held lock. Since A always acquires the lock first by
construction, this deterministically proves genuine blocking (via
elapsed-time assertion, not merely a plausible-looking final state) and
correct post-block behavior — identical epistemics to the existing
assign_trip race test.

Three scenarios, matching the phase's own §25 exactly:
  A. Simultaneous pause vs end of the same ACTIVE arrangement.
  B. Simultaneous duplicate skip of the same arrangement/date.
  C. Simultaneous resume vs end from PAUSED.

OPEN ISSUES
=============
None found that block S1E. Two items worth carrying forward as
context, neither introduced by this phase, neither a defect in the RPCs
themselves:

  1. `authenticated` (and `anon`) hold a bare TRUNCATE privilege on
     BOTH recurring_arrangements and (pre-existing, e.g. on `trips` too)
     several other tenant tables — confirmed via
     information_schema.table_privileges while investigating why a raw
     `SELECT ... FOR UPDATE` failed for the concurrency test's Session A
     under `authenticated`. TRUNCATE is not filtered by RLS at all (RLS
     only governs SELECT/INSERT/UPDATE/DELETE), so this grant is
     technically capable of wiping an entire table across every
     organization if reached. It is NOT reachable through this
     application's actual attack surface today — PostgREST (the only
     path any client, browser or mobile, ever uses to reach Postgres)
     exposes no TRUNCATE verb at all, and this grant already existed,
     unchanged, on `trips` and others before this phase began (verified
     directly, not merely assumed) — this migration neither introduced
     nor widened it. A schema-wide TRUNCATE-privilege revocation across
     every tenant table is a real, worthwhile hardening item, but it is
     a repository-wide audit well outside this phase's own scoped
     mission (RPC mutation boundary for two specific tables) and is
     flagged here rather than silently fixed or silently ignored.

  2. A raw client `SELECT ... FOR UPDATE` against recurring_arrangements
     or recurring_occurrence_exceptions fails outright for
     `authenticated` (Postgres's own FOR UPDATE clause requires the
     UPDATE privilege on the target table, which authenticated does not
     hold on either — confirmed empirically while building this phase's
     own concurrency test). This is not a gap — it is, if anything,
     additional defense-in-depth confirming the raw mutation boundary
     holds even for a client attempting to merely LOCK a row it cannot
     otherwise write to — but it did require this phase's own
     concurrency test harness to issue its manual locking step as the
     `postgres` role (before switching to `authenticated` for the actual
     RPC call) rather than as `authenticated` throughout, unlike the
     pre-existing mutation_concurrency_test.sh (which locks `trips`,
     a table `authenticated` DOES hold partial column UPDATE grants on).
     Documented here for anyone extending this concurrency-test pattern
     to another zero-UPDATE-grant table in a future phase.
