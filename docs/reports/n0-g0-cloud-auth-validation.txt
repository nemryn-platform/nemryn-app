3. AUTHENTICATION ARCHITECTURE
--------------------------------------------------------------------
**Sign in** (`src/app/sign-in/actions.ts`): reads email/password from
`FormData`, calls the real `supabase.auth.signInWithPassword()` —
never a shortcut. On failure, returns one single generic error code
(`INVALID_CREDENTIALS`) regardless of whether the account exists or
the password is wrong — confirmed by reading the code, not merely
the doc comment claiming it. `next` (the post-login redirect target)
is passed through `safeRedirectPath()` — an allowlist-based regex
(`^\/[A-Za-z0-9\-_/]*(?:\?[A-Za-z0-9\-_=&]*)?$`) that rejects
protocol-relative URLs, absolute URLs of any scheme, backslashes, and
any colon at all — a client-influenced `next` value cannot be used to
redirect a signed-in user off the application.

**Sign up** (`src/app/sign-up/actions.ts`): real `signUp()`, then
(only if a session came back immediately) `signup_create_organization`
— a SECURITY DEFINER RPC that atomically creates the caller's
UserProfile + a new Organization + their own `organization_admin`
Membership in one transaction, deriving identity from `auth.uid()`
only. If confirmation is required, full name/business name are
persisted in `signUp()`'s own `options.data` (Supabase's
`raw_user_meta_data`) — plain intent data, never trusted as
authorization — and completed later via `/complete-signup`, called
`complete_pending_signup()`, idempotent by construction (an advisory
lock + existing-Membership check).

**Email verification** (`/auth/confirm`, new): reads `token_hash`/
`type`, calls `verifyOtp()` on the SERVER Supabase client, writes the
session cookie directly, redirects to `/complete-signup`. See §8
Defect #1 for why this exists and its current (undeployed) status.

**Password recovery**: does not exist. See §8 Defect #2.

**Logout** (`src/lib/auth/sign-out-action.ts`): calls the real
`supabase.auth.signOut()` (invalidates the actual session — never
just deleting a cookie while the session stays valid server-side),
also clears the `zw_org_context` cookie, redirects to `/sign-in`.

**Session persistence**: session cookies are `httpOnly` (`sb-*`
prefix, set via `@supabase/ssr`'s own cookie adapter) — confirmed
directly, not assumed, in an earlier stable window of this same audit
session (`sb-127-auth-token.0`/`.1`, `Path=/`, `SameSite=lax`, ~400-day
`Max-Age`). `src/proxy.ts` refreshes the session on every non-static
request. An expired/missing/invalid session is handled uniformly by
`getUser()` returning `null` — every guard treats that identically to
"never signed in," never a special/differently-secured state.

4. TENANCY ARCHITECTURE
--------------------------------------------------------------------
Tenant identity is **always** derived from the caller's own live,
active Membership row — never from a client-supplied organization ID
— confirmed at every layer traced:

- `getActiveMemberships()` (`src/lib/auth/membership.ts`) queries
  `memberships` filtered by `user_id = <the caller's own auth.uid()>`
  AND `status = 'active'` — with an explicit, LOAD-BEARING comment
  explaining a real, previously-found subtlety: `memberships` also
  carries an org-admin-visibility RLS policy that would otherwise
  silently return every Membership in an org the caller ADMINISTERS,
  not just their own, if the `user_id` filter were dropped. This is
  exactly the class of "RLS is technically satisfied but the app query
  is still wrong" defect this audit was asked to hunt for — already
  found and fixed in a prior phase, with a regression test (ROLE-1)
  protecting it.
- `resolveOrganizationContext()` (`src/lib/auth/organization.ts`):
  single active Membership → auto-selected; multiple → requires the
  `zw_org_context` cookie to match one of the caller's OWN active
  Memberships (re-validated against a fresh DB query on every read,
  never trusted from the cookie value alone) — a stale/foreign value
  is treated identically to no cookie at all.
- `selectOrganizationAction()` (`src/app/select-organization/
  actions.ts`): the client DOES submit an `organizationId` in the
  form, but it is checked against a FRESH `getActiveMemberships()`
  call before being written to the cookie — an arbitrary/foreign UUID
  is rejected outright (re-renders the selector, never accepted). The
  cookie itself is `httpOnly` (not client-JS-readable/writable),
  `sameSite: lax`, `secure` in production.
- Every Server Action inspected (`createTripAction`, `addPassengerAction`,
  the dispatch/assignment actions, the driver-invite actions — 13
  files total) resolves `organizationId` from a fresh
  `requireOperationsAccess()`/`requireDriverAccess()` call, **never**
  from `formData.get("organization_id")` or any client-suppliable
  field — confirmed by grep across every `actions.ts` file (zero
  matches for a client-sourced `organization_id` read).
- RLS is the final authority regardless: even if an app-layer check
  were somehow bypassed, `has_org_role()`/`current_driver_id()`
  (both SECURITY DEFINER, `search_path` pinned, deriving everything
  from `auth.uid()`) independently re-gate every table and RPC. This
  was directly spot-checked live during this audit (§7).

No place was found where the frontend is trusted to determine
authorization — every consequential decision is re-derived
server-side, and RLS independently backstops it regardless.

5. RLS ARCHITECTURE
--------------------------------------------------------------------
16 tables, every one with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`
in its own creation migration (`pg_class.relrowsecurity = true` for
all 16, per `docs/security/rls-model.md`'s own prior direct
inspection). **Zero tables have any grant to `anon`** — confirmed via
`grep` across every migration file, zero matches for a client role
grant scoped to `anon`. 44 active policies, all `TO authenticated`,
none using a blanket `USING (true)`.

**DELETE is structurally impossible for every role, on every table,
tenant-scoped or not** — confirmed via `grep -rn "for delete\|grant
delete" supabase/migrations/*.sql`, zero matches anywhere in the
schema. This is the deliberate, sound design already in place (status-
based deactivation — e.g. Passenger `status`, Trip `state` — never a
hard DELETE, preserving audit history) — re-confirmed live this audit
via a direct spot-check query (§7): an authenticated org_admin
attempting `DELETE FROM trips` for their OWN organization's own trip
was denied with `permission denied for table trips`, the identical
denial a cross-tenant attempt would receive. Cross-tenant DELETE
isolation is therefore not merely proven, it is a trivial consequence
of DELETE being unreachable by anyone.

Helper functions underpinning nearly every policy:
- `has_org_role(p_org_id, p_roles)` — `exists(select 1 from
  memberships where organization_id = p_org_id and user_id =
  auth.uid() and status = 'active' and role = any(p_roles))`.
  SECURITY DEFINER, `search_path = public, pg_temp` pinned (prevents
  search_path-injection attacks).
- `current_driver_id(p_org_id)` — same shape, resolving the caller's
  own linked, active `drivers` row.

Both derive identity **exclusively** from `auth.uid()` (the session
JWT's own subject claim) — never a parameter the caller could
substitute another user's or another org's ID into for their own
authorization decision.

8. DEFECTS FOUND
--------------------------------------------------------------------

### Defect #1 — Email confirmation link never establishes a session (currently LIVE in production)

- **Severity:** P1 (production authentication unusable for this one
  specific flow — new-operator and Driver-invite email confirmation)
- **Description:** Clicking the confirmation link in a real Supabase
  confirmation email returns the visitor to an unauthenticated state
  instead of completing signup/invite acceptance.
- **Root cause:** Supabase's DEFAULT "Confirm signup" email template
  links via `{{ .ConfirmationURL }}`, which redirects through
  Supabase's own hosted `/auth/v1/verify` endpoint. That endpoint
  redirects the browser to Site URL with the new session encoded as a
  URL **fragment** (`#access_token=...`) — never sent to any server,
  only readable by client-side JavaScript. This application has no
  client-side code anywhere that reads `window.location.hash` for
  this purpose, so the fragment is silently discarded every time.
  Confirmed directly (not assumed) by following the actual link with
  `curl` and reading its `Location` header in the immediately-
  preceding work session.
- **Affected files:** none in isolation — this is a Supabase Dashboard
  email-template configuration gap, paired with the (now-fixed)
  absence of `src/app/auth/confirm/route.ts`.
- **Security impact:** none directly (no data exposure, no
  authorization bypass) — this is an availability/usability defect
  for one specific flow, not a security hole.
- **Status: ALREADY REMEDIATED IN THIS WORKING TREE, NOT YET DEPLOYED.**
  `src/app/auth/confirm/route.ts` (new) implements the canonical
  Supabase Next.js SSR pattern: reads `token_hash`/`type` as ordinary
  query parameters, calls `verifyOtp()` server-side, writes the
  session cookie directly, redirects to `/complete-signup`. Proven,
  in the immediately-preceding phase, with a REAL Mailpit-delivered
  email, a real link click, for both operator signup and Driver-
  invite signup — 12/12 checks passed across both flows, exactly-once
  Organization/Membership/UserProfile confirmed via direct database
  query in every run. Full detail: `docs/reports/P1-E4-S0A2-auth-
  confirmation-callback-fix-report.txt`.
- **Remaining work (outside this audit's own authority — no
  commit/push):** (a) deploy this fix (a human-authorized push), and
  (b) apply the required Confirm Signup email template change to the
  staging/production Supabase Dashboard — documented exactly in
  `docs/deployment/staging-auth-configuration.md` §Required Confirm
  Signup email template. Neither was done this phase, consistent with
  "Do not commit or push changes."

### Defect #2 — No password-recovery flow exists

- **Severity:** P2 (a real, pre-production gap — not a broken existing
  feature, a missing one; does not block core authentication for an
  operator who has not forgotten their password)
- **Description:** There is no "Forgot password?" link, route, or
  Server Action anywhere in the application.
- **Root cause:** never built — confirmed by exhaustive grep for
  `resetPasswordForEmail` across `src/`, zero matches.
- **Affected files:** none (nothing to point to — this is an absence).
- **Security impact:** none directly; an operational risk (an
  operator who forgets their password has no self-service recovery
  path today) rather than a security weakness.
- **Remediation:** build a real recovery flow (request → email link →
  `/auth/confirm`-style server-side callback → password update →
  authenticated state) before production launch. Explicitly NOT built
  this phase, per this phase's own scope (validation, not net-new
  features) — recorded here as the same PRE-PRODUCTION REQUIREMENT
  every prior staging-validation report in this repository has
  already flagged consistently.

**No P0 defect was found.** No cross-tenant access vulnerability, no
service-role/secret exposure, no client-trusted tenant ID, no RLS
bypass, no missing server-side route guard.
