TIMEZONE PRESENTATION
========================
The operator is never asked to choose a timezone anywhere in the create
or edit forms (§11) — no such field exists. `create_recurring_
arrangement` derives the timezone authoritatively from the Organization's
CURRENT timezone at creation time and stores it as an immutable snapshot

from the Organization's possibly-since-changed current timezone.

CONTROLLED TRIP CREATION ARCHITECTURE
========================================
New migration:
supabase/migrations/20260918090000_recurring_occurrence_trip_creation.sql

Audited `create_trip`'s own full current body (20260916110000_request_
trip_passenger_integrity.sql) before choosing an architecture — found it
already owns every invariant the new path needs (passenger existence/
same-org/active; address nonblank/bounded; hard-coded `state='scheduled'`;
one `trip_events` row; one `audit_events` row). Chose REUSE VIA A PLAIN
FUNCTION CALL over both (a) extending `create_trip`'s own signature
(would require `DROP FUNCTION` + re-grant, touching a working, tested,
already-shipped function for a benefit no greater than option b) and
(b) reimplementing the same validation/insert logic a second time (pure
duplication risk). `create_trip_for_recurring_occurrence` therefore:
locks the arrangement row FOR UPDATE, validates the service date
against the arrangement's own current facts, checks idempotency, derives
the exact UTC `scheduled_pickup_at`, then literally calls `public.
create_trip(...)` (a normal SQL function invocation — Postgres resolves
it under the CALLING function's own SECURITY DEFINER execution context,
which owns `create_trip` and therefore needs no separate EXECUTE grant
to invoke it), and finally sets `recurring_arrangement_id` on the
resulting row in the SAME transaction. Zero duplicated validation logic;
`create_trip` itself remains byte-for-byte unchanged (re-verified: its
own 3 focused test suites — create_trip_tests/create_trip_atomicity_
tests/create_trip_privilege_tests — all pass unchanged, see FOCUSED SQL
RESULTS).

`trips.recurring_arrangement_id` remains completely unreachable to any
client role — this migration adds no GRANT of any kind on that column
(re-verified via `information_schema.column_privileges` after applying:
`authenticated` still holds only SELECT+REFERENCES, no UPDATE, exactly
as it has been since S1B). The ONLY code path in this entire schema that
ever writes to that column is this one function's own internal UPDATE
statement, running under its own SECURITY DEFINER privilege.


SERVICE-DATE VALIDATION
==========================
Every check from §25 implemented and independently proven live (not
merely inferred from the UI only showing valid dates — §25's own
explicit "do not accept arbitrary dates merely because the UI only
normally shows valid ones"): arrangement exists in the authorized
organization (ZW002, no existence oracle); `service_date >= start_date`;
`service_date <= end_date` when set; weekday belongs to `days_of_week`;
not currently skipped; not before the arrangement-local current date
(resolved via the SAME DST-safe technique described below, never the
browser's or server's own "today"); before any EFFECTIVE pause/end
cutoff.

DELIBERATE DIVERGENCE FROM skip_recurring_occurrence, confirmed correct
by re-reading §25's own exact wording ("before any effective pause/end
cutoff," a single unified rule symmetric to `isPatternDate`) rather than
skip's own stricter, asymmetric "ended → reject unconditionally, no
date carve-out" rule (a deliberate S1D product decision specific to
DECLARING A NEW SKIP, not to catching up on a historically-legitimate
missing occurrence): a date strictly BEFORE an arrangement's own ended-
effective cutoff remains creatable even after the arrangement has since
been ended — live-proven (TEST RTC-07a/07b): a date on/after the cutoff
is rejected, but the immediately-preceding day still succeeds, exactly
mirroring `isPatternDate`'s own ended-case logic.


LOCAL TIME -> UTC STRATEGY
=============================
Audited existing timezone utilities first (§26's own explicit
instruction) — found `local-time.ts`'s `organizationLocalToUtc`, already
proven and tested, but reachable only from TypeScript, with no path from
SQL. Since the RPC itself must derive `scheduled_pickup_at` under its
OWN locked, authoritative read of the arrangement's `pickup_time`/
`timezone` (never a browser- or server-action-supplied timestamp a
malicious or stale caller could tamper with independently of the row
this function itself just locked), the identical algorithm was PORTED
— not reinvented — into a new internal-only SQL function, `_organization_
local_to_utc(date, time, timezone)`: the same fixed winter/summer
reference-instant offset-candidate technique, the same round-trip
validation, the same three-way `ok`/`nonexistent`/`ambiguous` result
contract. Never Postgres's own bare `timestamp AT TIME ZONE zone`
construct alone, which resolves a nonexistent or ambiguous local time to
SOME instant silently, with no indication anything was wrong — exactly
the outcome §26 forbids.


DST BEHAVIOR
==============
Empirically verified against Postgres's own live tzdata BEFORE writing
the helper into the migration (not merely reasoned about): queried
`America/New_York`'s real 2026 UTC offset across early March and late
October to find the exact real transition dates (spring-forward:
2026-03-08, 2:00 AM → 3:00 AM; fall-back: 2026-11-01, 2:00 AM → 1:00 AM),
then tested the helper directly against those real dates. All 5 DST
tests pass (see FOCUSED SQL RESULTS, DST-01 through DST-03b): a normal
date resolves correctly; 2:30 AM on the spring-forward date is correctly
detected as `nonexistent` (never silently guessed); 1:30 AM/3:30 AM
immediately before/after that same gap both resolve `ok` with the
correct, differing UTC offset; 1:30 AM on the fall-back date is
correctly detected as `ambiguous`; 00:30/03:30 immediately before/after
that repeated hour both resolve `ok` with the correct, differing UTC
offset. No safe existing behavior was found lacking, and no ambiguity
was left for the RPC to guess at — both `nonexistent` and `ambiguous`
cause `create_trip_for_recurring_occurrence` to raise a clean ZW006
rather than ever proceeding with a guessed instant.


TRIP CREATION IDEMPOTENCY
============================
No new UNIQUE(arrangement, date) constraint was added (§28's own
explicit "why not" — multiple linked Trips per date remain legitimate
for the domain in general, e.g. future outbound/return workflows).
Idempotency is enforced PROCEDURALLY, scoped to only this one action:
under the arrangement row's own lock, a qualifying (non-cancelled,
dated) linked Trip already satisfying the requested service date (in
the arrangement's own timezone — the identical rule the pure evaluator's
own `qualifyingTripsFor` already establishes as authoritative) is
returned as-is, `created=false`, no new Trip, no new audit event.
Live-proven (SQL, sequential): TEST RTC-10 — two sequential calls for
the same arrangement+date produce exactly 1 Trip row, with the second
call returning the identical `trip_id` and `created=false`.


TRIP CREATION CONCURRENCY
============================
New file: supabase/tests/recurring_trip_creation_concurrency_test.sh —
same genuine two-OS-process technique as the S1D concurrency suite
(never simulated via sequential calls). Session A locks the arrangement
row (as `postgres`, since `authenticated` holds no UPDATE grant on
`recurring_arrangements` and Postgres's own `FOR UPDATE` clause requires
it), holds it ~2s, then switches to `authenticated` and calls
`create_trip_for_recurring_occurrence`, then commits. Session B, launched
~0.3s later, calls the SAME RPC for the SAME arrangement+date directly.

Scenario A (no pre-existing Trip): Session B blocked ~1.8s (genuine row-
lock contention, not a lucky non-overlapping interleaving), then
correctly observed A's already-committed Trip and took the idempotent
no-op path — exactly 1 Trip row, exactly 1 `trip_created` audit event,
exactly 1 `recurring_occurrence_trip_created` audit event, no duplicates
of either. PASS.

Scenario B (a CANCELLED Trip already exists for the target date):
Session B blocked ~1.8s, and the race still produced exactly ONE
replacement Trip — never two — with the pre-existing cancelled Trip
completely untouched (byte-for-byte, re-verified after the race). PASS.

Per §32, ONLY this new test was run — the full existing concurrency
suite (S1D's own recurring-arrangement concurrency test, the Trip/
Request/driver-invite concurrency tests) was NOT re-run, since this
phase changed no row-lock or transaction semantics in any of them.
