15. READINESS MODEL
------------------------
`request-readiness-core.ts` — pure, zero runtime imports (`export type
RequestReadiness = "ready" | "needs_passenger" | "not_convertible" |
"accepted"`; `deriveRequestReadiness(input)`), no DB access, callable
by S2E without modification. Rules exactly as locked: state gates
first (declined/cancelled → not_convertible, accepted → accepted,
regardless of passenger linkage); otherwise pending-like states need
an actual active linked Passenger (`passengerId !== null &&
passengerActive`) → ready, else → needs_passenger. No numeric score,
no AI framing anywhere in the label set.

Active-passenger validity is checked against the linked Passenger's
REAL `status === "active"` — never inferred from `passenger_id IS NOT
NULL` alone. This was live-verified with a purpose-built edge-case
fixture: a Pending request linked to an `inactive` Passenger (Desmond
Okri) correctly renders "Passenger needed," not "Ready" (§29 screenshot
01, row 2) — the exact scenario this rule exists to prevent from being
silently wrong.

19. SERVICE-DATE FORMATTING
--------------------------------
`formatRequestServiceDate(preferredDate, preferredTime)`: date-only
when only a date is set ("Sep 20"), date+time when both are set

substitutes `created_at` for a missing service date. Live-verified all

A real bug was found and fixed during implementation (before any live
testing): the function originally formatted a `Date.UTC(...)`-
constructed date with `Intl.DateTimeFormat` but omitted `timeZone:

silently drift depending on the SERVER's own local timezone (the
underlying columns are plain `date`/`time`, not `timestamptz`, so this
would have been a real, environment-dependent rendering bug in
production). Fixed by adding `timeZone: "UTC"` explicitly to both
`Intl.DateTimeFormat` calls, with a code comment clarifying this is a
neutral formatting anchor, not a real timezone conversion.

32. A REAL BUG FOUND AND FIXED DURING LIVE TESTING
--------------------------------------------------------
The first live test run returned a correct `pendingCount` (from an
independent count-only query) but ZERO rows in the main list query —
a real correctness bug, not a test-script artifact. Root cause:
`transportation_requests` carries TWO foreign keys to `passengers` (a
plain `passenger_id` FK and the composite, tenant-safe
`(passenger_id, organization_id)` FK), which makes the unqualified
embedded-relation syntax `passengers(display_name, status)` genuinely
ambiguous to PostgREST (error PGRST201 — "Could not embed because more
than one relationship was found"). The query errors, and
`getRequestsList`'s existing (pre-existing, matches `trips-list.ts`'s
own convention) `if (error || !data) return { rows: [], ... }` swallow
silently returned empty rows while the independent count queries kept
succeeding — exactly the confusing symptom observed.

Confirmed directly against the local PostgREST endpoint via curl
(reproduced the PGRST201 error, then confirmed the FK-qualified hint
resolves it). Fixed in `requests-list.ts` by qualifying the embed as
`passengers!transportation_requests_passenger_id_organization_id_fkey(
display_name, status)` — the same composite-FK-hint convention already
used by `dispatch-board.ts`, `todays-operations.ts`, and
`trip-detail.ts` for the analogous `trips` → `passengers` embed. This
is a query-layer fix only, in a file created by this phase — no
Supabase migration, RPC, or RLS policy was touched (§34 confirms zero
Supabase diff both before and after this fix). Re-ran the full
typecheck/build/live-test suite after the fix; all green.

This bug would have shipped invisibly: every static check
(typecheck/lint/build/unit tests) passed cleanly both before and after
this fix, because none of them execute a real query against a database
with the actual dual-FK schema. It was caught only by live-testing
against the real local database, which is exactly why this phase
requires it.
