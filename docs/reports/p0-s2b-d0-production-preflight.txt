5. RECOVERY ARCHITECTURE
====================================================================

Confirmed, by direct code reading (§2) AND live re-execution (§17):

  /sign-in → "Forgot password?" → /forgot-password
    → supabase.auth.resetPasswordForEmail(email, { redirectTo:
      `${getAppOrigin()}/auth/confirm` })
    → (production) https://app.zenwardmobility.com/auth/confirm
    → ?token_hash=...&type=recovery
    → server-side supabase.auth.verifyOtp({ type: "recovery",
      token_hash }) in src/app/auth/confirm/route.ts
    → recovery marker cookie (zw-recovery-pending) + real Supabase
      session, both on the SAME redirect response
    → /auth/reset-password (gated: marker cookie AND getUser() both
      required)
    → supabase.auth.updateUser({ password })

Confirmed absent, by grep across the entire new/modified file set:

  - no custom reset token: no new column/table/migration exists
    anywhere in `supabase/migrations/` (§7 below); the ONLY "token" in
    this flow is Supabase's own recovery `token_hash`.
  - no application DB table for password recovery: confirmed — zero
    new migration files, zero new table references in any new file.
  - no privileged RPC: `updateUser()` is Supabase's own standard
    client method, called on the publishable-key client
    (`createServerSupabaseClient()`) — the SAME client every other
    Server Action in this codebase already uses.
  - no service-role credential: `grep -rln "service_role\|
    SERVICE_ROLE\|SUPABASE_SERVICE"` across every new/modified file
    this phase reviewed → zero matches.
  - no arbitrary redirect target: `/auth/confirm` takes no caller-
    suppliable `next`/redirect parameter (fixed destinations only,
    chosen from the verified `type`); `/forgot-password` and
    `/auth/reset-password` accept no redirect-target parameter at all.
