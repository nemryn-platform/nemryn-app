Refinement A (activation safety; ZD-259 / ZD-262):
- The single availability rule is _plus_inquiry_public_form. It requires: a key in the right format, a published form,
  an active organization, Plus write, and an allowlist row.
- Both the hosted-form config (get_public_plus_inquiry_form) and submission (submit_plus_inquiry) use it.
- plus_publish_inquiry_form refuses without the allowlist (ZW004 public_access_not_enabled), so staff configuration
  cannot bypass activation.
- Removing the allowlist row stops a published form immediately (test E10).
- No migration or seed adds an allowlist row.
- The global kill switch PLUS_INQUIRY_SUBMISSIONS (default OFF) is RESERVED for S7-B's server-only route, checked
  before any database call. It is documented in the canonical design §3; there is no database part, by design.
- Enabling synthetic testing for one organization cannot expose another: the allowlist is per organization and is
  checked inside the same function that resolves the key.

5. TENANT-ISOLATION APPROACH
----------------------------
- The public organization comes only from a published key, inside the service_role function. No parameter can name an
  organization, form, contact, status or owner.
- Staff functions take the organization from the server session and check plus_can_read / _require_plus_write /
  _require_plus_admin_write (has_org_role: an active membership in an active organization).
- Composite foreign keys everywhere: form ↔ inquiry; inquiry ↔ contact; opportunity ↔ inquiry; consent ↔
  (inquiry, organization, contact). A cross-tenant link is a foreign-key violation, never a link.
- Unknown and foreign ids return the identical ZW002 (no existence oracle).
- A Platform Admin without a membership sees nothing: RLS returns 0 rows and the functions return ZW002.
- Tests: D3, D4, D5, M3 (Org B contact), and the RLS row counts.

  resolver are unchanged.

  version and an inquiry_id; the consent FK binds them to the same contact.
