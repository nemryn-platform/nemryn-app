Conclusion: the direct UPDATE bypasses no applicable invariant.
- The only intentional difference is the version token. A token protects a human edit from overwriting newer data;
  the fill path is a server rule that can only set NULL fields under the lock, which gives the same guarantee without
  a token.
- Note (identical in both paths): updated_at = the writing transaction's now(), so it can be earlier than the
  committed value it replaces. It never repeats a value any client could hold, so a stale client always gets ZW003
  (no ABA).

B. In-flight public submission vs form disable / allowlist removal

Design facts (deployed):
- submit_plus_inquiry is VOLATILE. Availability is evaluated once, by _plus_inquiry_public_form (STABLE; plain reads
  with NO row lock). It requires: published form, active organization, Plus write, allowlist row.
- The insert's foreign-key check takes FOR KEY SHARE on the plus_inquiry_forms row.
  - plus_disable_inquiry_form takes SELECT … FOR UPDATE on the same row, so the two serialize on that row.
  - The allowlist removal (DELETE plus_inquiry_public_access) shares no lock with submissions.

Measured behaviour (concurrency S9–S12):
- S12: after a disable or an allowlist removal COMMITS, every new submission is unavailable — 6 parallel attempts
  each, nothing stored.
  ⇒ Immediate revocation for NEW submissions is GUARANTEED.
- S9 / S10: a submission whose availability check ran BEFORE the revocation committed is still stored.
  - S9: the insert waited on the disable's row lock and committed just after the disable.
  - S10: no shared lock with the allowlist removal.
  The window is bounded to requests already executing at the instant of revocation, and is further limited by the
  rate limit (5 / client / h, 60 / form / h).
- S11: a submission already in flight when a disable starts is stored with received_at before disabled_at, and the
  disable completes normally.

Assessment against the approved requirement (ZD-259 / ZD-262: removing the switch or the allowlist row stops the
form at once):
- NOT violated. "Stops the form" means no new submission is accepted, and S12 proves this for the database rule.
- The S7-B kill switch is read per request, so it is immediate for every new request.
- What the in-flight request does:
  - it creates only one row in the organization's own private inbox;
  - it creates nothing else: no contact, opportunity, Core row, notification or consent;
  - it is visible to staff, who can dismiss it.
- No code change was made, per the instruction "fix only if violated".
- Optional hardening (owner choice, not required): submit_plus_inquiry could re-check the form row with
  SELECT … FOR SHARE (status = 'published') and the allowlist row with FOR SHARE just before inserting. That makes a
  racing submission wait for the revocation and then refuse. Cost: public submissions would briefly block a disable
  / removal. Recommended only if strict "no row after revocation commits" semantics are wanted.
