3. AUTHORIZATION BEHAVIOUR
======================================================================================================================
  Who sees the Growth panel at all: unchanged (canOpenGrowth). Nobody else gets a placeholder or Growth data.

  "Add contact" is rendered only when ALL of these hold (RequestGrowthPanel → canOfferAddContact):
    - the Request has no attribution
    - canWriteGrowth: Plus effective state write AND capability write (an Organization Admin, or a Dispatcher with a
      write grant)
    - plus_request_contact_enabled(org) is true (the synthetic-only allowlist). It fails closed.

  When the organization is disabled: only "Link existing contact" is shown, with no notice (ZD-300).
  Read-only Plus, or a read grant: the panel without controls (unchanged).

  The UI is not the control. createContactForRequestAction re-checks:
    - requirePlusAccess
    - the form's organization against the session organization (WRONG_ORGANIZATION)
    - canWriteGrowth
  It then makes ONE call to plus_create_contact_for_request, which re-checks Plus write, the Core request-read role,
  the activation gate (ZW004 request_contact_not_enabled), tenancy, validation and duplicates (Stage A tests).
  The organization id sent to the database is the session's (g.context.organizationId), never the form's.

  Error handling (requestContactErrorMessage):
    ZW004 request_contact_not_enabled → "isn't available for this organization… You can still link an existing
                                        contact." (no reason or classification is disclosed)
    ZW004 already_attributed          → "linked … by someone else just now … Reload"
    ZW001 / ZW002 / ZW006 / unknown   → plain, non-disclosing messages
  Logging: console.error("[plus] request contact create failed", <code>) only. A unit test asserts that no submitted
  value can reach a log line.

4. FORM BEHAVIOUR
======================================================================================================================
  - The form opens inline inside the Growth panel, with no new page; the Request page stays in place. Focus starts
    on Name.
  - Prefill (buildRequesterPrefill) comes from requester_name, requester_phone and requester_email (when present),
    and the relationship mapped to a contact type:
      self → individual; family / caregiver → family_caregiver; facility_coordinator → facility_staff; other → other.
    Values are trimmed but never reformatted. A Core phone that breaks the contact rules (e.g. "call after 5pm") is
    shown as entered, and validation then asks staff to correct it.
  - Every field is editable. The label "Requester — the person who contacted you. This is not necessarily the
    passenger." is always shown.
  - No passenger field is passed, read or prefilled. RequesterFacts has no passenger property; a unit test and the
    browser checks confirm this.
  - Fields and rules match Growth → Contacts → New (validateContactForm):
      * Name, Phone, Email ("A phone number or an email address is required.")
      * Contact type
      * Preferred channel (phone by default, email when there is no phone)
      * Owner (optional; plus_list_contact_owner_options)
      * Do not contact (unticked)
    The optional job title is omitted, and the RPC passes NULL for it.
  - No consent fields. ADD_CONTACT_NOTICE states that no opportunity or communication consent is created. The
    database writes no consent row (Stage A C1).
  - Duplicates:
      * outcome possible_duplicates → the matches from the released plus_find_contact_matches (name, archived flag,
        "Same email and name", etc.). Nothing is written.
      * An ACTIVE match offers "Link this contact", which uses the released linkRequestAction / plus_link_request.
      * ARCHIVED matches are shown as "(archived — can't be linked)" with no button.
      * "Create a separate contact" resubmits with confirmDuplicate=true. Nothing is ever merged.
  - Pending state: every field and button is disabled while a submission is pending, and the submit button shows a
    spinner. Correctness under double clicks rests on the database transaction (Stage A CONC-1 / CONC-2; browser V6).
  - Refused submissions keep the typed values (echoed and re-mounted), and field errors carry aria-invalid plus the
    message.
  - Success:
      * the form closes
      * revalidatePath refreshes the Request page and the Growth layout
      * the panel shows the linked contact with "Open in Plus" (/operations/growth/contacts/<id>) and "Correct link"
      * the notice "Contact added and linked in Growth. The request itself is unchanged." survives the refresh
      * already_linked shows its own notice and the current link
