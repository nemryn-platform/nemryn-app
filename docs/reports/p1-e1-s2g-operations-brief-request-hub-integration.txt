3. REQUEST SUMMARY CONTRACT
------------------------------
`OperationsBriefRequestSummary` (operations-brief-core.ts):
  pendingRequestCount: number
  oldestPendingRequestCreatedAt: string | null
Definition (exactly matching Request Hub's Pending queue):
  transportation_requests WHERE organization_id = <current server-
  resolved organization> AND state = 'pending'.
No additional analytics, no score, no SLA, no urgency model, no fake
priority, no AI classification anywhere in this datum or its rendering.

4. DATA ACCESS
-----------------
`getRequestSummary` (src/lib/operations/operations-brief.ts) uses the
normal server-side RLS-respecting Supabase client
(`createServerSupabaseClient`) — the service role is never used anywhere
in this phase's code. `organizationId` is a plain parameter supplied by
the caller, which resolves it via `requireOperationsAccess` exactly like
every other Operations data-access module — never read from the browser.
`organization_id` is explicitly filtered in the query as defense in
depth, on top of RLS. No migration, no RPC, no RLS change, no GRANT
change — confirmed via `git status --porcelain supabase/` (§13).

ONE narrow query serves both fields: `.select("created_at", { count:
"exact" }).eq("organization_id", ...).eq("state", "pending")
.order("created_at", { ascending: true }).limit(1)`. PostgREST's
`count: "exact"` reflects the full filtered row count independent of
`.limit()`, so this single round trip returns both the organization's
real total pending count AND the single oldest pending row's
`created_at` — Request rows are never fetched individually merely to
compute a count or a single timestamp. Live-verified: this exact query
produced "4 requests" for Org A (matching Request Hub's own independent
pendingCount badge exactly — §9) from one query, not two.
