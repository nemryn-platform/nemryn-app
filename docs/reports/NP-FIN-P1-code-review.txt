4. FINANCIAL INTEGRITY REVIEW (independent inspection + new adversarial tests)
======================================================================================================================
Receipt allocation invariants
  - Three layers:
      RPC checks;
      a BEFORE INSERT guard that locks the receipt, then the invoice, and re-reads committed state;
      DEFERRED commit-time invariants (0 <= paid <= total; money only on issued invoices; allocated + refunded <= gross;
      reversed at net 0).
  - An unapply is a full mirror of one apply (composite self-FK + unique).
  Verified: I1-I11, Z1 / Z2, K1, K2, K10.                                                                      SOUND
Cross-payer and cross-tenant protection
  - Composite (id, organization_id) FKs on every link, plus an explicit cross_organization guard.
  - Payer identity is by scoped id only, never by name.
  - The cross-payer path needs the cross_payer_allocate permission + a reason, and is flagged and audited.
  Verified: X1-X5, I11, P2-P4, E2E E2 / E8.                                                                    SOUND
Duplicate transaction handling
  - Hard: idempotency keys (receipt, allocation request, unapply, refund, reversals) under an advisory lock, with replay
    comparing the money facts; provider_txn_id unique per organization + provider.
  - Soft: a likely duplicate staff reference (method + normalized reference + amount + date) needs explicit
    confirmation.
  Verified: D1-D5, K3, E2E E6.                                                                                 SOUND (see CR-3)
Invoice void versus allocation concurrency
  Verified: K5 (RPCs, both orders), K5b (direct owner bypass, both orders: refused by the row guard or the deferred
  check at COMMIT), I5, I10.                                                                                   SOUND
Refund and refund-correction lifecycle (the requested question)
  Can a correction create an invalid available balance?
    NO.
    - refundable = gross − net allocated − active (uncorrected) refunds, 0 once reversed.
    - A correction removes exactly that refund's amount from "active", once.
    - R10: 400 -> 1000, never above gross.
    - The deferred invariant enforces allocated + refunded <= gross at commit.
  Can it enable duplicate refunds?
    Not automatically.
    - A correction can run only once per refund (R11, K11).
    - Active refunds can never exceed gross: R11, and K11 in both orders (correction vs new refund at the same moment).
    - After a correction, a new refund is a separate, deliberate Admin action.
    - Residual: misuse risk. An Admin who "corrects" a refund that WAS paid out restores credit that could then be
      refunded or applied again. Controls: SENSITIVE (Admin only), reason required, audit row, the original refund kept
      and shown as "Corrected", UI text "Use this only when the refund was recorded by mistake". See CR-1.
  Can it misrepresent funds returned?
    - Corrected refunds stop counting everywhere: refunded_cents, the ledger summary "refunds this month",
      "collected this month", receipt print (active refunds only), receipt page (marked Corrected).
    - R12 verifies these reads.
    - A refund is labelled "Recorded by staff", never provider-confirmed (V4, E3).
  Ordering
    - A receipt with an active refund cannot be reversed.
    - A correction can target only a refund of the same receipt (composite FK, R13), and never a reversed receipt
      (row guard).                                                                                             SOUND
Receipt reversal behaviour
  - Only at net zero (no allocation, no active refund); once; reason code + reason.
  - The number and row are kept; reversed receipts cannot be allocated or refunded.
  - The NP-BILL-P1 reverse wrapper does unapply + reversal atomically, simple whole-receipt payments only.
  Verified: R4-R8, K8, W2, E2E E5.                                                                             SOUND
Provider confirmation versus staff evidence
  - CHECK: kinds provider_confirmed / reconciled require a non-staff source + source_ref; there is no FIN-P1 writer;
    the staff RPC accepts evidence kinds only.
  - The UI never shows "Provider confirmed" for staff entries.
  Verified: V1-V4, E2E E7.                                                                                     SOUND
Processing-fee accounting
  - fee 0..gross; net = gross − fee is a generated column.
  - Customer balances, allocations, refundable funds and "collected" all use GROSS: the fee is the agency's expense
    (OD-5) and never reduces what the customer paid.
  - Net is shown on the payment page for the agency's own reconciliation (FIN-P5).
  Verified: D5.                                                                                                CORRECT AS DESIGNED
Legacy NP-BILL-P1 compatibility

5. FINDINGS
======================================================================================================================
  CR-1 (Medium, procedural) Refund correction can be misused to restore credit for money that was actually paid out.
       - Mitigated by Admin-only, reason, audit, visible history.
       - Recommendation: before real financial use, (a) state in the operating procedure that corrections are for
         entry errors only, and (b) in FIN-P5 / P6, refuse a correction once the refund is provider-confirmed or
         reconciled.
       - No change made in this review (it would be behaviour beyond the approved scope).
  CR-2 (Low) Refunds have no "possible duplicate" warning, unlike receipts. Two refunds with different keys are allowed
       while funds remain. Mitigated by Admin-only and the refundable cap. Recommend adding a soft warning in FIN-P4.
  CR-3 (Info) The receipt "possible duplicate" check is advisory, not race-proof. Two simultaneous identical staff
       entries with different keys could both pass. Hard uniqueness exists for provider transaction ids. By design
       (soft check).
  CR-4 (Info) Requester-kind payer identity is per request: credit across two requests by the same family member needs
       Admin confirmation. Conservative by design (no name matching).
  CR-5 (Info) billing_payments SELECT stays for one transition release (ZD-268). Revoke in FIN-P1+1.
  No defect found that blocks commit / PR.
