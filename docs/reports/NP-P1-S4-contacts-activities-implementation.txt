======================================================================
One forward-only, additive migration:

  supabase/migrations/20261014100000_plus_contacts_activities.sql

It contains:
  - table public.plus_contacts, with constraints, five indexes, the set_updated_at and prevent_organization_id_change
    triggers, RLS, SELECT for authenticated and the policy plus_contacts_select_plus;
  - table public.plus_activities (append-only), with constraints, one index, RLS, SELECT for authenticated and the
    policy plus_activities_select_plus;
  - internal functions: _plus_user_can_write, _plus_contact_matches, _plus_staff_name, _plus_resolve_owner;
  - types: plus_contact_write_result, plus_activity_write_result;
  - nine RPCs (section 6), each with authenticated EXECUTE and anon/PUBLIC revoked.

It references only organizations, auth.users, memberships, membership_module_grants, user_profiles and the S1-S3 Plus
helpers. There are no forward dependencies: no plus_accounts, plus_opportunities or plus_tasks. It edits no earlier
migration and changes no Core object.

Two defects were found by the new tests and fixed in this (unreleased) migration before completion:
  - plus_update_contact built its changed-field list with `text[] || 'literal'`. PostgreSQL parsed the literal as an
    array, so every real edit failed with 22P02. Now uses array_append (SQL U3).
  - The 30-second duplicate guard in plus_log_contact_activity compared occurred_at with each transaction's own
    now(), so two simultaneous identical "now" entries were both written. It now compares the time only when one is
    given explicitly, and the contact row is locked FOR NO KEY UPDATE so concurrent logs serialize (CONC-C3).

4. CONTACTS SCHEMA (public.plus_contacts) -- domain model section 6
======================================================================
  | Column            | Type / default                       | Rule                                                        |
  |-------------------|--------------------------------------|-------------------------------------------------------------|
  | id                | uuid pk                              |                                                             |
  | organization_id   | uuid not null, FK organizations      | unique (id, organization_id) for composite FKs              |
  | display_name      | text not null                        | trimmed, 1-200                                              |
  | phone             | text                                 | trimmed, <= 40; digits, spaces and + ( ) . -; optional "x123" / "ext 123"; 7-20 digits |
  | email             | text                                 | stored trimmed + lower-cased, 3-254, basic address shape    |
  | contact_kind      | text not null                        | individual, family_caregiver, facility_staff, referral_source, other |
  | job_title         | text                                 | trimmed, 1-120                                              |
  | preferred_channel | text not null default 'phone'        | phone, email, none                                          |
  | do_not_contact    | boolean not null default false       | stored preference for future outreach to enforce            |
  | owner_user_id     | uuid, FK auth.users                  | validated by RPC: an eligible Plus writer                   |
  | status            | text not null default 'active'       | active, archived, redacted (reserved for PD-11; no function sets it) |
  | created_by        | uuid not null, FK auth.users         |                                                             |
  | created_at        | timestamptz default now()            |                                                             |
  | updated_at        | timestamptz default now()            | the version token                                           |

- Reachability check: phone IS NOT NULL OR email IS NOT NULL OR status = 'redacted'.
- Indexes:
  - (organization_id, status, display_name);
  - (organization_id, lower(display_name));
  - (organization_id, email) WHERE email IS NOT NULL;
  - (organization_id, phone) WHERE phone IS NOT NULL;
  - (organization_id, digits-only phone) WHERE phone IS NOT NULL.
- Duplicates are allowed: there is no unique key on email or phone.
- Deliberately absent (verified by SQL K6 and E2E B2): account_id (P3-S1), passenger_id, date of birth, address,
  health, diagnosis, mobility, insurance and trip fields.
- Archived rows are kept with their whole timeline. Nothing is ever hard-deleted.

5. ACTIVITY SCHEMA (public.plus_activities) -- domain model section 7, append-only
======================================================================
  - id;
  - organization_id (unique (id, organization_id));
  - contact_id: nullable, with composite FK plus_activities_contact_fkey (contact_id, organization_id) ->
    plus_contacts (id, organization_id);
  - activity_type;
  - body: trimmed, 1-2000;
  - from_stage, to_stage;
  - actor_user_id: not null, FK auth.users;
  - occurred_at;
  - recorded_at: when the row was written.

Named constraints, which P2-S1 / P2-S3 / P3-S1 replace deterministically:
  - plus_activities_subject_check: num_nonnulls(contact_id) = 1. P2-S1 makes it >= 1 with opportunity_id.
  - plus_activities_activity_type_check: note, call_logged, email_logged, meeting_logged, owner_changed,
    record_archived. These are only the types S4 produces. Opportunity, quote, consent, task and request types are
    NOT allowed.
  - plus_activities_body_required_check: a body is required for note and *_logged.
  - plus_activities_stage_check: from_stage / to_stage only on stage_changed, which S4 does not allow, so they are
    always NULL in S4.
  - plus_activities_occurred_check: occurred_at <= recorded_at + 5 minutes.

Immutability:
  - no INSERT, UPDATE, DELETE or TRUNCATE privilege for any client role;
  - no policy other than SELECT;
  - no function updates or deletes a row (verified by a pg_proc source scan, SQL L9).
  - This follows the existing append-only precedent (trip_events, audit_events): privileges, not triggers.

There is no metadata JSON column. Logging is a record of what staff did; Nemryn sends, calls and schedules nothing.

Additive deviations from the canonical shape:
  (a) recorded_at was added, so interactions logged after the fact stay honest ("logged <time>" in the UI).
  (b) The S4 type CHECK is a subset of the canonical list, as the brief requires. Later slices widen it.
Both are documented in plus-domain-model.md section 7.

6. RPC INVENTORY AND AUTHORIZATION RULES
======================================================================
Every RPC is SECURITY DEFINER with search_path pinned to (public, pg_temp), and authenticated EXECUTE only.
Organization binding comes from the server session; the browser never names the organization the database trusts.

Read (plus_can_read: an Admin while write / read_only; a Dispatcher with an active read or write grant while write):
  - plus_list_contacts(org, search, kind, status, limit, offset):
    - pages of 1-100 (the UI uses 25);
    - status active (default), archived or all;
    - search on name substring, email substring and phone digits (>= 3); LIKE wildcards are literal;
    - total_count is the filtered total; the owner appears by name only.
  - plus_get_contact(org, contact_id): ZW002 for no access AND for a foreign or unknown id (no existence oracle).
    Returns owner_membership_id (opaque), owner_can_write, created_by_name and updated_at.
  - plus_list_contact_activities(org, contact_id, limit, offset): newest first, with the actor's name.
  - plus_find_contact_matches(org, name, phone, email, exclude): up to 5 matches in that organization only.
Write (_require_plus_write: ZW002 when the caller cannot read; ZW001 when they can read but not write):
  - plus_list_contact_owner_options(org): active Admins and Dispatchers with an active WRITE grant. Membership handles
    and names only; no user ids or emails.
  - plus_create_contact(org, name, phone, email, kind, title, channel, dnc, owner_membership_id, confirm)
  - plus_update_contact(org, contact_id, expected_updated_at, ...): row lock, then version compare (ZW003); archived
    gives ZW004; identical values give changed = false.
  - plus_archive_contact(org, contact_id, expected_updated_at, reason): ZW003 when stale; changed = false when already
    archived.
  - plus_log_contact_activity(org, contact_id, type, body, occurred_at): loggable types only; the time may not be in
    the future (> 5 min) or more than 366 days back; archived gives ZW004.
Internal (no client EXECUTE): _plus_user_can_write, _plus_contact_matches, _plus_staff_name, _plus_resolve_owner.

Owner rule: a NEW owner must be an eligible Plus writer of THAT organization. Anyone else gives ZW006: a Dispatcher
without a grant or with a read grant, a Driver, an inactive member, or another organization's membership. An unchanged
owner who has since lost access is kept and flagged in the UI ("no longer has Nemryn Plus write access").

Concurrency: optimistic (updated_at) plus row locks. Edit / archive hold FOR UPDATE; log holds FOR NO KEY UPDATE.

Audit model:
  - The Plus timeline records owner_changed, record_archived and the four logged interaction types.
  - audit_events receives plus_contact_created, plus_contact_updated (the NAMES of changed fields only) and
    plus_contact_archived. No contact values are copied into the Core audit log.
  - These actions are not in the Core Settings -> Activity allow-list, so they do not appear there.

Service role: not used anywhere in S4.

8. DUPLICATE DETECTION BEHAVIOUR
======================================================================
- A match within the SAME organization is any of:
  - the same normalized email;
  - the same phone digits (>= 7 digits; formatting ignored);
  - the same name, ignoring case.
- On create: if any match exists and the person did not confirm, the database writes NOTHING and returns
  possible_duplicates = n. The UI then lists up to 5 matches (with links and "Same email / phone / name") and offers
  "Create as a separate contact". Confirming creates a new, separate row.
- Contacts are never merged and never auto-linked. Another organization's contacts are never matched or revealed
  (SQL D6).
- Known limit: two people creating the same new contact at exactly the same moment can both pass the check, because
  duplicates are allowed by design and the check is advisory.

15. SUPABASE FREE RECOVERY LIMITATION
======================================================================
- Production (wyocbivzgrbekuyqdfts) is on Supabase Free. No managed backup or PITR is available.
- The owner's private logical exports taken during S3 release preparation (schema, data, roles) exist, but they are
  NOT a verified recovery point. Their restorability has not been demonstrated here, and this phase did not connect to
  production to export anything.
- S4 migration production risk: LOW and additive. It creates two empty tables, functions and types; it modifies no
  existing row, table, function or policy, and existing data is untouched. The forward-compatibility run on a seeded
  production-head copy applied cleanly. The real risk is AFTER release: S4 creates the first CRM business records, and
  without PITR, operator error or corruption has no managed restore path.
- Recommended before the S4 release, owner-run with the owner's own credentials:
  1. Take a fresh logical export (schema + data), encrypted, stored outside the repository.
  2. VERIFY it: restore into a scratch local Supabase project, then run the privilege contract and spot-check row
     counts. Only a verified restore counts as a mitigation. It is still not equivalent to PITR.
  3. Repeat this before every later Plus release that changes data.
- Release order: migration FIRST (dry run must show exactly 20261014100000 pending), then post-migration verification
  (contract 0/29, functions present), THEN the app.
  - If the app ships first, every Contacts RPC is missing, the pages show their error state, and Growth itself still
    works.
  - The S3 app (208e7a5) is fully compatible with the S4 migration. It never calls the new objects. The only
    pre-existing object touched is the privilege-contract test file, not production.
- App recovery without deleting business records: roll the APP back (Vercel instant rollback to 208e7a5) and leave
  the database as it is. The tables and their rows stay intact and are simply not exposed by the older app. Never
  "roll back" by dropping the tables once real rows exist.
- Limits of reversing the migration: a down-migration would have to DROP plus_activities / plus_contacts (data loss),
  the functions and the types. That is acceptable only while the tables are empty (immediately after release). After
  the first records exist, the only safe recovery is forward: a new migration or an app rollback.
