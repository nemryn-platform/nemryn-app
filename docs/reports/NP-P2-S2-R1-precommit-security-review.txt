Database (migrations 20261015100000 / 110000 / 120000):
- plus_tasks:
  - Exactly one subject (CHECK). Subjects are validated under FOR NO KEY UPDATE: an active contact or an open

- plus_list_agent_recommendations returns contact PREFERENCES (do-not-contact, preferred channel, has phone/email),
  never phone or email values.

3. CODE CORRECTIONS AND REASONS
======================================================================
FIX R1-1 (genuine defect, concurrency; low severity, no security impact). File:
supabase/migrations/20261015110000_plus_growth_agent.sql, function plus_approve_agent_recommendation.
- Defect:
  - The approval revalidated the recommendation's situation BEFORE locking the opportunity, and never locked the
    contact.
  - A task, stage change or logged activity committed concurrently by another staff member was not seen. The
    approval then created a redundant task (two follow-ups) or a task from a stale recommendation.
- Reproduced before the fix with two new concurrency scenarios:
  - CONC-G4: approval racing a manual task on the same opportunity -> 2 tasks, recommendation "approved" (FAIL);
  - CONC-G5: approval racing a logged activity on the contact -> task created from a stale recommendation (FAIL).
- Fix: after the version check and before revalidation, take FOR NO KEY UPDATE locks on the opportunity, then on its
  primary contact. This is the same lock mode and order the existing writers use:
  - plus_create_task locks its subject;
  - plus_log_contact_activity locks the contact;
  - stage changes lock the opportunity;
  - contact edit and archive lock only the contact;
  - plus_update_opportunity locks the opportunity, then the contact.
  So no lock-order inversion is introduced. Each competing write either committed already, and the revalidation
  (a new READ COMMITTED snapshot) sees it, or it waits for the approval.
- After the fix:
  - CONC-G4 -> recommendation superseded, exactly 1 task (the manual one);
  - CONC-G5 -> superseded, 0 tasks;
  - G1-G3 unchanged. 5/5 PASS on three consecutive dev runs, plus the fresh and upgraded isolated runs.
- The migration is UNAPPLIED in production, so the file was corrected in place; no new migration is needed. The
  local dev database was updated with CREATE OR REPLACE of the same signature; grants and comment were kept.
- Test added: supabase/tests/plus_growth_agent_concurrency_test.sh, scenarios 4 and 5 (CONC-G4, CONC-G5), and a
  fourth fixture opportunity (CONC-G2 now expects 4 recommendations).
- Docs: docs/data/mutation-api.md approval contract now states the lock order.

FIX R1-2 (documentation consistency; no behaviour change).
- Defect: the header comment in supabase/migrations/20261015100000_plus_tasks.sql said "overdue" is evaluated in the
  organization timezone. The code (and test D1) defines overdue as due_at < now(), a timezone-independent instant;
  only "today" uses the organization timezone.
- Fixed:
  - the comment now states the canonical definitions;
  - product spec section 7.3 lists the same definitions once (overdue / due today / upcoming / no due date), noting
    that a task due earlier today is overdue, not due today.
- No SQL statement changed.

No other change was made. No improvement was invented.
