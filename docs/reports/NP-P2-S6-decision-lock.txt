3. REFINEMENT R1 — ADDRESS DIGEST: PLAIN SHA-256 vs KEYED HMAC-SHA-256
----------------------------------------------------------------------
Purpose of the digest (ZD-232): a narrow equality check. "Is the contact's CURRENT email / phone the one this grant was
given for?" The plaintext address lives in the same tenant row (plus_contacts.email / phone), and the comparison is
always made against it.

| Criterion | A. Plain SHA-256 | B. Keyed HMAC-SHA-256 |
|---|---|---|
| Dictionary / enumeration attack on a stolen digest | Weak. About 10¹⁰ phone numbers are enumerable in seconds to minutes; emails fall to a dictionary | Strong while the key stays secret |
| Entropy of the input | Phone about 33 bits; email low to moderate. Hashing adds no entropy | Same input. Security rests on the key |
| Exposure if the database is compromised | The attacker also reads the plaintext in plus_contacts, so the digest adds nothing | Same, unless the key is stored outside the database. With Supabase Vault (inside the same database) a database compromise exposes the key too |
| Exposure to clients | None: no client SELECT, never returned (ZD-240) | None |
| Normalisation consistency | Deterministic in SQL (lower / trim; digits only) | Same |
| Cross-tenant correlation | Mitigated: the organization id is part of the input, so the same phone in two organizations gives different digests | Mitigated by a per-tenant key or input |
| Key custody | None | A new secret in every environment (local, CI, production). It must not be in migrations, source or committed env files. Needs Vault provisioning plus an owner-run procedure |
| Availability in DB functions | Built-in sha256() (PostgreSQL ≥ 11); no extension | Needs pgcrypto hmac() plus a Vault read in a SECURITY DEFINER function; the function then depends on secret state |
| Rotation / historical verification | Not applicable; the version label "v1" in the input allows an algorithm change | Old digests become incomparable after rotation. Needs a key_version column and retained old keys, or recomputing every grant: a schema and contract change |
| Deployment dependencies | None beyond the migration | A secret must exist before the migration runs; a missing key breaks every grant |
| Retention / redaction / erasure | The digest is personal data (reversible for phones). PD-11 erasure must remove it with the plaintext | Also personal data while the key exists. Destroying a per-tenant key could neutralise digests ("crypto-shredding"), but that is a PD-11 design question |
| address_changed behaviour | Fully supported | Supported, but rotation without key_version would wrongly report address_changed for every grant |

Assessment:
- B protects only against an attacker who holds the digests but neither the plaintext nor the key. In this design the
  plaintext sits beside the digest, so that scenario requires a partial leak of the ledger alone. Even then, no client
  role can read the column.
- B would add:
  - a new secret-management architecture (Vault provisioning, owner-run key custody);
  - a key_version column and rotation semantics, which change the approved schema;
  - a hard deployment dependency.

DECISION (implementation refinement within the approved OD-S6-4 A, recorded for owner review):
- Plain SHA-256 with domain separation and a version label:

    sha256('nemryn.plus.consent-address.v1|' || organization_id || '|' || kind || '|' || normalized)

  - kind = 'email' or 'phone' (SMS and voice share the phone);
  - normalized = lower(trim(email)), or the phone's digits only.
- The approved representation is unchanged: a server-computed SHA-256 hex digest.
- The organization id and version label are additions to the hashed input, documented here and in design §2.6. They
  remove cross-tenant equality and allow a future change.

Privacy limitations, stated plainly:
- the digest is NOT anonymisation, NOT irreversible removal and NOT proof of compliance;
- a phone digest is reversible by enumeration; an email digest by dictionary;
- it is personal data and is handled like the address;
- PD-11 erasure must remove or neutralise it.

No material security blocker was found, so S6-A proceeded. If the owner later wants keyed digests, that is a separate
decision (Vault key custody, key_version column, rotation) and a later migration.

4. REFINEMENT R2 — CONCURRENCY AND REVOCATION ORDERING
-----------------------------------------------------
Mechanism:
- Consent writes lock the contact FOR NO KEY UPDATE; plus_update_contact locks it FOR UPDATE. These conflict, so every
  consent write and contact edit on one contact is serialized.
- seq is allocated at INSERT, after the lock, so for a contact seq order is the serialized write order.
- The DNC step runs inside plus_update_contact, under its lock, in the same transaction.

Verified by plus_communication_consents_concurrency_test.sh (12 scenarios plus the global invariant). Results are in
NP-P2-S6A-database-implementation.txt §11.

Required invariant: turning DNC on cannot leave an effective grant active, and clearing DNC cannot revive a previous
grant. VERIFIED.

5. REFINEMENT R3 — read_only AND SUBSCRIPTION-INDEPENDENT OPT-OUT
----------------------------------------------------------------
- Preserved OD-S6-11 A. In read_only:
  - Admins read state and history;
  - grants → ZW001; revocations → ZW001;
  - a DNC change through plus_update_contact → ZW001;
  - grant-holding Dispatchers lose read (ZW002).
- No helper, RPC or exception bypasses read_only. Tested in A9 / A10.
- Operational limitation: while Plus is read_only (expired, cancelled, elapsed trial or period), a customer's request
  to stop contact cannot be recorded in Plus. Nothing is sent in that state, because no Plus sending exists at all.
- MANDATORY NP-P4 PREREQUISITE (recorded in ZD-239, access model §6.5b, design §4.1):
  - Before any Plus outbound communication is enabled, a separately reviewed, subscription-independent opt-out
    mechanism must exist.
  - It must remain usable when Plus is expired, cancelled, read_only or otherwise unable to accept CRM writes.
  - Not built in S6-A; no read_only write exception was created.
