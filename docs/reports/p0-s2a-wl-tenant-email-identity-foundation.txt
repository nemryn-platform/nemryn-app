1. ARCHITECTURE
====================================================================

Locked rule (work item §1): **transactional communications initiated
by an organization are tenant-branded by default.** Nemryn provides
infrastructure — delivery (Resend), authorization, tenancy, auditing.
The organization provides its own visible identity — sender name,
verified sender email, reply-to email, and the organization name used
in content.

Before this phase, the driver-invitation email (the only transactional
email this application sends today, per the P0-S2A phase immediately
prior) used a single GLOBAL `EMAIL_FROM` environment variable,
defaulting to a hardcoded `"Zenward Mobility <no-reply@zenwardmobility.com>"`
string, plus a footer reading "Sent by Zenward Mobility on behalf of
{Organization Name}." Both were correct only by the coincidence that
the one existing tenant happens to be named "Zenward Mobility" — wrong
in principle, and an active liability the moment a second organization
exists (it would impersonate Zenward Mobility's own unverified domain
in every OTHER organization's outbound mail, and its footer would be
factually wrong for any tenant but Zenward Mobility).

This phase replaces both with a genuinely per-tenant model:

  Organization proposes         → upsert_organization_email_sender
  identity (name/email/domain/     (Organization Admin, own org only;
  reply-to)                        ALWAYS lands at verification_status
                                    = 'pending' — no client write can
                                    ever set 'verified')
         ↓
  Human verifies the domain      → the operator adds Resend's DNS
  through Resend (unchanged,       records to their own domain's zone
  manual, per work item §12/§13)   (SPF/DKIM)
         ↓
  Platform certifies it          → set_organization_email_verification_status
                                    (Platform Admin ONLY — has_org_role
                                    plays no part in this function's
                                    authorization at all)
         ↓
  resolveOrganizationEmailIdentity() → the ONE place any email-sending
  code asks "whose identity is       code in this application decides
  this?" — resolved FRESH on           a sender identity. Verified live:
  every send, never cached from        disabling a sender changes the
  invite-creation time                 very next send immediately;
                                        re-verifying restores it
                                        immediately.
         ↓
  Verified → tenant's own name + domain + reply-to used.
  Anything else (pending / disabled / no row at all) → the tenant's
  real NAME is still shown (trustworthy, sourced from `organizations`
  itself), but the technical address is a NEUTRAL, platform-controlled
  fallback — never the tenant's own unverified domain.

`EMAIL_FROM` still exists, but its role is now narrow and documented:
the platform's OWN infra fallback only (§5/§8 below) — never the
source of any tenant's visible identity again.

2. SCHEMA / CONFIG MODEL
====================================================================

New migration:
`supabase/migrations/20260914100000_organization_email_senders.sql`

Table `organization_email_senders` — one row per organization (the
smallest production-suitable model; a future multi-sender-per-org need
is a deliberate, separate extension, not built here):

  id                    uuid, PK
  organization_id       uuid, FK -> organizations, UNIQUE
  sender_name           text, not null
  sender_email          text, not null (its own domain must equal
                          sender_domain — enforced in the RPC, see §3)
  reply_to_email        text, nullable
  sender_domain         text, not null
  verification_status   text, not null, default 'pending'
                          CHECK IN ('pending','verified','disabled')
  created_at, updated_at  timestamptz, trigger-maintained

Required concepts from the work item — all present:
`organization_id`, `sender_name`, `sender_email`, `reply_to_email`,
`sender_domain`, `verification_status` (3-state, as specified),
`created_at`, `updated_at`.

A tenant cannot mark its own domain verified by manipulating a browser
request: `verification_status` has no path to `'verified'` reachable by
an organization's own admin at all — see §4.

3. RLS POLICIES
====================================================================

RLS enabled immediately on table creation (deny-by-default, same
invariant as every other table in this codebase).

  SELECT — `organization_email_senders_select_org_admin`:
    Organization Admin, own org only (`has_org_role`). No other role
    (not even Dispatcher) can read it.

  INSERT / UPDATE / DELETE — **no grant to `authenticated` exists at
  all.** Every mutation goes through one of two SECURITY DEFINER
  functions:

  `upsert_organization_email_sender(p_organization_id, p_sender_name,
  p_sender_email, p_sender_domain, p_reply_to_email)`:
    - Organization Admin only, own org only (`has_org_role`, re-checked
      live).
    - Validates: non-blank fields within length limits; plausible email
      shape for `sender_email`/`reply_to_email`; plausible hostname
      shape for `sender_domain`; **`sender_email`'s own domain must
      equal the claimed `sender_domain`** (a tenant cannot propose
      verification of a domain their own address doesn't belong to).
    - **ALWAYS resets `verification_status` to `'pending'`** on every
      successful call — including a byte-for-byte resubmission of
      already-verified values (tested explicitly — §11 test H). This is
      the actual mechanism that makes "no client write may allow
      `pending -> verified`" true: the function has no branch that can
      ever write `'verified'`.
    - One row per org (`ON CONFLICT (organization_id) DO UPDATE`).
    - Writes an `audit_events` row.

  `set_organization_email_verification_status(p_organization_id,
  p_status)`:
    - **Platform Admin ONLY** (`is_platform_admin()`) — `has_org_role`
      is never consulted. An organization's own admin cannot call this
      successfully for their OWN organization (tested — §11 test D).
    - The sole path to `'verified'` (also usable to set `'disabled'` or
      revert to `'pending'`).
    - Writes an `audit_events` row.

No RLS policy on any EXISTING table was modified. No existing migration
was modified. This phase added one new migration file only.

4. SENDER RESOLUTION
====================================================================

`src/lib/email/resolve-organization-identity.ts` —
`resolveOrganizationEmailIdentity(organizationId)`. Server-only. The
ONE function in the codebase that decides an email's sender identity —
no other application code independently constructs one (work item §5's
own explicit requirement). Currently the only two call sites
(`createDriverInviteAction`/`resendDriverInviteAction`,
`src/app/operations/drivers/actions.ts`) both go through it, fresh, on
every call.

Resolution:

  organizationName = organizations.name   (ALWAYS — trustworthy,
                                            server-resolved, independent
                                            of email-verification state)

  IF a row exists AND verification_status === 'verified':
    senderName   = row.sender_name  (falls back to organizationName if blank)
    senderEmail  = row.sender_email                <- tenant's OWN domain
    replyToEmail = row.reply_to_email
    usingPlatformFallback = false

  ELSE (no row / pending / disabled):
    senderName   = organizationName                <- STILL tenant-branded
    senderEmail  = platform fallback address        <- NEVER the tenant's
                                                        claimed/unverified domain
    replyToEmail = null
    usingPlatformFallback = true

Verified live (§11) for ALL FOUR logical states: `verified`, `pending`
(proposed but not yet certified), `disabled` (certified, then
revoked), and `not_configured` (no row exists at all).

====================================================================
5. FALLBACK BEHAVIOR
====================================================================

`src/lib/email/send.ts`'s `platformFallbackFrom()` — the platform's own
default "From" string. Used (a) by the resolver as the source of the
fallback technical ADDRESS (via `extractEmailAddress`,
`src/lib/email/address-format.ts` — a new, pure, unit-tested helper),
and (b) as `sendEmail()`'s own last-resort default for any future email
type that doesn't yet resolve a per-tenant identity.

**Changed default value:** `"Notifications <notifications@resend.dev>"`
— replacing the OLD default `"Zenward Mobility <no-reply@zenwardmobility.com>"`.
The old default violated work item §8 ("Do not allow fallback logic to
falsely impersonate an unverified tenant") directly: it asserted
Zenward Mobility's own domain in the technical envelope for EVERY
organization the fallback might ever apply to, without that domain
ever having been verified through Resend. The new default is honest
about being platform infrastructure and claims no specific domain.

`EMAIL_FROM` remains configurable to override this default (documented,
in `.env.example` and `docs/deployment/environment-variable-inventory.md`,
as PLATFORM FALLBACK ONLY — never a tenant's identity). It is not the
long-term source of any organization's visible sender identity, and the
fallback path never impersonates an unverified tenant's domain — the
resolver only ever falls back to this platform address, never to a
tenant's own claimed-but-unverified `sender_email`/`sender_domain`.

====================================================================
6. VERIFICATION ENFORCEMENT
====================================================================

Two independent, deliberately redundant layers:

  1. DATABASE — no client-facing function can ever write `'verified'`
     (§3). A tenant can propose forever; only a platform admin's call
     certifies.
  2. APPLICATION — `resolveOrganizationEmailIdentity` reads
     `sender_email`/`sender_domain` ONLY when
     `verification_status === "verified"`. Even a hypothetical future
     bug that let unverified fields be READ would still not make them
     USED — this function is the one gate.

An unverified/disabled/missing sender is NEVER used to send from that
tenant's claimed domain — verified live across all four states (§11).
An explicit delivery/configuration signal (`usingPlatformFallback`,
`verificationStatus`) is always available to the resolver's caller;
nothing is silently pretended.

7. ZENWARD CONFIGURATION PATH
====================================================================

No verified state was fabricated for Zenward Mobility. Its
`organization_email_senders` row does not exist in any real (staging/
production) database — this phase did not create one there, only
proved the mechanism locally. The exact, documented human procedure
(full detail: `docs/product/tenant-email-identity-model.md` §10,
`docs/deployment/driver-invite-email-production-checklist.md` §B):

  1. An Organization Admin for Zenward Mobility calls
     `upsert_organization_email_sender` with sender_name="Zenward
     Mobility", sender_email="notifications@zenwardmobility.com",
     sender_domain="zenwardmobility.com", and an operator-chosen
     reply_to_email. Lands at `pending`.
  2. A human verifies `zenwardmobility.com` as a sending domain in
     Nemryn's own Resend account (DNS records on the sending domain
     only — does not touch `app.zenwardmobility.com`'s own routing/DNS
     or the hosted Supabase project).
  3. A platform admin calls `set_organization_email_verification_status`
     to mark it `verified`.
  4. Usable immediately — no deployment needed; the very next
     invitation email uses it (verified live this phase).

====================================================================
8. REPLY-TO HANDLING
====================================================================

`reply_to_email` is validated server-side (well-formed email shape) at
proposal time inside `upsert_organization_email_sender`. It is passed
through `EmailMessage.replyTo` -> Resend's own `reply_to` API parameter
only when the resolved identity is `verified` and has one configured —
an unverified/fallback identity never sets a reply-to (there is nothing
tenant-specific and trustworthy to put there yet). `sendViaResend`
(`src/lib/email/send.ts`) was extended with one new conditional field
(`reply_to`) — no other behavior in that function changed.
