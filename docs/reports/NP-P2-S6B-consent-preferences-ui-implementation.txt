3. UI (PHASES 1, 2, 6)
----------------------
- Placement: directly after Details and before Open tasks (checked by DOM order). Header actions, details and editing,
  tasks, linked requests, opportunities, timeline and breadcrumbs are unchanged.
- Panel anatomy:
  - Panel surface="raised"; data-testid="contact-consents";
  - SectionHeader "Communication preferences" (h2) with the Phosphor ChatCircleText icon on the accent tone;
  - description: "What this person told your team about being contacted. A recorded consent isn't permission to
    send, and Nemryn sends nothing."
- State: a semantic table (sr-only caption; channel row headers; purpose column headers) with all six cells: Email /
  Text messages (SMS) / Phone calls × Service follow-up / Marketing.
  - Each cell has a StatusBadge with the approved label: Consent recorded, No record, Revoked, Recorded for a previous
    address, Suppressed — do not contact, Contact archived.
  - The meta line shows the method, the capture date and "by <staff>", and "correction" where relevant.
  - Recorded and effective states are both exposed (as data attributes, for tests).
  - "Consent recorded" is evidence wording. No label says allowed / approved / permitted / opted in (unit and E2E
    tests).
- Footnote: "The preferred channel in Details is a convenience for your team. It isn't consent."
- Empty state (no record and DNC off): the V2 EmptyState, "No communication preferences recorded. Nemryn never
  assumes consent…"
- Error state: a critical AttentionState with reload guidance, distinct from the empty state.
- History:
  - a native <details>, collapsed by default, with "History (n)" from total_count;
  - newest first;
  - each entry shows the channel · purpose · Granted / Revoked; the method and capture date; "recorded <time> by
    <staff>"; the evidence note (ZD-242); "Corrects an earlier entry" / "Corrected"; and for do_not_contact rows,
    "Recorded automatically when Do not contact was switched on.";
  - 20 entries per page through the RPC (?consentHistory=N), with Newer / Older links; a page past the end falls back
    to the newest page.
- Never shown: address_digest, idempotency_key, internal function names. E2E A6 scans the full page HTML for the stored
  digest and key.

4. RECORD / REVOKE / CORRECT (PHASES 3, 4, 5)
--------------------------------------------
- One dialog, using the existing Dialog, RadioGroup, Input type=date, Textarea and Checkbox:
  - channel: email is disabled without an email and SMS / calls without a phone, with the reason shown;
  - purpose, with "Separate from follow-up";
  - method: verbal_phone / in_person / written / email_reply only;
  - date: default today, min today − 365 days, max today;
  - note: ≤ 500 characters, with the existing no-medical-details notice;
  - the required self-confirmation checkbox (grants only).
  The commit stays disabled until the entry is valid.
- Idempotency: one key per dialog (consent-<uuid>), so a retry of the same intent reuses it; a replay gives "That
  entry was already recorded."
- Server action recordConsentAction:
  - requirePlusAccess plus the organization binding (the form must be from the session's workspace) plus
    canWriteGrowth;
  - pure validation, mirroring the RPC;
  - the date is converted in the organization timezone (today → NULL = now; a past date → midday local);
  - then plus_record_consent or plus_revoke_consent. "mode" only selects the RPC; the form carries no actor, recorded
    time, order, digest or status;
  - revalidatePath on success;
  - error codes and messages mapped to plain copy, with role=alert for errors and role=status for success.
  - The RPC remains the authority.
- Revocation: header "Record revocation" (any channel / purpose; allowed for archived and DNC contacts) and per-cell
  "Revoke" on granted cells (full accessible name). It is always a new row (E2E A9: the grant row is untouched).
- Correction:
  - "This entry was recorded in error" appears only on the pair's latest entry, never on a do_not_contact system
    entry;
  - it records the opposite state with corrects_consent_id and a REQUIRED note;
  - it is offered only when that opposite write is itself allowed.
  - A stale correction gives a clear ZW003 alert (E2E A13).
  - Older evidence gives the stale_evidence copy (A14).
  - Neither DNC, entitlement nor ordering rules can be bypassed: the same RPCs decide.

9. DIFFERENCES FROM THE APPROVED DESIGN (all within ZD-228 … ZD-242; recorded in design §5.9)
--------------------------------------------------------------------------------------------
- A header "Record revocation" lets staff record an opt-out for any channel / purpose, alongside the per-cell Revoke.
- No stacked phone layout. Operations is tablet / desktop only, by the approved shell notice.
- History pages are server-rendered through ?consentHistory=N (20 per page) rather than "Show more".
- Corrections record the opposite state and are offered only where that write is itself allowed.
- History labels "Granted" / "Revoked". All user-facing wording uses "revocation", never "withdrawal".
