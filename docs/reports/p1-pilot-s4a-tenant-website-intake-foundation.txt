ARCHITECTURE CHOSEN
------------------------
browser (external tenant website)
  -> POST /api/public-intake/website  (Next.js Route Handler, this repo)
  -> schema validation (pure, src/lib/public-intake/website-intake-core.ts)
  -> submit_public_transportation_request  (narrow SECURITY DEFINER RPC)
  -> request_intake_integrations lookup (tenant resolution, internal only)
  -> transportation_requests INSERT (state='pending', source='web')
  -> existing Request Hub review lifecycle, completely unmodified from
     this point forward

WHY this shape, not a raw PostgREST/supabase-js call from the tenant
website directly to the RPC:
  1. A tenant website team should not need to know Nemryn's Supabase
     project URL/anon key or embed the supabase-js SDK just to submit a
     form — a plain JSON POST to one Nemryn-owned URL is a smaller, more
     stable integration surface for a third party to maintain.
  2. This route is the one place every possible failure (malformed JSON,
     oversized payload, an unexpected field, a rejected RPC call) is
     guaranteed to collapse into the SAME generic response — materially
     harder to guarantee if a raw PostgREST error could ever reach the
     browser directly (PostgREST's own error JSON shape differs from
     this app's own safe-error conventions and was never designed to be
     shown to an unauthenticated third party).
  3. This is the natural, and only, place to add the real anti-abuse
     control S4B requires, without ever touching the database layer
     again (see ANTI-ABUSE STATUS below).

WHY a SECURITY DEFINER RPC, not a raw INSERT (even from trusted server
code): identical reasoning to every other mutation in this schema
(`log_transportation_request`, `create_trip`, etc.) — one authoritative,
testable business boundary, reusable by any future trusted client
(there will eventually be more than one integration type), rather than
re-implementing field validation/tenant-resolution/idempotency
identically in every caller. The RPC is also independently callable via
PostgREST directly (it is granted to `anon`) — the Route Handler is a
convenience and a second validation layer, never the sole security
boundary. The RPC's own validation is authoritative in every case; the
Route Handler's pure-core validation exists only to fail fast and
produce a friendlier error before ever reaching the database.

TENANT-RESOLUTION MODEL
----------------------------
No `organization_id` parameter exists anywhere in
`submit_public_transportation_request`'s signature — structurally, not
merely by convention. The organization is resolved ENTIRELY from
`p_integration_external_id`, an opaque string looked up in the new
`request_intake_integrations` table (globally unique `external_id`
column — deliberately NOT scoped per-organization, since the whole point
is the caller presents only this one value with no other context). This
mirrors `redeem_driver_invite`'s own established precedent exactly (that
function also takes no `organization_id` parameter, resolving it entirely
from the invite row it's given).

`external_id` is treated as PUBLIC, not a secret (this is explicit in
both the table's own column comment and the phase brief) — it selects a
tenant, it does not authenticate a caller. Security does not depend on
it being hard to guess or undiscoverable. What actually protects tenant
isolation:
  - The composite foreign key `transportation_requests
    (intake_integration_id, organization_id) references
    request_intake_integrations (id, organization_id)` — the database
    itself physically rejects any row whose `intake_integration_id`
    names an integration belonging to a DIFFERENT organization than the
    row's own `organization_id`. This is not merely defense-in-depth
    against a bug in the RPC's own logic; it is a second, independent,
    structural guarantee that holds even if that logic were ever wrong.
  - `request_intake_integrations` itself has zero grants to any role
    (`anon`/`authenticated`) and RLS enabled with zero policies — the
    ONLY code path that ever reads it is the SECURITY DEFINER function
    itself (which runs as the function owner, `postgres`, and therefore
    bypasses RLS the same way every other SECURITY DEFINER function in
    this schema already does for its own tables).
  - A disabled integration and a nonexistent `external_id` raise the
    IDENTICAL error (`invalid_input`, ZW006) — no existence oracle,
    mirroring `has_org_role`'s own "not_found is not_found regardless of
    why" contract carried to this new boundary.

IDEMPOTENCY MODEL
----------------------
A client-supplied `idempotencyKey` (required, ≤200 chars) is paired with
the resolved `intake_integration_id` under a PARTIAL unique index:

  create unique index transportation_requests_intake_idempotency_idx
    on transportation_requests (intake_integration_id, external_submission_ref)
    where intake_integration_id is not null and external_submission_ref is not null;

The RPC's own INSERT targets this index with `ON CONFLICT (...) WHERE
... DO NOTHING`, then re-selects the (possibly already-committed) row
when its own INSERT did not win. This is safe under GENUINE concurrent
submission purely from Postgres's own unique-index insertion arbitration
— no advisory lock, no `SELECT ... FOR UPDATE` is used or needed, because
there is no pre-existing row to lock (the row does not exist until
exactly one of the racing INSERTs creates it). Proven with a real
two-OS-process test, not a sequential simulation — see CONCURRENCY
RESULTS below. Staff-entered Requests are completely unaffected: both
columns are NULL for every one of them, and the partial index's own WHERE
clause means NULL,NULL never participates in the uniqueness constraint at
all.

ORIGIN/DOMAIN MODEL
------------------------
`request_intake_integrations.allowed_origins` (nullable `text[]`) is an
OPTIONAL, per-integration allow-list. When configured non-empty, the RPC
rejects a submission whose `p_origin` (the Route Handler's own read of
the request's `Origin` header) is not a member of that array — same
generic `invalid_input` response as every other rejection. When NOT
configured, no Origin restriction applies at all for that integration.
This is explicitly documented, in the migration's own column comment and
the RPC's own function comment, as a SECONDARY, non-authoritative signal:
a non-browser caller (curl, a server-to-server script) can set an
arbitrary Origin header, so this control has zero value against that
attacker class — it is real protection only against a genuine BROWSER
making a same-origin-policy-respecting cross-site request the operator
did not intend, which is the one scenario where a browser cannot lie
about its own Origin. Tenant isolation itself never depends on this
control in any way — verified live (BONUS-B1/B2 in the SQL test file).

ANTI-ABUSE STATUS
----------------------
No production-capable rate limiting or bot-protection mechanism exists
anywhere in this repository today (confirmed by inspection before
writing any code — no such infrastructure, no relevant dependency, no
existing pattern to reuse). Per the phase's own explicit instruction,
this phase does NOT install a new third-party paid service and does NOT
fabricate an in-memory rate limiter (which would provide zero real
protection under a serverless deployment, where each invocation may get
its own process). The Route Handler's own comment (`src/app/api/
public-intake/website/route.ts`) is the architectural hook S4B needs: a
real rate limiter, keyed by `integrationExternalId` and/or client IP
against a durable shared store, would be one additional check inserted
at a clearly marked point, returning the identical generic rejection on
a throttled request. THIS IS THE PRIMARY REASON S4B, not S4A, is where
any real integration may be activated — see OPEN ISSUES.

PUBLIC INTAKE CONTRACT
---------------------------
`POST /api/public-intake/website`, `Content-Type: application/json`,
body (all fields required unless marked optional):
```
{
  "integrationExternalId": string (<=200 chars),
  "idempotencyKey": string (<=200 chars),
  "requesterName": string (<=200 chars),
  "requesterRelationship": "self" | "family" | "caregiver" | "facility_coordinator" | "other",
  "requesterPhone": string (<=50 chars),
  "pickupDescription": string (<=2000 chars),
  "destinationDescription": string (<=2000 chars),
  "returnTripNeeded": "yes" | "no" | "not_sure",
  "requesterEmail": string | null (optional, <=320 chars),
  "preferredDate": "YYYY-MM-DD" | null (optional),
  "preferredTime": "HH:MM" | "HH:MM:SS" | null (optional),
  "assistanceNotes": string | null (optional, <=4000 chars),
  "additionalNotes": string | null (optional, <=4000 chars)
}
```
No `organizationId`, `passengerId`, `source`, or `state` field is ever
accepted — an unexpected top-level key of ANY kind causes the whole
payload to be rejected (never silently ignored). Response shapes:
  Success: `200 { "ok": true }`
  Rejection (any cause): `400 { "ok": false, "error": "invalid_request",
  "message": "We couldn't process this request. Please check the
  information provided and try again." }`
Every distinct internal cause — malformed JSON, oversized body, an
unexpected field, a missing/invalid field, a disabled/nonexistent
integration, an Origin mismatch, an RPC-level validation failure —
collapses to the SAME response. No raw SQL/Postgres/PostgREST/ZW code,
table/column/policy name, or internal UUID is ever returned.

OPEN ISSUES
--------------
1. Anti-abuse infrastructure does not exist yet (see ANTI-ABUSE STATUS
   above) — this is the PRIMARY blocker for any real production
   activation. S4B must not activate a real tenant integration until a
   genuine, durable rate-limiting mechanism is in place at the Route
   Handler's own marked insertion point.
2. `request_intake_integrations` has no operator-facing management UI or
   RLS read policy in this phase (deliberately, per the phase's own
   "do not build a general integrations platform" instruction) — every
   integration row in this phase was created directly via `psql` as
   postgres, exactly like every SQL test's own fixture setup. S4B (or a
   later phase) will need SOME provisioning path — even a manually-run
   migration/seed per pilot tenant would satisfy the "disabled by
   default, deliberately activated" contract without building a full UI.
3. The Route Handler's CORS policy is currently permissive
   (`Access-Control-Allow-Origin: *`) — correct and intentional given
   this endpoint sets/reads no cookies and grants no session (see PUBLIC
   INTAKE CONTRACT's own reasoning), but worth re-confirming during S4B
   once a real tenant website's actual calling pattern is known, in case
   that tenant's own security review prefers a narrower CORS policy for
   their own reasons (not a Nemryn-side requirement).
4. No structured/durable audit logging exists for public-intake
   successes specifically (only a safe, fixed-message `console.error` on
   REJECTION, matching this codebase's own established logging
   convention exactly — see `website-intake.ts`'s own comment). A
   successful submission is fully traceable via the real
   `request_events` row it creates (event_type='request_logged',
   metadata contains only the safe `intake_integration_id`, never any
   payload content) — this was judged sufficient observability for S4A;
   revisit if S4B's own real-traffic volume needs dashboarding.

ROLLBACK CONSIDERATIONS
----------------------------
Nothing in this phase is committed, so there is nothing to roll back at
the git level. If this work were later committed and needed reverting:
the migration is a clean, independent set of additive DDL statements
(new table, two new nullable columns, one new composite type, one new
function) with no destructive statement and no risk to any pre-existing
row — reversing it is a straightforward companion migration (drop the
function, drop the two columns + their index/FK, drop the type, drop the
table), in that dependency order. The application-side changes (the new
Route Handler, the two new `src/lib/public-intake/` files, the small
`RequestDetailsPanel`/`request-detail.ts` additions) are equally
independent and revertible with no cross-feature entanglement — Request
Hub's own existing behavior for every staff-entered Request is provably
unaffected either way (SQL TEST 16, E2E scenario A).
