2. ORIGINAL DEAD-END
-------------------------
Read `docs/reports/p1-e1-s2e-request-detail-readiness-passenger-linked-
trips.txt` in full before starting. S2E correctly derived readiness
from the linked Passenger's REAL status (never merely
`passenger_id !== null`), but its own §19 explicitly gated the Search/
Add UI on `passenger === null` — meaning a pending Request whose
linked Passenger had since gone inactive showed "Passenger needed"
with genuinely no path to resolve it: the Passenger card rendered
read-only, and the search/add mechanism never appeared because a
Passenger WAS technically linked. A real, reachable operational dead
end, not a hypothetical one — closing it is this phase's entire scope.


3. AUTHORITATIVE RPC BEHAVIOR
-----------------------------------
Re-read `link_request_passenger` directly from
`supabase/migrations/20260916100000_request_mutation_foundation.sql`
(lines 327-402) before writing any UI code — not re-derived from the
S2B/S2E reports' prose alone. Confirmed directly:
  - Request must be `pending` (line 369-371: any other state raises
    ZW004 `illegal_transition`).
  - Target Passenger must be `status = 'active'` AND
    `organization_id = p_organization_id` (line 376-381, ZW006
    otherwise — no existence oracle: nonexistent, foreign-org, and
    inactive are all the identical error).
  - Linking a DIFFERENT Passenger while pending IS permitted — the
    function's only "already linked" check (line 383) is an idempotent
    no-op comparison against the SAME `passenger_id` being re-supplied;
    there is no `v_request.passenger_id is null` guard anywhere before
    the `update` on line 391. A request already linked to an inactive
    Passenger can be relinked to a different, active one with no RPC
    change required — confirmed directly in source, exactly as this
    phase's own CONTEXT section stated.
  - `accepted`/`declined`/`cancelled` remain rejected (ZW004), same
    mechanism as the pending check above.
No RPC change was made or needed.


4. FINAL PRODUCT RULE
--------------------------
LOCKED, implemented exactly as specified: general Passenger
reassignment was NOT introduced. A linked ACTIVE Passenger on a
pending Request still renders with zero replacement control (§8/§10
below) — the first-release product still does not support casual
reassignment. Replacement is exposed in EXACTLY one condition:
`state === "pending" && passenger !== null && passenger.status !==

readiness condition, not ordinary record editing — the recovery UI is

unlinked flow does not require, specifically because there is an
existing relationship being replaced.

8. EXPLICIT CONFIRMATION BEHAVIOR
----------------------------------------
Two layers of deliberate friction, both required and both
implemented:
  1. The recovery search/add UI itself is NOT shown by default — it
     stays behind a "Select active Passenger" button the operator must
     click first (`recoveryFlowOpen`, initially `false`). The ordinary
     unlinked flow has no equivalent gate, since there is nothing to
     replace there. This is the phase's own core distinction (§6): "there
     is already an existing relationship being replaced."
  2. Once opened, the SAME select-then-confirm mechanism S2E already
     built applies unchanged: selecting a search candidate sets local
     state only (never mutates), a preview card appears showing the
     NOT-YET-linked candidate, and only an explicit "Link Passenger"
     button click submits the real `linkPassengerAction`. Live-verified
     directly: after selecting "Beatrix Sundberg," the page still showed
     "Cornelius Blackwood" (the original inactive Passenger) as the
     CURRENTLY linked one — proving selection alone never mutates,
     exactly as required.

10. ACTIVE PASSENGER PROTECTION
------------------------------------
`isInactiveLinkedPending` is `false` whenever `passenger.status ===
"active"`, so NEITHER the recovery notice NOR any search/add UI
renders for a normally-linked active Passenger — this distinction is
explicit in code (two separate, independently-named boolean
conditions, not a single collapsed flag), matching §8's own explicit
"this distinction must be explicit in code" instruction. Live-verified:
a pending Request linked to an active Passenger shows the read-only
card and Ready readiness ONLY — no button, no notice, no search UI of
any kind.


11. NON-PENDING PROTECTION
-------------------------------
`isInactiveLinkedPending` also requires `state === "pending"`, so
accepted/declined/cancelled Requests never show the recovery notice or
any link control, regardless of the linked Passenger's status — the
RPC's own ZW004 rejection remains the authoritative backstop, but the
UI never even offers the attempt. Live-verified against three
purpose-built fixtures (accepted+inactive, declined+inactive,
cancelled+inactive, each with a genuinely linked-but-inactive
Passenger) — in all three cases the Passenger card correctly still
shows the inactive linkage (historical/current, never hidden) with
zero recovery affordance.
