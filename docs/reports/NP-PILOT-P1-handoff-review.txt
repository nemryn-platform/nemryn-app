1. EXISTING WORKFLOW (audit)
======================================================================================================================
Conversion (Growth → Core)
  - Opportunity page "Create transportation request" (BookingRequestDialog, mode convert) → convertOpportunityAction →
    plus_convert_opportunity_to_request: requires Plus write AND the Core request role; calls Core's own
    log_transportation_request as the staff member with requester name / phone / email from the ACTIVE contact, source
    mapped from the opportunity, the opportunity's service type, and passenger = NULL. Writes a converted_from_opportunity
    attribution, marks the opportunity converted, audits. Idempotent per key. Rebooking from a contact page is the same
    via plus_create_rebooking_request.
  - The request is PENDING; Core owns accept / decline, passenger, trip creation, dispatch.
Passenger step (Core request page)
  - "Passenger needed" readiness; RequestPassengerPanel searches active passengers, links via link_request_passenger
    (Organization Admin / Dispatcher, same organization, ACTIVE passenger, pending / accepted request without trips;
    same passenger again = no-op), or "Add New Passenger" prefilled ONLY from the request's requested_passenger_name
    snapshot (a deliberate rule: the requester may not be the rider).
Data Growth already holds
  - Contact: name, phone, email, kind (individual / family_caregiver / facility_staff / referral / other), DNC.
  - Inquiry (if the opportunity came from the website form): requester relationship (self / family / caregiver /
    facility staff / other), timeframe, free-text question — NO pickup / destination / rider name.
  - Opportunity: title, service type, inquiry type, source.
  - Quote: service type, round trip, distance, prices — NO addresses or dates.
  - Earlier requests of the contact (attributions) and the passengers linked to them.
Friction found
  F1 The conversion form starts blank: "Who is requesting" defaults to Self and "Return trip" to No even when the inquiry
     said "family member" and the accepted quote was priced as a round trip — staff re-enter what Growth knows.
  F2 Every converted / rebooked request arrives as "Passenger needed": no passenger can be chosen at conversion, and the
     Add New Passenger prefill is empty for converted requests (no requested_passenger_name snapshot is written).
  F3 Repeat customers: staff must search for the same rider again on every rebooking.
  F4 The form does not say that pickup / destination are not stored in Growth.
  Already working (kept): Core approval / scheduling / dispatch; the request page shows its Growth link
  (RequestGrowthPanel); trips carry request_id; Billing's quote import follows request → opportunity → quote.

2. CHANGES MADE (existing schema and APIs only)
======================================================================================================================
1. Suggested, editable prefill in the conversion / rebooking form (handoff-core.ts handoffPrefill):
   - Who is requesting: from the website inquiry's own answer, else only an unambiguous contact kind
     (family / caregiver → Family member, facility staff → Facility coordinator); "individual" suggests nothing.
   - Return trip: "Yes" only when the newest ACCEPTED (else newest live SENT) quote was priced as a round trip.
   - Each suggestion is shown with its source ("Suggested — … Check before continuing"). Nothing else is prefilled;
     pickup and destination are marked "Not stored in Growth — enter …" (F4). No address, date, time or assistance need
     is ever invented.
2. Optional "Who will ride?" choice (F2, F3):
   - Lists the organization's ACTIVE passengers (same query Core forms use, under RLS); hints ranked first: rode before
     for this contact (passengers on the contact's earlier requests), same phone (10+ digits), same name. Hints only —
     NOTHING is pre-selected; default "Decide on the request page" keeps today's flow.
   - Choosing a passenger requires an explicit "I've checked that <name> is the person who will ride" confirmation
     (Review stays disabled until then); the review shows "<name> (will be linked)".
   - After the request is created, the server action links the chosen passenger through Core's own
     link_request_passenger (the database enforces role, organization, active status, request state). Linked only for
     a NEWLY created request — a replayed submit never changes an existing request's passenger. If the link is refused
     (inactive, another organization, race), the request is still created exactly as today ("Passenger needed") with a
     plain note; no error codes or names leak.
   - New passengers are still created on the request page (Core ownership unchanged).
3. Unchanged by design: no auto-approval or scheduling, no passenger creation from Growth, consent / DNC reminders
   intact, quote reference and opportunity → request attribution untouched, Trip Detail → Billing → quote import path
   untouched (verified end to end).
