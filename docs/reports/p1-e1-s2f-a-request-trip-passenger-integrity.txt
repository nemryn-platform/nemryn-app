2. SUSPECTED GAP
---------------------
Read all four required prior reports in full (S2A, S2B, S2E, S2E-R1)
before starting. S2E/S2E-R1 established that a pending Request is
ready for conversion only with a linked ACTIVE Passenger, resolved
explicitly via `link_request_passenger` — never inferred or auto-
matched. The suspected gap: `create_trip` (which predates Request Hub
entirely — P1-E3-S0A) was never updated to cross-check its own
`p_passenger_id` parameter against the Request it's converting, so
nothing in the database actually enforced that a Trip created "from" a
Request carries the SAME Passenger the Request itself resolved to.


3. DEFINITIVE SOURCE FINDING
---------------------------------
Read `create_trip` directly from
`supabase/migrations/20260831120000_controlled_trip_creation.sql`
(lines 138-151, the entire `if p_request_id is not null then ... end
if;` block) — confirmed no later migration replaces or modifies it
before this phase (`grep -rl "create or replace function public.

The ONLY checks performed against the locked Request row are:

inferred: YES, an authenticated organization_admin/dispatcher could
call `create_trip(p_passenger_id => Passenger B, p_request_id =>
<Request linked to Passenger A>)` (both same-org/active) and succeed.
YES, a Request with `passenger_id IS NULL` could be converted directly
by supplying any valid active Passenger.

15. ATOMICITY
------------------
Proven directly within TEST C and TEST G's own before/after counts:
`trips`, `trip_events` (matched via `metadata->>'request_id'`), and
`audit_events` (matched via `after_data->>'request_id'`) row counts
for the specific Request under test are IDENTICAL before and after a
rejected mismatched-Passenger call — a passenger mismatch produces
literally zero side effects, not a partial write later rolled back.
This follows directly from the guard clause's position: `raise
exception` executes BEFORE the `insert into trips` statement is ever
reached in the function body, and Postgres's own function-level
transaction semantics (unchanged, not modified by this migration) roll
back anything already attempted within the same statement on any
exception. No existing atomicity test needed to be extended —
`create_trip_atomicity_tests.sql` (re-run clean, §18) already proves
the function's overall single-transaction guarantee at a mechanism
level (a forced trigger failure leaves no partial Trip/event rows);
this phase's own TEST C/G prove the SAME guarantee specifically for
the new rejection path, using the more direct method of simply
counting rows around a real (not forced) rejection.


16. CONCURRENCY
--------------------
The Request row lock (`for update`) already fully covers this new
check — no new race is introduced and no new concurrency test was
needed, documented here rather than assumed:
`v_request.passenger_id` is read from the SAME row locked
`for update` in the SAME statement immediately above the new guard —
not a separate query, not client-supplied data, not re-read later.
Postgres's row-level locking guarantees whichever transaction (this
`create_trip` call, or a concurrent `link_request_passenger` call on
the identical Request) acquires the lock first fully commits or rolls
back before the other's lock acquisition can proceed; the second
transaction then evaluates its own check against the NOW-current
committed row, never a stale value. This is the exact same guarantee
`request_lifecycle_concurrency_test.sh` already proves for the
pre-existing state check immediately above the new guard clause — re-
run this phase (§20) and still PASS, with Session B's rejection now
literally executing one function (line-shifted only by this phase's
own added comments) after the check that guarantee was originally
written to prove. No new concurrency script was added.
