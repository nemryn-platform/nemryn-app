5. SERVICETYPE VALIDATION
=============================================================================
Closed allow-list, matching Zenward-Web's own `SERVICE_TYPES`
(`src/lib/request-intake/service-types.ts` in that repository) value-for-
value: `medical_appointment`, `dialysis`, `rehabilitation`,
`hospital_discharge`, `recurring_care`, `senior_medical`,
`wheelchair_transportation`, `other`. Enforced at three independent
layers: (1) `website-intake-core.ts`'s pure pre-check (fast client-facing
rejection); (2) the RPC's own inline `not in (...)` check (authoritative —
identical pattern to `p_return_trip_needed`'s own existing check); (3) a
table-level CHECK constraint on `transportation_requests.service_type`
(defense in depth, matching this schema's own established double/triple-
validation convention). FINAL RULE: optional at every layer — absent means
NULL, never coerced to `'other'` or any default; an unrecognized value is
rejected outright, never silently dropped or coerced. Zenward-Web's own
form will always send a valid value in practice, but the column and every
validation layer treat it as genuinely optional for forward compatibility
with a hypothetical future non-Zenward integration.

6. RECURRINGSCHEDULE VALIDATION
=============================================================================
Wire shape (JSON, matches the phase brief's own spec and Zenward-Web's own
`RecurringSchedule` type field-for-field):
```
{
  "daysOfWeek": ["monday" | "tuesday" | ... | "sunday", ...],
  "startDate": "YYYY-MM-DD",
  "endDate": "YYYY-MM-DD",            // optional
  "appointmentTime": "HH:MM",         // optional
  "returnTripExpected": true | false  // optional
}
```
Validation (enforced identically at the pure-core pre-check AND the RPC,
the same two-layer discipline as every other field):
  - must be a plain object; an array, primitive, or an object containing
    any key outside the five known ones is rejected outright;
  - `daysOfWeek`: 1-7 distinct values from the allow-listed weekday-name
    set — a duplicate, an unrecognized string, an empty array, or a
    wrong-typed element is rejected;
  - `startDate`: required; must be a REAL calendar date (`isRealIsoDate` /
    the pure-core equivalent — rejects e.g. `2026-02-30`, `2026-13-01`, not
    merely shape-matched);
  - `endDate`: optional; when present, must also be a real calendar date
    and `>= startDate` (equal is accepted, before is rejected);
  - `appointmentTime`: optional; strict 24-hour `HH:MM` (hour 00-23,
    minute 00-59 — `25:00`/`12:60` rejected, unlike the existing lenient
    `preferredTime` field's own shape-only regex, which this new field
    deliberately does NOT reuse);
  - `returnTripExpected`: optional; a strict boolean only — `"true"`, `1`,
    or any other truthy/falsy non-boolean value is rejected, never
    coerced.
`daysOfWeek` and `startDate` are atomic — the table itself enforces "both
present or both absent" via `transportation_requests_recurring_schedule_
atomic_check`, so `startDate` without `daysOfWeek` (or vice versa) cannot
exist as a stored row even if some future code path tried to construct one
directly. This describes what the requester WANTS ONLY. No Trip, no
`recurring_arrangements` row, no series of any kind is ever created by
this endpoint — an operator who wants to honor the request creates an
actual recurring arrangement separately, through the existing Recurring
Care workflow, exactly as before this phase.

7. PERSISTENCE DESIGN
=============================================================================
Structured, typed columns — NOT a JSONB blob. This follows two direct,
explicit precedents already established in this schema: (1)
`20260831100100_mutation_result_types.sql`'s own comment states a
composite/typed return shape is chosen "instead of an ad hoc jsonb blob";
(2) `recurring_arrangements.days_of_week smallint[]` (ISO weekday numbers,
1=Monday..7=Sunday, backed by `_is_canonical_days_of_week()`) is the
existing, "locked" convention for exactly this kind of weekday-set data.
New columns on `transportation_requests`:
  `service_type text` — nullable, CHECK-constrained to the closed
    allow-list (mirrors `source`'s own CHECK-constrained-enum pattern,
    20260916100000).
  `recurring_days_of_week smallint[]` — nullable, CHECK-constrained via
    the REUSED `public._is_canonical_days_of_week()` function (unchanged,
    not duplicated) — the exact same canonical-format rule
    `recurring_arrangements` already enforces.
  `recurring_start_date date`, `recurring_end_date date`,
    `recurring_appointment_time time`, `recurring_return_trip_expected
    boolean` — all nullable.
Wire-to-storage conversion (day NAMES -> canonical ISO weekday NUMBERS)
happens entirely inside the RPC (the sole authority), never in
application TypeScript — `website-intake.ts` passes the day-name
`text[]` straight through unchanged; the RPC converts and validates.
`additionalNotes`/`assistanceNotes` are completely unaffected — neither
`serviceType` nor `recurringSchedule` is ever folded into them (proven by
SQL TEST R2-1, §12).

16. EXACT FINAL FLAT JSON CONTRACT — WHAT ZENWARD-WEB MUST SEND
=============================================================================
`POST https://app.nemryn.com/api/public-intake/website`,
`Content-Type: application/json`:
```json
{
  "integrationExternalId": "string, <=200 chars, required",
  "idempotencyKey": "string, <=200 chars, required — a fresh UUID per NEW logical submission, reused unchanged on a genuine retry",
  "requesterName": "string, <=200 chars, required",
  "requesterRelationship": "self | family | caregiver | facility_coordinator | other, required",
  "requesterPhone": "string, <=50 chars, required",
  "pickupDescription": "string, <=2000 chars, required",
  "destinationDescription": "string, <=2000 chars, required",
  "returnTripNeeded": "yes | no | not_sure, required",
  "requesterEmail": "string, <=320 chars — optional, omit or null if blank",
  "preferredDate": "YYYY-MM-DD — optional, omit or null if blank",
  "preferredTime": "HH:MM or HH:MM:SS — optional, omit or null if blank",
  "assistanceNotes": "string, <=4000 chars — optional, omit or null if blank",
  "additionalNotes": "string, <=4000 chars — optional, omit or null if blank",
  "serviceType": "medical_appointment | dialysis | rehabilitation | hospital_discharge | recurring_care | senior_medical | wheelchair_transportation | other — optional, omit or null if not selected",
  "recurringSchedule": {
    "daysOfWeek": ["monday", "...", "sunday"],
    "startDate": "YYYY-MM-DD",
    "endDate": "YYYY-MM-DD",
    "appointmentTime": "HH:MM",
    "returnTripExpected": true
  },
  "passengerName": "string, <=200 chars — optional, omit or null if blank"
}
```
`recurringSchedule` itself is entirely optional — omit or send `null` for
a one-time request. When present, only `daysOfWeek` and `startDate` are
required inside it; `endDate`/`appointmentTime`/`returnTripExpected` may
each be omitted independently. **SUPERSEDED (see the §3 correction
