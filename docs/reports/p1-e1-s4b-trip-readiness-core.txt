------------------------------------------------------------------------
FINAL STATE VOCABULARY
------------------------------------------------------------------------
Exactly three values, as locked by the phase (no implementation
evidence emerged to justify a fourth):

  READY — `state === 'scheduled'` and no supported reason applies.
  NEEDS_PREPARATION — `state === 'scheduled'` and one or more reasons
    apply.
  NOT_APPLICABLE — `state !== 'scheduled'` (every in-progress and every
    terminal state) — reasons always empty.

No score, no percentage, no AI classification anywhere in the module.

------------------------------------------------------------------------
FINAL REASON VOCABULARY
------------------------------------------------------------------------
  NO_SCHEDULE — `scheduledPickupAt === null`.
  NEEDS_DRIVER — `!hasActiveAssignment`.
  NEEDS_VEHICLE — `hasActiveAssignment && assignedVehicleId === null`
    (never fires merely because there is no assignment at all — that is
    exclusively NEEDS_DRIVER's own condition; verified mutually
    exclusive by a dedicated unit test).
  DRIVER_INACTIVE — `hasActiveAssignment && driverStatus === 'inactive'`.
  VEHICLE_INACTIVE — `hasActiveAssignment && assignedVehicleId !== null
    && vehicleStatus === 'inactive'`.
  PASSENGER_INACTIVE — `passengerStatus === 'inactive'` (independent of
    assignment state).
  OPEN_EXCEPTION — `openExceptionCount > 0` — identical meaning to Trip
    Assurance's own check, never a second definition.

Every reason a Trip qualifies for is returned simultaneously — the
evaluator never stops after the first match (verified directly by the
multi-reason unit tests and the live "H" fixture, which returns all 4
of its applicable reasons at once).

------------------------------------------------------------------------
REASON ORDERING
------------------------------------------------------------------------
Fixed array `REASON_ORDER = [NO_SCHEDULE, NEEDS_DRIVER, NEEDS_VEHICLE,
DRIVER_INACTIVE, VEHICLE_INACTIVE, PASSENGER_INACTIVE, OPEN_EXCEPTION]`
— a presentation-friendly "preparation checklist" order (schedule it,
assign a Driver, assign a Vehicle, confirm the assigned Driver is still
valid, confirm the assigned Vehicle is still valid, confirm the
Passenger is still valid, resolve any flagged issue). This is
DELIBERATELY NOT the same kind of thing as Trip Assurance's own
priority order — Assurance's order picks which ONE result wins;
Readiness's order only fixes the DISPLAY sequence of however many
reasons are simultaneously true. Verified stable regardless of the
order facts are supplied in (dedicated unit test).

ASSURANCE SHARED-FACT STRATEGY
------------------------------------------------------------------------
`trip-assurance.ts` was read in full again this phase and is completely
UNCHANGED — confirmed via `git diff --stat src/lib/operations/trip-
assurance.ts` returning empty both before and after this phase's work.
It was not renamed, not refactored, not duplicated.

Trip Readiness does NOT call `evaluateTripAssurance` and does NOT
import from `trip-assurance.ts` at all. This was a deliberate decision,
directly following S4B's own correction #2: Assurance intentionally
COLLAPSES multiple facts into one highest-priority result; Readiness
must PRESERVE every applicable reason. Reusing Assurance's own single
collapsed output would silently discard every reason but one — exactly
the mistake the phase's own corrections warned against. Instead, the
two modules share MEANING, not code: "active assignment exists" and
"open exception count" are computed from the identical underlying
source shape in both places (`trip_assignments` row with `ended_at IS
NULL`; a real open `trip_exceptions` row) — the data-access wrapper
(`trip-readiness.ts`) derives these facts using the exact same
`ended_at IS NULL` filter and the exact same `status='open'` filter
Assurance's own callers (`todays-operations.ts`, `dispatch-board.ts`)
already use, never a second, independently-drifting interpretation of
either concept.

No refactor of `trip-assurance.ts` or its callers was performed or
proposed — regression risk to the already-shipped, already-live
Assurance feature is exactly zero from this phase's own changes.

DATA-ACCESS DESIGN
------------------------------------------------------------------------
`src/lib/operations/trip-readiness.ts` — `getTripReadiness(tripId,
organizationId)`:

  1. One query: `trips` filtered by `id` + `organization_id` (explicit,
     never left to RLS alone), embedding `passengers(status)` and
     `trip_assignments(id, ended_at, vehicle_id, drivers(status),
     vehicles(status))` — the exact same composite-FK-hint convention
     `trip-detail.ts`/`dispatch-board.ts` already use
     (`trips_passenger_id_organization_id_fkey`,
     `trip_assignments_trip_id_organization_id_fkey`,
     `trip_assignments_driver_id_organization_id_fkey`,
     `trip_assignments_vehicle_id_organization_id_fkey` — all 4
     confirmed to exist as real constraint names via
     `pg_constraint` before use, not assumed).
  2. One small head-only count query against `trip_exceptions`,
     mirroring `operations-brief.ts`'s own `getRequestSummary` pattern.
  3. The pure `deriveTripReadiness` call.

Two round trips total, both scoped to exactly one Trip id — no N+1. A
malformed/nonexistent/foreign-org `tripId` resolves to `null` (no
existence oracle), matching `trip-detail.ts`'s own established
convention exactly. `createServerSupabaseClient` (normal RLS) is used
throughout; the service role is never referenced anywhere in this
module. `organizationId` is a plain parameter the caller must already
have resolved via `requireOperationsAccess` — never trusted from the
browser.

A small-set (multiple Trips at once) variant was deliberately NOT built
in this phase, per S4B's own explicit boundary ("S4C owns tomorrow
querying/aggregation") — noted as straightforward future work in OPEN
ISSUES below, not built ahead of schedule.

limitation, not solved here — matching S4B's own explicit instruction
not to attempt a fix in this phase. If a future "Unscheduled work"
surface is ever wanted, that is new, separate product work, not implied
by anything built in this phase.
