===========================================================================
QUERY ARCHITECTURE
===========================================================================
A SEPARATE query path from `getProofOfServiceReview` (S1D), deliberately
lighter (§8): no Passenger display name, no Driver/Vehicle name/label
embeds — the summary only ever needs counts, never presentation labels.
  1. Trip candidates: `id, completed_at, pickup_description,
     destination_description, passengers(id)` only — chunked (see SCALE
     below), each chunk requesting `{ count: "exact" }` so the TRUE
     window total is known from PostgREST itself.
  2. Completion assignments: `trip_id, vehicle_id` only, filtered to
     `end_reason = 'trip_completed'` — the same S1C-established
     authority, never "active assignment."
  3. Required lifecycle events: `trip_id, event_type, occurred_at`,
     pre-filtered to the 6 `REQUIRED_LIFECYCLE_EVENT_TYPES`.
  4. Open exceptions: `trip_id` only, `status = 'open'`.
Composed via the SAME pure functions S1B/S1C already established
(`evaluateLifecycleEventChain`, `classifyCompletionAssignmentCardinality`,
`deriveTripProofOfService`) — no second Proof-of-Service evaluator exists
anywhere in this codebase (§7, confirmed by direct source inspection: the
whole-window path imports these exact same functions from
trip-proof-of-service-core.ts/trip-proof-of-service-evidence.ts, never
reimplementing any of their logic).

===========================================================================
SCALE / CHUNKING
===========================================================================
`supabase/config.toml` confirms this project's configured `max_rows =
1000` — PostgREST silently caps ANY query's returned rows at this value
regardless of what `.range()` requests, so an unbounded single
`.select()` was never assumed safe (§9's own explicit warning heeded).
  - Trip candidates are fetched in pages of `WHOLE_WINDOW_TRIP_PAGE_SIZE
    = 1000` (matching the server's own configured cap exactly), looping
    via `.range()` until a page returns fewer rows than requested.
  - The first page's own `{ count: "exact" }` result is checked against
    `WHOLE_WINDOW_SAFETY_CAP = 5000` (a deliberately generous ceiling —
    docs/product/product-definition.md's own small/mid NEMT operator
    framing puts any real organization nowhere near this volume in a
    single day) BEFORE any further fetching occurs; exceeding it returns
    `{ status: "unavailable" }` immediately rather than truncating and
    reporting a false count.
  - Evidence queries (2-4) are issued once PER ID-CHUNK of
    `WHOLE_WINDOW_ID_CHUNK_SIZE = 150` Trip ids (never once per Trip —
    this is chunking, not N+1). 150 was chosen deliberately, not
    arbitrarily: `trip_events` can return up to 6 rows per Trip under the
    required-type filter, so 150 × 6 = 900 stays safely under the
    1000-row cap even before accounting for anomalous duplicate-event
    data.
  - A TRUNCATION GUARD backs the chunk-size arithmetic rather than
    trusting it alone: every evidence query also requests
    `{ count: "exact" }`, and the returned row count is compared against
    that SAME query's own authoritative count after every fetch — any
    mismatch (a silent `max_rows` truncation) fails the whole summary
    closed to `{ status: "unavailable" }` immediately, per §9's own
    explicit "truthfulness > convenience" instruction.
  - The accumulated whole-window Trip count is also cross-checked against
    the first page's own authoritative `count` after the paging loop
    completes; any mismatch also fails closed.

===========================================================================
NO N+1
===========================================================================
Confirmed by direct source inspection: no query exists inside a
per-Trip loop anywhere in `getYesterdayProofOfServiceResults`. Query
round trips scale with the WINDOW SIZE divided by chunk size, never with
the Trip count directly: for the 30-Trip fixture set used in local
validation, this was exactly 1 page-1 Trip query + 1 evidence chunk
(30 Trips fits in one 150-Trip chunk) × 3 queries (assignments/events/
exceptions, issued in parallel via `Promise.all`) = 4 total round trips —
identical in shape to S1D's own already-validated 4-round-trip page-view
architecture, just scoped to the whole window instead of one page.

ERROR ISOLATION
===========================================================================
`getProofOfServiceSummary` (operations-brief.ts) is wrapped in its own
`.catch(() => null)` in BOTH `getOperationsBrief` and
`src/app/operations/page.tsx`, mirroring `tomorrowReadinessPromise`/
`recurringCarePromise`'s own established independent-promise pattern
exactly — started before the main `Promise.all` so it overlaps in
wall-clock time, awaited and caught separately so a genuine failure
degrades only this one block. Additionally, `getYesterdayProofOfServiceResults`
and `getProofOfServiceSummary` themselves never throw for any internal
failure (query error, safety-cap trip, or detected truncation) — every
such path explicitly returns `{ status: "unavailable" }` / `null`, a
defense-in-depth layer beneath the outer `.catch`.

A live REVOKE-based fault-injection E2E test (mirroring the earlier
Recurring Care S1F precedent's `revoke select on public.recurring_arrangements`
technique) was ATTEMPTED and found NOT cleanly isolable to Proof-of-
Service: `getYesterdayProofOfServiceResults` shares every one of its 4
source tables (`trips`, `trip_assignments`, `trip_events`,
`trip_exceptions`) with `getTodaysOperations` (confirmed directly —
`todays-operations.ts` itself queries all 4 of the same tables, including
an embedded `trip_assignments` relation). Revoking SELECT on any of them
crashed the ENTIRE Overview page via `getTodaysOperations`'s own uncaught
query — a genuine, PRE-EXISTING architectural fact this phase did not
introduce (that function has no `try`/`catch` of its own, unlike every
Brief sub-block). Recurring Care's own equivalent test worked cleanly
only because it has its OWN dedicated table with no such overlap;
Proof-of-Service deliberately introduces no new table (this phase's own
explicit "no schema change" mandate), so no equivalently isolated live
fault-injection target exists without also touching RLS (also explicitly
forbidden this phase) or restarting the PostgREST container to lower its
configured `max_rows` (not a targeted, in-place, reversible fault).
Error isolation was therefore verified at the SOURCE level instead (see
above) rather than via a live E2E fault demonstration — documented here
transparently, not silently substituted. See OPEN ISSUES.

   authoritative `count`) is a direct, mechanical check that does not

   low-risk gap, not an unverified assumption about the safety
