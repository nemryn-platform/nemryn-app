6. ELIGIBILITY AND STAGE RULES
======================================================================

  - Plus WRITE (_require_plus_write) and the Core request role (_plus_require_core_request_read; Core re-checks it).
  - A private-pay opportunity of THIS organization (ZW002 otherwise, no oracle).
  - An open stage: lost -> ZW004 illegal_transition; converted -> ZW004 already_converted.

  - NO Request already linked to the opportunity (P2-S3 manual link) -> ZW004 linked_request_exists. The conservative

one stage_changed (from the previous stage to converted).

  - The deferred guard refuses ANY 'converted' without its conversion attribution at commit (SQL S3: a direct update

7. IDEMPOTENCY GUARANTEES
======================================================================
- Key: 8-200 characters of [A-Za-z0-9._:-]. The UI uses "<mode>-<crypto.randomUUID()>", one per opened form. The key is
  stored as plus_request_attributions.conversion_idempotency_key (unique per organization; R1 contract kept).
- Same key + same operation (conversion of THAT opportunity / rebooking of THAT contact) -> the ORIGINAL Request,
  changed=false, and nothing written: no Request, activity, audit or Core event (SQL I1, R4; CONC-C1/C2/C8; E2E A13).
- An already converted opportunity + a different key -> ZW004 already_converted (SQL I2; CONC-C3).
- A key of another operation (other opportunity / contact / method) -> ZW006, and never that Request (SQL I3, R4;
  CONC-C4).
- A double click -> one Request (CONC-C1; E2E A6). A browser retry after a timeout reuses the form's key -> the same
  Request.
- The key is never proof of authority: Plus write and the Core role are checked BEFORE the replay lookup (SQL P3: a
  converting Dispatcher downgraded to read-only cannot even replay).
- Any failure after the Core insert rolls the Core Request back (SQL F3; CONC-C10). No orphan Request is possible.

8. CONCURRENCY / LOCKING STRATEGY AND LOCK ORDER
======================================================================
  1. pg_advisory_xact_lock(hashtext('plus-booking:' || org || ':' || key)): serializes one operation per key.
  2. plus_opportunities FOR UPDATE (conversion): serializes with edits, stage moves, other conversions and P2-S3 links
     (which take FOR SHARE).
  3. plus_contacts FOR SHARE: blocks a concurrent archive (FOR UPDATE) until commit.
  4. log_transportation_request: Core INSERTs; no Plus lock.
  5. Attribution / activities / audit INSERTs.
No cycle:
  - every existing Plus writer takes the opportunity before the contact (P2-S1 update, P2-S3 link and correction);
  - contact edit and archive take only the contact;
  - no other path takes the advisory lock;
  - Core request functions never touch Plus.

  - restore the 20261015130000 body of plus_update_request_attribution.
  - AFTER conversions exist: Core Requests created by conversion are legitimate Core records and must NOT be deleted.
    Rolling back would leave their attributions with link methods no RPC can create; keep the constraints, or migrate
    those rows deliberately. A forward fix is preferred to a rollback once used.
