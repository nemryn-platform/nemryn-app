    a uniform, schema-wide condition, not a per-table anomaly.

ROOT CAUSE
============
Confirmed by direct pg_default_acl inspection (not assumed, not
inferred from "it's probably a Supabase default"):

  select tablename, tableowner from pg_tables where schemaname='public';
    -> all 20 rows show owner = `postgres`.

  select defaclrole::regrole, defaclacl from pg_default_acl da
    join pg_namespace n on n.oid=da.defaclnamespace
    where n.nspname='public' and defaclobjtype='r';
    -> two rows:
       supabase_admin | {postgres=arwdDxtm/supabase_admin, anon=arwdDxtm/..., authenticated=arwdDxtm/..., service_role=arwdDxtm/...}
       postgres       | {postgres=arwdDxtm/postgres, anon=Dxtm/postgres, authenticated=Dxtm/postgres, service_role=Dxtm/postgres}

The SECOND row is the actual, active root cause: a pre-existing default
ACL — equivalent to `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN
SCHEMA public GRANT TRUNCATE, REFERENCES, TRIGGER ON TABLES TO anon,
authenticated, service_role` — that was ALREADY IN PLACE before this
repository's very first migration ever ran (grep-confirmed: no migration
in this repo's history ever issued this statement). Since every
CREATE TABLE in every migration in this repository's history has run as
`postgres` (the role `supabase db reset`/migrations apply as, confirmed
via table ownership above), and Postgres automatically applies whatever
default ACL is registered for the creating role at the instant of table
creation, every one of the 20 tables silently inherited TRUNCATE,
REFERENCES, TRIGGER, and MAINTAIN for anon/authenticated/service_role
the moment it was created — with zero explicit GRANT statement anywhere,
and with no individual migration author having any practical way to
notice it without deliberately running the exact pg_default_acl query
above.

CLASSIFICATION (per work item §18's own explicit request — not merely
"pre-existing"): this is a **Supabase platform/bootstrap default**, set
up as part of the local Supabase CLI's own Postgres image initialization
before any repository migration ever executes — NOT a historical
`GRANT ALL` statement (none exists), NOT a migration-specific grant (none
exists), and NOT something introduced or widened by any phase of this
project's own history, including S1D. It is the SAME category of
platform default already documented in Supabase's own general project
behavior: DML privileges (SELECT/INSERT/UPDATE/DELETE) are deliberately
left OUT of the default (confirmed: the default ACL grants only `Dxtm`,
never `arwd`, to anon/authenticated — every DML grant in this schema has
always required, and still requires, an explicit per-table `grant
select/insert/update/delete` statement, which is exactly why this
project's own established discipline of narrow per-table grants has
never accidentally over-exposed DML). TRUNCATE/REFERENCES/TRIGGER were
apparently left IN the default, likely because the platform's own
default posture treats them as lower-risk given PostgREST's own API
surface never exposes them — a reasonable platform-level default for a
generic project, but not the correct least-privilege posture for this
specific application's own threat model, which is why this phase exists.

PREVENTING RECURRENCE: fixed at the default-ACL layer itself (see
DEFAULT PRIVILEGE HARDENING below), not merely on the 20 tables that
happen to exist today — every future migration will keep creating tables
as `postgres` (no reason to change that), and this migration's own
`ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ...`
statement ensures no future table can ever silently reacquire these
three privileges again, without requiring any future migration author to
remember to revoke them by hand.


DEFAULT ACL AUDIT
===================
Two distinct default-ACL entries exist for schema public, obj_type='r'
(relation/table):

  1. Owning role `postgres` — the one that matters (every table in this
     schema is created by this role). BEFORE this phase: granted `Dxtm`
     (TRUNCATE, REFERENCES, TRIGGER, MAINTAIN) to anon, authenticated,
     AND service_role. AFTER this phase's migration: anon/authenticated
     now show only `m` (MAINTAIN — see OPEN ISSUES); service_role is
     completely untouched, still `Dxtm`.

  2. Owning role `supabase_admin` — grants the FULL `arwdDxtm` set
     (including SELECT/INSERT/UPDATE/DELETE) to anon/authenticated/
     service_role for any table `supabase_admin` might ever create in
     `public`. This entry is CURRENTLY INERT for this application — no
     table in this schema has ever been created by `supabase_admin`
     (confirmed via the same table-ownership query; all 20 are owned by
     `postgres`). It was deliberately NOT touched by this phase: altering
     another role's own default ACL entry is exactly the kind of
     "casually alter service_role/supabase_admin" action work item §5
     explicitly forbids, and since it is provably unused today, there is
     no live exposure to remediate. Documented here as a latent
     observation, not a defect requiring action in this phase — flagged
     honestly rather than silently left undocumented, per work item §18.

Proven live (not merely asserted): a probe table created by `postgres`
in `public` RIGHT NOW, inside a transaction that was immediately rolled
back (leaving zero permanent objects — verified via `to_regclass()`
returning NULL afterward), inherited NO TRUNCATE/REFERENCES/TRIGGER for
either anon or authenticated — proving the default-ACL fix genuinely
protects tables that do not exist yet, not merely the 20 that existed at
migration time. See client_privilege_surface_tests.sql TEST 12/12b.

membership in pg_database_owner) — no client-facing role can create
arbitrary database objects today. No unexpected CREATE grant was found;
no revocation was necessary or performed for this item.


HARDENING MIGRATION
======================
New migration (historical migrations were not edited, per this
repository's own established remediation discipline — see the
migration's own header comment for the ZD-092/ZD-101/P1-E3-S8A
precedent this follows exactly):
supabase/migrations/20260917120000_client_privilege_surface_hardening.sql

Two statements, both scoped to anon/authenticated only:

  revoke truncate, references, trigger
    on all tables in schema public
    from anon, authenticated;

  alter default privileges for role postgres in schema public
    revoke truncate, references, trigger
    on tables
    from anon, authenticated;

No RLS policy touched. No SELECT/INSERT/UPDATE/DELETE grant touched, at
either table or column level. service_role, postgres, and supabase_admin
are not mentioned in either statement — their own privileges (and
supabase_admin's own separate, currently-inert default ACL entry) are
completely unaffected.


TRUNCATE REVOCATION
======================
Revoked from anon and authenticated on all 20 current public tables via
the `revoke ... on all tables in schema public` statement (schema-wide,
not a per-table list that could drift out of sync). Verified via
has_table_privilege across all 20 tables: 0/20 show TRUNCATE for either
role, post-migration (was 20/20 pre-migration). service_role retains
TRUNCATE on all 20 tables, confirmed unchanged. Live raw TRUNCATE

recurring_occurrence_exceptions specifically) genuinely denied with
`permission denied for table <name>` — not merely inferred from
has_table_privilege — with zero data loss (trip row count confirmed
identical before/after each attempt, since Postgres's permission check
runs before any row is touched).


TRIGGER REVOCATION
======================
Revoked identically to TRUNCATE, same statement, same scope. 0/20 tables
show TRIGGER for anon/authenticated post-migration (was 20/20 before).
No repository requirement was found — searched — that depends on

REFERENCES REVOCATION
========================
Revoked identically, same statement, same scope. 0/20 tables show
REFERENCES for anon/authenticated post-migration (was 20/20 before). Same
reasoning as TRIGGER: REFERENCES only matters for a role attempting to
CREATE a new FOREIGN KEY constraint referencing the table, which likewise
requires CREATE on the schema (also confirmed absent) — already
structurally inert before this migration, in addition to being
unnecessary. No repository requirement was found that depends on
anon/authenticated holding REFERENCES on any table.


DEFAULT PRIVILEGE HARDENING
==============================
`alter default privileges for role postgres in schema public revoke
truncate, references, trigger on tables from anon, authenticated;` —
targets the exact role (postgres) and schema (public) the pre-existing
default ACL entry was already registered against (read directly from
pg_default_acl before writing this statement, not guessed). Running this
as the `postgres` role itself (identical to how every migration in this
repository's history has always run) requires no elevated privilege
beyond what every prior migration already used — altering one's own
default privileges needs no special grant.

Verified live, twice: (1) direct pg_default_acl re-inspection after the
migration shows the `postgres`-owner row's ACL for anon/authenticated
reduced from `Dxtm` to bare `m` (MAINTAIN — see OPEN ISSUES); (2) a real
probe table created fresh (then rolled back, leaving no permanent
object) inherited none of the three revoked privileges. Default
SELECT/INSERT/UPDATE/DELETE behavior was not touched — it was never part
of this default ACL to begin with (confirmed: the pre-existing default
never included `a`/`r`/`w`/`d` for anon/authenticated at all), so there
was nothing to "not remove" here beyond what was already true.


RLS IMPACT
============
Zero RLS policies were created, modified, or dropped anywhere in this
phase. This hardening operates entirely below/alongside RLS, exactly as
work item §9 specifies — TRUNCATE was never filtered by RLS in the first
place (a Postgres-level fact, not a gap this project's own RLS design
ever claimed to cover), so removing the TRUNCATE grant closes a gap RLS
structurally could never have closed regardless of policy design.

OPEN ISSUES
=============
None found that block S1E. Two items worth carrying forward as context,
neither a defect, both explicitly out of this phase's own scope:

  1. MAINTAIN (PostgreSQL 17's newest table-level privilege, letter code
     `m` — governs VACUUM/ANALYZE/CLUSTER/REINDEX/REFRESH MATERIALIZED
     VIEW/LOCK TABLE on the table) was part of the SAME pre-existing
     default ACL entry (`Dxtm`) as the three privileges this phase was
     explicitly scoped to remove, and remains granted to anon/
     authenticated on all 20 tables and in the default ACL for future
     ones. It was deliberately left untouched: the phase's own §2/§4
     scope explicitly and only names TRUNCATE, REFERENCES, and TRIGGER —
     MAINTAIN is never mentioned — and per the phase's own repeated
     instruction not to "broaden scope silently," it was not folded in
     without being asked. MAINTAIN does not bypass RLS the way TRUNCATE
     does and, like REFERENCES/TRIGGER, most of its constituent
     operations are DDL-adjacent and not reachable via PostgREST; `LOCK
     TABLE` specifically is reachable without DDL privilege and could in
     principle be used for a denial-of-service lock, though again only
     via a raw Postgres connection this application's own architecture
     never exposes to any client. Flagged here, not fixed, pending an
     explicit future decision on whether to include it in a follow-up
     hardening pass.

  2. The `supabase_admin`-owner default ACL entry for schema public
     (`arwdDxtm` — the FULL privilege set, including DML) to
     anon/authenticated/service_role remains in place. It is currently
     provably inert (no table in this schema has ever been, or currently
     is, owned by `supabase_admin`), and altering another role's own
     default ACL is outside what work item §5 authorizes this phase to
     touch. If any future migration were ever accidentally applied under
     the `supabase_admin` role instead of `postgres` (nothing in this
     repository's current tooling does this, and there is no known reason
     it ever would), the new table would silently receive full DML access
     for anon/authenticated with no RLS gate implied by the grant itself
     (RLS would still need to be separately enabled and policied, exactly
     as it already must be for every `postgres`-owned table today) —
     documented as a latent, currently-unexploitable observation, not an
     active gap.
